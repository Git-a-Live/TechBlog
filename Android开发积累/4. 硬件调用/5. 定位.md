Android 获取设备位置有两条技术路线：**`LocationManager`**（框架层原生 API，直接与系统 LocationService 交互）和 **`FusedLocationProviderClient`**（融合定位，来自 Google Play services，自动融合 GPS、Wi-Fi、基站、传感器等多种信号源）。实际项目里除非有特殊原因，一般都推荐使用融合定位，它在精度、功耗与实现成本上优于直接使用 `LocationManager`。

本节以 `FusedLocationProviderClient` 为主线展开，涉及权限配置、获取当前位置、持续更新三个核心环节，最后补充后台定位与前台服务类型的注意事项。

## 权限配置

定位是典型的敏感权限，必须在 Manifest 声明并运行时动态申请。定位权限有三个，作用各不相同：

```xml
<!-- 精确位置：GPS 级精度，通常 50 米以内，好的情况可到几米 -->
<uses-permission android:name="android.permission.ACCESS_FINE_LOCATION" />
<!-- 粗略位置：约 3 平方公里范围，仅用基站/Wi-Fi 推断 -->
<uses-permission android:name="android.permission.ACCESS_COARSE_LOCATION" />
<!-- 后台定位：Android 10（API 29）起，需要在后台持续获取位置时单独声明 -->
<uses-permission android:name="android.permission.ACCESS_BACKGROUND_LOCATION" />
```

> 官方文档明确：粗略定位（`ACCESS_COARSE_LOCATION`）给出的估计在约 3 平方千米量级；精确定位（`ACCESS_FINE_LOCATION`）通常在 50 米以内，好的情况下可到几米甚至更好。

### 版本差异

不同 Android 版本的授权行为有显著差异，需注意：

- **Android 10（API 29）+**：后台定位需**单独申请** `ACCESS_BACKGROUND_LOCATION`，且必须与前台权限**分开、分步骤**申请。若一次性把前后台权限一起请求，系统会忽略后台权限。
- **Android 11（API 30）+**：首次弹出的授权对话框**不再提供「始终允许」选项**，用户只能先授予「仅在使用时允许」，之后再到系统设置里手动改为「始终允许」。
- **Android 12（API 31）+**：授权对话框允许用户在 **「精确」与「粗略」之间二选一** 。即使应用声明了 `ACCESS_FINE_LOCATION`，用户仍可能只授予粗略位置，应用应能正常降级运行。

### 运行时申请

用 Activity Result API 申请，一次请求可以同时带上粗细两种权限：

```kotlin
private val requestLocationPermission =
    registerForActivityResult(ActivityResultContracts.RequestMultiplePermissions()) { grants ->
        val fineOk = grants[Manifest.permission.ACCESS_FINE_LOCATION] ?: false
        val coarseOk = grants[Manifest.permission.ACCESS_COARSE_LOCATION] ?: false
        if (fineOk || coarseOk) {
            // 已获得至少一种定位权限，可开始获取位置
        }
    }

// 需要时调用
requestLocationPermission.launch(
    arrayOf(
        Manifest.permission.ACCESS_FINE_LOCATION,
        Manifest.permission.ACCESS_COARSE_LOCATION
    )
)
```

申请前通常还要先检查是否已授权：

```kotlin
fun hasLocationPermission(): Boolean =
    ContextCompat.checkSelfPermission(this, Manifest.permission.ACCESS_FINE_LOCATION) ==
        PackageManager.PERMISSION_GRANTED ||
    ContextCompat.checkSelfPermission(this, Manifest.permission.ACCESS_COARSE_LOCATION) ==
        PackageManager.PERMISSION_GRANTED
```

## 获取当前位置

融合定位通过 `FusedLocationProviderClient` 提供三类获取位置的方式，按使用场景选择：

| 方法 | 说明 | 适用场景 |
| :---: | :---: | :---: |
| `getLastLocation()` | 返回系统**最近一次**缓存的位置，可能为 `null` | 需要快速、低功耗地拿到一个「大概」位置 |
| `getCurrentLocation()` | 主动请求**一次**新鲜定位 | 只需在某个时刻获取一次准确位置 |
| `requestLocationUpdates()` | **持续**接收位置更新回调 | 导航、轨迹记录等需要连续定位 |

先拿到客户端实例（需在引入依赖 `com.google.android.gms:play-services-location` 之后）：

```kotlin
private lateinit var fusedLocationClient: FusedLocationProviderClient

// onCreate 中初始化
fusedLocationClient = LocationServices.getFusedLocationProviderClient(this)
```

### 获取最近位置

`getLastLocation()` 是异步的，返回 `Task<Location?>`：

```kotlin
// 注意先检查权限，否则抛 SecurityException
if (hasLocationPermission()) {
    fusedLocationClient.lastLocation
        .addOnSuccessListener { location ->
            // location 可能为 null：设备从未产生过位置缓存
            if (location != null) {
                val lat = location.latitude
                val lng = location.longitude
            }
        }
}
```

### 获取单次新鲜位置

`getCurrentLocation()` 触发一次新的定位计算，比 `getLastLocation()` 更新鲜，但要等定位完成。旧版签名传入 `Priority` 与 `CancellationToken`：

```kotlin
val cancellationTokenSource = CancellationTokenSource()

if (hasLocationPermission()) {
    fusedLocationClient.getCurrentLocation(
        Priority.PRIORITY_HIGH_ACCURACY,
        cancellationTokenSource.token
    ).addOnSuccessListener { location ->
        if (location != null) {
            // 拿到一次新鲜定位
        }
    }
}
```

> 新版还提供了 `getCurrentLocation(CurrentLocationRequest, CancellationToken)` 重载，用 `CurrentLocationRequest.Builder` 设置精度与超时。核心思路一致：单次、可取消。

## 持续更新位置

持续定位需要三样东西：一个 `LocationRequest`（定位请求配置）、一个 `LocationCallback`（结果回调）、一个 `Looper`（回调运行的线程）。

### 配置 LocationRequest

```kotlin
val locationRequest = LocationRequest.Builder(
    Priority.PRIORITY_HIGH_ACCURACY,   // 精度优先
    10_000L                            // 请求间隔（毫秒）
).apply {
    setMinUpdateIntervalMillis(5_000L) // 最快更新间隔，防止过于频繁
    setWaitForAccurateLocation(false)  // 是否等待足够精度再回调
    setMaxUpdateDelayMillis(30_000L)   // 位置更新可延迟合并上报的最大时长（可选）
}.build()
```

`Priority` 提供四个精度档位，是功耗与精度的权衡：

| 常量 | 说明 |
| :---: | :---: |
| `PRIORITY_HIGH_ACCURACY` | 高精度，优先使用 GPS，功耗最高 |
| `PRIORITY_BALANCED_POWER_ACCURACY` | 平衡功耗，街区级精度（约 100 米） |
| `PRIORITY_LOW_POWER` | 低功耗，城市级精度（约 10 千米） |
| `PRIORITY_NO_POWER` | 被动定位，不主动触发，只接收其他应用已获取的位置 |

### 注册回调

```kotlin
private val locationCallback = object : LocationCallback() {
    override fun onLocationResult(result: LocationResult) {
        for (location in result.locations) {
            val lat = location.latitude
            val lng = location.longitude
        }
    }
}

// 第二个参数是 Looper，决定回调在哪个线程执行；传 null 表示沿用调用线程
fusedLocationClient.requestLocationUpdates(
    locationRequest,
    locationCallback,
    Looper.getMainLooper()
)
```

### 停止更新

不再需要定位时必须移除回调，否则会持续耗电：

```kotlin
fusedLocationClient.removeLocationUpdates(locationCallback)
```

## 后台定位与前台服务

如果应用需要在退到后台后继续获取位置（如导航、运动轨迹），仅靠上面的调用是不够的——Activity 一旦不可见，前台定位权限就失效了。

正确做法是：**用一个「location」类型的前台服务承载持续定位**。关键配置如下：

```xml
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_LOCATION" />

<service
    android:name=".LocationService"
    android:foregroundServiceType="location"
    android:exported="false" />
```

版本约束要点：

- **Android 10（API 29）+**：在后台持续定位，必须声明前台服务类型 `location`。
- **Android 14（API 34）+**：前台服务类型成为**强制要求**，且启动服务时需同时持有 `FOREGROUND_SERVICE_LOCATION` 权限与粗细定位权限，否则在服务调用 `startForeground()` 或定位 API 时抛 `SecurityException`。
- 服务内调用 `ServiceCompat.startForeground()` 提升为前台服务，并展示常驻通知。

> 若需要在完全脱离前台服务（如定时任务、地理围栏）场景下拿到后台位置，才需要 `ACCESS_BACKGROUND_LOCATION`。这属于更重的授权（需用户在系统设置中开启「始终允许」），普通应用应尽量避免。
