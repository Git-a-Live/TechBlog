WorkManager是Google推出的用于在**后台执行可延期的、必须可靠运行的异步任务**的一种组件。它内部封装了一套自研的调度框架（底层默认基于JobScheduler），统一处理了任务持久化、约束满足、失败重试以及应用退出或设备重启后的恢复等细节，开发者无需关心不同系统版本之间的调度差异。

WorkManager与[[5. Service]]有很大不同，它只是一个处理定时任务的工具，可确保应用退出甚至手机重启的情况下，之前注册的任务仍可得到执行。此外，WorkManager注册的周期性任务**不一定会准时执行**，因为系统可能会将几个触发时间临近的几个任务放在一起执行，从而减少CPU唤醒次数和资源消耗。

## 基本用法

在使用WorkManager之前，需要在build.gradle文件中添加如下依赖：

```groovy
dependencies {
    //Java syntax
    implementation "androidx.work:work-runtime:$work_version"

    //Kotlin + coroutines
    implementation "androidx.work:work-runtime-ktx:$work_version"
}
```

> 注：截至 2026 年 11 月，WorkManager 最新稳定版为 2.12.0（2026 年 9 月发布）；自 2.11.0 起 minSdk 提升到 API 23、2.12.0 起提升到 API 24，并要求 compileSdk ≥ 33。

WorkManager的基本用法通常有三步：

1. **定义一个后台任务，并实现具体的业务逻辑**；
```kotlin
    class DemoWorker(appContext: Context, workerParams: WorkerParameters):
       Worker(appContext, workerParams) {
        override fun doWork(): Result {
            //在此处编写具体的后台任务逻辑
            return Result.success() //失败则返回Result.failure()或Result.retry()
        }
    }
   ```
2. **配置该后台任务的运行条件和约束信息，并构建后台任务请求**；
```kotlin
    //单次任务请求：
    val request = OneTimeWorkRequest.Builder(DemoWorker::class.java)
    ··· //链式配置
    .build()

    //周期任务请求：
    val request = PeriodicWorkRequest.Builder(DemoWorker::class.java, time, TimeUnit.XXX)
    ··· //链式配置
    .build()
    //周期性任务的时间间隔不能小于15分钟，以降低设备性能消耗
   ```
3. **将该后台任务请求请求传入WorkManager的`enqueue()`方法中，系统会在适合的时间运行**。
```kotlin
    WorkManager.getInstance(context).enqueue(request)
   ```

## 配置WorkRequest

WorkRequest的构建实际上可以非常复杂，主要就是通过[[创建型设计模式#三、Builder|Builder]]链式调用若干设置方法对WorkRequest的运行条件和约束信息进行配置。常用的设置方法有：

+ setInitialDelay()：设置后台任务在指定时间后开始运行
+ addTag()：设置任务标签，同一标签可以管理多个后台任务
+ setBackoffCriteria()：如果后台任务返回Result.retry()，则在一段时间后重新执行任务
+ setConstraints()：设置后台任务的运行条件

运行条件的编写方法和WorkRequest类似：

```kotlin
val constraint = Constraints.Builder()
    ··· //链式配置
    .build()
```

常见设置方法：

+ setRequiredNetworkType()：设置后台任务在某种网络类型下运行
+ setRequiresCharging()：设置后台任务在某个充电状态下运行
+ setTriggerContentMaxDelay()：设置触发后台任务的最大延迟时间
+ setTriggerContentUpdateDelay()：设置触发内容更新的延迟时间
+ setRequiresBatteryNotLow()：设置后台任务在电池电量不低时运行
+ setRequiresDeviceIdle()：设置后台任务在设备空闲（无用户交互）时运行
+ setRequiresStorageNotLow()：设置后台任务在存储空间不低时运行

## 链式任务

WorkManager的链式任务机制很简单，就是调用一个`beginWith()`和若干`then()`来有序执行一系列后台任务：

```kotlin
WorkManager.getInstance(context)
.beginWith(task1)
.then(task2)
.then(···)
···
.enqueue()
```

>注意，使用WorkManager的链式任务时，只有前一个后台任务执行成功之后，下一个后台任务才会执行。

**在一些定制过的Android系统上，应用随时可能会被杀掉，因此在这种情况下，不能依赖WorkManager去实现核心功能。**

## CoroutineWorker（推荐）

如果项目中已经引入了`work-runtime-ktx`，则推荐直接继承`CoroutineWorker`。它的`doWork()`是一个**挂起函数**，运行在后台协程中，无需手动切换线程，写法更简洁：

```kotlin
class SyncWorker(appContext: Context, workerParams: WorkerParameters) :
    CoroutineWorker(appContext, workerParams) {

    override suspend fun doWork(): Result {
        return try {
            // 直接调用挂起函数，自动运行在后台线程
            repository.syncFromNetwork()
            Result.success()
        } catch (e: IOException) {
            Result.retry()   // 可重试的错误（如网络异常）
        } catch (e: Exception) {
            Result.failure() // 不可恢复的错误
        }
    }
}
```

> 注意：无论是`Worker`还是`CoroutineWorker`，`doWork()`都受执行窗口限制（默认最多10分钟），超时会被系统强制停止并标记为失败。

## 任务输入输出数据

WorkManager通过`Data`对象在任务之间传递数据。`Data`只支持基本类型及它们的数组等可序列化类型：

```kotlin
// 提交任务时传入输入数据（workDataOf 是 work-runtime-ktx 提供的扩展函数）
val request = OneTimeWorkRequestBuilder<SyncWorker>()
    .setInputData(workDataOf("user_id" to 42, "action" to "sync"))
    .build()

// Worker 内部读取输入数据、返回输出数据
override suspend fun doWork(): Result {
    val userId = inputData.getInt("user_id", -1)
    val action = inputData.getString("action")
    val output = workDataOf("synced_count" to 10)
    return Result.success(output)
}
```

任务的产出可以通过`WorkInfo.outputData`读取（详见下节"观察任务状态"）。

## 观察任务状态

`WorkInfo`封装了任务的id、标签、状态、进度（progress）以及输出数据（outputData）等信息，可通过LiveData（或Flow）观察：

```kotlin
val workManager = WorkManager.getInstance(context)

// 按 id 观察；也可用 getWorkInfosByTagLiveData() / getWorkInfosForUniqueWorkLiveData()
workManager.getWorkInfoByIdLiveData(request.id)
    .observe(this) { info ->
        when (info?.state) {
            WorkInfo.State.ENQUEUED -> { /* 已入队，等待满足约束 */ }
            WorkInfo.State.RUNNING -> {
                val progress = info.progress.getInt("progress", 0) // 读取任务进度
            }
            WorkInfo.State.SUCCEEDED -> {
                val count = info.outputData.getInt("synced_count", 0) // 读取输出数据
            }
            WorkInfo.State.FAILED -> { /* 失败 */ }
            WorkInfo.State.BLOCKED -> { /* 被尚未完成的前置任务阻塞 */ }
            WorkInfo.State.CANCELLED -> { /* 已取消 */ }
            else -> Unit
        }
    }
```

> 任务进度通过Worker内部调用`setProgress(workDataOf("progress" to 50))`上报，配合上面的`info.progress`即可实现进度条效果。

## 任务唯一性

为避免同名任务被重复入队，WorkManager提供了"唯一任务"机制：

```kotlin
// 一次性任务的唯一性
workManager.enqueueUniqueWork(
    "sync_work",
    ExistingWorkPolicy.KEEP, // KEEP/REPLACE/APPEND
    request
)

// 周期性任务的唯一性
workManager.enqueueUniquePeriodicWork(
    "hourly_sync",
    ExistingPeriodicWorkPolicy.KEEP, // KEEP/UPDATE
    periodicRequest
)
```

+ `ExistingWorkPolicy.KEEP`：若同名任务已存在（未完成），则丢弃新任务；
+ `ExistingWorkPolicy.REPLACE`：取消旧任务并入队新任务；
+ `ExistingWorkPolicy.APPEND`：把新任务追加到旧任务之后形成链式执行；
+ `ExistingPeriodicWorkPolicy`只有`KEEP`与`UPDATE`两个取值（周期任务不存在"追加"概念）。

## 取消任务

```kotlin
workManager.cancelWorkById(request.id)    // 按 id 取消
workManager.cancelUniqueWork("sync_work") // 按唯一名称取消
workManager.cancelAllWorkByTag("upload")  // 按标签取消
workManager.cancelAllWork()               // 取消所有任务
```

> 取消只能影响尚未执行或正在排队中的任务；对于正在运行中的`Worker`，取消后仍需在`doWork()`内部配合`isStopped`（CoroutineWorker中通过协程取消自动处理）自行退出。

## AlarmManager 集成使用

AlarmManager是Android系统提供的另一种定时机制。与WorkManager的定位不同：**AlarmManager负责"精确时间"的触发**（如闹钟、定时提醒），**WorkManager负责"可延期、必须可靠执行"的后台任务**。官方推荐的做法是——用AlarmManager做准点触发，耗时任务再转交给WorkManager执行。

### 权限声明

精确闹钟（exact alarm）在Android 12（API 31）起需要特殊权限：

```xml
<!-- 适用于闹钟/日历等以精确时间为核心功能的应用（Android 13+ 可选，自动授予） -->
<uses-permission android:name="android.permission.USE_EXACT_ALARM" />

<!-- 或：需用户手动授予、可被撤销的精确闹钟权限（适用场景更广） -->
<uses-permission android:name="android.permission.SCHEDULE_EXACT_ALARM" />
```

二者的区别：`USE_EXACT_ALARM`自动授予、不可撤销，但Google Play对其使用场景有严格限制（仅闹钟/日历等核心功能）；`SCHEDULE_EXACT_ALARM`需用户授权、可能被撤销，适用场景更广。

### 基本使用

```kotlin
// 1. 获取 AlarmManager
val alarmManager = context.getSystemService(Context.ALARM_SERVICE) as AlarmManager

// 2. 构建 PendingIntent（指向 BroadcastReceiver）
val intent = Intent(context, AlarmReceiver::class.java)
val pendingIntent = PendingIntent.getBroadcast(
    context,
    0,
    intent,
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
)

// 3. 触发时间（5 分钟后）
val triggerAt = System.currentTimeMillis() + 5 * 60_000

// 4. 设置闹钟（Android 12+ 需判断精确闹钟权限）
if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.S && !alarmManager.canScheduleExactAlarms()) {
    // 未授权精确闹钟：降级为非精确闹钟（仍能穿透 Doze，仅时间有偏差）
    alarmManager.setAndAllowWhileIdle(AlarmManager.RTC_WAKEUP, triggerAt, pendingIntent)
} else {
    alarmManager.setExactAndAllowWhileIdle(AlarmManager.RTC_WAKEUP, triggerAt, pendingIntent)
}
```

### 接收广播

```kotlin
class AlarmReceiver : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        // 触发点只做轻量操作；耗时任务交给 WorkManager
        val workRequest = OneTimeWorkRequestBuilder<DemoWorker>().build()
        WorkManager.getInstance(context).enqueue(workRequest)
    }
}
```

```xml
<receiver android:name=".AlarmReceiver" />
```

### 重启后重新注册

AlarmManager的闹钟在设备重启后会全部丢失，需监听开机广播重新注册：

```xml
<uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED" />

<receiver android:name=".BootReceiver" android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.BOOT_COMPLETED" />
    </intent-filter>
</receiver>
```

### 选择建议

+ **准点触发（闹钟、定时提醒）**：用AlarmManager（`setExactAndAllowWhileIdle`）；
+ **可延期、需可靠执行的后台任务**：用WorkManager；
+ **组合使用**：AlarmManager准点触发 + 在BroadcastReceiver里`enqueue`一个WorkManager任务，兼顾"准点"与"可靠"。
