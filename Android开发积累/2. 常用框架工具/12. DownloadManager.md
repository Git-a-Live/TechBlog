[DownloadManager](https://developer.android.google.cn/reference/android/app/DownloadManager)是Google官方在Android SDK当中提供的一个系统服务，用于负责那些基于HTTP/HTTPS协议的耗时下载任务。使用DownloadManager，开发者可以简化文件下载功能的开发。

## 前置工作

使用DownloadManager不需要额外导入任何依赖库，只需要在AndroidManifest.xml文件中加入网络以及存储访问权限：

```xml
<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.WRITE_EXTERNAL_STORAGE"/>
```

> 注：`WRITE_EXTERNAL_STORAGE` 仅对 Android 9（API 28）及以下版本有效；Android 10（API 29）起引入分区存储（Scoped Storage），建议改用 `setDestinationInExternalFilesDir()`（应用专属目录，无需权限）或 `setDestinationInExternalPublicDir()`（公共目录，由系统托管），而不是手工拼接 `file://` URI。

## 基本使用

由于DownloadManager是系统服务，因此通常跟其他系统服务一样，要通过以下方式获取`DownloadManager`对象：

```kotlin
val downloadManager = context.getSystemService(Context.DOWNLOAD_SERVICE) as DownloadManager
```

获得这一对象之后，才能执行后面的一系列业务逻辑。

### 创建和执行下载请求

创建下载请求的方式较为简单，通常如下列代码所示：

```kotlin
import android.app.DownloadManager.Request

val downloadUrl: String = "···"
val file: File = File(···)
val downloadRequest: Request = Request(Uri.parse(downloadUrl))
        // 设置可以执行下载任务的网络环境
        .setAllowedNetworkTypes(Request.NETWORK_WIFI or Request.NETWORK_MOBILE)
        // 设置通知栏可见性、标题以及任务描述
        .setNotificationVisibility(Request.VISIBILITY_VISIBLE)
        .setTitle("···")
        .setDescription("···")
        // 禁止或允许数据漫游时下载
        .setAllowedOverRoaming(true)
        // 设置文件存放目录
        .setDestinationUri(Uri.fromFile(file))
        // 设置文件类型
        .setMimeType("···")
        // 禁止或允许使用计费流量下载
        .setAllowedOverMetered(true)
        // 设置下载任务的请求头
        .addRequestHeader(···)

// 提交下载任务并获取任务ID以便进行追踪
val downloadId: Long = downloadManager.enqueue(downloadRequest)
```

如果下载任务启动时遭遇网络环境不满足、SD卡未挂载完成以及超过最大并发数等异常情况，DownloadManager会自行暂停下载任务，直到恢复正常下载条件。

> 注：`setAllowedOverMetered()` 与 `setAllowedOverRoaming()` 自 API 24 起已弃用（计费网络与漫游下载默认始终允许）。

### 获取下载信息

获取下载信息需要通过`DownloadManager.Query`对象和ContentProvider组件：

```kotlin
val downloadQuery: DownloadManager.Query = DownloadManager.Query().setFilterById(downloadId)
val cursor: Cursor? = downloadManager.query(downloadQuery)

cursor?.apply {
    if (moveToFirst()) {
        // 已经下载文件大小
        getLong(getColumnIndexOrThrow(DownloadManager.COLUMN_BYTES_DOWNLOADED_SO_FAR))
        // 下载文件的总大小
        getLong(getColumnIndexOrThrow(DownloadManager.COLUMN_TOTAL_SIZE_BYTES))
        // 下载状态代码
        val currentStatus = getInt(getColumnIndex(DownloadManager.COLUMN_STATUS))
        // 下载文件的URI
        getString(getColumnIndexOrThrow(DownloadManager.COLUMN_LOCAL_URI))
        when (currentStatus) {
            DownloadManager.STATUS_SUCCESSFUL -> {
                // TODO: 下载成功
            }
            DownloadManager.STATUS_FAILED -> {
                // TODO: 下载失败
            }
            else -> Unit
        }
    }
}
```

如果要监听下载状态，实际上有两种方式，一种比较简单，即通过子线程定时更新`Cursor`对象，然后按照上面的示例代码把状态信息读取出来，再传递给回调；另一种则是继承`ContentObserver`类，重写其`onChange()`方法，然后对其注册和注销监听。后者调用`onChange()`的频率通常不受开发者控制，因此在界面待更新元素过多且网速较快的情况下，快速执行`onChange()`将会对界面性能产生不利影响。

## 第三方替代框架

DownloadManager虽然稳定省心，但也存在一些固有限制：单线程下载导致速度受限、自定义鉴权/请求头能力弱、批量任务与优先级控制不足、进度需自行轮询或监听。因此在需要"多线程分块下载、精细控制、批量队列"的场景下，开发者往往会选择第三方下载框架来替代它。以下是几个较主流的方案。

### FileDownloader

[FileDownloader](https://github.com/lingochamp/FileDownloader)是流利说（lingochamp）团队开源的老牌文件下载引擎，曾是DownloadManager最主流的替代方案。其核心能力包括：

+ 多任务、多线程（多连接）分块下载，显著提升大文件下载速度；
+ 断点续传（基于数据库持久化断点信息）；
+ 排队调度与高并发控制；
+ 组件可替换（连接、输出流、数据库等均可自定义）。

```groovy
implementation 'com.liulishuo.filedownloader:library:1.7.7'
```

需要注意两点：其一，FileDownloader采用独立进程（`:filedownloader`）运行下载服务，内存开销相对较大；其二，**作者已将开发重心转移到其继任者OkDownload上，FileDownloader此后只做bug修复、不再新增功能**。

### OkDownload

[OkDownload](https://github.com/lingochamp/okdownload)是FileDownloader的"精神续作"（官方自称FileDownloader2），由同一核心作者重构。相比FileDownloader，它抛弃了多进程的笨重设计，全面拥抱OkHttp，架构更轻量、模块化，单元测试覆盖率也更高。

```groovy
implementation 'com.liulishuo.okdownload:okdownload:1.0.7'
implementation 'com.liulishuo.okdownload:sqlite:1.0.7'   // 断点信息存储
implementation 'com.liulishuo.okdownload:okhttp:1.0.7'   // 基于 OkHttp 的连接
```

同样需要留意的是，OkDownload的最新版本1.0.7发布于2019年12月，此后也已多年未更新。

### Fetch

[Fetch](https://github.com/tonyofrancis/Fetch)是一个较现代的下载管理器库，API简单、可定制性强，支持后台持续下载、并发下载、暂停/恢复、任务优先级、分组下载、ETA/速度上报、通知栏以及SAF（Storage Access Framework）等，其新版内部基于WorkManager进行调度。

```groovy
// 需先在 settings.gradle 中添加 JitPack 仓库
implementation 'com.github.tonyofrancis.Fetch:fetch2:3.4.1'
```

Fetch最新版本3.4.1发布于2024年12月，此后维护节奏同样明显放缓。

### 其他方案

+ [Aria](https://github.com/AriaLyy/Aria)：功能全面（支持下载、上传、FTP等），断点续传与批量任务支持完善，但依赖较复杂；
+ [PRDownloader](https://github.com/MindorksOpenSource/PRDownloader)：轻量级下载库，支持并发下载与暂停/恢复，适合简单场景。

### 选型建议

综合来看，可以得出以下结论：

1. **能满足需求时优先用系统DownloadManager**：它由系统进程承载，App被划掉后下载仍不中断、自带通知栏进度，这份稳定性是三方库难以比拟的，绝大多数常规下载（如APK更新）用它就够了；
2. **需要精细控制时才考虑三方库**：当需要多线程分块加速、自定义鉴权/请求头、批量任务与优先级队列、应用内可控的暂停/恢复/重试等能力时，再引入FileDownloader/OkDownload/Fetch等；
3. **必须正视第三方库自身的维护状态**：上述替代框架大多也已停止或大幅放缓维护（FileDownloader转OkDownload、OkDownload停在2019年、Fetch停在2024年），引入前需评估其与当前Android版本及compileSdk的兼容性风险；
4. **追求极致可控可自研**：若三方库仍不满足且对性能/体积有要求，可基于OkHttp（Range头 + 文件IO）+ Room（持久化断点）自行实现，控制力最强但成本最高。
