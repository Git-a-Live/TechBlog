广播机制被广泛应用于计算机领域，在Android开发中自然也有这样一套机制。Android开发中的广播机制比较灵活，每个应用都可以针对自己感兴趣的广播内容进行注册，这样就只会接收到自己关心的广播信息。这些广播信息既可以由系统发出，也可以由其他应用程序发出。**发出广播采用的是Intent，接收广播则使用Broadcast Receiver（广播接收器）**。

## 广播的类型

| 类型 | 投递方式 | 是否可截断 | 发送方法 |
|:--|:--|:--:|:--|
| **标准广播** | 所有匹配的接收器都会收到，**顺序不确定** | 否 | `sendBroadcast()` |
| **有序广播** | 按优先级**串行**投递，上一个返回后才轮到下一个 | 是 | `sendOrderedBroadcast()` |

> 有序广播常被描述成“同步执行”，这个说法容易误解：串行指的是**接收器之间**一个接一个，而不是发送方阻塞等待。`sendOrderedBroadcast()` 和 `sendBroadcast()` 一样，调用后立刻返回。

## 广播注册

| 方式 | 注册位置 | 生效期 | 能否接收隐式广播 |
|:--|:--|:--|:--|
| **上下文注册**（原称动态注册） | 代码中调用 `registerReceiver()` | `registerReceiver()` 到 `unregisterReceiver()` 之间 | 可以 |
| **清单声明**（原称静态注册） | `AndroidManifest.xml` 中的 `<receiver>` | 安装后长期有效，应用未运行也能被拉起 | **Android 8.0 起多数不允许** |

### 上下文注册

```kotlin
class MainActivity : AppCompatActivity() {

    private val demoReceiver = DemoBroadcastReceiver()

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)

        val filter = IntentFilter("ActionTag")

        // 只接收本应用发出的广播：RECEIVER_NOT_EXPORTED
        // 需要接收其他应用的广播：改用 RECEIVER_EXPORTED
        // 只接收系统广播：不传 flags，直接用 registerReceiver(receiver, filter)
        ContextCompat.registerReceiver(
            this,
            demoReceiver,
            filter,
            ContextCompat.RECEIVER_NOT_EXPORTED
        )
    }

    override fun onDestroy() {
        super.onDestroy()
        // 注册与反注册必须成对出现，漏掉就会持有 Activity 造成泄漏
        unregisterReceiver(demoReceiver)
    }
}

class DemoBroadcastReceiver : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        // 运行在主线程，只做轻量处理
    }
}
```

> **Android 14（API 34）起，注册接收器必须说明导出行为。** 官方文档原文：以 Android 14 或更高版本为目标平台、且使用上下文注册的应用，必须指定 `RECEIVER_EXPORTED` 或 `RECEIVER_NOT_EXPORTED`，否则会抛出 `SecurityException`。
>
> 但有一个**例外**：如果这个接收器**只**用于接收系统广播，则不应指定标志。因为 `RECEIVER_NOT_EXPORTED` 虽然能收到部分系统广播，却收不到蓝牙、电话这类**高权限应用**发出的广播——它们属于 Android 框架的一部分，但不在系统 UID 下运行。需要接收全部系统广播时，只能用 `RECEIVER_EXPORTED`。
>
> 混合场景（既要收本应用广播，又要收系统广播）官方建议**拆成两个接收器**，分别注册。

`ContextCompat.registerReceiver()` 由 `androidx.core:core` 提供（项目里通常已通过 `core-ktx` 间接引入），它把标志位的版本差异封装掉了，比自己判断 `Build.VERSION` 更稳妥。

### 清单声明

Broadcast Receiver的清单注册和Activity类似，也是分手动和非手动两种。手动注册不仅需要自己继承BroadcastReceiver编写子类，还要在AndroidManifest文件中注册，因此在实际开发中更推荐通过`File`➡`New`➡`Other`➡`Broadcast Receiver`的途径创建并自动注册，如下图所示。

![[Screenshot 2020-11-30 110452.png]]

`Exported`属性表示是否允许其他应用向这个接收器发送广播，`Enabled`属性表示是否启用这个Broadcast Receiver。完成创建之后，Android Studio会自动创建一个BroadcastReceiver的子类：

```kotlin
class MyReceiver : BroadcastReceiver() {

    override fun onReceive(context: Context, intent: Intent) {
        // 广播到达时的处理逻辑
        TODO("MyReceiver.onReceive() is not implemented")
    }
}
```

同时，AndroidManifest文件中也会自动新建`<receiver>`标签并完成初步注册。但要真正接收广播，还需要开发者自行补上`<intent-filter>`：

```xml
<application>

    <receiver
        android:name=".MyReceiver"
        android:enabled="true"
        android:exported="false">

        <intent-filter>
            <action android:name="com.example.app.ACTION_TAG" />
        </intent-filter>

    </receiver>

</application>
```

清单声明一直是被持续收紧的对象，因为它的特点正是“应用没运行也能被拉起”——这长期被用于后台唤醒。当前需要遵守的限制：

+ **Android 8.0（API 26）**：以 API 26 及以上为目标平台时，**清单声明的接收器无法接收大多数隐式广播**（即并非专门发给该应用的广播）。少数例外见官方“隐式广播例外”清单，如开机、时区变更等。
+ **Android 12（API 31）**：只要写了`<intent-filter>`，就必须显式声明`android:exported`，漏写会导致应用无法在 Android 12 及以上设备安装。
+ **Android 14（API 34）**：隐式 Intent 只能送达**已导出**的组件。应用内的广播接收器若为`exported="false"`，发送时必须用显式 Intent（`Intent(context, MyReceiver::class.java)` 或 `setPackage()`），否则不会送达。
+ **停止状态**：应用安装后从未启动、或被用户“强制停止”，会处于 stopped 状态，收不到广播。发送方若确实需要送达，可加`Intent.FLAG_INCLUDE_STOPPED_PACKAGES`。
+ **Android 14 的缓存状态**：应用处于 cached 状态时，系统会把广播排队，等应用回到活跃状态再统一投递，内容相同的广播还可能被合并。

> 这些限制的直接后果是：**除了开机、网络、电量这类系统事件，广播不该再作为应用内的通信手段**。跨模块传消息用 `SharedFlow` / `StateFlow`，后台任务用 `WorkManager`，两者都不受上述限制约束。

## 广播发送

### 标准广播

```kotlin
val intent = Intent("ActionTag").apply {
    setPackage(packageName)          // 限定目标应用，见下方说明
    putExtra("key", value)           // 广播同样可以携带数据
}
sendBroadcast(intent)
```

和Activity一样，`ActionTag`既可以用系统提供的标准 action，也可以用自定义内容。自定义 action 建议加包名前缀（如`com.example.app.ACTION_TAG`），避免与其他应用撞名。

`setPackage()` 不是可选项，它同时解决三个问题：

+ Android 8.0 起，清单声明的接收器收不到隐式广播，加上包名后这条广播就变得“够显式”，可以送达；
+ Android 14 起，隐式 Intent 只送达已导出组件，限定包名同样满足该规则；
+ 广播只发给指定应用，不会被同设备上的其他应用顺手收到。

### 有序广播

```kotlin
val intent = Intent("ActionTag").apply {
    setPackage(packageName)
}

// 第二个参数是"接收方必须持有的权限"，传 null 表示不限制
sendOrderedBroadcast(intent, null)
```

`receiverPermission` 的语义常被搞反：它约束的是**接收方**——接收方必须持有这个权限，才能收到你发的广播；传`null`则不限制。这与`<receiver android:permission="...">`正好相反，后者约束的是**发送方**。

不限制接收方时，先后顺序由清单里的`android:priority`决定：

```xml
<receiver
    android:name=".MyReceiver"
    android:enabled="true"
    android:exported="false">

    <!-- priority 是整数，数值越大越先收到；未设置按 0 处理 -->
    <intent-filter android:priority="100">
        <action android:name="ActionTag" />
    </intent-filter>

</receiver>
```

优先级有三条边界必须知道：

+ **同优先级时顺序未定义**。这不是“退化成标准广播”——广播仍是有序的，仍可被截断，只是同优先级接收器之间的先后不由系统保证。
+ **Android 16 起，跨进程传递广播的顺序不再由优先级保证**。官方文档明确：无法保证`android:priority`或`IntentFilter.setPriority()`在不同进程之间传递广播的顺序，**优先级只在同一应用进程内有效**。
+ 优先级会被自动限制在`(SYSTEM_LOW_PRIORITY + 1, SYSTEM_HIGH_PRIORITY - 1)`区间内，只有系统组件才能使用这两个边界值。

有序广播的真正价值是**沿链路回传结果**，这一点标准广播做不到：

```kotlin
// 接收方：把处理结果写回广播，供后续接收器和发送方读取
override fun onReceive(context: Context, intent: Intent) {
    setResultCode(Activity.RESULT_OK)
    setResultData("processed")
    setResultExtras(Bundle().apply { putString("key", "value") })

    // 截断：后续接收器将收不到这条广播
    abortBroadcast()
}
```

```kotlin
// 发送方：传入 resultReceiver，在链路走完后拿到最终结果
sendOrderedBroadcast(
    intent,
    null,
    object : BroadcastReceiver() {
        override fun onReceive(context: Context, intent: Intent) {
            val code = resultCode
            val data = resultData
            val extras = getResultExtras(true)
        }
    },
    null,                       // scheduler，传 null 用主线程
    Activity.RESULT_OK,         // initialCode
    null,                       // initialData
    null                        // initialExtras
)
```

`abortBroadcast()`只对有序广播有效；对`sendBroadcast()`发出的标准广播调用它不会生效，也不会报错。

## 权限与安全

广播的权限是双向的，方向的区分比 API 记忆更重要：

| 想达到的效果 | 手段 | 约束的是谁 |
|:--|:--|:--|
| 只有持有某权限的应用才能收到我发的广播 | `sendBroadcast(intent, "权限名")` | **接收方** |
| 只有持有某权限的应用才能给我发广播 | `<receiver android:permission="权限名">` | **发送方** |
| 声明本应用要用到某权限 | `<uses-permission android:name="..." />` | 自己 |

应用内部使用的广播，推荐自定义一个`signature`级权限，把接收器锁在签名相同的应用之间：

```xml
<!-- 定义权限：只有同签名的应用才能被授予 -->
<permission
    android:name="com.example.app.permission.INTERNAL_BROADCAST"
    android:protectionLevel="signature" />

<application>

    <receiver
        android:name=".MyReceiver"
        android:exported="true"
        android:permission="com.example.app.permission.INTERNAL_BROADCAST">

        <intent-filter>
            <action android:name="com.example.app.ACTION_TAG" />
        </intent-filter>

    </receiver>

</application>
```

权限缺失的后果分两种情形：缺少`RECEIVE_BOOT_COMPLETED`这类**接收权限**时，广播静默不到达，不会崩溃；而发送受保护广播时缺少**发送权限**，才会抛`SecurityException`。

```xml
<!-- 接收开机广播必须声明该权限 -->
<uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED" />
```

## 耗时任务与超时

`onReceive()`默认运行在主线程（注册时传入自定义`Handler`才能换线程），且**广播本身有超时限制**：当前 AOSP 的默认值是 10 秒（`BroadcastConstants.DEFAULT_TIMEOUT`，实际还会乘以设备性能系数`HW_TIMEOUT_MULTIPLIER`）。超时会触发 ANR，日志里的原因形如：

```text
ANR in com.example.app
Reason: Broadcast of Intent { act=ActionTag flg=0x10 cmp=com.example.app/.MyReceiver }
```

另一个常被忽略的点是：**`onReceive()`返回后，进程随时可能被系统回收**。所以“在`onReceive()`里起个子线程继续跑”并不可靠——接收器实例已经失效，进程也可能先被杀掉。

需要异步处理时，用`goAsync()`把广播的活跃期延长到后台任务结束：

```kotlin
class MyReceiver : BroadcastReceiver() {

    override fun onReceive(context: Context, intent: Intent) {
        val pendingResult = goAsync()

        // appScope 应为应用级作用域：CoroutineScope(SupervisorJob() + Dispatchers.IO)
        appScope.launch {
            try {
                doHeavyWork()
            } finally {
                pendingResult.finish()      // 必须调用，否则广播一直处于活跃状态
            }
        }
    }
}
```

> `goAsync()`只是允许你把工作挪到别的线程，**并不延长 10 秒的超时**。真正耗时（下载、批量写库）应当交给`WorkManager`，让系统按约束条件调度，而不是硬扛在广播里。

## 本地广播与它的替代

标准广播和有序广播都属于**全局广播**：同一设备上的其他应用也能收到。若广播里带有重要数据，就有被截获的风险；反过来，其他应用不断发送垃圾广播也会拖累系统。本地广播（Local Broadcast）原本就是为解决这个问题而设计的——它只在进程内传递。

但`LocalBroadcastManager`已经废弃，时间线需要说清楚：

+ **2018-12-17**：`androidx.localbroadcastmanager:1.1.0-alpha01` 起标记为弃用；
+ **2022-01-12**：发布 `1.1.0`，**该库被完全废弃且不再有新版本**，官方给出的迁移方向是“可观察模式的其他实现，合适的选项可能是 LiveData 或响应式流，取决于用例”。

也就是说，现在新建项目不该再引入这个库。应用内跨模块通信的常规做法是：

+ **事件**（一次性的、发生过就结束）：`MutableSharedFlow`，配合`tryEmit()`做非阻塞发送；
+ **状态**（订阅即得当前值）：`StateFlow`，配合[[LiveData组件]]里的观察思路理解其与 UI 的关系；
+ **与 UI 生命周期绑定**：`repeatOnLifecycle`或`collectAsStateWithLifecycle()`，原理见[[8. Kotlin协程：进阶部分#StateFlow 与 SharedFlow|StateFlow 与 SharedFlow]]；
+ **后台任务完成通知**：`WorkManager`的`WorkInfo`本身就是`Flow`，不需要再借广播中转。

广播仍然保留的正当场景只有三类：接收**系统广播**（开机、网络变化、电量、时区）、与**其他应用或系统组件**交互、以及**跨进程**通知。应用内部的模块间通信不再属于这一类。

## 调试

```shell
# 向指定应用发送一条带字符串参数的广播（-p 限定包名）
adb shell am broadcast -a com.example.app.ACTION_TAG -p com.example.app --es key value

# 直接发给某个接收器（显式）
adb shell am broadcast -n com.example.app/.MyReceiver -a com.example.app.ACTION_TAG

# 查看系统中已注册的接收器与最近的广播记录
adb shell dumpsys activity broadcasts
```

配合 Logcat 过滤`BroadcastQueue`、`BackgroundManager`等 tag，可以看清一条广播被投递或丢弃的原因。
