Content Provider用于**在不同应用程序之间有选择地共享数据**。它允许一个应用访问另一个应用的数据，同时通过权限机制保证只暴露允许共享的那部分，避免用户数据被随意读取。

四大组件里只有它**不由 Intent 启动**：客户端拿到的入口是`ContentResolver`，用`content://`开头的 URI 定位数据，再用`query`/`insert`/`update`/`delete`完成 CRUD。系统自带的联系人、媒体库（`MediaStore`）、日历都是 Content Provider。

## URI 的结构

```text
content://com.example.app.provider/tasks/1
```

拆开看是四段：`content://`是固定的 scheme，`com.example.app.provider`是 authority，`/tasks`是 path，末尾的`/1`是指向单条记录的 id（可选）。

| 部分        | 含义                                                   |
| :-------- | :--------------------------------------------------- |
| `content` | 固定 scheme，表示由 ContentResolver 路由                     |
| authority | 提供方的唯一标识，惯例是`applicationId + ".provider"`，**必须全局唯一** |
| path      | 区分同一应用内的不同表，如`tasks`、`users`                         |
| id        | 可选，指向单条记录，如`1`                                       |

authority 并不是“包名”本身，只是习惯上以包名为前缀。同一设备上两个应用声明相同 authority，后者会安装失败。

拼单条记录的 URI 不要手拼字符串，用`ContentUris`：

```kotlin
val itemUri = ContentUris.withAppendedId(uri, id)      // 追加 /id
val id = ContentUris.parseId(itemUri)                  // 取回 id
```

## 运行时权限

访问其他应用的数据通常需要权限。普通权限只需在清单里声明，**危险权限还必须在运行时向用户申请**：

```xml
<uses-permission android:name="android.permission.READ_CONTACTS" />
```

```kotlin
// 1. 检查是否已授权
val granted = ContextCompat.checkSelfPermission(
    this,
    Manifest.permission.READ_CONTACTS
) == PackageManager.PERMISSION_GRANTED
```

申请与接收结果推荐用 Activity Result API，它替代了已废弃的`onRequestPermissionsResult()`：

```kotlin
// 2. 在 Activity 创建阶段无条件注册
private val requestContacts = registerForActivityResult(
    ActivityResultContracts.RequestMultiplePermissions()
) { result ->
    if (result[Manifest.permission.READ_CONTACTS] == true) {
        readContacts()
    } else {
        // 用户拒绝：降级处理，不要假设权限一定拿到
    }
}

// 3. 需要时发起申请
private fun ensureContactsPermission() {
    if (ContextCompat.checkSelfPermission(this, Manifest.permission.READ_CONTACTS)
        == PackageManager.PERMISSION_GRANTED
    ) {
        readContacts()
    } else {
        requestContacts.launch(arrayOf(Manifest.permission.READ_CONTACTS))
    }
}
```

> 几个易错点。第一，**申请结果可能全部为拒绝**，业务逻辑必须有降级分支，不能默认“申请了就会给”。第二，`ActivityCompat.requestPermissions()`配合`onRequestPermissionsResult()`仍能工作，但 androidx 已把该回调标记为废弃，新代码不要再用。第三，用户勾选“不再询问”后再申请，系统会**直接回调拒绝而不弹窗**，此时只能引导用户去设置页手动开启。

## 用 ContentResolver 访问数据

`ContentResolver`实例由`Context.getContentResolver()`提供（不是 ContentResolver 自己的方法）。四个方法对应数据库的 CRUD，只是把“表名”换成了 URI。

### 查询

```kotlin
val uri = Uri.parse("content://com.example.app.provider/tasks")

val cursor = contentResolver.query(
    uri,
    arrayOf("_id", "title", "done"),   // projection：要哪些列，null 表示全部
    "done = ?",                        // selection：where 条件，? 是占位符
    arrayOf("0"),                      // selectionArgs：依次替换占位符
    "title ASC"                        // sortOrder：排序，null 表示默认顺序
)

cursor?.use { c ->
    val idIndex = c.getColumnIndexOrThrow("_id")
    val titleIndex = c.getColumnIndexOrThrow("title")
    while (c.moveToNext()) {
        val id = c.getLong(idIndex)
        val title = c.getString(titleIndex)
    }
}
```

`use { }`会在代码块结束时自动关闭 Cursor，等价于`try/finally`，应优先使用。

`query()`的五个参数与 SQL 的对应关系：

| 参数 | 对应 SQL | 说明 |
|:--|:--|:--|
| `uri` | `FROM table` | 定位哪张表 |
| `projection` | `SELECT col1, col2` | 为 null 时返回全部列 |
| `selection` | `WHERE col = ?` | 为 null 时不筛选 |
| `selectionArgs` | — | 依次替换`?`，避免 SQL 注入 |
| `sortOrder` | `ORDER BY col` | 为 null 时顺序由提供方决定 |

除`uri`外的参数都可以传 null，四者组合起来相当于`SELECT * FROM table`。

### 增删改

```kotlin
// 插入：返回新记录的 URI，失败返回 null
val values = contentValuesOf("title" to "写周报", "done" to 0)
val newUri = contentResolver.insert(uri, values) ?: error("插入失败")

// 更新：返回受影响的行数
val updated = contentResolver.update(
    newUri,
    contentValuesOf("done" to 1),
    null,
    null
)

// 删除：返回受影响的行数
val deleted = contentResolver.delete(uri, "done = ?", arrayOf("1"))
```

> 并非所有 Provider 都支持全部操作。有的只读（如系统联系人里的某些表），有的不允许按条件删除，调用后可能抛`UnsupportedOperationException`或`SecurityException`，需要按提供方的文档来。

### 批量操作

多条写入逐条调用会多次跨进程，用`applyBatch()`合并成一次事务：

```kotlin
val operations = arrayListOf(
    ContentProviderOperation.newInsert(uri)
        .withValue("title", "任务 A")
        .build(),
    ContentProviderOperation.newUpdate(uri)
        .withValue("done", 1)
        .withSelection("_id = ?", arrayOf("1"))
        .build()
)

try {
    contentResolver.applyBatch("com.example.app.provider", operations)
} catch (e: OperationApplicationException) {
    // 整批回滚
}
```

### 监听数据变化

Provider 在写入后调用`notifyChange()`，客户端注册`ContentObserver`即可收到通知：

```kotlin
val observer = object : ContentObserver(Handler(Looper.getMainLooper())) {
    override fun onChange(selfChange: Boolean, uri: Uri?) {
        // 重新查询或刷新界面
    }
}

// notifyForDescendants = true 时，子路径（如 /tasks/1）的变化也会通知
contentResolver.registerContentObserver(uri, true, observer)

// 不用时必须反注册，否则泄漏
contentResolver.unregisterContentObserver(observer)
```

## 实现自己的 Content Provider

> **Provider 的接口是 SQL 风格的契约，但底层不一定是数据库。** `query()` 的四个参数照搬了`SELECT`/`WHERE`/`ORDER BY`的形状，`Cursor` 又和`SQLiteDatabase.query()`返回同一个类型，所以看上去“就是 SQL”。
>
> 但`Cursor`的本质是**带类型列的行集合**，与 SQLite 没有绑定关系。`FileProvider`就是反例：它的`query()`用`MatrixCursor`临时拼出一行，内容是文件名和大小；`insert()`/`update()`直接抛`UnsupportedOperationException`。Provider 背后可以是文件、内存 Map、SharedPreferences，甚至一次网络请求——只要能把结果包装成 Cursor 就行。SQLite 只是最常见的那种实现。

Android Studio 提供了模板：`File`➡`New`➡`Other`➡`Content Provider`，填写 authority 等属性后会自动生成子类与清单声明。

![[cp_1.png]]

模板会生成六个待实现的方法：

```kotlin
class DemoContentProvider : ContentProvider() {

    override fun onCreate(): Boolean {
        // 初始化，返回 true 表示成功
        return true
    }

    override fun query(
        uri: Uri,
        projection: Array<String>?,
        selection: String?,
        selectionArgs: Array<String>?,
        sortOrder: String?
    ): Cursor? = null

    override fun insert(uri: Uri, values: ContentValues?): Uri? = null

    override fun update(
        uri: Uri,
        values: ContentValues?,
        selection: String?,
        selectionArgs: Array<String>?
    ): Int = 0

    override fun delete(uri: Uri, selection: String?, selectionArgs: Array<String>?): Int = 0

    override fun getType(uri: Uri): String? = null
}
```

### UriMatcher 路由

同一个 Provider 要处理“整张表”和“单条记录”两类 URI，靠`UriMatcher`分发。`addURI()`接收 authority、path 和自定义 code；path 支持两种通配符：

| 通配符 | 匹配 |
|:--|:--|
| `#` | 任意长度的**数字**，用于 id |
| `*` | 任意长度的**字符串** |

```kotlin
private val matcher = UriMatcher(UriMatcher.NO_MATCH).apply {
    addURI(AUTHORITY, "tasks", TASKS)
    addURI(AUTHORITY, "tasks/#", TASK_ID)
}

// match() 返回 addURI 时登记的 code，都不匹配则返回 UriMatcher.NO_MATCH（-1）
when (matcher.match(uri)) {
    TASKS -> { /* 操作整表 */ }
    TASK_ID -> { /* 操作单条 */ }
    else -> throw IllegalArgumentException("Unknown URI: $uri")
}
```

> **`UriMatcher` 只是路由，不是安全边界。** 它决定“这个 URI 走哪段代码”，并不阻止访问。真正的保护来自三处：清单里的`android:exported`、`readPermission`/`writePermission`，以及**未匹配分支必须抛异常而不是返回全表数据**。如果`else`分支写成了“默认查全部”，那么任何构造出的 URI 都能读到数据。

### 一份可用的实现

以下将其接入 SQLite 上，四个 CRUD 方法全部落地：

```kotlin
class TaskDbHelper(context: Context) : SQLiteOpenHelper(context, "tasks.db", null, 1) {

    override fun onCreate(db: SQLiteDatabase) {
        db.execSQL(
            """
            CREATE TABLE tasks (
                _id INTEGER PRIMARY KEY AUTOINCREMENT,
                title TEXT NOT NULL,
                done INTEGER NOT NULL DEFAULT 0
            )
            """.trimIndent()
        )
    }

    override fun onUpgrade(db: SQLiteDatabase, oldVersion: Int, newVersion: Int) {
        db.execSQL("DROP TABLE IF EXISTS tasks")
        onCreate(db)
    }
}
```

```kotlin
class TaskProvider : ContentProvider() {

    private lateinit var helper: TaskDbHelper

    private val matcher = UriMatcher(UriMatcher.NO_MATCH).apply {
        addURI(AUTHORITY, "tasks", TASKS)
        addURI(AUTHORITY, "tasks/#", TASK_ID)
    }

    override fun onCreate(): Boolean {
        // 主线程执行，且早于 Application.onCreate()，只做轻量初始化
        helper = TaskDbHelper(requireNotNull(context))
        return true
    }

    override fun query(
        uri: Uri,
        projection: Array<String>?,
        selection: String?,
        selectionArgs: Array<String>?,
        sortOrder: String?
    ): Cursor {
        val (where, args) = when (matcher.match(uri)) {
            TASKS -> selection to selectionArgs
            TASK_ID -> "_id = ?" to arrayOf(uri.lastPathSegment.toString())
            else -> throw IllegalArgumentException("Unknown URI: $uri")
        }
        return helper.readableDatabase.query(
            "tasks", projection, where, args, null, null, sortOrder ?: "_id DESC"
        )
    }

    override fun insert(uri: Uri, values: ContentValues?): Uri {
        val id = helper.writableDatabase.insert("tasks", null, values)
        if (id == -1L) throw SQLException("Insert failed: $uri")
        notifyChanged(uri)
        return ContentUris.withAppendedId(CONTENT_URI, id)
    }

    override fun update(
        uri: Uri,
        values: ContentValues?,
        selection: String?,
        selectionArgs: Array<String>?
    ): Int {
        val count = when (matcher.match(uri)) {
            TASKS -> helper.writableDatabase.update("tasks", values, selection, selectionArgs)
            TASK_ID -> helper.writableDatabase.update(
                "tasks", values, "_id = ?", arrayOf(uri.lastPathSegment.toString())
            )
            else -> throw IllegalArgumentException("Unknown URI: $uri")
        }
        if (count > 0) notifyChanged(uri)
        return count
    }

    override fun delete(uri: Uri, selection: String?, selectionArgs: Array<String>?): Int {
        val count = when (matcher.match(uri)) {
            TASKS -> helper.writableDatabase.delete("tasks", selection, selectionArgs)
            TASK_ID -> helper.writableDatabase.delete(
                "tasks", "_id = ?", arrayOf(uri.lastPathSegment.toString())
            )
            else -> throw IllegalArgumentException("Unknown URI: $uri")
        }
        if (count > 0) notifyChanged(uri)
        return count
    }

    override fun getType(uri: Uri): String = when (matcher.match(uri)) {
        TASKS -> "vnd.android.cursor.dir/vnd.$AUTHORITY.tasks"
        TASK_ID -> "vnd.android.cursor.item/vnd.$AUTHORITY.tasks"
        else -> throw IllegalArgumentException("Unknown URI: $uri")
    }

    private fun notifyChanged(uri: Uri) {
        context?.contentResolver?.notifyChange(uri, null)
    }

    companion object {
        const val AUTHORITY = "com.example.app.provider"
        const val TASKS = 1
        const val TASK_ID = 2
        val CONTENT_URI: Uri = Uri.parse("content://$AUTHORITY/tasks")
    }
}
```

### getType 与 MIME

`getType()`返回该 URI 对应数据的 MIME 类型，规则固定为两种：

| URI 形态 | MIME |
|:--|:--|
| 以 path 结尾（整表） | `vnd.android.cursor.dir/vnd.<authority>.<path>` |
| 以 id 结尾（单条） | `vnd.android.cursor.item/vnd.<authority>.<path>` |

这里的`dir`表示“目录/集合”，`item`表示单条记录。客户端拿它判断能否处理这类数据，`Intent`按 type 匹配时也依赖它。

### 清单声明与权限

```xml
<provider
    android:name=".provider.TaskProvider"
    android:authorities="${applicationId}.provider"
    android:exported="true"
    android:readPermission="com.example.app.permission.READ_TASKS"
    android:writePermission="com.example.app.permission.WRITE_TASKS" />
```

+ `android:exported`：**默认值是`false`**（targetSdk ≥ 17 时），要供其他应用访问必须显式写`true`；
+ `android:readPermission` / `android:writePermission`：分别约束读写，也可用`android:permission`同时约束两者。它们引用的权限要**先在提供方应用里用`<permission>`声明**，再由调用方用`<uses-permission>`申请；
+ `android:grantUriPermissions`：允许通过 Intent 临时授予某个 URI 的访问权，配合`FLAG_GRANT_READ_URI_PERMISSION`使用；
+ `<path-permission>`：按路径细分权限，例如只开放`tasks`而隐藏`users`。

```xml
<!-- 细化到路径：/public 前缀按单独权限控制 -->
<provider
    android:name=".provider.TaskProvider"
    android:authorities="${applicationId}.provider"
    android:exported="true">

    <path-permission
        android:pathPrefix="/public"
        android:readPermission="com.example.app.permission.READ_PUBLIC" />
</provider>
```

## FileProvider：最常见的自定义 Provider

如今绝大多数应用自定义 Provider 的目的只有一个——**把私有文件以`content://`形式分享出去**。Android 7.0（API 24）起禁止用`file://` URI 跨应用传文件（否则抛`FileUriExposedException`），拍照、裁剪、分享都必须走`FileProvider`。

```xml
<provider
    android:name="androidx.core.content.FileProvider"
    android:authorities="${applicationId}.fileprovider"
    android:exported="false"
    android:grantUriPermissions="true">

    <meta-data
        android:name="android.support.FILE_PROVIDER_PATHS"
        android:resource="@xml/file_paths" />
</provider>
```

`res/xml/file_paths.xml`声明哪些目录可以暴露，未列出的目录一律不可访问：

```xml
<paths>
    <cache-path name="cache" path="." />
    <files-path name="files" path="." />
    <external-files-path name="external" path="." />
</paths>
```

```kotlin
// 1. 生成 content:// URI
val file = File(cacheDir, "share.jpg")
val uri = FileProvider.getUriForFile(this, "$packageName.fileprovider", file)

// 2. 附带临时读权限发给目标应用
val intent = Intent(Intent.ACTION_SEND).apply {
    type = "image/jpeg"
    putExtra(Intent.EXTRA_STREAM, uri)
    addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION)
}
startActivity(Intent.createChooser(intent, "分享图片"))
```

接收方不需要任何存储权限，直接用 ContentResolver 打开：

```kotlin
contentResolver.openInputStream(uri)?.use { input ->
    // 读取文件内容
}
```

拍照场景同理，只是把授权换成`FLAG_GRANT_WRITE_URI_PERMISSION`，并把 URI 放进`MediaStore.EXTRA_OUTPUT`。

## 生命周期与性能

| 方法 | 线程 | 时机 |
|:--|:--|:--|
| `onCreate()` | **主线程** | 应用启动时，**早于`Application.onCreate()`** |
| `query`/`insert`/`update`/`delete`/`getType` | Binder 线程池，**可并发** | 客户端每次调用 |

由此有两条硬约束：

+ **`onCreate()`不能做耗时操作**。它会计入应用冷启动时间，且有多个 Provider 时会按`android:initOrder`依次创建，一个慢会拖住全部。数据库的建表应交给`SQLiteOpenHelper`，等首次真正访问时才打开；
+ **数据方法必须线程安全**。多个客户端可能同时调用，共享的游标、缓存、数据库连接都要考虑并发。

另外，查询结果通过`CursorWindow`跨进程传输，单个窗口有大小上限。结果集很大时必须分页（`LIMIT`/`OFFSET`，或按`_id`分段），否则会出现窗口分配失败（`CursorWindowAllocationException`）、单行过大（`SQLiteBlobTooBigException`），或者只填充了部分行。Cursor 用完不关则会同时泄漏 CursorWindow 与文件描述符。

## 选型：是否需要自行编写 Provider

| 需求 | 方案 |
|:--|:--|
| 把文件/图片分享给其他应用或相机 | **`FileProvider`** |
| 存入系统相册、读取媒体 | `MediaStore`（系统 Provider，直接操作 URI） |
| 应用内部持久化 | **Room**（底层是 SQLite，不需要 Provider） |
| 应用内模块共享数据 | Room + `Flow`，不涉及跨进程 |
| 真正向其他应用暴露结构化数据 | 自定义 Content Provider + 权限 |

> 从 Android 11（API 30）起有**软件包可见性**限制：客户端要访问其他应用的 Provider，需要在清单里声明目标 authority，否则可能“看不到”提供方。

```xml
<queries>
    <provider android:authorities="com.example.app.provider" />
</queries>
```

> 自己写 Provider 在 2026 年已不是默认选项。它只在“**必须向外部应用暴露数据**”时才值得，其余场景用 Room、`FileProvider`、`MediaStore` 就够了。
