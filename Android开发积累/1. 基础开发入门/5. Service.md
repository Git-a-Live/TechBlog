Service是Android提供的**没有界面的组件**，用于执行不需要用户交互的长时任务。它依赖应用的进程，而非独立运行——**进程被系统终止，Service随之消亡**，所以它不是“保活”手段。

Service本身**不创建线程**：`onCreate()`、`onStartCommand()`、`onBind()` 都运行在应用主线程。耗时操作必须自己切到子线程或协程，否则会直接拖住 UI。

## 生命周期与启动方式

创建Service的常规途径是`File`➡`New`➡`Service`，在配置窗口里选择`Exported`、`Enabled`等属性后，Android Studio会同时生成子类与清单声明，如下图所示。

![[Screenshot 2020-12-02 133642.png]]

Service有两条启动路径，二者的生命周期不同，也可以混用：

| 路径 | 入口 | 结束方式 | 典型用途 |
|:--|:--|:--|:--|
| **启动式** | `startService()` / `startForegroundService()` | `stopService()` 或 `stopSelf()` | 后台跑任务，不要求与界面交互 |
| **绑定式** | `bindService()` | 最后一个客户端 `unbindService()` | 界面需要调用服务里的方法 |

### 启动式：startService 与 onStartCommand

```kotlin
class DemoService : Service() {

    override fun onCreate() {
        super.onCreate()
        // 第一次创建时调用，早于 onStartCommand
    }

    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        // 每次 startService() 都会调用，可能被调用多次；
        // 需要区分的任务从 intent 的 action 或 extra 中取
        return START_NOT_STICKY
    }

    override fun onBind(intent: Intent): IBinder? = null   // 启动式服务返回 null

    override fun onDestroy() {
        super.onDestroy()
        // 释放资源
    }
}
```

`onStartCommand()`的返回值决定**服务被系统杀掉后是否重建**，这是最容易忽略的一处：

| 返回值 | 行为 |
|:--|:--|
| `START_STICKY` | 重建服务，但**不重投** intent（参数为 null） |
| `START_NOT_STICKY` | 不重建，除非又有新的启动请求 |
| `START_REDELIVER_INTENT` | 重建并**重投最后一个** intent，适合下载、上传这类不可丢的任务 |
| `START_STICKY_COMPATIBILITY` | 旧版本的兼容值，不保证重建 |

Activity侧的控制方式仍然是Intent：

```kotlin
// 启动
val intent = Intent(this, DemoService::class.java)
startService(intent)

// 停止
stopService(intent)
```

服务自己停止则调用`stopSelf()`；如果一次启动对应一次任务，用`stopSelf(startId)`更精确——它会先比对`startId`，避免把后续启动的任务一起停掉。

> **Android 8.0（API 26）起，应用在后台时不能再用`startService()`启动后台服务**，否则抛`IllegalStateException`（Android 12+ 的具体类型是`BackgroundServiceStartNotAllowedException`）。替代做法是`startForegroundService()`，并且必须在超时前调用`startForeground()`把服务提升为前台，否则同样会崩。

### 绑定式：bindService 与服务通信

要让Activity调用Service里的方法，需要三步：在Service里定义一个`Binder`内部类、让`onBind()`返回该实例、在客户端把它向下转型。

```kotlin
class DemoService : Service() {

    private val demoBinder = DemoBinder()

    override fun onBind(intent: Intent): IBinder = demoBinder

    inner class DemoBinder : Binder() {
        fun getProgress(): Int = 42          // 客户端可以直接调用
    }
}
```

```kotlin
private var demoBinder: DemoService.DemoBinder? = null

private val connection = object : ServiceConnection {
    override fun onServiceConnected(name: ComponentName, service: IBinder) {
        // 注意：这里要转型，而不是 new 一个 DemoBinder
        demoBinder = service as DemoService.DemoBinder
        demoBinder?.getProgress()
    }

    override fun onServiceDisconnected(name: ComponentName) {
        // 只在服务端进程意外死亡时回调；正常 unbind 不会触发
        demoBinder = null
    }
}

override fun onStart() {
    super.onStart()
    val intent = Intent(this, DemoService::class.java)
    bindService(intent, connection, BIND_AUTO_CREATE)
}

override fun onStop() {
    super.onStop()
    // 必须与 bindService 成对出现，否则会泄漏 ServiceConnection
    unbindService(connection)
    demoBinder = null
}
```

`bindService()`的第三个参数是标志位，常用取值：

| 标志 | 作用 |
|:--|:--|
| `BIND_AUTO_CREATE` | 绑定即创建服务，最常用 |
| `BIND_NOT_FOREGROUND` | 不因绑定把服务所在进程提到前台优先级 |
| `BIND_ABOVE_CLIENT` / `BIND_IMPORTANT` | 提高服务进程的 oom 优先级 |
| `BIND_DEBUG_UNBIND` | 调试用，帮助发现忘记解绑的问题 |

同一个Service在**同一个进程**里只有一个实例，多个Activity绑定拿到的是同一个`Binder`对象——但跨应用时，每个客户端拿到的是各自的代理对象。

### 两种方式混用时的生命周期

| 场景 | 创建时机 | 销毁条件 |
|:--|:--|:--|
| 只`startService()` | `onCreate()` → `onStartCommand()` | `stopService()` 或 `stopSelf()` |
| 只`bindService()` | `onCreate()` → `onBind()` | 最后一个客户端 `unbindService()` |
| 两者都有 | `onCreate()` 只执行一次 | **既要`stopService()`，又要全部`unbindService()`** |

也就是说，混用时只调用其中一个，服务不会销毁——这是“服务停不掉”的最常见原因。若只有绑定关系，`stopService()`是无效的。

## 前台服务

前台服务会在状态栏常驻一条通知，把进程优先级提到前台，从而**降低被回收的概率**。它不是为了“更快”，而是为了“不被杀”，并且系统要求用户知情。

```kotlin
private const val CHANNEL_ID = "sync"
private const val NOTIFICATION_ID = 1001
private const val REQUEST_CODE = 0

class SyncService : Service() {

    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        // Android 14 起，类型必须已在清单中声明，否则抛 MissingForegroundServiceTypeException
        ServiceCompat.startForeground(
            this,
            NOTIFICATION_ID, // 通知 ID，不能为 0
            buildNotification(),
            ServiceInfo.FOREGROUND_SERVICE_TYPE_DATA_SYNC
        )
        return START_NOT_STICKY
    }

    override fun onBind(intent: Intent): IBinder? = null
}
```

从Activity侧启动，必须用`startForegroundService()`而不是`startService()`：

```kotlin
val intent = Intent(this, SyncService::class.java)
ContextCompat.startForegroundService(this, intent)
```

### 声明类型与权限（Android 14 起强制）

```xml
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_DATA_SYNC" />

<application>

    <service
        android:name=".SyncService"
        android:exported="false"
        android:foregroundServiceType="dataSync" />

</application>
```

+ `android:foregroundServiceType`声明服务类型，多种类型用`|`分隔，例如`camera|microphone`；
+ 每种类型对应一个`FOREGROUND_SERVICE_<TYPE>`权限，**Android 14（API 34）起缺少权限会抛`SecurityException`**；
+ 类型未声明时，`startForeground()`会抛`MissingForegroundServiceTypeException`；
+ 常见类型有`dataSync`、`mediaPlayback`、`location`、`camera`、`microphone`、`connectedDevice`、`mediaProjection`、`shortService`等。

### 启动与超时限制

`startForegroundService()`只是“申请”，服务必须在限定时间内调用`startForeground()`将通知挂上。这个时限随版本变化：

| 版本          | 时限                                                      | 超时后果                                           |
| :---------- | :------------------------------------------------------ | :--------------------------------------------- |
| Android 8.0 | **5 秒**（`SERVICE_START_FOREGROUND_TIMEOUT`）             | ANR                                            |
| Android 12  | **10 秒**                                                | 抛`ForegroundServiceDidNotStartInTimeException` |
| 当前 AOSP     | **30 秒**（`DEFAULT_SERVICE_START_FOREGROUND_TIMEOUT_MS`） | 同上                                             |

> 还有两条硬限制。**Android 12（API 31）起，应用在后台时无法启动前台服务**，否则抛`ForegroundServiceStartNotAllowedException`，只有少数场景（如精确闹钟、高优先级 FCM、正在通话）例外；**Android 14 起，服务类型与所需权限必须齐备**。因此“后台默默拉起前台服务”这条路在现代 Android 上基本走不通，需要长期后台执行的任务应改用`WorkManager`。

### 通知渠道（Android 8.0 起必需）

```kotlin
private fun buildNotification(): Notification {
    val manager = getSystemService(NotificationManager::class.java)

    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.O) {
        val channel = NotificationChannel(
            CHANNEL_ID,
            "数据同步", // 用户可见的名称
            NotificationManager.IMPORTANCE_LOW // 前台服务通知不得低于 LOW
        )
        manager.createNotificationChannel(channel)
    }

    val pendingIntent = PendingIntent.getActivity(
        this,
        REQUEST_CODE,
        Intent(this, MainActivity::class.java),
        // Android 12 起必须显式指定可变性，否则抛 IllegalArgumentException
        PendingIntent.FLAG_IMMUTABLE or PendingIntent.FLAG_UPDATE_CURRENT
    )

    return NotificationCompat.Builder(this, CHANNEL_ID)
        .setContentTitle("正在同步")
        .setContentText("已同步 3/10 项")
        .setSmallIcon(R.drawable.ic_sync) // 必须设置，否则通知不显示
        .setContentIntent(pendingIntent)
        .setOngoing(true) // 前台服务通知通常不可滑动清除
        .build()
}
```

`NotificationChannel`的三个构造参数：

+ `channelId`：通道ID，任意字符串，全局唯一即可；
+ `channelName`：通道名称，**用户可见**，需要认真命名；
+ `importance`：重要等级，决定是否有声音、是否横幅提示。

| 等级 | 表现 |
|:--|:--|
| `IMPORTANCE_HIGH` | 有声音，并以横幅（heads-up）形式弹出 |
| `IMPORTANCE_DEFAULT` | 有声音，正常显示 |
| `IMPORTANCE_LOW` | 无声音，状态栏显示图标 |
| `IMPORTANCE_MIN` | 无声音，仅在通知栏折叠区域显示 |
| `IMPORTANCE_NONE` | 关闭该通道 |

`NotificationChannel`的常用方法：

| 方法 | 用途 |
|:--|:--|
| `getId()` | 获取通道ID |
| `getName()` | 获取通道名称 |
| `getImportance()` | 获取重要等级 |
| `enableLights(Boolean)` | 是否显示通知灯 |
| `setLightColor(Int)` | 设置通知灯颜色 |
| `enableVibration(Boolean)` | 是否振动 |
| `setSound(Uri, AudioAttributes)` | 设置提示音 |
| `setGroup(String)` | 设置所属通知组 |
| `setBypassDnd(Boolean)` | 是否绕过“请勿打扰” |
| `setLockscreenVisibility(Int)` | 锁屏上的可见性 |
| `canShowBadge()` | 是否允许显示角标 |

## 通知

通知用于应用在后台时向用户传递信息，可以在Activity、Service、BroadcastReceiver中创建，方式一致。核心入口是`NotificationManagerCompat.notify(id, notification)`，前台服务则用`startForeground(id, notification)`。

```kotlin
// 与通知渠道、前台服务共用同一个 ID
NotificationManagerCompat.from(this).notify(NOTIFICATION_ID, notification)
```

几个常用设置：

+ **点击后自动消失**：`.setAutoCancel(true)`，或手动`NotificationManagerCompat.from(this).cancel(id)`；
+ **长文本/大图**：`.setStyle(NotificationCompat.BigTextStyle().bigText(longText))` 或 `BigPictureStyle().bigPicture(bitmap)`，下拉后可展开查看。多个`setStyle()`只有最靠近`build()`的那次生效；`BigTextStyle`会覆盖`setContentText()`的内容；
+ **优先级**：`setPriority()`只对**Android 8.0 以下**有效，8.0 起以通知渠道的`importance`为准，设置它不会有任何效果。

> **Android 13（API 33）起，发通知需要运行时权限`POST_NOTIFICATIONS`。** 前台服务也受此约束：应用**不需要**该权限就能启动前台服务，但拿不到权限时用户看不到那条常驻通知（服务仍在运行，系统会在任务管理器中提示）。因此申请权限与启动服务的顺序要分开考虑，不能假设“通知一定可见”。

## 跨进程通信：AIDL

前面的`Binder`只适用于**同一进程**：`service as DemoService.DemoBinder`能成立，是因为客户端和服务端共享同一个虚拟机。一旦Service被配置到独立进程（或由**另一个应用**绑定），这个转型会直接抛`ClassCastException`——跨进程传过来的只是`BinderProxy`，不是原来的对象。

AIDL（Android Interface Definition Language）解决的就是这件事：它根据`.aidl`接口文件生成`Stub`（服务端）与`Proxy`（客户端）两套代码，把参数按 Parcel 序列化后通过 Binder 驱动传递。

### 什么时候该用 AIDL

| 场景 | 方案 |
|:--|:--|
| 同一进程内，界面调用服务方法 | 本地`Binder`（上一节），**不要用AIDL** |
| 跨进程，客户端不需要并发调用 | `Messenger`（内部仍是Binder，请求串行排队） |
| **跨应用，且服务端要并发处理多个客户端** | **AIDL** |
| 只是共享结构化数据 | `ContentProvider` |
| 应用内模块间通信 | 不需要IPC，用`SharedFlow`/`StateFlow` |

官方原话：只有在需要**不同应用**的客户端通过IPC访问服务、并且希望在服务中进行多线程处理时，才有必要使用AIDL。

### 工程配置（AGP 8.0 起必须手动开启）

> **AGP 8.0 把`android.defaults.buildfeatures.aidl`的默认值从`true`改成了`false`。** 新建工程直接写`.aidl`会编译失败，提示找不到生成的接口。必须在模块的`build.gradle.kts`里显式打开：

```kotlin
android {
    buildFeatures {
        aidl = true
    }
}
```

`.aidl`文件放在`src/main/aidl/`下，目录层级要与`package`声明一致，例如`src/main/aidl/com/example/app/IRemoteService.aidl`。

在`Project`视图下右键点击目标包，选择`New`➡`AIDL`➡`AIDL File`，只需填写文件名，如下图所示：

### 编写 .aidl

```aidl
// src/main/aidl/com/example/app/IRemoteService.aidl
package com.example.app;

import com.example.app.Task;
import com.example.app.IRemoteCallback;

interface IRemoteService {
    // 接口内可以定义 String 与 int 常量
    const int VERSION = 1;

    int getPid();

    List<Task> getTasks();

    void addTask(in Task task);

    void registerCallback(IRemoteCallback callback);

    void unregisterCallback(IRemoteCallback callback);

    // oneway：客户端调用后立即返回，不等待服务端执行
    oneway void fireAndForget(int value);
}
```

```aidl
// src/main/aidl/com/example/app/IRemoteCallback.aidl
package com.example.app;

import com.example.app.Task;

oneway interface IRemoteCallback {
    void onTaskAdded(in Task task);
}
```

自定义类型需要**两个文件**：数据类本身，以及一个只声明`parcelable`的`.aidl`：

```aidl
// src/main/aidl/com/example/app/Task.aidl
package com.example.app;

parcelable Task;
```

```kotlin
// 数据类实现 Parcelable，包名必须与 Task.aidl 一致
@Parcelize
data class Task(val id: Long, val title: String) : Parcelable
```

AIDL支持的数据类型：

+ Java基本类型（`int`、`long`、`boolean`、`float`、`double`、`byte`、`char`、`short`）
+ `String`、`CharSequence`
+ `Parcelable`（含AIDL生成的其他接口）
+ `List`：**支持泛型**，如`List<Task>`；接收端实际类型始终是`ArrayList`
+ `Map`：**不支持参数化类型**，`Map<String, Integer>`这种写法编译不通过；接收端实际类型始终是`HashMap`。官方建议改用`Bundle`
+ `IBinder`

参数方向必须标注，原语、`String`、`IBinder`、AIDL接口默认是`in`且不可更改：

| 方向 | 含义 |
|:--|:--|
| `in` | 客户端 → 服务端，服务端拿到的是副本 |
| `out` | 服务端 → 客户端，服务端修改后客户端能读到 |
| `inout` | 双向，开销最大 |

> 方向标记直接决定序列化开销：只读参数坚持用`in`。`out`/`inout`会额外做一次回写，对大对象影响明显。
>
> 可空参数与返回值**必须**用`@nullable`注解，例如`@nullable String getName();`，否则运行时可能拿到 null 而 Kotlin 侧按非空处理，直接崩溃。

### 实现服务端

```kotlin
class RemoteService : Service() {

    private val tasks = CopyOnWriteArrayList<Task>()
    private val callbacks = RemoteCallbackList<IRemoteCallback>()

    private val binder = object : IRemoteService.Stub() {

        override fun getPid(): Int = Process.myPid()

        override fun getTasks(): List<Task> = tasks

        override fun addTask(task: Task) {
            tasks += task
        }

        override fun registerCallback(callback: IRemoteCallback) {
            callbacks.register(callback)
        }

        override fun unregisterCallback(callback: IRemoteCallback) {
            callbacks.unregister(callback)
        }

        override fun fireAndForget(value: Int) {
            // oneway 调用，客户端不会等待这里执行完
        }
    }

    override fun onBind(intent: Intent): IBinder = binder
}
```

清单声明要点：

```xml
<permission
    android:name="com.example.app.permission.REMOTE_SERVICE"
    android:protectionLevel="signature" />

<application>

    <service
        android:name=".RemoteService"
        android:exported="true"
        android:permission="com.example.app.permission.REMOTE_SERVICE"
        android:process=":remote">

        <intent-filter>
            <action android:name="com.example.app.REMOTE_SERVICE" />
        </intent-filter>

    </service>

</application>
```

+ `android:exported="true"`：允许其他应用绑定，跨应用必需；
+ `android:permission`：**必加**，否则任何应用都能调用该服务。用`signature`级权限把调用方限制在同签名应用内；
+ `android:process=":remote"`：**可选**。它的作用是在同一个应用内模拟独立进程（`:`前缀表示私有进程）。跨应用场景下并不需要它——真正的“另一个进程”由另一个应用提供。

### 客户端绑定与调用

```kotlin
private var remoteService: IRemoteService? = null

private val connection = object : ServiceConnection {

    override fun onServiceConnected(name: ComponentName, service: IBinder) {
        // 关键一步：把 BinderProxy 转成接口代理
        remoteService = IRemoteService.Stub.asInterface(service)

        // 可选：监听服务端进程死亡
        service.linkToDeath({
            remoteService = null
        }, 0)
    }

    override fun onServiceDisconnected(name: ComponentName) {
        // 只在对端进程意外死亡时回调
        remoteService = null
    }
}

fun bindRemoteService() {
    val intent = Intent("com.example.app.REMOTE_SERVICE").apply {
        setPackage("com.example.app")
    }
    bindService(intent, connection, Context.BIND_AUTO_CREATE)
}
```

`Stub.asInterface()`会先用`queryLocalInterface()`判断该 `IBinder` 是否为本地对象：若是则直接返回实例，否则包一层 `Proxy`，之后每个方法调用都变成一次 Binder 事务。

> **Android 11（API 30）起的软件包可见性**：绑定其他应用的服务前，需要在清单里用`<queries>`声明目标包名或 action，否则`bindService()`可能因为“看不到”而失败。

### 回调：RemoteCallbackList

服务端反向通知客户端（进度、事件）时，不要自己维护一个`MutableList<IRemoteCallback>`——客户端进程死掉后，列表里会残留失效的 Binder，之后再调用就会抛`DeadObjectException`。正确做法是用`RemoteCallbackList`：

```kotlin
// 服务端：广播时 beginBroadcast() 与 finishBroadcast() 必须成对
fun notifyTaskAdded(task: Task) {
    val count = callbacks.beginBroadcast()
    try {
        for (i in 0 until count) {
            callbacks.getBroadcastItem(i).onTaskAdded(task)
        }
    } finally {
        callbacks.finishBroadcast()
    }
}
```

它会自动在每个回调上挂`DeathRecipient`，对端进程死亡时自动移除该回调。

### 线程模型与边界

+ **调用不在主线程执行**：跨进程调用由 Binder 线程池处理（每个进程的线程池有上限），服务端实现**必须线程安全**，且多个客户端会并发进来；
+ **调用默认同步**：客户端在主线程调用会一直阻塞到服务端返回，可能引发ANR。放进协程或子线程，例如`withContext(Dispatchers.IO) { remoteService?.getTasks() }`；
+ **`oneway`不阻塞**：调用方发送后立即返回，但要求方法返回`void`；同一个客户端的`oneway`调用仍按顺序到达；
+ **事务有大小上限**：单次事务约1MB，且按进程共享，超出抛`TransactionTooLargeException`。大列表要分页，不要一次性传；
+ **异常不会按原类型穿透**：只有`Parcel.writeException()`支持的类型（`SecurityException`、`IllegalArgumentException`、`IllegalStateException`、`NullPointerException`、`UnsupportedOperationException`、`ServiceSpecificException`等）会传回客户端，自定义异常类型无法保真。因此不要把控制流建立在“跨进程抛自定义异常”上。

调试时可以看服务是否真的跑在独立进程：

```shell
# 查看服务所在进程与状态
adb shell dumpsys activity services com.example.app

# 确认进程列表里出现了 :remote
adb shell ps -A | grep com.example.app
```

## 选型：什么时候还需要 Service

| 需求 | 推荐方案 |
|:--|:--|
| 用户可感知的持续任务（播放、导航、录音） | **前台服务**（必须声明类型与权限） |
| 可延迟、需要重试的后台任务（同步、上传） | **`WorkManager`**，自带约束、重试与持久化 |
| 只在界面存活期间需要的能力 | 直接放在`ViewModel` + 协程，不必用Service |
| 跨应用提供能力 | 绑定式Service（必要时用AIDL） |
| 应用内模块通信 | `SharedFlow` / `StateFlow` |

> `IntentService`自**API 30**起已废弃，`JobIntentService`同样废弃。它们当年的职责（后台串行处理任务）现在由`WorkManager`和协程承担，新代码不应再使用。
