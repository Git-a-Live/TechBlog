屏幕适配的对象不是「屏幕」，而是应用实际占据的**窗口**。同一台设备上，分屏、画中画、自由窗口、折叠态、车机多屏都会让可用区域变化，物理屏幕尺寸在这些场景里不提供任何布局依据。`WindowManager` 提供窗口的边界、密度与 insets，是唯一在全部窗口形态下都成立的测量基准。

以物理屏幕为基准的旧 API 已陆续废弃：`Display.getSize()` 与 `Display.getMetrics()` 自 Android 11（API 30）废弃，`getRealSize()` 与 `getRealMetrics()` 自 Android 12（API 31）废弃。它们返回整块显示区域，在分屏下会把窗口宽度算成屏幕宽度，直接导致布局错位。

## 从屏幕到窗口

|维度|物理屏幕|应用窗口|
|:--|:--|:--|
|获取方式|`Display`（已废弃的 metrics 系列）|`WindowManager.getCurrentWindowMetrics()`|
|分屏|始终返回整屏|返回当前分屏区域|
|折叠|内外屏切换时跳变|随窗口所在屏幕变化|
|自由窗口|无意义|返回拖拽后的实际尺寸|
|多屏|默认主屏|按窗口所在 Display 返回|

`Configuration` 与 `WindowMetrics` 都能描述窗口，差别在单位与 insets：

- `Configuration.screenWidthDp` / `screenHeightDp`：以 dp 表示**应用窗口**的可用区域，**不含** insets。分屏时等于应用窗口宽度，而非设备屏幕宽度；嵌入式 Activity 场景下等于该 Activity 自身的宽度。
- `WindowMetrics.getBounds()`：以像素表示窗口在 `MATCH_PARENT` 下占据的区域，**包含** insets 覆盖的部分。
- `WindowMetrics.getWindowInsets()`：单独给出 insets，需要调用方自行扣减。

两者相差一个 insets。用 `bounds` 直接当内容区域，在 edge-to-edge 下会被状态栏或导航栏压住；用 `screenWidthDp` 去算像素坐标，则会少算系统栏占用的空间。布局决策用 dp（`Configuration` 或 `WindowSizeClass`），绘制与裁剪用像素（`bounds` 减 insets）。

一个具体差距：1080×2400、density 2.75 的设备，整屏约 393dp 宽；进入 50/50 分屏后，窗口宽度只剩 196dp。按屏幕宽度设计的 3 栏布局，每栏原本 131dp，在被压到 196dp 的窗口里只剩 65dp，文字与卡片同时失效。此时 `Display.getRealMetrics()` 仍返回 1080px，而 `getCurrentWindowMetrics().bounds` 返回 540px——两者的差值就是分屏造成的可用区域损失。

## 方案谱系与选型

屏幕适配的方案按基准只有三类：**设计稿、设备资源、窗口**。其余做法都是这三类的组合或变体。

|方案|基准|做法|主要代价|现状|
|:--|:--|:--|:--|:--|
|density 篡改（业内称头条方案，代表库 AndroidAutoSize）|设计稿宽度|修改 `DisplayMetrics.density` / `scaledDensity`，设计稿 px 直接当 dp|全局生效，三方库、系统字号、WebView 一起变；分屏后无唯一基准|遗留项目常见，新项目不推荐|
|smallestWidth + 多套 dimens|设备最小宽度|按 `sw<N>dp` 生成 `values-sw320dp/dimens.xml` 等多套尺寸|组合多、包体增大；`sw` 不随窗口实时变化|存量国内项目主流|
|宽高限定符穷举|具体分辨率|`values-1920x1080` 逐套适配|组合爆炸，长宽比与折叠屏无法覆盖|已淘汰|
|百分比布局|父容器比例|`PercentFrameLayout` / `PercentRelativeLayout`|API 26.1.0 起废弃|被 ConstraintLayout 取代|
|约束与权重|可用空间|ConstraintLayout 的 percent / ratio / Guideline；`LinearLayout` weight；Compose 的 `weight`|复杂页面约束数量膨胀|通用手段，与窗口方案叠加|
|多倍图与矢量资源|像素密度|mdpi～xxxhdpi、`VectorDrawable`、WebP|只解决图片图标，不解决布局|必做基础项|
|字号与无障碍缩放|用户字号偏好|sp、`lineHeight` 用 sp|Android 14 起 `scaledDensity` 不再准确|必做基础项|
|窗口尺寸类（本篇主线）|应用窗口|`WindowMetrics` + 断点 + 多档布局|需要设计侧提供多档稿|新项目的推荐主方案|

三处容易混淆的区别：

- **density 方案与 sw 方案不在同一层。** 前者改全局换算常量，所有 dp/sp 一起变；后者只切换一份 dimens 资源，字号与图片仍按系统密度走。前者改动面小但污染全局，后者隔离性好但资源量大。
- **百分比布局已废弃。** `PercentFrameLayout` 与 `PercentRelativeLayout` 自 API 26.1.0 废弃，官方给出的替代是 ConstraintLayout 的百分比约束与 Guideline。
- **字号适配不是可选项。** Android 14 起系统支持字号放大到 200%，并采用非线性曲线：大号文本的放大比例小于小号文本。由此 `DisplayMetrics.scaledDensity` 不再准确，`Configuration.fontScale` 只能作参考，sp 与 px 的互转必须走 `TypedValue.applyDimension()` / `TypedValue.deriveDimension()`。

按项目形态的取舍：

|场景|建议组合|
|:--|:--|
|新项目、多形态（手机 / 折叠 / 平板）|窗口断点 + 约束布局 + 多倍图/矢量 + sp 字号|
|存量国内项目|保留 sw 多套 dimens，新增页面改用窗口断点，逐步替换 density 缩放|
|固定分辨率车机 / 定制大屏|窗口断点 + 局部等比缩放（限定单页或单组件）+ `WindowMetrics` 运行时校验|
|电视|窗口断点（档位少）+ 安全区 + 大字号，不使用 density 缩放|
|游戏与自绘|独立体系：viewport + 正交矩阵 + 安全区|

三种基准的可靠性依次递增：设计稿基准随设备漂移，资源基准随组合爆炸，窗口基准是唯一随容器变化的。现代方案以窗口断点为骨架，用约束与权重消化档位内的差异，再用多倍图与 sp 字号兜住像素与可读性。

## WindowManager 提供的三类数据

```kotlin
val windowManager = context.getSystemService(WindowManager::class.java)
val metrics = windowManager.currentWindowMetrics            // API 30+
val bounds = metrics.bounds                                 // 像素，含 insets
val density = metrics.density                               // 窗口密度
val insets = metrics.windowInsets.getInsetsIgnoringVisibility(
    WindowInsets.Type.systemBars() or WindowInsets.Type.displayCutout()
)
val contentWidthPx = bounds.width() - insets.left - insets.right
```

|数据|来源|典型用途|注意|
|:--|:--|:--|:--|
|当前窗口边界|`getCurrentWindowMetrics().bounds`|计算可用像素、对齐绘制区域|含 insets，必须先扣减|
|窗口密度|`WindowMetrics.getDensity()`|dp 与 px 换算|多屏设备的副屏密度可能不同|
|窗口 insets|`WindowMetrics.getWindowInsets()`|避开系统栏、刘海、输入法|可见性会变化，需要监听|
|最大窗口边界|`getMaximumWindowMetrics()`|判断「最大化后能放多少」|不用于常规布局；结果仍受当前 Context 限制|

`getMaximumWindowMetrics()` 容易被误用。它返回的是窗口在当前系统状态下**可能达到**的最大区域：全屏时等于屏幕，分屏时等于该任务扩展到全屏后的区域。官方明确 `getCurrentWindowMetrics()` 才是选择布局时应该用的 API，最大边界只用于需要预判展开尺寸的场景。

Context 的类型会影响结果。与某个 Display 关联的 `WindowManager` 必须从该 Display 的 UI context 取得（`createWindowContext` 之后调用 `getSystemService`），用 Activity 的 metrics 代表副屏会得到错误数据。

## 兼容层：androidx.window

平台 `WindowMetrics` 自 API 30 提供。要覆盖更低版本，使用 Jetpack WindowManager（稳定版 1.5.1，2025-11-19）：

```kotlin
implementation("androidx.window:window:1.5.1")
```

```kotlin
val metrics = WindowMetricsCalculator.getOrCreate()
    .computeCurrentWindowMetrics(activity)
```

- `computeCurrentWindowMetrics(activity)` 在 API 29 及以上保证准确；更低版本在多窗口与导航栏偏移场景下是尽力而为的近似值。
- `computeMaximumWindowMetrics(activity)` 在 API 29 及以下等价于 `Display.getRealSize()`。
- 只传 `@UiContext`（Activity 或 window context）。传 Application Context 会抛 `IllegalArgumentException`，或得到排除装饰区域的结果。

平台与兼容层的语义一致，差别只在可用版本。新代码用平台 API，最低版本低于 30 时用兼容层，避免两套逻辑并存。

## 从像素到断点

有了窗口尺寸，下一步是把它映射成有限的布局档位。直接按像素等比缩放会把「可用空间」误当成「缩放系数」，在分屏与多屏上产生字号失真。窗口尺寸类（Window Size Class）用断点解决这个问题（2026-11 官方数值）：

|宽度档位|范围|高度档位|范围|
|:--|:--|:--|:--|
|compact|宽度 < 600dp|compact|高度 < 480dp|
|medium|600dp ≤ 宽度 < 840dp|medium|480dp ≤ 高度 < 900dp|
|expanded|840dp ≤ 宽度 < 1200dp|expanded|高度 ≥ 900dp|
|large|1200dp ≤ 宽度 < 1600dp|—|—|
|xlarge|宽度 ≥ 1600dp|—|—|

断点与设备类型无关：平板竖屏可能落在 medium，手机横屏可能是 compact 高度，折叠屏展开后可能从 medium 跳到 expanded。布局只依据档位，不依据 `isTablet` 之类的设备判断。

```kotlin
val config = activity.resources.configuration
val sizeClass = WindowSizeClass.compute(
    widthDp = config.screenWidthDp.toFloat(),
    heightDp = config.screenHeightDp.toFloat()
)
val twoPane = sizeClass.isWidthAtLeastBreakpoint(
    WindowSizeClass.WIDTH_DP_MEDIUM_LOWER_BOUND
)
```

Compose 侧用 Material 3 Adaptive 直接取当前窗口的档位：

```kotlin
@Composable
fun App() {
    val sizeClass = currentWindowAdaptiveInfo(
        supportLargeAndXLargeWidth = true
    ).windowSizeClass

    if (sizeClass.isWidthAtLeastBreakpoint(WindowSizeClass.WIDTH_DP_MEDIUM_LOWER_BOUND)) {
        TwoPaneLayout()
    } else {
        OnePaneLayout()
    }
}
```

`currentWindowAdaptiveInfo()` 的 V2 版本（`currentWindowAdaptiveInfoV2()`）已在新版文档中取代旧函数；升级依赖时以当前版本的文档为准，两者返回的 `WindowSizeClass` 用法一致。`supportLargeAndXLargeWidth` 需要显式开启，否则 large 与 xlarge 档位不会出现在结果里。

## 布局落地

**View 体系。** 布局切换靠资源限定符，但要用 `w<N>dp` 而不是 `sw<N>dp`：前者跟随当前窗口宽度，分屏后会重新匹配；后者表达的是应用可能见到的最小宽度，不适合做「当前是不是双栏」的判断。

```
res/layout/activity_main.xml          单栏
res/layout-w600dp/activity_main.xml   双栏
```

双栏结构优先用 `SlidingPaneLayout`，它自带折叠与拖拽行为，避免手写两套 `LinearLayout` 权重。屏幕较宽但窗口变窄时，`SlidingPaneLayout` 会自动退回单栏。常规布局约束的写法见 [[9. UI 开发|UI 开发]]。

`android:configChanges` 不要拦截 `screenSize` / `smallestScreenSize` / `orientation`。拦截后 Activity 不重建，资源限定符不会重新匹配，`layout-w600dp` 切换不会发生，等于把窗口适配关掉。若因状态保持必须拦截，需要自行重新 inflate 布局并重新读取 insets。

**Compose 体系。** 断点判断集中在页面级 Composable，向下传递布尔值或档位，而不是让每个子组件各自读全局尺寸：

```kotlin
@Composable
fun Content(twoPane: Boolean) {
    if (twoPane) {
        Row {
            ListPane(Modifier.weight(1f))
            DetailPane(Modifier.weight(2f))
        }
    } else {
        ListPane(Modifier.fillMaxSize())
    }
}
```

局部自适应（卡片是否显示副标题、按钮是否换行）用 `BoxWithConstraints` 判断自身可用空间，属于组件内部决策；页面骨架的切换仍由窗口档位决定。两者混用会让同一断点在两处出现不同结果。Compose 布局能力的层次划分见 [[5. 自定义组件与布局|自定义组件与布局]]。

### 尺寸变化的监听

窗口尺寸可能在运行期变化，三个层级的监听点对应三类决策：

|层级|入口|适用|
|:--|:--|:--|
|Activity / Fragment|`onConfigurationChanged`（未拦截 configChanges 时 Activity 重建）|切换页面骨架、重新 inflate|
|View|`OnLayoutChangeListener`、`onSizeChanged`|拿到实际内容尺寸，调整绘制与子 View 布局|
|Compose|`currentWindowAdaptiveInfo()` 随配置重组；局部用 `BoxWithConstraints`|页面档位与组件内自适应|

不要在定时任务里轮询 `getCurrentWindowMetrics()`：窗口变化由系统派发，轮询既拿不到中间状态，也会在动画期间产生大量无意义读取。

### 分屏场景的运行时注意点

分屏把可用区域压窄只是表象，风险集中在运行期行为：

|注意点|现象|处理|
|:--|:--|:--|
|拖动分隔线的连续变化|闪烁、卡顿、反复重建|状态放 `ViewModel` / `rememberSaveable`，尺寸回调不做重活|
|断点临界抖动|在 600dp、840dp 附近双栏与单栏反复切换|进入与退出用不同阈值（如 600dp 进、560dp 退）|
|输入法压缩|分屏后再弹键盘，剩余高度不足 360dp|`imePadding()` 或 `WindowInsets.ime`，避免固定高度加底部按钮|
|Surface 重建|视频黑屏、相机预览拉伸|播放器放 `ViewModel`，Surface 创建时 attach、销毁时 detach|
|多恢复|另一侧操作导致本应用暂停播放或定位|按 `Lifecycle.State.STARTED` 判断，不在 `onPause` 里停|
|焦点切换|两个窗口同时跑动效|`onWindowFocusChanged` 暂停非必要动画|
|最小尺寸|被拖到极窄后布局塌陷|`<layout android:minWidth/minHeight>` 声明下限|
|画中画|复用分屏布局导致控件被裁|PiP 单独布局，按 `onPictureInPictureModeChanged` 分支|

四点补充：

- `isInMultiWindowMode()` 只回答「是否多窗口」，不提供宽度；分屏、自由窗口、画中画都返回 true，布局分支仍以窗口宽度或断点为准。
- 多窗口不改变生命周期，但进入、退出、拖动分隔线都会触发配置变化。不要用 `configChanges` 阻止重建，用状态保存承接。
- 车机与大屏可能固定为 1/3 + 2/3，不要假设用户总能给出 1/2，也不要按分屏比例写布局分支。
- 系统级分屏没有设置比例的 API；只有应用内 Activity Embedding 可用 `SplitAttributes.SplitType.ratio()` 指定自己任务内的分栏比例。

## Insets 与 edge-to-edge

Android 15（API 35）起，targetSdk 35 的应用在 Android 15 及以上强制 edge-to-edge；targetSdk 36 的应用在 Android 16 及以上设备上连退出开关也失效。窗口默认铺满整屏，系统栏透明覆盖在内容之上，不适配 insets 就会被遮挡。

View 侧的标准处理：

```kotlin
ViewCompat.setOnApplyWindowInsetsListener(root) { view, windowInsets ->
    val bars = windowInsets.getInsets(
        WindowInsetsCompat.Type.systemBars() or WindowInsetsCompat.Type.displayCutout()
    )
    view.updatePadding(bars.left, bars.top, bars.right, bars.bottom)
    WindowInsetsCompat.CONSUMED
}
```

两处细节：

- `WindowInsetsCompat.CONSUMED` 在 Android 10 及以下会阻断向同级 View 的分发，导致其他视图重复留白或漏留白。需要跨版本一致行为时，在消费之前调用 `ViewGroupCompat.installCompatInsetsDispatch(root)`（androidx.core 1.16.0-alpha01 起提供）。
- 列表类视图配合 `clipToPadding="false"`，内容才能滚到系统栏后面，而不是被永久裁掉。

Compose 侧用 `WindowInsets.safeDrawing` 一次覆盖系统栏、刘海与输入法：

```kotlin
Scaffold(contentWindowInsets = WindowInsets.safeDrawing) { padding ->
    Content(Modifier.padding(padding))
}
```

insets 是动态的：输入法弹出、系统栏隐藏、折叠形态变化都会改变数值。一次性读取 `WindowMetrics.getWindowInsets()` 只能用于初始化，持续布局必须监听变化（View 的 insets listener、Compose 的 `WindowInsets` 状态）。

电视场景没有系统栏，但存在物理溢出与观看距离问题：安全边距按设计规范预留，不能靠 insets 代替，也不能把关键内容贴近物理边缘。

## 折叠屏与多屏

折叠设备的可用区域由铰链决定，`WindowInfoTracker` 把折叠特征作为数据流暴露：

```kotlin
lifecycleScope.launch {
    WindowInfoTracker.getOrCreate(this@MainActivity)
        .windowLayoutInfo(this@MainActivity)
        .collect { layoutInfo ->
            val folding = layoutInfo.displayFeatures
                .filterIsInstance<FoldingFeature>()
                .firstOrNull()
            twoPane = folding?.isSeparating == true
        }
}
```

判断依据是 `isSeparating`：为 true 表示铰链把窗口分成两个物理区域，此时双栏布局能避开铰链；为 false（例如半折叠的桌面模式）则应按水平分区处理。`orientation` 给出铰链方向（`HORIZONTAL` / `VERTICAL`），`state` 区分 `FLAT` 与 `HALF_OPENED`，`occlusionType` 表示铰链是否遮挡内容。

多屏（车机、外接显示器）与折叠不同：每块屏有独立的 Display 与密度，窗口落在哪块屏由系统决定。

- 枚举屏幕用 `DisplayManager.getDisplays()`，不要假设只有一块屏。
- 副屏的尺寸必须从该 Display 的 UI context 取 `WindowMetrics`，Activity 的 metrics 只代表它自己所在的窗口。
- 副屏密度可能不同，dp 与 px 的换算必须用对应窗口的 `density`，不能复用主屏的 `DisplayMetrics`。

## 密度方案的边界

常见的「设计稿等比缩放」做法是修改 `DisplayMetrics` 的 `density`、`densityDpi`、`scaledDensity`，让设计稿的像素值可以直接当 dp 使用。它在固定分辨率、单一窗口的定制设备上能快速对齐视觉稿，但代价明确：

- 修改作用于 `Resources`，应用内所有 dp/sp 换算、图片解码、三方库与系统控件一起改变，难以局部回退。
- 与系统字体大小设置冲突：`scaledDensity` 被覆盖后，用户在系统里调大字号可能失效。
- 分屏、折叠、自由窗口下没有唯一的「设计稿基准宽度」，比例系数随窗口变化而失真。
- WebView、视频画面、`Canvas` 绘制各自使用独立密度，容易出现文字与图形不同步缩放。

现代工程用 dp/sp + 窗口断点 + 权重/约束表达布局，密度只作为换算常量使用。确有必要按设计稿缩放时，把影响范围限制在单页或单组件：Compose 可用 `CompositionLocalProvider(LocalDensity provides Density(...))` 局部覆盖，View 可在自定义控件的测量阶段按比例换算，避免改动全局 `Resources`。

## 常见误区

|做法|问题|替代|
|:--|:--|:--|
|`Display.getRealMetrics()` 取宽高做布局|API 31 废弃，返回整屏，分屏与折叠下错误|`getCurrentWindowMetrics()`|
|把 `bounds` 直接当内容区域|bounds 含 insets，内容被系统栏遮挡|bounds 减 insets，或用 `safeDrawing`|
|用 `sw<N>dp` 判断当前双栏|sw 表达可能见到的最小宽度，不跟随窗口变化|`w<N>dp` 或 `WindowSizeClass`|
|按屏幕宽度等比缩放全部尺寸|字号在分屏/大屏上失真，留白失控|断点 + 权重/约束|
|锁定 `screenOrientation` 固定布局|Android 16 起 targetSdk 36 在 sw600dp+ 忽略方向限制|按窗口自适应，横竖屏同构|
|修改全局 `density` 适配设计稿|影响三方库、系统字体与 WebView|局部 `Density` 覆盖或改用约束布局|
|只测一台手机|分屏、折叠、多屏问题不会暴露|模拟器多形态 + `adb shell wm` 改尺寸|
|`resizeableActivity="false"` 限制窗口|Android 12 起大屏忽略该属性，限制无效|移除该属性，按可调整窗口设计|

## 验证

```bash
# 模拟不同窗口尺寸与密度
adb shell wm size 1280x720
adb shell wm density 240

# 恢复默认
adb shell wm size reset
adb shell wm density reset

# 查看窗口边界、insets 与焦点窗口
adb shell dumpsys window displays
```

- 分屏：开发者选项开启「强制将活动设为可调整大小」，长按最近任务进入分屏，拖动分隔线观察断点切换。
- 折叠：使用可调整尺寸的模拟器设备定义，切换折叠姿态验证 `FoldingFeature` 回调。
- 多屏：模拟器支持添加副屏，或在车机设备上验证副屏密度与窗口 metrics。
- 布局检查：Layout Inspector 查看实际测量尺寸与 insets；Compose 用多设备 `@Preview` 覆盖 compact/medium/expanded 三档。
- 自动化：`androidx.window.testing` 提供伪造 `WindowLayoutInfo` 的规则，可在不改变设备形态的前提下测试折叠分支。

## 工程清单

- 布局决策只读窗口尺寸（dp），像素计算只读 `WindowMetrics`，两者不交叉。
- 断点判断集中在页面级，向下传状态；组件内部才用 `BoxWithConstraints`。
- edge-to-edge 下所有贴边视图都处理 insets，列表开启 `clipToPadding=false`。
- 折叠与多屏按 `isSeparating` 与所在 Display 分别处理，不复用主屏密度。
- 不修改全局 `density`；确需缩放时限制在单页或单组件。
