大屏设备（电视、机顶盒、投影、车机）没有触摸输入，用户与界面的全部交互来自遥控器的方向键、确认键与返回键。开发重点因此不在「点击响应」，而在**按键事件的分发**与**焦点状态的流转**。

Android 没有名为「遥控器」的 API。系统把遥控器当作普通输入设备，产生 `KeyEvent`，界面能否被顺畅操作，取决于焦点体系是否被正确设计。红外发射、蓝牙配对属于厂商方案，键码与协议由硬件决定，不在系统能力范围内——这部分只体现为「拿到什么键码就处理什么键码」。

## 交互模型

|维度|手机 / 平板|大屏|
|:--|:--|:--|
|输入源|触摸、软键盘|方向键、确认键、返回键、媒体键|
|命中方式|坐标命中|焦点跳转|
|界面密度|高，可滚动长列表|低，按行组织，一屏信息量受限|
|观看距离|30～50 cm|约 3 m（10 英尺界面）|
|失败恢复|用户重新点击|焦点丢失后难以找回，需要返回重进|

触摸是坐标命中：用户点哪儿，事件就到哪儿，点空可以重试。遥控是焦点跳转：焦点是全局唯一的活动元素，每次按键把它移到「下一个」，移动路径由布局与焦点规则共同决定。用户不会「点空」，但会「走丢」。

两条由此推出的约束：焦点移动路径必须确定且可预测；任何时刻都必须存在一个可见的焦点。界面上的每个可交互元素都要能被若干次方向键到达，且不会掉进死循环。

## 按键事件的分发链路

物理按键 → Linux input 子系统 → `InputManagerService` → `WindowManagerService` → 目标窗口的 `ViewRootImpl` → `DecorView.dispatchKeyEvent` → Activity / View 树。

三个可拦截的位置：

|层级|入口|特点|
|:--|:--|:--|
|Activity|`dispatchKeyEvent`、`onKeyDown`|最早接触事件，适合全局快捷键|
|View|`dispatchKeyEvent`、`onKeyDown`、`onKeyUp`|父子冒泡，父容器可先行拦截|
|Compose|`Modifier.onPreviewKeyEvent`、`Modifier.onKeyEvent`|前者自上而下，后者自下而上|

Compose 的两个修饰符方向相反：`onPreviewKeyEvent` 在子节点之前收到事件，用于拦截方向键；`onKeyEvent` 只在子节点未消费时冒泡到父节点。返回 `true` 即消费，事件不再向下或向上传递。

```kotlin
Box(
    Modifier.onPreviewKeyEvent { event ->
        if (event.type == KeyEventType.KeyDown && event.key == Key.DirectionCenter) {
            onConfirm()
            true
        } else {
            false
        }
    }
) {
    // 内容
}
```

长按的判定依赖 `repeatCount`：按住不放时系统持续派发 `KeyDown`，`repeatCount` 从 0 递增。Compose 的 `KeyEvent` 通过 `event.nativeKeyEvent.repeatCount` 读取；View 侧若要触发 `onKeyLongPress`，必须在 `onKeyDown` 里先调用 `event.startTracking()`，否则回调不会到达。

常用键码：

|键码|含义|使用场景|
|:--|:--|:--|
|`KEYCODE_DPAD_UP` / `DOWN` / `LEFT` / `RIGHT`|方向键|焦点移动，通常交由系统处理|
|`KEYCODE_DPAD_CENTER` / `KEYCODE_ENTER`|确认|触发当前焦点项|
|`KEYCODE_BACK`|返回|导航回退（受预测性返回影响，见下文）|
|`KEYCODE_MEDIA_PLAY_PAUSE` / `NEXT` / `PREVIOUS`|媒体控制|播放器快捷键|
|`KEYCODE_MENU`|菜单|部分遥控器提供|
|`KEYCODE_VOLUME_UP` / `DOWN`|音量|多数设备由系统直接处理|

系统保留键不会分发给应用：`KEYCODE_HOME`、`KEYCODE_RECENTS`、`KEYCODE_POWER`。音量键在多数电视与盒子上同样由系统消费，应用只能在部分设备上观察到。把音量调节做成应用内功能，属于对设备的错误假设。

厂商差异是常态：语音键、数字键、彩色键没有统一键码，可能上报 `KEYCODE_UNKNOWN`，也可能是厂商自定义值。可配置的键码映射表比硬编码判断更可靠，遇到未知键码时保留日志而不是静默丢弃。

调试时用 adb 模拟按键，便于脚本化复现：

```bash
adb shell input keyevent KEYCODE_DPAD_DOWN
adb shell input keyevent 20          # 20 是 DPAD_DOWN 的键值
adb shell input keyevent KEYCODE_DPAD_CENTER
```

## 焦点体系

### 两套实现的对应关系

View 侧的焦点属性建立在普通 View 体系之上（见 [[9. UI 开发|UI 开发]]），Compose 侧则归入焦点与输入处理（见 [[5. 自定义组件与布局|自定义组件与布局]]）。两套 API 名称不同，判定规则一致。

|能力|View|Compose|
|:--|:--|:--|
|声明可聚焦|`android:focusable`、`setFocusable()`|`Modifier.focusable()`|
|指定相邻焦点|`nextFocusUp` / `Down` / `Left` / `Right`|`Modifier.focusProperties { up = ... }`|
|主动请求焦点|`requestFocus()`|`FocusRequester.requestFocus()`|
|焦点组|`descendantFocusability`|`Modifier.focusGroup()`|
|焦点记忆|自行保存与恢复|`Modifier.focusRestorer()`|

两套体系共用同一个 `FocusFinder` 算法：以当前焦点矩形为起点，沿按键方向投射一条 beam，候选控件按「与 beam 的垂直距离」和「沿 beam 方向的距离」加权评分，取最优者。这解释了布局中的常见现象——视觉上相邻的两行，如果控件矩形没有对齐，方向键会跳过其中一行，或者跳到屏幕另一侧的控件上。

### 四个基本动作

**声明可聚焦。** `Modifier.focusable()` 让节点进入焦点链；`clickable()` 内部已包含可聚焦与按键处理，普通可点击项不必重复添加。`focusTarget()` 只参与焦点链、不处理输入，用于容器级别的焦点管理。

**请求初始焦点。** 用 `FocusRequester` 指定首个焦点，在 `LaunchedEffect` 中调用。组合阶段直接调用会抛 `IllegalStateException`，因为此时节点尚未 attach。

```kotlin
val firstRequester = remember { FocusRequester() }

LazyRow(modifier = Modifier.focusRestorer(firstRequester)) {
    itemsIndexed(items) { index, item ->
        Card(
            modifier = if (index == 0) Modifier.focusRequester(firstRequester) else Modifier
        ) {
            // 卡片内容
        }
    }
}

LaunchedEffect(Unit) { firstRequester.requestFocus() }
```

**改写方向。** `focusProperties` 覆盖默认的 2D 搜索，只在默认算法失效时使用——两列列表之间的对齐、侧边栏与内容区的跳转、需要跳过装饰性控件的位置。滥用会让焦点路径变得不可预测，后续维护者无法从布局推断按键结果。

```kotlin
Row(
    Modifier.focusProperties {
        right = contentRequester    // 从侧边栏向右直接进入内容区
    }
) {
    // 侧边栏
}
```

`FocusProperties` 的 `onEnter` / `onExit` 用于在焦点进入或离开容器时重定向，例如导航栏获得焦点时自动落到当前选中项。旧版本使用的 `enter` / `exit` 属性已被替换。

**记忆与恢复。** `LazyRow`、`LazyColumn`、`LazyVerticalGrid` 本身是焦点组，附加 `Modifier.focusRestorer()` 后，焦点离开再回来会落在上次停留的项，而不是第一项。普通 `Row` / `Column` 不建立焦点边界，需要 `focusGroup()` 与 `focusRestorer()` 同时使用。

`focusRestorer` 早期版本接受 `onRestoreFailed` 的 lambda 重载（1.6.0 引入），Compose UI 1.8 起废弃，当前签名接受一个 `FocusRequester` 作为恢复失败时的后备目标。

跨页面返回时，容器可以记录离开前的焦点：导航前往详情页前调用 `FocusRequester.saveFocusedChild()`，返回后调用 `restoreFocusedChild()`。列表数据被重新加载时，硬编码的位置会指向错误的项，这种场景应改为按业务状态（例如当前选中的内容 id）指定焦点。

### 焦点陷阱

|症状|原因|处理|
|:--|:--|:--|
|焦点停在屏幕外|列表未把焦点项滚入可视区|`Modifier.bringIntoViewRequester` + 获焦时调用 `bringIntoView()`|
|每次回到列表都从第一项开始|未启用焦点恢复|列表加 `focusRestorer`|
|焦点在容器内循环，出不去|`focusProperties` 覆盖了默认搜索，或父容器消费了方向键|检查覆盖规则与 `onPreviewKeyEvent` 的返回值|
|返回后焦点消失|页面重建未指定首焦点|重建后显式 `requestFocus()`|
|滚动时焦点乱跳|焦点绑定在列表位置而非数据 key|按 id 记录焦点项，避免复用错位|
|首屏无焦点，按键无反应|依赖「第一个可聚焦元素自动获焦」|进入页面时显式请求焦点|

## 焦点视觉反馈

焦点是逻辑状态，用户感知到的是视觉状态。边框、覆盖、缩放三种效果都能只改绘制属性完成，不参与测量，因此不影响焦点移动速度。

三种实现的共同前提是拿到焦点状态：

```kotlin
var focused by remember { mutableStateOf(false) }

Box(
    Modifier
        .onFocusChanged { focused = it.isFocused }
        .focusable()
)
```

使用 `clickable` 的组件也可以从 `MutableInteractionSource` 取 `collectIsFocusedAsState()`，语义等价，代码量更大。

### 边框

`Modifier.border` 在组件边界内侧描边，宽度与颜色可随焦点状态动画过渡：

```kotlin
val strokeWidth by animateDpAsState(if (focused) 3.dp else 1.dp, label = "strokeWidth")
val strokeColor by animateColorAsState(
    if (focused) MaterialTheme.colorScheme.primary else Color.Transparent,
    label = "strokeColor"
)

Box(
    Modifier
        .border(strokeWidth, strokeColor, RoundedCornerShape(12.dp))
        .padding(12.dp)
)
```

- 描边不占布局空间，宽度变化时内容不位移；用 `padding` 模拟边框会让焦点切换触发重新布局。
- 圆角必须与背景 shape 一致，否则边框与背景边缘错位。
- 未聚焦时用透明色而不是移除 `border`，modifier 链保持稳定，状态切换的重组范围更小。

View 侧最小实现是把焦点边框放进 `foreground`，由状态选择器切换，不必在焦点回调里改背景：

```xml
<!-- res/drawable/focus_border.xml -->
<selector xmlns:android="http://schemas.android.com/apk/res/android">
    <item android:state_focused="true">
        <shape android:shape="rectangle">
            <corners android:radius="12dp" />
            <stroke android:width="3dp" android:color="@color/focus_stroke" />
        </shape>
    </item>
    <item>
        <shape android:shape="rectangle">
            <corners android:radius="12dp" />
            <stroke android:width="1dp" android:color="@android:color/transparent" />
        </shape>
    </item>
</selector>
```

```xml
<androidx.cardview.widget.CardView
    android:layout_width="240dp"
    android:layout_height="135dp"
    android:focusable="true"
    android:foreground="@drawable/focus_border" />
```

`android:foreground` 在 API 23 起对所有 View 可用。前景绘制在矩形边界内，不受卡片圆角裁剪，因此描边的圆角半径必须与卡片一致，否则四角会露出直角。

### 覆盖

在内容之上叠一层半透明色，不改变轮廓与尺寸，图片卡片上比描边更自然。用 `drawWithContent` 实现不需要额外布局节点：

```kotlin
Box(
    Modifier
        .clip(RoundedCornerShape(12.dp))
        .drawWithContent {
            drawContent()
            if (focused) {
                drawRect(Color.White.copy(alpha = 0.12f))
            }
        }
)
```

- `drawWithContent` 先绘制内容再覆盖矩形，不参与命中测试，也不进入语义树。
- 覆盖按矩形绘制，圆角卡片必须在外层 `clip(shape)`，否则四角会露在圆角之外。
- 需要渐变或多层叠加时，改为 `Box` 内的 `Modifier.matchParentSize()` 子层，对该子层做 alpha 动画，并加 `clearAndSetSemantics {}` 防止读屏重复播报。
- 透明度按底色选取：暗色背景用白色 0.08～0.14，浅色背景用黑色同区间。

View 侧对应 `foreground` 加 `ColorDrawable`，焦点回调里只改 alpha，避免每次创建对象：

```kotlin
val overlay = ColorDrawable(Color.WHITE).apply { alpha = 0 }
view.foreground = overlay
view.setOnFocusChangeListener { _, hasFocus ->
    overlay.alpha = if (hasFocus) 30 else 0
}
```

### 缩放

缩放让焦点项从周围内容中浮起，在 3 米观看距离下比颜色变化更容易察觉：

```kotlin
val scale by animateFloatAsState(
    targetValue = if (focused) 1.08f else 1f,
    animationSpec = tween(durationMillis = 150),
    label = "scale"
)

Box(
    Modifier.graphicsLayer {
        scaleX = scale
        scaleY = scale
    }
)
```

- `graphicsLayer` 的 lambda 在绘制阶段读取动画值，帧更新不触发重组与重新测量，是三种效果里开销最低的。
- 父容器默认裁剪（`LazyRow` 即如此），放大后的边缘会被切掉；容器需留出与缩放幅度匹配的空白，1.08 倍对应约 4% 的尺寸余量。
- 缩放不改变布局占位，相邻项会视觉重叠，间距按放大后的尺寸预留。
- 缩放中心默认为控件中心，靠近屏幕边缘的项放大后可能溢出，这类位置改用边框更稳妥。
- 与边框叠加时，`graphicsLayer` 写在 `border` 之前会连同描边一起放大；写在之后则描边保持原宽度，仅内容缩放。

View 侧用属性动画：

```kotlin
view.setOnFocusChangeListener { v, hasFocus ->
    val target = if (hasFocus) 1.08f else 1f
    v.animate().scaleX(target).scaleY(target).setDuration(150).start()
}
```

### 组合与取舍

|效果|远距离可辨识度|开销|适用场景|
|:--|:--|:--|:--|
|边框|中|低，一次描边绘制|列表项密集、需要明确边界|
|覆盖|低|最低，一次矩形填充|图片卡片、暗色背景|
|缩放|高|中，需处理裁剪与重叠|首屏推荐位、卡片式布局|

- 同一界面选一到两种即可，边框与缩放的组合最常用；三种同时启用会让焦点反馈显得杂乱，描边与放大还会互相干扰。
- 三种效果都只改绘制属性。用动画改 `padding`、`size`、`elevation` 会触发重新布局，连按方向键时表现为掉帧。
- 参数在同一应用内统一：时长 150 ms 左右、缩放 1.05～1.10、边框 2～3 dp。参数不一致会让不同页面的焦点反馈像是拼装的。
- tv-material 组件已内置缩放、边框、发光、容器颜色四种指示，使用库组件时直接配置 `Defaults`；手写实现面向自定义组件与非 tv 库的场景。

## Compose for TV

TV 界面用 `androidx.tv` 系列库构建，稳定版本如下（2026-05 发布）：

```kotlin
implementation("androidx.tv:tv-material:1.1.0")
implementation("androidx.tv:tv-foundation:1.0.0")
```

两套 Material 不要混用。`androidx.tv.material3` 与 `androidx.compose.material3` 各自持有独立的 `MaterialTheme`，混用会出现颜色、字体、形状不一致，且组件内部的焦点反馈与间距假设不同。

tv-material 把上述反馈封装成组件参数（缩放、边框、发光、容器颜色），配置 `Defaults` 即可，不需要手写 `onFocusChanged` 或 `OnFocusChangeListener`：

```kotlin
Card(
    onClick = { onSelect(item) },
    scale = CardDefaults.scale(focusedScale = 1.1f)
) {
    // 卡片内容
}
```

两个迁移事实需要明确：

- Leanback 整个制品已废弃，官方声明为「此制品及其类已废弃。请改用 Compose for TV」。存量项目可以继续编译，但不接收新能力。
- tv-foundation 中的 `TvLazyRow` / `TvLazyColumn` 自 1.0.0-alpha11（2024-07）起弃用，改用标准 `LazyRow` / `LazyColumn` 配合 `focusRestorer`。TV 专用懒加载布局曾解决的「焦点项保持在屏幕固定位置」，现在由焦点恢复与 `bringIntoView` 共同承担。

TV 组件不会自动给首个元素焦点，页面进入时显式 `requestFocus()` 是唯一可靠做法；焦点请求失败（节点未 attach、容器不可见）时应有降级路径，避免整屏按键无响应。

## 返回键与预测性返回

Android 13 引入预测性返回。Android 16 起，targetSdk 36 的应用在搭载 Android 16 及以上的设备上默认启用预测性返回系统动画，**系统不再调用 `onBackPressed()`，也不再分派 `KEYCODE_BACK`**。

对遥控器开发的影响是直接的：靠 `onKeyDown` 判断 `KEYCODE_BACK` 的写法在目标版本上完全失效，返回逻辑必须迁移到返回导航 API：

```kotlin
// Activity
onBackPressedDispatcher.addCallback(this) {
    // 处理返回
}

// Compose
BackHandler(enabled = isDetailVisible) {
    // 关闭详情
}
```

TV 的返回语义通常分三层：退出沉浸式列表 → 返回上一级 → 退出应用。用多个 `BackHandler` 的 `enabled` 顺序表达层级，比在按键回调里维护状态更稳定，也能与系统返回手势、预测性返回动画保持一致。

## 清单与设备声明

```xml
<uses-feature
    android:name="android.software.leanback"
    android:required="false" />
<uses-feature
    android:name="android.hardware.touchscreen"
    android:required="false" />

<application android:banner="@drawable/tv_banner">
    <activity
        android:name=".MainActivity"
        android:exported="true">
        <intent-filter>
            <action android:name="android.intent.action.MAIN" />
            <category android:name="android.intent.category.LEANBACK_LAUNCHER" />
        </intent-filter>
    </activity>
</application>
```

- `android.hardware.touchscreen` 声明为非必需，是 Google Play 识别 TV 应用的必需条件，缺失会导致应用不出现在电视端。
- `android.software.leanback` 的 `required` 设为 `false` 表示同一 APK 同时支持手机与电视；设为 `true` 则只在 TV 上分发。
- 横幅使用 320×180 px 的 xhdpi 资源，图片中必须包含文字，每种语言分别提供。
- 电视入口单独声明 `LEANBACK_LAUNCHER`，缺少该 category 时应用不会出现在电视主屏。

横屏不能依赖 `android:screenOrientation`：targetSdk 36 起，最小宽度 ≥ 600dp 的显示屏会忽略屏幕方向、尺寸与宽高比限制（Android 16 行为变更）。TV 布局按横屏设计，但不能把方向锁死作为前提。

## 性能与验证

焦点移动必须即时。缩放、发光等动画只做视觉反馈，不能阻塞焦点转移；动画时长一旦超过一帧的感知阈值，连按方向键会出现焦点追不上按键的现象。动画应只作用于获得焦点的项，避免全列表重组。

低端盒子的 CPU 与内存远低于手机。焦点变化会触发局部重组，`onFocusChanged` 回调里不应做图片解码、网络请求或全局状态刷新。

验证手段分三层：

- TV 模拟器覆盖焦点逻辑与布局，按键用 `adb shell input keyevent` 脚本化连按，可稳定复现焦点丢失。
- 真机覆盖解码、DRM 与遥控器键码，语音键、数字键、彩色键在不同盒子上并不一致。
- 长按、快速连按需要单独测试：`repeatCount` 的阈值、连按时的焦点顺序，都是模拟器难以完全复现的场景。
