大屏设备（电视、机顶盒、投影、车机）没有触摸输入，用户与界面的全部交互来自遥控器的方向键、确认键与返回键。开发重点因此不在「点击响应」，而在**按键事件的分发**与**焦点状态的流转**。

Android 没有名为「遥控器」的 API。系统把遥控器当作普通输入设备，产生 `KeyEvent`，界面能否被顺畅操作，取决于焦点体系是否被正确设计。红外发射、蓝牙配对属于厂商方案，键码与协议由硬件决定，不在系统能力范围内——这部分只体现为「拿到什么键码就处理什么键码」。

## 交互模型

|维度|手机 / 平板|大屏|
|:--|:--|:--|
|输入源|触摸、软键盘|方向键、确认键、返回键、媒体键|
|命中方式|坐标命中|焦点跳转|
|界面密度|高，可滚动长列表|低，按行组织，一屏信息量受限|
|观看距离|30～50 cm|约 3 m（10 英尺界面）|
|失败恢复|用户重新点击|焦点丢失后难以找回，需要返回重进|

触摸是坐标命中：用户点哪儿，事件就到哪儿，点空可以重试。遥控是焦点跳转：焦点是全局唯一的活动元素，每次按键把它移到「下一个」，移动路径由布局与焦点规则共同决定。用户不会「点空」，但会「走丢」。

两条由此推出的约束：焦点移动路径必须确定且可预测；任何时刻都必须存在一个可见的焦点。界面上的每个可交互元素都要能被若干次方向键到达，且不会掉进死循环。

## 按键事件的分发链路

物理按键 → Linux input 子系统 → `InputManagerService` → `WindowManagerService` → 目标窗口的 `ViewRootImpl` → `DecorView.dispatchKeyEvent` → Activity / View 树。

三个可拦截的位置：

|层级|入口|特点|
|:--|:--|:--|
|Activity|`dispatchKeyEvent`、`onKeyDown`|最早接触事件，适合全局快捷键|
|View|`dispatchKeyEvent`、`onKeyDown`、`onKeyUp`|父子冒泡，父容器可先行拦截|
|Compose|`Modifier.onPreviewKeyEvent`、`Modifier.onKeyEvent`|前者自上而下，后者自下而上|

Compose 的两个修饰符方向相反：`onPreviewKeyEvent` 在子节点之前收到事件，用于拦截方向键；`onKeyEvent` 只在子节点未消费时冒泡到父节点。返回 `true` 即消费，事件不再向下或向上传递。

```kotlin
Box(
    Modifier.onPreviewKeyEvent { event ->
        if (event.type == KeyEventType.KeyDown && event.key == Key.DirectionCenter) {
            onConfirm()
            true
        } else {
            false
        }
    }
) {
    // 内容
}
```

长按的判定依赖 `repeatCount`：按住不放时系统持续派发 `KeyDown`，`repeatCount` 从 0 递增。Compose 的 `KeyEvent` 通过 `event.nativeKeyEvent.repeatCount` 读取；View 侧若要触发 `onKeyLongPress`，必须在 `onKeyDown` 里先调用 `event.startTracking()`，否则回调不会到达。

常用键码：

|键码|含义|使用场景|
|:--|:--|:--|
|`KEYCODE_DPAD_UP` / `DOWN` / `LEFT` / `RIGHT`|方向键|焦点移动，通常交由系统处理|
|`KEYCODE_DPAD_CENTER` / `KEYCODE_ENTER`|确认|触发当前焦点项|
|`KEYCODE_BACK`|返回|导航回退（受预测性返回影响，见下文）|
|`KEYCODE_MEDIA_PLAY_PAUSE` / `NEXT` / `PREVIOUS`|媒体控制|播放器快捷键|
|`KEYCODE_MENU`|菜单|部分遥控器提供|
|`KEYCODE_VOLUME_UP` / `DOWN`|音量|多数设备由系统直接处理|

系统保留键不会分发给应用：`KEYCODE_HOME`、`KEYCODE_RECENTS`、`KEYCODE_POWER`。音量键在多数电视与盒子上同样由系统消费，应用只能在部分设备上观察到。把音量调节做成应用内功能，属于对设备的错误假设。

厂商差异是常态：语音键、数字键、彩色键没有统一键码，可能上报 `KEYCODE_UNKNOWN`，也可能是厂商自定义值。可配置的键码映射表比硬编码判断更可靠，遇到未知键码时保留日志而不是静默丢弃。

调试时用 adb 模拟按键，便于脚本化复现：

```bash
adb shell input keyevent KEYCODE_DPAD_DOWN
adb shell input keyevent 20          # 20 是 DPAD_DOWN 的键值
adb shell input keyevent KEYCODE_DPAD_CENTER
```

## 焦点体系

### 两套实现的对应关系

View 侧的焦点属性建立在普通 View 体系之上（见 [[9. UI 开发|UI 开发]]），Compose 侧则归入焦点与输入处理（见 [[5. 自定义组件与布局|自定义组件与布局]]）。两套 API 名称不同，判定规则一致。

|能力|View|Compose|
|:--|:--|:--|
|声明可聚焦|`android:focusable`、`setFocusable()`|`Modifier.focusable()`|
|指定相邻焦点|`nextFocusUp` / `Down` / `Left` / `Right`|`Modifier.focusProperties { up = ... }`|
|主动请求焦点|`requestFocus()`|`FocusRequester.requestFocus()`|
|焦点组|`descendantFocusability`|`Modifier.focusGroup()`|
|焦点记忆|自行保存与恢复|`Modifier.focusRestorer()`|

两套体系共用同一个 `FocusFinder` 算法：以当前焦点矩形为起点，沿按键方向投射一条 beam，候选控件按「与 beam 的垂直距离」和「沿 beam 方向的距离」加权评分，取最优者。这解释了布局中的常见现象——视觉上相邻的两行，如果控件矩形没有对齐，方向键会跳过其中一行，或者跳到屏幕另一侧的控件上。

### 四个基本动作

**声明可聚焦。** `Modifier.focusable()` 让节点进入焦点链；`clickable()` 内部已包含可聚焦与按键处理，普通可点击项不必重复添加。`focusTarget()` 只参与焦点链、不处理输入，用于容器级别的焦点管理。

**请求初始焦点。** 用 `FocusRequester` 指定首个焦点，在 `LaunchedEffect` 中调用。组合阶段直接调用会抛 `IllegalStateException`，因为此时节点尚未 attach。

```kotlin
val firstRequester = remember { FocusRequester() }

LazyRow(modifier = Modifier.focusRestorer(firstRequester)) {
    itemsIndexed(items) { index, item ->
        Card(
            modifier = if (index == 0) Modifier.focusRequester(firstRequester) else Modifier
        ) {
            // 卡片内容
        }
    }
}

LaunchedEffect(Unit) { firstRequester.requestFocus() }
```

**改写方向。** `focusProperties` 覆盖默认的 2D 搜索，只在默认算法失效时使用——两列列表之间的对齐、侧边栏与内容区的跳转、需要跳过装饰性控件的位置。滥用会让焦点路径变得不可预测，后续维护者无法从布局推断按键结果。

```kotlin
Row(
    Modifier.focusProperties {
        right = contentRequester    // 从侧边栏向右直接进入内容区
    }
) {
    // 侧边栏
}
```

`FocusProperties` 的 `onEnter` / `onExit` 用于在焦点进入或离开容器时重定向，例如导航栏获得焦点时自动落到当前选中项。旧版本使用的 `enter` / `exit` 属性已被替换。

**记忆与恢复。** `LazyRow`、`LazyColumn`、`LazyVerticalGrid` 本身是焦点组，附加 `Modifier.focusRestorer()` 后，焦点离开再回来会落在上次停留的项，而不是第一项。普通 `Row` / `Column` 不建立焦点边界，需要 `focusGroup()` 与 `focusRestorer()` 同时使用。

`focusRestorer` 早期版本接受 `onRestoreFailed` 的 lambda 重载（1.6.0 引入），Compose UI 1.8 起废弃，当前签名接受一个 `FocusRequester` 作为恢复失败时的后备目标。

跨页面返回时，容器可以记录离开前的焦点：导航前往详情页前调用 `FocusRequester.saveFocusedChild()`，返回后调用 `restoreFocusedChild()`。列表数据被重新加载时，硬编码的位置会指向错误的项，这种场景应改为按业务状态（例如当前选中的内容 id）指定焦点。

### 焦点陷阱

|症状|原因|处理|
|:--|:--|:--|
|焦点停在屏幕外|列表未把焦点项滚入可视区|`Modifier.bringIntoViewRequester` + 获焦时调用 `bringIntoView()`|
|每次回到列表都从第一项开始|未启用焦点恢复|列表加 `focusRestorer`|
|焦点在容器内循环，出不去|`focusProperties` 覆盖了默认搜索，或父容器消费了方向键|检查覆盖规则与 `onPreviewKeyEvent` 的返回值|
|返回后焦点消失|页面重建未指定首焦点|重建后显式 `requestFocus()`|
|滚动时焦点乱跳|焦点绑定在列表位置而非数据 key|按 id 记录焦点项，避免复用错位|
|首屏无焦点，按键无反应|依赖「第一个可聚焦元素自动获焦」|进入页面时显式请求焦点|

## 焦点视觉反馈

焦点是逻辑状态，用户感知到的是视觉状态。边框、覆盖、缩放三种效果都能只改绘制属性完成，不参与测量，因此不影响焦点移动速度。

三种实现的共同前提是拿到焦点状态：

```kotlin
var focused by remember { mutableStateOf(false) }

Box(
    Modifier
        .onFocusChanged { focused = it.isFocused }
        .focusable()
)
```

使用 `clickable` 的组件也可以从 `MutableInteractionSource` 取 `collectIsFocusedAsState()`，语义等价，代码量更大。

### 边框

`Modifier.border` 在组件边界内侧描边，宽度与颜色可随焦点状态动画过渡：

```kotlin
val strokeWidth by animateDpAsState(if (focused) 3.dp else 1.dp, label = "strokeWidth")
val strokeColor by animateColorAsState(
    if (focused) MaterialTheme.colorScheme.primary else Color.Transparent,
    label = "strokeColor"
)

Box(
    Modifier
        .border(strokeWidth, strokeColor, RoundedCornerShape(12.dp))
        .padding(12.dp)
)
```

- 描边不占布局空间，宽度变化时内容不位移；用 `padding` 模拟边框会让焦点切换触发重新布局。
- 圆角必须与背景 shape 一致，否则边框与背景边缘错位。
- 未聚焦时用透明色而不是移除 `border`，modifier 链保持稳定，状态切换的重组范围更小。

View 侧最小实现是把焦点边框放进 `foreground`，由状态选择器切换，不必在焦点回调里改背景：

```xml
<!-- res/drawable/focus_border.xml -->
<selector xmlns:android="http://schemas.android.com/apk/res/android">
    <item android:state_focused="true">
        <shape android:shape="rectangle">
            <corners android:radius="12dp" />
            <stroke android:width="3dp" android:color="@color/focus_stroke" />
        </shape>
    </item>
    <item>
        <shape android:shape="rectangle">
            <corners android:radius="12dp" />
            <stroke android:width="1dp" android:color="@android:color/transparent" />
        </shape>
    </item>
</selector>
```

```xml
<androidx.cardview.widget.CardView
    android:layout_width="240dp"
    android:layout_height="135dp"
    android:focusable="true"
    android:foreground="@drawable/focus_border" />
```

`android:foreground` 在 API 23 起对所有 View 可用。前景绘制在矩形边界内，不受卡片圆角裁剪，因此描边的圆角半径必须与卡片一致，否则四角会露出直角。

### 覆盖

在内容之上叠一层半透明色，不改变轮廓与尺寸，图片卡片上比描边更自然。用 `drawWithContent` 实现不需要额外布局节点：

```kotlin
Box(
    Modifier
        .clip(RoundedCornerShape(12.dp))
        .drawWithContent {
            drawContent()
            if (focused) {
                drawRect(Color.White.copy(alpha = 0.12f))
            }
        }
)
```

- `drawWithContent` 先绘制内容再覆盖矩形，不参与命中测试，也不进入语义树。
- 覆盖按矩形绘制，圆角卡片必须在外层 `clip(shape)`，否则四角会露在圆角之外。
- 需要渐变或多层叠加时，改为 `Box` 内的 `Modifier.matchParentSize()` 子层，对该子层做 alpha 动画，并加 `clearAndSetSemantics {}` 防止读屏重复播报。
- 透明度按底色选取：暗色背景用白色 0.08～0.14，浅色背景用黑色同区间。

View 侧对应 `foreground` 加 `ColorDrawable`，焦点回调里只改 alpha，避免每次创建对象：

```kotlin
val overlay = ColorDrawable(Color.WHITE).apply { alpha = 0 }
view.foreground = overlay
view.setOnFocusChangeListener { _, hasFocus ->
    overlay.alpha = if (hasFocus) 30 else 0
}
```

### 缩放

缩放让焦点项从周围内容中浮起，在 3 米观看距离下比颜色变化更容易察觉：

```kotlin
val scale by animateFloatAsState(
    targetValue = if (focused) 1.08f else 1f,
    animationSpec = tween(durationMillis = 150),
    label = "scale"
)

Box(
    Modifier.graphicsLayer {
        scaleX = scale
        scaleY = scale
    }
)
```

- `graphicsLayer` 的 lambda 在绘制阶段读取动画值，帧更新不触发重组与重新测量，是三种效果里开销最低的。
- 父容器默认裁剪（`LazyRow` 即如此），放大后的边缘会被切掉；容器需留出与缩放幅度匹配的空白，1.08 倍对应约 4% 的尺寸余量。
- 缩放不改变布局占位，相邻项会视觉重叠，间距按放大后的尺寸预留。
- 缩放中心默认为控件中心，靠近屏幕边缘的项放大后可能溢出，这类位置改用边框更稳妥。
- 与边框叠加时，`graphicsLayer` 写在 `border` 之前会连同描边一起放大；写在之后则描边保持原宽度，仅内容缩放。

View 侧用属性动画：

```kotlin
view.setOnFocusChangeListener { v, hasFocus ->
    val target = if (hasFocus) 1.08f else 1f
    v.animate().scaleX(target).scaleY(target).setDuration(150).start()
}
```

### 组合与取舍

|效果|远距离可辨识度|开销|适用场景|
|:--|:--|:--|:--|
|边框|中|低，一次描边绘制|列表项密集、需要明确边界|
|覆盖|低|最低，一次矩形填充|图片卡片、暗色背景|
|缩放|高|中，需处理裁剪与重叠|首屏推荐位、卡片式布局|

- 同一界面选一到两种即可，边框与缩放的组合最常用；三种同时启用会让焦点反馈显得杂乱，描边与放大还会互相干扰。
- 三种效果都只改绘制属性。用动画改 `padding`、`size`、`elevation` 会触发重新布局，连按方向键时表现为掉帧。
- 参数在同一应用内统一：时长 150 ms 左右、缩放 1.05～1.10、边框 2～3 dp。参数不一致会让不同页面的焦点反馈像是拼装的。
- tv-material 组件已内置缩放、边框、发光、容器颜色四种指示，使用库组件时直接配置 `Defaults`；手写实现面向自定义组件与非 tv 库的场景。

## Compose for TV

TV 界面用 `androidx.tv` 系列库构建，稳定版本如下（2026-05 发布）：

```kotlin
implementation("androidx.tv:tv-material:1.1.0")
implementation("androidx.tv:tv-foundation:1.0.0")
```

两套 Material 不要混用。`androidx.tv.material3` 与 `androidx.compose.material3` 各自持有独立的 `MaterialTheme`，混用会出现颜色、字体、形状不一致，且组件内部的焦点反馈与间距假设不同。

tv-material 把上述反馈封装成组件参数（缩放、边框、发光、容器颜色），配置 `Defaults` 即可，不需要手写 `onFocusChanged` 或 `OnFocusChangeListener`：

```kotlin
Card(
    onClick = { onSelect(item) },
    scale = CardDefaults.scale(focusedScale = 1.1f)
) {
    // 卡片内容
}
```

两个迁移事实需要明确：

- Leanback 已整体标注废弃，官方声明为「此制品及其类已废弃。请改用 Compose for TV」，但制品仍有版本发布（最新 1.3.0-alpha02，2026-06），存量项目需要继续维护，具体见下一节。
- tv-foundation 中的 `TvLazyRow` / `TvLazyColumn` 自 1.0.0-alpha11（2024-07）起弃用，改用标准 `LazyRow` / `LazyColumn` 配合 `focusRestorer`。TV 专用懒加载布局曾解决的「焦点项保持在屏幕固定位置」，现在由焦点恢复与 `bringIntoView` 共同承担。

TV 组件不会自动给首个元素焦点，页面进入时显式 `requestFocus()` 是唯一可靠做法；焦点请求失败（节点未 attach、容器不可见）时应有降级路径，避免整屏按键无响应。

## Leanback（存量项目）

Leanback 是 View 体系的 TV 工具包，提供成套的 Fragment、行容器与焦点驱动网格。新界面优先 Compose for TV，但存量工程里的 Leanback 页面在可预见的维护周期内不会消失，理解它的组件划分与焦点模型是接手这类项目的门槛。

### 组件地图

|组件|职责|
|:--|:--|
|`BrowseSupportFragment`|主浏览页，内部由 Headers（左侧导航）与 Rows（内容行）组成，adapter 元素必须是 `Row` 子类|
|`RowsSupportFragment`|内容行容器，通过 `getRowsSupportFragment()` 获取|
|`DetailsSupportFragment`|详情页，左侧信息、右侧操作|
|`PlaybackSupportFragment`|播放控制层（控制行、缓冲条、背景），不含画面|
|`VideoSupportFragment`|继承前者，额外提供 `SurfaceView` 与视频尺寸回调|
|`SearchSupportFragment`|搜索页，结果由 `SearchResultProvider` 提供，语音搜索需要录音权限|
|`GuidedStepSupportFragment`|多步向导对话框，常用于引导与设置|
|`ErrorSupportFragment`|错误页|
|`HorizontalGridView` / `VerticalGridView`|焦点驱动的网格容器；1.2.0 起拆分到独立制品 `leanback-grid`，保持二进制兼容|

### 工程接入

依赖坐标（2026-05 的稳定版本）：

```kotlin
implementation("androidx.leanback:leanback:1.2.0")
// 只需要网格时可用更小的制品
implementation("androidx.leanback:leanback-grid:1.0.0")
```

主题决定控件外观与字号，承载 Leanback 页面的 Activity 必须使用 `Theme.Leanback` 或其子类，否则控件样式错乱、部分组件在初始化阶段直接抛异常：

```xml
<activity
    android:name=".TvActivity"
    android:theme="@style/Theme.Leanback" />
```

Activity 只负责挂载入口 Fragment，页面切换交给 FragmentManager：

```kotlin
class TvActivity : FragmentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_tv)

        if (savedInstanceState == null) {
            supportFragmentManager.beginTransaction()
                .replace(R.id.container, MainFragment())
                .commit()
        }
    }
}
```

页面结构上，Browse 是骨架，其余页面都是压在它上面的独立 Fragment：

```
TvActivity
└── MainFragment (BrowseSupportFragment)
    ├── Headers（由每个 Row 的 HeaderItem 派生）
    ├── RowsSupportFragment（内容行）
    ├── DetailsSupportFragment（详情，点击卡片后进入）
    ├── VideoSupportFragment（播放）
    └── GuidedStepSupportFragment（设置、引导）
```

Headers 不是独立数据源：每个 `Row` 通过 `HeaderItem` 描述导航项，数量天然一致。自定义 `Row` 子类还需要在 `MainFragmentAdapterRegistry` 中登记对应的 `FragmentFactory`，否则该行无法展开为独立页面。

### 最小骨架

```kotlin
class MainFragment : BrowseSupportFragment() {
    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)

        title = "影视库"
        headersState = BrowseSupportFragment.HEADERS_ENABLED
        brandColor = ContextCompat.getColor(requireContext(), R.color.brand)

        adapter = ArrayObjectAdapter(ListRowPresenter()).apply {
            add(
                ListRow(
                    HeaderItem(1, "最近观看"),
                    ArrayObjectAdapter(CardPresenter()).apply { items.forEach { add(it) } }
                )
            )
        }
        setOnItemViewClickedListener { _, item, _, _ -> openDetail(item) }
    }
}
```

- 适配器分两层：`BrowseSupportFragment` 收 `Row`，行内收业务数据；`ListRowPresenter` 决定行的呈现方式，`CardPresenter` 决定卡片外观。
- adapter 在 `onViewCreated` 中挂载。`onActivityCreated` 自 Fragment 1.3 起废弃；Fragment 重建时 view 会重新创建，adapter 也需要重新挂载，否则列表为空。

### 数据流与 Presenter

Leanback 的列表由三层构成：`ObjectAdapter` 持有数据，`Presenter` 决定单个 item 的视图，`PresenterSelector` 按数据类型选择 Presenter。`Presenter` 实例应在构造时创建并复用，绑定阶段只更新视图：

```kotlin
class CardPresenter : Presenter() {
    override fun onCreateViewHolder(parent: ViewGroup): ViewHolder {
        val view = LayoutInflater.from(parent.context)
            .inflate(R.layout.item_card, parent, false)
        return ViewHolder(view)
    }

    override fun onBindViewHolder(viewHolder: ViewHolder, item: Any) {
        val movie = item as Movie
        viewHolder.view.findViewById<TextView>(R.id.title).text = movie.title
    }

    override fun onUnbindViewHolder(viewHolder: ViewHolder) {
        // 释放图片加载回调、停止动画
    }
}
```

一行内混有多种数据类型时，用 `ClassPresenterSelector` 按类型分派：

```kotlin
val selector = ClassPresenterSelector().apply {
    addClassPresenter(Movie::class.java, CardPresenter())
    addClassPresenter(Banner::class.java, BannerPresenter())
}
val rowAdapter = ArrayObjectAdapter(selector)
```

`onBindViewHolder` 会被高频调用，其中不能做图片解码或网络请求；这些工作交给图片库，`onUnbindViewHolder` 负责取消尚未完成的加载，否则快速滚动时会出现图片错位。

行的呈现参数集中在 `ListRowPresenter` 与 `RowPresenter`：行高、阴影、选中效果分别由 `setRowHeight()`、`setShadowEnabled()`、`setSelectEffectEnabled()` 控制，电视上的行距与焦点轮廓直接由它们决定。聚焦放大程度由构造参数决定，取值从 `ZOOM_FACTOR_NONE` 到 `ZOOM_FACTOR_LARGE`；多行网格用 `setNumRows()` 开启。

数据刷新遵循 adapter 的通知协议：局部变化用 `notifyItemRangeChanged()` / `notifyArrayItemRangeChanged()`，插入与删除用对应的 `notifyItemRangeInserted()` / `notifyItemRangeRemoved()`。整表重建会同时丢失焦点位置与滚动位置，在电视上是明显的体验退化。分页场景可引入 `androidx.leanback:leanback-paging:1.1.0`，把 Paging 3 的数据源接到 `ArrayObjectAdapter`；数据量有限时手工分页更直接。

### 详情页

详情页与目录页同构，也是一个 `ObjectAdapter` 装多个 `Row`，只是第一行换成 `DetailsOverviewRow`：

```kotlin
private val overviewPresenter =
    FullWidthDetailsOverviewRowPresenter(DescriptionPresenter()).apply {
        setOnActionClickedListener { action ->
            if (action.id == ACTION_PLAY) startPlayback()
        }
    }

override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
    super.onViewCreated(view, savedInstanceState)

    val overview = DetailsOverviewRow(movie).apply {
        setImageDrawable(poster)
        addAction(Action(ACTION_PLAY, "播放", playIcon))
        addAction(Action(ACTION_FAVORITE, "收藏", starIcon))
    }

    val selector = ClassPresenterSelector().apply {
        addClassPresenter(DetailsOverviewRow::class.java, overviewPresenter)
        addClassPresenter(ListRow::class.java, ListRowPresenter())
    }
    adapter = ArrayObjectAdapter(selector).apply {
        add(overview)
        add(ListRow(HeaderItem(2, "演员"), castAdapter))
        add(ListRow(HeaderItem(3, "相关推荐"), relatedAdapter))
    }
}

private class DescriptionPresenter : Presenter() {
    override fun onCreateViewHolder(parent: ViewGroup): ViewHolder {
        val view = LayoutInflater.from(parent.context)
            .inflate(R.layout.item_description, parent, false)
        return ViewHolder(view)
    }

    override fun onBindViewHolder(viewHolder: ViewHolder, item: Any) {
        val movie = item as Movie
        viewHolder.view.findViewById<TextView>(R.id.title).text = movie.title
        viewHolder.view.findViewById<TextView>(R.id.description).text = movie.description
    }
}
```

- `DetailsOverviewRow` 只承载主视觉与操作按钮，演员、推荐等信息仍用 `ListRow` 组织，整页塞进一个 Row 会让焦点移动变得不可控。
- 操作按钮的点击由 `FullWidthDetailsOverviewRowPresenter.setOnActionClickedListener` 处理，与行内 item 的点击监听是两条链路，二者不要互相代理。
- 详情页由 Browse 的点击回调启动；若详情作为自定义 `Row` 的目标，走 `MainFragmentAdapterRegistry` 登记，而不是在点击回调里手工 `replace()`。

### 焦点与选中

Leanback 的网格自己接管焦点：方向键由 `BaseGridView` 消费，焦点移动带动滚动，选中位置通过 `setSelectedPosition()`、`getSelectedPosition()` 与 `OnChildViewHolderSelectedListener` 读取。这与普通 `RecyclerView` 逐项 `focusable` 的模型相反——item 根布局再声明可聚焦，会与网格的焦点管理冲突，表现为按键跳项或焦点停在原地。

跨行跳转由 `focusOutFront` / `focusOutEnd` 控制，即网格首列、末列再按方向键时的出口；项内对齐由 `ItemAlignmentFacet` 描述。这两处是维护老项目时最常见的焦点问题来源。

焦点到达边缘时内容如何跟动，由 `setFocusScrollStrategy()` 决定：对齐项、对齐窗口或纯滚动。它与 `focusOutFront` / `focusOutEnd` 一起决定跨行行为，调整时需要同时验证首列、末列与行首、行尾四种位置。

### 播放链路

`PlaybackGlue` 把控制逻辑与播放器解耦：`PlayerAdapter` 封装具体播放器，`PlaybackTransportControlGlue` 负责控制层行为，`PlaybackGlueHost` 负责把控制层挂到界面：

```kotlin
val adapter = MediaPlayerAdapter(requireContext())
val glue = PlaybackTransportControlGlue(requireContext(), adapter)
glue.host = VideoSupportFragmentGlueHost(videoFragment)
```

- `VideoSupportFragmentGlueHost` 自 1.1.0 起提供，构造时传入 `VideoSupportFragment`；纯控制层场景对应 `PlaybackSupportFragmentGlueHost`。
- 播放控制行由 Glue 生成，不需要手工构造 `PlaybackControlsRow`；只有调整按钮集合或换用自定义控制行时，才需要替换 `PlaybackRowPresenter`。
- `MediaPlayerAdapter` 覆盖 `MediaPlayer` 的能力范围。使用 ExoPlayer 或 media3 的工程需要自行实现 `PlayerAdapter`，Leanback 的公开参考中已无对应适配类。
- 自定义 `PlayerAdapter` 必须提供时长、当前位置、播放状态与 seek 能力，并在准备完成、缓冲变化时回调，否则控制层的进度条与按钮状态不会更新。
- 数据源由 `PlayerAdapter` 设置。需要「准备好即播」时调用 `playWhenPrepared()`：`play()` 在 `isPrepared()` 为 false 时不执行任何操作。
- 播放状态由 Glue 与 Host 驱动，业务侧不要在 `onResume` 里直接操作播放器；页面切走后的暂停与恢复由宿主生命周期回调完成。

### 搜索页

`SearchSupportFragment` 自带搜索框与结果行，应用只需实现 `SearchResultProvider`：

```kotlin
class SearchFragment : SearchSupportFragment(), SearchSupportFragment.SearchResultProvider {

    private val results = ArrayObjectAdapter(ListRowPresenter())

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setSearchResultProvider(this)
        title = "搜索影视"
    }

    override fun getResultsAdapter(): ObjectAdapter = results

    override fun onQueryTextChange(newQuery: String): Boolean {
        updateResults(newQuery)
        return true      // 结果已变化
    }

    override fun onQueryTextSubmit(query: String): Boolean {
        updateResults(query)
        return true
    }
}
```

- 三个方法缺一不可：`getResultsAdapter()` 提供承载结果的 adapter，两个查询回调返回 `Boolean`，表示结果是否随本次查询改变。
- 结果更新走 adapter 的通知方法，不要新建 adapter——Fragment 持有的是 `getResultsAdapter()` 返回的实例，换实例不会刷新界面。
- 语音搜索需要 `RECORD_AUDIO` 权限。首次进入会自动启动识别，从 instance state 恢复时不会，需要在用户点击麦克风时调用 `startRecognition()`。
- `setSearchQuery(String, Boolean)` 用于预填或外部触发查询，第二个参数决定是否立即提交。

### 向导流程

`GuidedStepSupportFragment` 用于设置、首次引导与确认对话框，三个回调必须覆写：

```kotlin
class QualityStepFragment : GuidedStepSupportFragment() {

    override fun onCreateGuidance(savedInstanceState: Bundle?): GuidanceStylist.Guidance =
        GuidanceStylist.Guidance("画质", "选择默认清晰度", "设置", icon)

    override fun onCreateActions(
        actions: MutableList<GuidedAction>,
        savedInstanceState: Bundle?
    ) {
        actions += GuidedAction.Builder(requireContext())
            .id(ACTION_AUTO)
            .title("自动")
            .description("根据带宽选择")
            .build()
        actions += GuidedAction.Builder(requireContext())
            .id(ACTION_1080P)
            .title("1080P")
            .build()
    }

    override fun onGuidedActionClicked(action: GuidedAction) {
        when (action.id) {
            ACTION_AUTO -> saveQuality(Quality.AUTO)
            ACTION_1080P -> saveQuality(Quality.P1080)
        }
        finishGuidedStepSupportFragments()
    }
}
```

- 启动用静态 `add(fragmentManager, fragment)`；作为 Activity 根页面时用 `addAsRoot(activity, fragment, id)`。多步流程必须逐级 `add` 压栈，否则返回栈与转场动画都不正确。
- 整条流程必须用代码构建，不能写在 XML 里；每一步都是独立的 Fragment 子类。
- 主题必须能解析到 GuidedStep 主题（Activity 使用 Leanback 主题即可），否则左右分栏与动作列表的样式失效。

### 背景与视觉

目录页的整屏背景由 `BackgroundManager` 统一管理：`getInstance(activity)` 取得实例，`setBitmap()`、`setColor()`、`setDrawable()` 切换内容，页面销毁时 `release()`。背景需要随选中项变化时，在 `OnItemViewSelectedListener` 中更新，不要在布局里给每个 Fragment 各挂一层背景图——两层背景叠加会出现闪屏与残留。

### 维护高频问题

|现象|原因|处理|
|:--|:--|:--|
|启动崩溃或控件样式缺失|Activity 未使用 `Theme.Leanback`|主题改为继承 `Theme.Leanback`|
|方向键跳项、焦点卡住|item 根布局自行声明 `focusable`|移除 item 级可聚焦，选中态交给网格|
|头部导航展开时返回键行为异常|返回未先收起 Headers|`setHeadersTransitionOnBackEnabled(true)`|
|页面重建后列表为空|adapter 在 `onCreate` 中设置且未重建|改在 `onViewCreated` 中挂载，`onActivityCreated` 已废弃|
|搜索无结果|未设置 `SearchResultProvider`，或查询回调返回 false、adapter 实例被替换|设置 provider，复用 `getResultsAdapter()` 的实例并通过通知刷新|
|语音搜索无响应|未声明 `RECORD_AUDIO`，或状态恢复后未重新启动识别|声明权限，在麦克风点击时调用 `startRecognition()`|
|向导页样式异常或崩溃|流程用 XML 声明，或主题不含 GuidedStep|改为代码构建每一步 Fragment，主题使用 Leanback|
|播放页退出后仍有声音|Glue 未随页面销毁解除|`onDestroyView` 中 `pause()` 并 `host = null`|
|快速滚动时图片错位|`onUnbindViewHolder` 未取消未完成的加载|在解绑时取消请求或停止动画|
|背景闪烁或残留|布局内自设背景与 `BackgroundManager` 叠加|背景只保留 `BackgroundManager` 一处，销毁时 `release()`|

### 与 Compose 共存

迁移不必整屏切换。`ComposeView` 可以直接作为 Presenter 的 item，也可以作为独立 Fragment 的根视图：

```kotlin
class ComposeCardPresenter : Presenter() {
    override fun onCreateViewHolder(parent: ViewGroup): Presenter.ViewHolder {
        val view = ComposeView(parent.context).apply {
            setViewCompositionStrategy(
                ViewCompositionStrategy.DisposeOnViewTreeLifecycleDestroyed
            )
            setContent { TvCard() }
        }
        return Presenter.ViewHolder(view)
    }
}
```

- 网格焦点由 `BaseGridView` 统一管理，`ComposeView` 内的可聚焦元素参与同一条焦点链；Compose 内容若在 `onPreviewKeyEvent` 中消费方向键，外层网格收不到事件，跨行移动会失效。
- `ComposeView` 需要绑定生命周期，否则组合不会随 Fragment 销毁而释放；`DisposeOnViewTreeLifecycleDestroyed` 适用于 Fragment 场景。
- 主题不会自动传递：Leanback 的 `Theme.Leanback` 只作用于 View 体系，Compose 内容需要用 `TvTheme` 或 `MaterialTheme` 重新包裹，否则字号与焦点色与周围不一致。
- 混合期保留单一导航栈：Compose 页面作为 Fragment 的根视图，页面切换仍由 FragmentManager 驱动；同时引入 Navigation Compose 会形成两套返回栈，返回键顺序难以对齐。
- 迁移顺序按耦合度从低到高：独立详情页与设置页 → 列表卡片（Presenter 内嵌 Compose）→ Browse / Rows 骨架 → 播放链路。播放与 MediaSession、DRM 耦合最深，放在最后处理。

### 版本与取舍

1.2.0 是当前的稳定线（2025-04-23），1.3.0-alpha02（2026-06-17）的改动集中在 minSdk 与少量 API 调整，没有新增组件。这决定了维护期的两个判断：

- 新页面不再以 Leanback 为设计目标，能独立成页的先做 Compose；仍依赖 Browse 的 Headers / Rows 骨架、或复用 PlaybackGlue 播放链路的页面，继续留在 Leanback 成本更低。
- 上游只做维护性更新，遇到框架缺陷通常需要自行绕行。绕行方案应限制在应用层（自定义 Presenter、替换 Fragment），不要依赖未公开的内部实现，否则升级 alpha 版本时容易失效。

## 返回键与预测性返回

Android 13 引入预测性返回。Android 16 起，targetSdk 36 的应用在搭载 Android 16 及以上的设备上默认启用预测性返回系统动画，**系统不再调用 `onBackPressed()`，也不再分派 `KEYCODE_BACK`**。

对遥控器开发的影响是直接的：靠 `onKeyDown` 判断 `KEYCODE_BACK` 的写法在目标版本上完全失效，返回逻辑必须迁移到返回导航 API：

```kotlin
// Activity
onBackPressedDispatcher.addCallback(this) {
    // 处理返回
}

// Compose
BackHandler(enabled = isDetailVisible) {
    // 关闭详情
}
```

TV 的返回语义通常分三层：退出沉浸式列表 → 返回上一级 → 退出应用。用多个 `BackHandler` 的 `enabled` 顺序表达层级，比在按键回调里维护状态更稳定，也能与系统返回手势、预测性返回动画保持一致。

## 清单与设备声明

```xml
<uses-feature
    android:name="android.software.leanback"
    android:required="false" />
<uses-feature
    android:name="android.hardware.touchscreen"
    android:required="false" />

<application android:banner="@drawable/tv_banner">
    <activity
        android:name=".MainActivity"
        android:exported="true">
        <intent-filter>
            <action android:name="android.intent.action.MAIN" />
            <category android:name="android.intent.category.LEANBACK_LAUNCHER" />
        </intent-filter>
    </activity>
</application>
```

- `android.hardware.touchscreen` 声明为非必需，是 Google Play 识别 TV 应用的必需条件，缺失会导致应用不出现在电视端。
- `android.software.leanback` 的 `required` 设为 `false` 表示同一 APK 同时支持手机与电视；设为 `true` 则只在 TV 上分发。
- 横幅使用 320×180 px 的 xhdpi 资源，图片中必须包含文字，每种语言分别提供。
- 电视入口单独声明 `LEANBACK_LAUNCHER`，缺少该 category 时应用不会出现在电视主屏。

横屏不能依赖 `android:screenOrientation`：targetSdk 36 起，最小宽度 ≥ 600dp 的显示屏会忽略屏幕方向、尺寸与宽高比限制（Android 16 行为变更）。TV 布局按横屏设计，但不能把方向锁死作为前提。

## 性能与验证

焦点移动必须即时。缩放、发光等动画只做视觉反馈，不能阻塞焦点转移；动画时长一旦超过一帧的感知阈值，连按方向键会出现焦点追不上按键的现象。动画应只作用于获得焦点的项，避免全列表重组。

低端盒子的 CPU 与内存远低于手机。焦点变化会触发局部重组，`onFocusChanged` 回调里不应做图片解码、网络请求或全局状态刷新。

验证手段分三层：

- TV 模拟器覆盖焦点逻辑与布局，按键用 `adb shell input keyevent` 脚本化连按，可稳定复现焦点丢失。
- 真机覆盖解码、DRM 与遥控器键码，语音键、数字键、彩色键在不同盒子上并不一致。
- 长按、快速连按需要单独测试：`repeatCount` 的阈值、连按时的焦点顺序，都是模拟器难以完全复现的场景。
