代码扫描覆盖的是“代码还没跑起来就能发现的问题”，以下按四个方向整理：

- **单元测试覆盖率**：测试到底执行到了哪些代码，回答“测试覆盖是否充分”；
- **静态代码扫描**：不运行程序，直接从源码与字节码里找问题；
- **开源组件扫描**：项目引进了哪些第三方库，它们有没有已知漏洞与许可证风险；
- **SonarQube**：把前几类结果汇总成平台数据、按质量门禁判断，并导出可对外交付的报告。

## 单元测试覆盖率

测试本身怎么写见 [[2. 单元测试]]，本节只谈覆盖率怎么采集与呈现。它同时适用于本地单元测试与插桩测试——两者的开关、任务、报告路径不同，但产物可以合并。

JaCoCo 通过字节码插桩记录“哪些指令真的被执行过”，再按行、分支、方法、类汇总成百分比。它回答的是**是否执行到**，而非**是否正确编写**——一个没有任何断言的测试，照样能把覆盖率刷到 100%。所以覆盖率的正确用法是找“0% 的类”和“分支全红的方法”，而不是拿总比例当 KPI。

### 启用与版本

AGP 内置了 JaCoCo 集成，按构建变体开关即可，不需要自己 apply JaCoCo 插件：

```kotlin
android {
    buildTypes {
        debug {
            // 本地测试（含 Robolectric）的覆盖率
            enableUnitTestCoverage = true
            // 插桩测试的覆盖率
            enableAndroidTestCoverage = true
        }
    }
}
```

这两个开关取代了已废弃的 `testCoverageEnabled`——老写法只能笼统地开启“测试覆盖率”，新写法把本地测试和插桩测试分开，因为两者的采集链路完全不同。

AGP 自带一个 JaCoCo 版本，通常够用。若项目用较新的 JDK 编译，需要按 class 文件版本对齐，否则报告阶段会报 `Unsupported class file major version 65`（65 对应 Java 21）：

```kotlin
android {
    testCoverage {
        jacocoVersion = "0.8.15"
    }
}
```

| JaCoCo | 支持的 class 版本 | 对 Kotlin / Compose 的改进 |
| --- | --- | --- |
| 0.8.11 | Java 21 | 基线 |
| 0.8.13 | Java 23 / 24 | 内联函数按调用点统计行覆盖；过滤 Compose 编译器、value class、suspend lambda 的部分合成字节码 |
| 0.8.14 | Java 25 | 过滤 Compose 可暂停组合（pausable composition）生成的字节码；过滤 kotlinx.serialization 生成的方法 |
| 0.8.15 | Java 26 | 过滤接口默认实现的兼容方法、`@JvmStatic` 生成方法；改进 `when` + String 的分支过滤 |
| 0.8.16 | Java 27 | 当前最新 |

Kotlin 项目建议至少用 **0.8.13**：在此之前，内联函数的行覆盖会被算到声明处而不是调用处，`inline` 用得多的代码覆盖率会明显偏低。Compose 项目建议 **0.8.14+**，否则组合函数生成的大量合成代码会把分母撑大。

### 运行并查看结果

```bash
# 本地测试覆盖率（含 Robolectric）
./gradlew :app:createDebugUnitTestCoverageReport

# 插桩测试覆盖率（需要连接设备）
./gradlew :app:createDebugAndroidTestCoverageReport

# 带 flavor 的变体，任务名用完整变体名
./gradlew :app:createFreeDebugUnitTestCoverageReport
```

报告位置固定，直接开 `index.html`：

| 测试类型 | 报告路径 |
| --- | --- |
| 本地测试 | `app/build/reports/coverage/test/debug/index.html` |
| 插桩测试 | `app/build/reports/coverage/androidTest/debug/connected/index.html` |

常见问题：**只要有相关测试失败，AGP 就不会生成覆盖率报告**。CI 上看到“报告目录是空的”，应先检查测试是否失败，而非怀疑 JaCoCo 配置。

Android Studio 里也可以直接右键测试类 → **Run with Coverage**，结果出现在 Coverage 工具窗口，适合即时查看；但它走的是 IDE 的采集通道，与 Gradle 任务的产物不是同一份，CI 仍应以 Gradle 任务为准。

### 看懂报告

报告按包 → 类 → 方法 → 行逐层下钻，颜色含义：

- **绿色**：该行指令全部执行；
- **黄色**：部分覆盖（分支只走了一半，或一行里有未执行的指令）；
- **红色**：完全没执行。

四个指标的含义与用途不同：

| 指标 | 统计对象 | 适用 |
| --- | --- | --- |
| 指令覆盖率（Instructions） | 字节码指令 | 最细，但对 Kotlin 语法糖敏感 |
| 分支覆盖率（Branches） | `if` / `when` 的分支 | 找漏测的边界条件 |
| 行覆盖率（Lines） | 源码行 | 最直观，团队沟通常用 |
| 方法 / 类覆盖率 | 方法、类是否被执行 | 找“整块没测”的模块 |

阅读时要有心理准备：**Android 项目的行覆盖率天然偏低**，因为分母里混进了大量非手写代码——

- `R`、`R$*`、`BuildConfig`、`Manifest`；
- Hilt / Dagger 生成的 `Hilt_*`、`*_Factory`、`*_MembersInjector`、`*_HiltModules*`；
- Compose 编译器生成的 `ComposableSingletons` 与 `$composable` lambda；
- Kotlin 编译器为默认参数生成的 `$default` 方法、为属性生成的内联访问器；
- 数据类的 `copy` / `componentN` / `equals` / `hashCode`。

不排除这些，报告的绝对数值没有参考价值；排除之后，同一个项目的数字往往会掉 10~20 个百分点——这是正常的，不是退步。

### 自定义报告：排除生成代码并输出 XML

AGP 的内置任务以 HTML 为主。需要排除生成代码、或者要给 SonarQube / CI 仪表盘喂 XML 时，用 Gradle 的 `JacocoReport` 自己注册一个：

```kotlin
// app/build.gradle.kts
import org.gradle.testing.jacoco.tasks.JacocoReport

plugins {
    jacoco
}

// 生成代码与测试代码，不计入分母
val coverageExcludes = listOf(
    "**/R.class",
    "**/R$*.class",
    "**/BuildConfig.*",
    "**/Manifest*.*",
    "**/BR.*",
    // Hilt / Dagger
    "**/Hilt_*",
    "**/*_HiltModules*",
    "**/*_Factory.class",
    "**/*_MembersInjector.class",
    "**/dagger/hilt/internal/**",
    // Compose 合成
    "**/*ComposableSingletons*",
    // 测试自身
    "**/*Test.class",
    "**/*TestKt.class",
)

tasks.register<JacocoReport>("jacocoDebugReport") {
    dependsOn("testDebugUnitTest")
    group = "verification"
    description = "合并 javac 与 Kotlin 产物，产出排除生成代码后的覆盖率报告"

    val buildDir = layout.buildDirectory.get().asFile

    classDirectories.setFrom(
        fileTree(buildDir.resolve("intermediates/javac/debug/classes")) { exclude(coverageExcludes) },
        fileTree(buildDir.resolve("tmp/kotlin-classes/debug")) { exclude(coverageExcludes) },
    )
    sourceDirectories.setFrom(files("src/main/java", "src/main/kotlin"))

    // 注意这里是 AGP 写执行数据的位置，不是 build/jacoco/
    executionData.setFrom(
        fileTree(buildDir.resolve("outputs/unit_test_code_coverage/debugUnitTest")) {
            include("*.exec")
        },
    )

    reports {
        html.required.set(true)
        xml.required.set(true)   // 给 Sonar / 覆盖率平台用
        csv.required.set(false)
    }
}
```

```bash
./gradlew :app:jacocoDebugReport
# HTML: app/build/reports/jacoco/jacocoDebugReport/html/index.html
# XML : app/build/reports/jacoco/jacocoDebugReport/jacocoDebugReport.xml
```

这份 XML 不只是给人看：下文 SonarQube 通过 `sonar.coverage.jacoco.xmlReportPaths` 读的就是它，所以路径要按 Sonar 的约定（相对根目录）来配。

两个必须说清的点：

- **Kotlin 的 class 不在 `intermediates/javac` 下**。只配 javac 目录，报告里会只剩 Java 类；Kotlin 编译产物在 `build/tmp/kotlin-classes/<variant>/`，两个目录都要加。
- `executionData` 的路径是 `build/outputs/unit_test_code_coverage/<variant>UnitTest/*.exec`。老教程里的 `build/jacoco/*.exec` 属于 AGP 4.x 时代，现在那里是空的。

写 Kotlin DSL 时不应使用 `"${layout.buildDirectory}/..."` 拼接字符串——`layout.buildDirectory` 是 `Provider`，插值出来是 `provider(...)` 而不是路径，报告会静默变成 0%。要么 `layout.buildDirectory.get().asFile`，要么用 `layout.buildDirectory.dir("...")` 的 Provider 重载。

### 合并多模块与多种测试类型

单模块的本地测试覆盖率由上面的任务解决。要一份**跨模块**的汇总，就在根工程注册一个聚合任务，把各模块的 class 目录与执行数据并进来：

```kotlin
// 根 build.gradle.kts
import org.gradle.testing.jacoco.tasks.JacocoReport

plugins {
    jacoco
}

val coveredModules = listOf(":core", ":data", ":app")

tasks.register<JacocoReport>("jacocoAggregatedReport") {
    dependsOn(coveredModules.map { "$it:testDebugUnitTest" })
    group = "verification"

    val buildDirs = coveredModules.map { project(it).layout.buildDirectory.get().asFile }
    val coverageExcludes = listOf("**/R.class", "**/R$*.class", "**/BuildConfig.*", "**/Hilt_*", "**/*_Factory.class")

    classDirectories.setFrom(
        buildDirs.map { dir ->
            fileTree(dir.resolve("intermediates/javac/debug/classes")) { exclude(coverageExcludes) }
        },
        buildDirs.map { dir ->
            fileTree(dir.resolve("tmp/kotlin-classes/debug")) { exclude(coverageExcludes) }
        },
    )
    sourceDirectories.setFrom(
        coveredModules.flatMap {
            listOf(project(it).file("src/main/java"), project(it).file("src/main/kotlin"))
        },
    )
    executionData.setFrom(
        buildDirs.map { dir ->
            fileTree(dir) { include("outputs/unit_test_code_coverage/debugUnitTest/*.exec") }
        },
    )

    reports {
        html.required.set(true)
        xml.required.set(true)
    }
}
```

要把**插桩测试**也算进去，把 `.ec` 一并加进 `executionData`（`jacocoDebugReport` 里对应片段的替换写法如下）：

```kotlin
val dir = layout.buildDirectory.get().asFile
executionData.setFrom(
    fileTree(dir.resolve("outputs/unit_test_code_coverage/debugUnitTest")) { include("*.exec") },
    fileTree(dir.resolve("outputs/code_coverage/debugAndroidTest/connected")) { include("**/*.ec") },
)
```

`connectedDebugAndroidTest` 产出的原始数据是 `.ec`（不是 `.exec`），路径在 `build/outputs/code_coverage/<variant>AndroidTest/connected/` 下。

从 **AGP 9.5.0-alpha05** 起，官方提供了开箱的合并能力，不必自己写任务：在 `gradle.properties` 里加 `android.experimental.reportAggregationSupport=true`，然后跑

```bash
# 当前模块，合并所有测试类型
./gradlew :app:testAllSuites --continue

# 当前模块 + 依赖模块（适用于 app 模块或开启了发布的 library 模块）
./gradlew :app:testAllSuitesWithDependencies --continue
```

报告落在 `app/build/reports/testAllSuites/coverage-report/`（带依赖时为 `testAllSuitesWithDependencies/coverage-report/`），首页就是全模块汇总，可以逐层下钻。该功能仍是实验性，任务名与开关后续可能调整；AGP 版本不够时按上面的自定义任务做。

### 覆盖率门禁

报告是给人看的，门禁是给 CI 拦的。用 `JacocoCoverageVerification` 给关键模块设下限：

```kotlin
import org.gradle.testing.jacoco.tasks.JacocoCoverageVerification

tasks.register<JacocoCoverageVerification>("jacocoDebugVerification") {
    dependsOn("testDebugUnitTest")

    val buildDir = layout.buildDirectory.get().asFile
    val coverageExcludes = listOf("**/R.class", "**/R$*.class", "**/BuildConfig.*", "**/Hilt_*", "**/*_Factory.class")

    classDirectories.setFrom(
        fileTree(buildDir.resolve("intermediates/javac/debug/classes")) { exclude(coverageExcludes) },
        fileTree(buildDir.resolve("tmp/kotlin-classes/debug")) { exclude(coverageExcludes) },
    )
    sourceDirectories.setFrom(files("src/main/java", "src/main/kotlin"))
    executionData.setFrom(
        fileTree(buildDir.resolve("outputs/unit_test_code_coverage/debugUnitTest")) { include("*.exec") },
    )

    violationRules {
        rule {
            // BUNDLE = 整个模块；也可用 CLASS / PACKAGE / SOURCEFILE
            element = "BUNDLE"
            limit {
                counter = "LINE"
                value = "COVEREDRATIO"
                minimum = "0.60".toBigDecimal()
            }
        }
        // 核心模块的类单独设限，比整体门槛更严
        rule {
            element = "CLASS"
            includes = listOf("com.example.core.*")
            limit {
                counter = "BRANCH"
                value = "COVEREDRATIO"
                minimum = "0.70".toBigDecimal()
            }
        }
    }
}
```

`element = "CLASS"` 更适合“每个类都不被遗漏”，但只要有任何一个生成的类漏排，构建就会莫名其妙失败；实际项目中通常用 `BUNDLE` 卡整体、再用 `includes` 圈出核心模块加码。

CI 里串起来大致是这样：

```yaml
- name: Unit tests with coverage
  run: ./gradlew :app:createDebugUnitTestCoverageReport

- name: Coverage gate
  run: ./gradlew :app:jacocoDebugVerification

- name: Upload report
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: coverage-report
    path: app/build/reports/coverage/test/debug
```

两条原则：**阈值只设下限、不追涨幅**（否则会催生“执行但不断言”的测试）；**只在核心模块设门禁**，UI 层和生成代码多的模块设了也守不住。

### 覆盖率的常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 报告目录为空 | 有测试失败，AGP 直接跳过报告 | 先让 `testDebugUnitTest` 全绿 |
| 报告里没有自己的类 | 类不在该变体的 `src/main`、没被任何用例执行、或被排除规则误伤 | 检查 `classDirectories` 与排除列表 |
| Kotlin 类全丢 | 只配了 `intermediates/javac` | 补 `tmp/kotlin-classes/<variant>` |
| 覆盖率数字明显虚高 | 生成代码、测试代码进了分母/分子 | 加排除规则，重新对比 |
| 覆盖率突然掉 10%+ | 升级了 Kotlin / Compose，合成代码变多 | 升级 JaCoCo 到 0.8.15+，或接受基线漂移 |
| `Unsupported class file major version 65` | JaCoCo 版本低于 JDK | `testCoverage { jacocoVersion = "0.8.15" }` |
| Robolectric 下报 `no location info` / 无法处理已插桩类 | JaCoCo 尝试插桩 JDK 内部类 | `tasks.withType<Test> { jacoco { includeNoLocationClasses = true; excludes = listOf("jdk.internal.*") } }` |

## 静态代码扫描

静态扫描不运行程序，靠规则匹配源码、字节码和资源文件。它抓的是“一定会出问题”的写法：调用了高于 minSdk 的 API、布局里写死中文、`when` 分支漏了、方法过长难以维护。

三类工具分工不同，不要互相替代：

| 工具 | 看什么 | 典型问题 | 能自动修 |
| --- | --- | --- | --- |
| Android Lint | 源码 + 资源 + 清单 + 依赖 | API 级别、资源未使用、权限缺失、Compose 误用 | 部分（`lint --fix` / IDE） |
| Detekt | Kotlin 语法树 | 复杂度、代码异味、坏味道命名、异常吞掉 | 不能 |
| ktlint | 代码格式 | 缩进、空行、import 顺序、尾逗号 | 能（`ktlintFormat`） |

关键区别：**Lint 懂 Android，Detekt 懂 Kotlin，ktlint 只管格式**。三者都配不冲突。

### Android Lint

Lint 内置在 AGP 里，不需要额外依赖。常用任务：

```bash
./gradlew lint              # 默认变体（一般是 debug）
./gradlew lintDebug         # 指定变体
./gradlew lintRelease
./gradlew lintVitalRelease  # release 构建时自动跑的“致命问题”子集
```

报告默认写在 `app/build/reports/` 下：

```text
lint-results-debug.html   # 人看
lint-results-debug.xml    # CI 或 Sonar 解析
lint-results-debug.sarif  # 开了 sarifReport 才有，喂 GitHub Code Scanning
```

配置集中在模块级 `android { lint { } }`：

```kotlin
// app/build.gradle.kts
android {
    lint {
        // 有 error 就中断构建。新项目建议一开始就 true
        abortOnError = true
        // warning 是否也当 error；规范严格的团队才开
        warningsAsErrors = false
        // release 构建时检查 fatal 级问题（lintVitalRelease）
        checkReleaseBuilds = true
        // 连依赖模块一起分析，否则判断不了“库里的资源有没有被用到”
        checkDependencies = true
        // 测试代码默认不查
        checkTestSources = false

        // 关闭规则必须写清理由，评审时能看到
        disable += listOf("MissingTranslation", "UnusedResources")
        // 默认关闭、但团队需要的规则
        enable += listOf("RtlHardcoded")

        // 存量问题冻结，只拦新增
        baseline = file("lint-baseline.xml")

        // HTML/XML 默认就生成；SARIF 要显式开
        sarifReport = true
        textReport = true
    }
}
```

> Kotlin DSL 里要写 `disable += listOf("A", "B")`。官方文档的示例是 `disable += "TypographyFractions" + "TypographyQuotes"`，在 Kotlin 里这是**字符串拼接**，得到的是 `"TypographyFractionsTypographyQuotes"` 这个不存在的 id，两条规则都不会被关闭。

规则的严重级别也可以放在 `lint.xml` 里，比 DSL 更适合按路径精细控制：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<lint>
    <!-- 全项目关闭 -->
    <issue id="MissingTranslation" severity="ignore" />

    <!-- 只对特定文件放宽，不要整条规则关掉 -->
    <issue id="HardcodedText">
        <ignore path="src/main/res/layout/debug_panel.xml" />
    </issue>

    <!-- 默认 warning 提升为 error -->
    <issue id="NewApi" severity="error" />
</lint>
```

单点抑制用 `@SuppressLint("NewApi")`（Kotlin）或 `tools:ignore="UnusedResources"`（XML）。抑制注解同样要写理由，否则日后难以判断是否可删除。

**存量治理**：老项目启用 Lint 后会得到大量告警。正确做法是先建立基线，把存量冻结，只拦新增：

```bash
# 生成/更新 lint-baseline.xml（会随报告一起输出）
./gradlew lintDebug -Dlint.baselines.continue=true
```

`lint-baseline.xml` 要提交进版本库；修完一批存量后删掉重建，基线才会缩小。

几个容易忽略的点：

- **Lint 不会因为 `assembleDebug` 就完整跑一遍**，CI 必须显式执行 `./gradlew lint`；
- `checkDependencies = true` 会让模块连同依赖一起分析，library 之间会重复计算、耗时明显上升，通常只在 app 模块开；
- Compose 项目自带一批检查（`ComposableNaming`、`ComposeUnrememberedState`、`ComposeModifierMissing`），不应将其关闭——`Modifier` 漏传、状态忘记 `remember` 都是运行时才暴露的问题；
- 需要团队私有规则时，写一个 `lint-rules` 模块，依赖 `com.android.tools.lint:lint-api`（版本随 AGP 走），再用 `lintChecks(project(":lint-rules"))` 挂进主模块。

### Detekt

Detekt 面向 Kotlin 代码结构，抓 Lint 不覆盖的问题：方法太长、嵌套太深、`catch` 里什么都不做、魔法数字、命名不符合约定。

**版本注意**：2.0 目前仍是 alpha（截至 2026-11 为 `2.0.0-alpha.6`），插件 id 已从 `io.gitlab.arturbosch.detekt` 改为 `dev.detekt`，`build { maxIssues }` 被 `failOnSeverity` 取代。生产项目先用稳定的 1.23.8。

```kotlin
// build.gradle.kts
import io.gitlab.arturbosch.detekt.Detekt

plugins {
    id("io.gitlab.arturbosch.detekt") version "1.23.8"
}

detekt {
    // 以默认规则集为底，再叠加自己的配置
    buildUponDefaultConfig = true
    config.setFrom(files("$rootDir/config/detekt/detekt.yml"))
    baseline = file("$rootDir/config/detekt/baseline.xml")
}

tasks.withType<Detekt>().configureEach {
    reports {
        html.required.set(true)
        xml.required.set(true)
        sarif.required.set(true)
    }
}
```

```yaml
# config/detekt/detekt.yml
complexity:
  LongMethod:
    threshold: 60        # 默认 60，按团队实际调整
  LongParameterList:
    functionThreshold: 8

style:
  MagicNumber:
    active: false        # 数值配置多的项目先关，否则全是噪音
  MaxLineLength:
    maxLineLength: 120
  ReturnCount:
    max: 4
```

```bash
./gradlew detekt                       # 全部分析
./gradlew detektDebug                  # 指定变体
./gradlew detektBaseline               # 生成基线
```

报告在 `build/reports/detekt/detekt.html`。和 Lint 一样，**先开少量规则、建基线、再逐步收紧**；一次性打开全部规则只会得到一份无人关注的清单。

Detekt 1.x 可以通过 `detekt-formatting` 包装 ktlint 的规则，但那会把格式问题混进静态分析报告。更清晰的做法是让 ktlint 单独管格式。

### ktlint

ktlint 只做一件事：按 Kotlin 官方风格（或 Android Studio 风格）格式化代码。它的价值不在“发现问题”，而在**消除格式争议**——没有它，每次 code review 都要为缩进和 import 顺序争论一次。

```kotlin
// build.gradle.kts
plugins {
    id("org.jlleitschuh.gradle.ktlint") version "14.2.0"
}
```

```bash
./gradlew ktlintCheck    # 只检查，CI 用这个
./gradlew ktlintFormat   # 就地修复，本地用这个
```

风格由根目录的 `.editorconfig` 决定，不需要在 Gradle 里配：

```ini
[*.{kt,kts}]
ktlint_code_style = android_studio
max_line_length = 120
```

`ktlint_code_style` 有两个常用值：`kotlin_official`（默认，Kotlin 官方规范）和 `android_studio`（Android Studio 默认格式）。团队任选其一，**保持统一即可**。

引入 ktlint 的第一天会产生一个巨大的格式化 diff，必须单独提交一次（只格式化、不改逻辑），否则 review 时真正的改动会被淹没。

### 落地顺序

1. **先跑 `ktlintFormat` 统一格式**，单独提交；
2. 打开 Lint，生成 `lint-baseline.xml` 冻结存量，CI 执行 `./gradlew lint` 并 `abortOnError = true`；
3. 加 Detekt，只开 `LongMethod`、`ComplexMethod` 这类高价值规则，稳定后再扩；
4. CI 里三条命令串起来：`ktlintCheck` → `lint` → `detekt`，任何一个红就挡住合并。

## SonarQube

SonarQube 不是“又一个 linter”，而是把前面几类结果汇总起来的平台：它自己带 Java / Kotlin 的规则引擎，也能读 JaCoCo 的覆盖率、外部工具的 SARIF，然后做三件单个工具做不到的事——**留存历史趋势、按质量门禁卡合并、产出可交付的报告**。

### 服务器

自建只需一条 Docker 命令或解压官方 zip，监听 9000 端口，这里不展开。选版本时注意：

- 生产环境用 **LTA（长期活跃版）**，当前是 **2026.5**；SonarQube 从 2025 年起改成日历版本号（`YYYY.Release.Patch`），每两个月发一个版本，LTA 的支持周期更长。
- 免费的是 **Community Build**，但有三个限制必须提前知道：**只分析主分支**（没有分支分析和 PR 装饰）、**不含污点分析**（注入类漏洞扫不出来）、**一次只处理一个分析任务**。要分支与 PR 装饰，得 Developer 版及以上。
- 建项目后生成 token：**用户 token（User Token）**，不是 Project Analysis Token——后者权限不够，很多接口会 401。

### Gradle 配置

SonarScanner for Gradle 插件当前版本 **7.5.0.8588**。版本门槛：7.0 起支持 Gradle 9，7.2 起支持配置缓存，**7.3 起支持 AGP 9**——用 AGP 9 的项目必须 ≥ 7.3。

```kotlin
// 根 build.gradle.kts
plugins {
    id("org.sonarqube") version "7.5.0.8588"
}

sonar {
    properties {
        property("sonar.projectKey", "com.example.app")
        property("sonar.projectName", "Example App")
        property("sonar.host.url", "https://sonar.example.com")
        // token 不写进仓库：用环境变量 SONAR_TOKEN，scanner 会自动读取
        // property("sonar.token", "sqp_xxx")   ← 不要这么干

        // 覆盖率：复用上文 JaCoCo 产出的 XML
        property(
            "sonar.coverage.jacoco.xmlReportPaths",
            "app/build/reports/jacoco/jacocoDebugReport/jacocoDebugReport.xml",
        )
        // 单元测试报告，Sonar 用它算测试数量与失败率
        property("sonar.junit.reportPaths", "app/build/test-results/testDebugUnitTest")

        // 生成代码不进分析，否则技术债、重复率、覆盖率分母全被污染
        property("sonar.exclusions", "**/build/**,**/generated/**,**/R.java,**/BuildConfig.java")
        property("sonar.coverage.exclusions", "**/di/**,**/*_Factory.java,**/Hilt_*.java")

        // 等质量门结果再结束，CI 才有意义（默认是不等）
        property("sonar.qualitygate.wait", "true")
        property("sonar.qualitygate.timeout", "300")
    }
}
```

多模块项目把插件应用在**根工程**：服务器、token、质量门这类整体配置写在根工程的 `sonar { }` 里，对全部分析生效；`sonar.sources`、分支名这类模块特有的属性写在该模块自己的 `sonar { }` 里。要跳过某个模块，在它的块里设 `isSkipProject = true`。

执行时必须**先把产物跑出来**，再跑 `sonar`：

```bash
export SONAR_TOKEN=sqp_xxxxxxxx

./gradlew testDebugUnitTest jacocoDebugReport sonar
```

从 scanner 3.0 起，`sonar` 任务不再自动挂编译与测试任务。少了前面那两步，结果是“覆盖率 0%、Java 分析缺字节码”，而不是报错——这是最常见的问题。

老教程里的 `sonar.login` 已被 `sonar.token` 取代；`sonar.qualitygate.wait` 一旦打开，CI 会在门禁不过时直接失败，而不是“上传成功就绿灯”。

### 看懂结果与门禁

- **质量门（Quality Gate）** 默认是 “Sonar way”：新代码 0 个新 bug、0 个新漏洞、覆盖率 ≥ 80%、重复率 ≤ 3%、安全热点 100% 复核。
- **Clean as You Code**：门禁只卡“新代码”，老项目才可能落地。全量卡覆盖率的老项目，第一天就会把门禁关掉。
- 新代码的判定基准要在项目里设（上一版本 / 最近 N 天 / 对比某分支）。选“对比 main”，每个 PR 只负责其修改的行；这需要完整 git 历史，CI 上不应使用浅克隆。

### 导出对外报告

先纠正一个常见误解：**SonarSource 官方不提供导出 CSV / DOCX 的按钮，也没有官方导出 jar**。Web 界面只有基础的打印视图，数据本身要通过 Web API 取。真正能做到“一个 jar 出 docx / xlsx / csv”的是社区工具，不是官方产物。

#### 方案一：sonar-cnes-report（推荐）

法国国家空间研究中心（CNES）开源，GPL-3.0（内部使用没问题，二次分发修改版需开源），是这个场景的事实标准。当前版本 **5.0.4**，单个可执行 jar（约 42 MB），只要求 JRE 8+。

两种用法：命令行独立跑（适合 CI），或丢进 `$SONAR_HOME/extensions/plugins` 重启后在界面里点 “CNES Report”（适合非技术同事自助导出）。

```bash
java -jar sonar-cnes-report-5.0.4.jar \
  -s https://sonar.example.com \
  -t "$SONAR_TOKEN" \
  -p com.example.app \
  -o ./reports \
  -a "质量组" \
  -d 2026-11-12
```

默认会把所有格式都生成到 `-o` 指定的目录：

```text
reports/
├── *.docx    # 汇总报告：代码量、质量门状态、技术债、问题分布
├── *.xlsx    # 问题明细（可筛选、可透视）
├── *.csv     # 同一份明细的 CSV，给第三方工具
├── *.md      # Markdown 版，便于进 Git
└── …         # 分析所用的质量配置快照
```

常用参数：

| 参数 | 作用 |
| --- | --- |
| `-p` | 项目 key（不是项目名） |
| `-s` | 服务器地址，含协议与端口 |
| `-t` | **用户 token**，Project Analysis Token 权限不够 |
| `-o` | 输出目录 |
| `-a` / `-d` | 报告作者 / 报告日期（`yyyy-MM-dd`） |
| `-r` | 自定义 Word 模板，交付时换成公司抬头 |
| `-x` | 自定义 Excel 模板 |
| `-l` | 报告语言，`en_US`（默认）或 `fr_FR` |
| `-b` | 指定分支，需要 Developer 版或分支插件 |
| `-w` `-e` `-f` `-m` | 分别关闭 report / xlsx / csv / markdown |

**对外交付的关键在模板**：`-r` 指向自己的 `.docx`，工具会把 `$ISSUES_DETAILS`、`$QUALITY_GATE_STATUS` 这类占位符替换成真实数据。正确做法是拿官方模板改（保留占位符、加公司封面与页眉），而不是从空白文档开始写——删掉占位符，对应章节就会是空的。

#### 方案二：Web API 自己出 CSV

不想引第三方 jar（或只要一份 CSV）时，直接调 API 拉数据。`/api/issues/search` 的 `ps` 上限是 500，必须翻页：

```bash
#!/usr/bin/env bash
set -euo pipefail
KEY=com.example.app
HOST=https://sonar.example.com

echo "type,severity,component,line,message,rule" > issues.csv
page=1
while :; do
  resp=$(curl -sS -u "$SONAR_TOKEN:" \
    "$HOST/api/issues/search?componentKeys=$KEY&types=BUG,VULNERABILITY,CODE_SMELL&ps=500&p=$page")
  rows=$(jq -r '.issues[]
    | [.type, .severity, .component, (.line // ""), .message, .rule]
    | @csv' <<<"$resp")
  [ -z "$rows" ] && break
  printf '%s\n' "$rows" >> issues.csv
  total=$(jq -r '.paging.total' <<<"$resp")
  [ $((page * 500)) -ge "$total" ] && break
  page=$((page + 1))
done
```

几个细节：认证用 `-u "$TOKEN:"`（用户名位置放 token、密码留空）；`@csv` 会按 RFC 4180 自动加引号转义，消息里带逗号或换行也不会串列（改成手工拼字符串时才需要自己处理）；`total` 从响应里读，不应自行猜测页数。

#### 方案三：商业插件

bitegarden 的 **Report for SonarQube Server**（约 400€/年/实例）能在界面里直接导出 PDF、Excel、ODT，模板可定制、支持分支。注意它**不产出 docx**——要 Word 交付，还是得走 CNES。

### 接进 CI

```yaml
- name: Analyze
  run: ./gradlew testDebugUnitTest jacocoDebugReport sonar
  env:
    SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}

- name: Export delivery report
  run: |
```

### 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 覆盖率一直 0% | 没先跑 `jacocoDebugReport`，或 XML 路径写错 | 路径相对**根目录**写，先手动确认文件存在 |
| 多模块只有主模块有覆盖率 | 只配了一个 `xmlReportPaths` | 每个模块单独配，或用逗号分隔多个 XML 路径 |
| 401 Unauthorized | 用了 Project Analysis Token，或 token 过期 | 换用户 token |
| 分支 / PR 没数据 | Community Build 只分析主分支 | 升级 Developer 版，或只做主分支门禁 |
| 技术债、重复率异常高 | 生成代码没排除 | 补 `sonar.exclusions` |
| 报告里某一章是空的 | 自定义模板删掉了占位符 | 用官方模板改，保留 `$XXX` 占位符 |
| `sonar` 任务很慢 | 每次都是全量分析 | 缓存 `~/.sonar/cache`；分析范围用 `sonar.inclusions` 收敛 |

## 开源组件扫描

一个 Android 应用动辄几百个依赖（含传递依赖），其中绝大多数并非自行编写。开源组件扫描（SCA，Software Composition Analysis）回答三个问题：

- 这些库里有没有**已知漏洞**（CVE）；
- 它们的**许可证**能不能商用、会不会传染；
- 版本是否已**落后或停更**。

### 依赖树

扫描的前提是知道“实际用了什么版本”。声明 4.9.0、实际解析成 4.12.0 是常态（约束、传递依赖、BOM 都会抬版本），而漏洞是按**解析后**的版本匹配的：

```bash
# 运行时依赖的完整解析结果
./gradlew :app:dependencies --configuration releaseRuntimeClasspath

# 某个库是被谁引进来的
./gradlew :app:dependencyInsight --dependency okhttp --configuration releaseRuntimeClasspath
```

`dependencyInsight` 在排查“这个有漏洞的版本是哪个库带进来的”时特别有用，输出里会给出依赖路径与最终选择原因。

### 漏洞扫描

#### OWASP Dependency-Check

开源方案里覆盖最广的一个，走 NVD 数据，按 CPE 匹配。Gradle 插件当前版本 13.0.0。

```kotlin
// app/build.gradle.kts
plugins {
    id("org.owasp.dependencycheck") version "13.0.0"
}

dependencyCheck {
    // CVSS ≥ 7 视为高危，直接让构建失败；先只出报告，稳定后再开
    failBuildOnCVSS = 7.0f
    // 误报与“已评估但暂不修”的项写进抑制文件，每条注明理由与到期时间
    suppressionFile = "$rootDir/config/dependency-check-suppressions.xml"
}
```

```bash
# 必须先配 NVD API Key，否则数据同步慢到基本不可用
export NVD_API_KEY=xxxxxxxx

./gradlew :app:dependencyCheckAnalyze
```

报告在 `build/reports/dependency-check/`（默认只出 HTML；要接进流水线解析时，在 `dependencyCheck { }` 里加 `formats` 同时输出 JSON）。几个必须知道的点：

- **NVD API Key 是硬性前提**。没有 key 时官方限流极严，首次同步 NVD 全量数据可能跑上几十分钟甚至超时；key 在 NVD 官网免费申请。
- **首次运行会下载几百 MB 的 NVD 数据**并解压到本地数据目录。CI 上一定要缓存这个目录（`data.directory` 可指定位置），否则每次流水线都重新下载。
- 它按 CPE 匹配，**误报率不低**（尤其是带 native 库或改名 fork 的包）。抑制文件是必需项，不是可选项。
- 12.1.0 之前的版本因为 NVD API 变更已经不可用，不应照搬旧教程的 8.x / 9.x 配置。

#### Dependabot

如果代码在 GitHub 上，这是成本最低的一层：不需要任何 Gradle 配置，只加一个 yml。

```yaml
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "gradle"
    directory: "/"
    schedule:
      interval: "weekly"
    open-pull-requests-limit: 5
```

它会做两件事：发现依赖有安全公告时开 alert（在 Security 面板），以及按周提版本升级 PR。局限是只覆盖 GitHub Advisory Database 里有记录的包——冷门库、只在 NVD 有记录的库它看不到。所以它和 Dependency-Check 是互补关系，不是二选一。

#### Snyk

商业方案，准确率和修复建议明显好于开源工具，有免费额度。CLI 用法：

```bash
snyk test --all-sub-projects --severity-threshold=high
```

代价是要把依赖清单上传到它的服务端，对隐私敏感的团队需要评估。

### 许可证合规

漏洞扫描关注“是否会遭受攻击”，许可证关注“是否允许商用”。GPL / AGPL 的传染性、CC-BY-NC 的“禁止商用”，都可能在上架或法务审计时才暴露出来，那时改依赖的成本远高于现在。

最简便的做法是复用 SBOM：CycloneDX 生成的 `bom.json` 里带 `licenses` 字段，直接过滤即可。

```bash
./gradlew cyclonedxBom

# 列出所有 GPL / AGPL 组件
jq -r '.components[]
  | select(any(.licenses[]?; (.license.id // .license.name) | test("GPL|AGPL"; "i")))
  | "\(.name) \(.version)"' build/reports/cyclonedx/bom.json
```

把输出与团队的白名单比对，命中就人工确认。规模大了再上 FOSSA、ORT 这类专门的合规平台。

### 版本与停更

有漏洞的前提是还在维护；停更三年的库即使当前没有 CVE，也不该继续用。查版本落后用 ben-manes 的 versions 插件：

```kotlin
// build.gradle.kts
plugins {
    id("io.github.ben-manes.versions") version "0.67.0"
}
```

```bash
./gradlew dependencyUpdates
```

结果同时打印到控制台并写入 `build/dependencyUpdates/report.txt`（另有 HTML 版），按 release / rc / alpha 渠道区分可升级的层级。

版本与用法上有两点要注意：**插件 id 已从 `com.github.ben-manes.versions` 改为 `io.github.ben-manes.versions`**（旧 id 仍能用但会告警）；多模块项目推荐改用 settings 插件 `io.github.ben-manes.versions.settings`，在 `settings.gradle.kts` 里应用一次，全工程只出一份合并报告。

停更判断无现成工具可替代，可依据三个信号判断：Maven Central 上最后一次发布时间、仓库是否归档、Issue 区是否有长期无人处理的崩溃。

### SBOM

SBOM（Software Bill of Materials）是“这个包里到底有什么”的机器可读清单。以前是可选项，现在越来越多场景强制要求（甲方交付、欧盟 CRA、漏洞爆发时的自查）。

```kotlin
// 根 build.gradle.kts：聚合全工程的 SBOM
plugins {
    id("org.cyclonedx.bom") version "3.5.1"
}
```

```bash
./gradlew cyclonedxBom
# 聚合清单：build/reports/cyclonedx/bom.json
# 单模块清单：build/reports/cyclonedx-direct/
```

插件应用在哪个模块，产物就落在哪个模块的 `build/reports/` 下；应用在根工程时才是全工程一份。

生成的 `bom.json` 可以直接喂给 OSV-Scanner、Grype、Trivy 等扫描器，也可以上传到 Dependency-Track 持续监控——新 CVE 公布时，不用重新构建就能知道哪些已发布版本受影响。

### 供应链完整性

前面几层都在看“依赖有没有问题”，这一层看“依赖有没有被换掉”。Gradle 支持为每个依赖记录校验和，仓库被投毒或中间人劫持时构建会直接失败：

```bash
# 生成 gradle/verification-metadata.xml
./gradlew --write-verification-metadata sha256 help
```

生成后提交该文件，之后每次解析依赖都会校验。代价是升级依赖时要同步更新校验和（`--write-verification-metadata sha256` 重跑一次），适合发布类项目，不适合天天改依赖的实验项目。

### 落地顺序与常见问题

建议按成本从低到高铺：

1. **Dependabot / Renovate**：零配置，先拿到安全公告；
2. **`dependencyUpdates`**：每月看一次版本落后情况；
3. **SBOM**：接进构建，交付和自查都用得上；
4. **Dependency-Check**：先只出报告跑两周，把误报写进抑制文件，再开 `failBuildOnCVSS` 门禁；
5. **许可证过滤**：基于 SBOM 做，不额外引入工具。
