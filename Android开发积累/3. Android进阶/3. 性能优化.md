性能优化并非收尾阶段的一次性工作，而是贯穿开发过程的主线：卡顿、ANR、内存泄漏、耗电，每一项都直接影响留存与评分。内容按问题类型组织——ANR、布局、绘制、启动、内存、电量，最后提供一套测量工具。

## ANR

ANR（Application Not Responding）是系统判定主线程无法及时处理输入或绘制时给出的反馈。发生时会弹窗提示（部分定制系统会禁用提示），严重影响体验。

![[Screenshot 2020-12-12 141622.png]]

ANR 的本质是**主线程在限定时间内没响应**，系统按消息队列的超时机制来发现它。四类典型超时：

| 类型 | 超时阈值 |
| --- | --- |
| Input dispatching | 输入事件 5 秒内未处理 |
| BroadcastReceiver `onReceive()` | 前台 10 秒 / 后台 60 秒 |
| Service | 前台 20 秒 / 后台 200 秒 |
| ContentProvider publish | 10 秒 |

分析手段（按由浅入深）：

1. **Logcat**：ANR 发生时会有 `am_anr` 相关日志，指明进程、组件与原因；
2. **traces 文件**：`/data/anr/` 下的 trace 文件记录了各线程栈，重点看 `main` 线程卡在哪一行；可用 `adb shell dumpsys activity lastanr` 快速取最近一次 ANR 的概要；
3. **`kill -3 <pid>`**：向进程发 SIGQUIT 主动 dump 线程栈（`jps`/`jstack` 是 JVM 工具，Android 上并不适用——这是常见误用）；
4. **Perfetto / Systrace**：看主线程在哪段代码上耗时，配合 `androidx.tracing` 打点更精确；
5. **ApplicationExitInfo（API 30+）**：`ActivityManager.getHistoricalProcessExitReasons()` 能拿到带时间戳的 ANR 记录，适合线上/后台统计。

规避的核心只有一条：**别让主线程长时间阻塞**——耗时操作放后台线程、避免 CPU 满载、控制内存防止 GC 频繁。

## 布局优化

布局优化的目标是**减少层级和控件数量**，降低测量（measure）与布局（layout）阶段的耗时，避免 UI 绘制卡帧。

### 优化布局层级

核心是避免无用嵌套。传统 View 时代大量嵌套 `LinearLayout` 会把 View 树越堆越高；`ConstraintLayout` 能用一层表达复杂的相对约束，所以 Google 把它设为默认布局。

> 这里也要纠正一个流传很广的说法：“原生开发已经被 H5/小程序取代，不用关心布局性能了”。事实是原生仍是高性能与复杂交互的主流选择，Compose 时代照样要做渲染优化——只是工具从 View 树变成了重组（recomposition）。布局（或重组）优化在任何 UI 方案下都成立。

### 布局代码复用

复用不只是可维护性，还能减少重复的测量与实例化。

**`<include>`**：把复用布局嵌进目标布局，用法见 [[9. UI 开发#include 与 merge|先前的说明]]，这里不赘述。

**`<merge>`**：配合 `<include>` 消除多余的 ViewGroup。当被 include 的布局根节点和宿主容器的类型相同（比如都是垂直 `LinearLayout`），用 `<merge>` 代替根节点，include 时就不会多套一层：

```xml
<!-- 被复用的布局，根节点用 merge，include 时会原地展开 -->
<merge xmlns:android="http://schemas.android.com/apk/res/android">
    <TextView android:id="@+id/title" ... />
    <TextView android:id="@+id/subtitle" ... />
</merge>
```

`<merge>` 本身不是布局类型，它是给 include 看的标记：include 时系统会忽略这个标记，直接把它的子控件展开到宿主里。

**`<ViewStub>`**：按需加载的“占位符”，本身零尺寸、不参与绘制，等真正用到时再 inflate：

```kotlin
// 方式一：让它可见，触发加载
viewStub.visibility = View.VISIBLE

// 方式二：手动 inflate，返回被加载布局的根 View
val root = viewStub.inflate()
val title = root.findViewById<TextView>(R.id.title)
```

注意两点：`inflate()` 返回的是**根 View**（不是“被引用控件的 id”）；`ViewStub` 一旦 inflate 就会被替换掉，不能反复调用。

### 绘制优化

绘制优化聚焦 `onDraw()`：**不应在 `onDraw()` 中执行耗时或重复分配对象的操作**。它可能被频繁调用（滚动、动画每一帧都可能触发），单帧超过 16 ms（60 Hz 下）就会掉帧。常见问题在于：`onDraw` 里 `new` 对象、用反射取资源、做耗时计算，都会让绘制超时。

## 卡顿与帧

卡顿（jank）和 ANR 是一体两面：ANR 是“严重到弹窗”，卡顿是“掉帧但没到阈值”。

60 Hz 屏每帧预算约 16.6 ms，90 Hz 约 11 ms，120 Hz 约 8.3 ms。主线程每一帧要完成输入处理 → 动画 → measure/layout/draw（或 Compose 的组合、布局、绘制）。任何一步超预算，这一帧就丢。

排查用 **Systrace / Perfetto**：录制一段交互，看主线程的帧时间线，找到哪段代码在“超时”。Android Studio Profiler 的 CPU/内存面板也能直接看掉帧区间。打点可以用 `androidx.tracing:tracing` 的 `trace { }` 包住可疑代码，trace 里就能看到对应区段。

## 启动优化

启动耗时是用户对性能的第一印象。启动分三种：

- **冷启动**：进程从无到有，要创建 Application、加载 Activity，耗时最长；
- **温启动**：进程还在，Activity 销毁后重建；
- **热启动**：Activity 还在栈里，只是回到前台。

冷启动的常见优化点：

1. **`Application.onCreate()` 轻量化**：第三方 SDK 的初始化能延迟就延迟，或放进子线程（注意线程安全的 SDK 才能这么干）；
2. **首屏只做必要渲染**：复杂的首页布局延迟到首帧之后再加载（`ViewStub`、`App Startup` 库的延迟初始化）；
3. **Baseline Profile**：让 ART 在安装时就编译好启动路径上的热点方法，跳过解释与 JIT 预热，官方数据首启可提升约 30%。生成方式与原理见 [[21. Android虚拟机：从Dalvik到ART#编译策略的演进]]；
4. **避免首帧前的同步 IO / 反射**：数据库、文件、`Class.forName` 都别放启动关键路径。

Jetpack 的 **`androidx.startup`（App Startup）** 用来把各库的初始化统一收敛、并按需延迟，替代各 SDK 自己在 `ContentProvider` 里偷跑初始化的做法。

## 内存优化

应用运行在沙箱里，每个进程能用的内存有限。超出限制不会“优雅失败”，而是被 **LMK（Low Memory Killer）** 直接杀掉。内存问题分两类：溢出与泄漏。

### 内存溢出

OOM 是申请内存时无内存可用。常见原因：短时间加载大量数据、泄漏堆积、短时间创建过多对象、以及**堆上限本身太小**。

Android 不给应用固定堆大小，上限由设备与 `dalvik.vm.heapsize` 决定。`android:largeHeap="true"` 能申请更大的堆，但那是给真正需要大堆的应用（图片处理、游戏）用的“宽限”，不是解决泄漏的银弹——**先排查泄漏，再考虑 largeHeap**。

内存抖动是 OOM 的近亲：短时间内大量创建对象 → 触发 GC → 再大量创建，内存曲线周期性涨跌。根源是循环里、`onDraw` 里、`onMeasure` 里不断分配临时对象。抖动不一定 OOM，但会让 GC 频繁、帧率掉。

### 内存泄漏

泄漏是 GC 无法回收“已经用不到”的对象。它在临界点前毫无症状，之后突然 OOM 崩溃。常见来源：

- 长生命周期对象持有短生命周期对象的引用（Activity 被单例、静态变量、匿名内部类持有）；
- 注册了监听器/广播但忘了注销；
- 资源（Cursor、Bitmap、流、Binder）没释放。

按频率分：常发性、偶发性、一次性、隐式四类。解决的根本是减少缺陷——静态/成员变量慎用、注册与注销成对、避免线程长期持有引用。

检测工具：

- **LeakCanary**（见 [[7. LeakCanary]]）：运行时自动检测 Activity/Fragment 泄漏并给出引用链，最省心；
- **Android Studio Profiler**：手动抓 heap dump，对比前后两次，看哪些对象数量异常增长；
- **Lint**：开发期的静态提示（比如 `StaticFieldLeak`）。

## 电量优化

电量优化的核心原则是：**应用按需运行**。具体措施：

- 少唤醒、合并唤醒（`WorkManager` 的约束与批处理）；
- 网络、蓝牙、定位用完即关，定位优先用低功耗的 fused location；
- 后台任务交给 `WorkManager`，它按充电、Wi-Fi、空闲等约束调度，而不是自己起长驻服务；
- 网络请求集中批量发送，压缩传输数据；
- 充电 + Wi-Fi 时才做大块同步。

Google 的 **Battery Historian**（或用 Perfetto 的 battery 数据）可以按时间线看到是谁在耗电，比猜高效得多。

## 测量工具

优化要“先测量、再动手、后验证”，否则就是盲改：

| 工具 | 用途 |
| --- | --- |
| Android Studio Profiler | CPU、内存、网络、电量的实时采样，日常排查首选 |
| Perfetto / Systrace | 帧时间线、主线程耗时、GC、启动各阶段，定位卡顿与启动瓶颈 |
| Macrobenchmark | 在真机上测启动、滚动、帧率的量化基准，能给出 P50/P90 数值 |
| Baseline Profile | 生成启动热点 profile，配合 Macrobenchmark 验证收益 |
| Battery Historian | 电量时间线分析 |
| LeakCanary | 内存泄漏自动检测 |

一套典型闭环：**Perfetto 定位卡在哪 → 针对性优化 → Macrobenchmark 量化前后对比**。没有数值的“感觉变快了”不可靠，也留不下证据。

## 小结

- ANR 的根子是主线程超时，四类阈值要记牢；现代排查靠 Perfetto + `dumpsys activity lastanr`，而不是 `jstack`。
- 布局优化靠扁平化与按需加载；Compose 时代的等价物是减少重组。
- 卡顿与启动是一回事的两面，冷启动是重灾区，Baseline Profile + 轻量 `Application.onCreate` 最有效。
- 内存问题分溢出与泄漏，先排查泄漏再谈 `largeHeap`。
- 一切优化从测量开始：Perfetto 定位，Macrobenchmark 验证。
