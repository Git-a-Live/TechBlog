单元测试（Unit Test）用于对模块、函数或类做正确性检验，是 TDD（Test Driven Development，测试驱动开发）的组成部分。它的收益主要有三点：

1. 便于后期重构——有测试兜底，改结构才敢下手；
2. 反馈快——本地测试跑在 JVM 上，秒级出结果；
3. 缩小关注范围——失败点直接指向被破坏的那一小段逻辑。

Google 官方的表述是：通过针对代码创建和运行单元测试，可以验证各个单元的逻辑是否正确；每次构建后运行单元测试，能快速捕捉并修复由代码更改导致的软件回归。同时官方也强调，**单元测试不适用于验证复杂的界面交互**——那属于 UI 测试的职责。

此处所称的“单元测试”是**测试层级**的概念，并非某个框架的名称。Android Studio 中常见的几个概念并不在同一层级：

| 名称 | 角色 |
| --- | --- |
| JUnit | 测试框架，提供 `@Test`、断言、运行器模型 |
| AndroidJUnitRunner | 插桩测试的运行器，负责把测试 APK 装到设备上并执行 |
| Robolectric | 在 JVM 上模拟 Android 框架实现的运行时，让本地测试能拿到 `Context` |
| Espresso / Compose Test / UI Automator | UI 操作与断言库，跑在设备上 |
| MockK / Mockito | 测试替身（mock）库，用来隔离依赖 |

开发中应避免本末倒置：不应为一行 `a + b` 也写测试，也不应为覆盖率去断言 `assertNotNull`。测试应当围绕**行为**和**边界**写，而不是围绕实现细节写——否则重构时测试会成为阻力。

## 测试分层

Android 的测试按运行环境分成三层，越往下越慢、越贵、越少：

| 层级 | 源码目录 | 运行环境 | 能做什么 | 典型耗时 |
| --- | --- | --- | --- | --- |
| 本地测试 | `src/test/` | 开发机 JVM | 纯逻辑、ViewModel、Repository、工具类 | 毫秒级 |
| 本地测试 + Robolectric | `src/test/` | 开发机 JVM（模拟框架） | 需要 `Context`、资源、`Looper` 的逻辑 | 百毫秒级 |
| 插桩测试 | `src/androidTest/` | 真机 / 模拟器 | 真实框架 API、数据库、Binder、UI | 秒级到分钟级 |

三个目录都由 Android Studio 在新建项目时自动创建。运行时对应三组 Gradle 任务：

```bash
# 全部本地测试（所有变体）
./gradlew test

# 只跑 debug 变体的本地测试
./gradlew testDebugUnitTest

# 只跑某一个类
./gradlew testDebugUnitTest --tests "com.example.EmailValidatorTest"

# 插桩测试（需要已连接设备或已启动模拟器）
./gradlew connectedDebugAndroidTest
```

`testImplementation` 与 `androidTestImplementation` 的分工很关键：前者只进本地测试的 classpath，后者只进测试 APK。写错配置的典型症状是“本地测试里 `ApplicationProvider` 找不到”。

## 本地测试

### 最小测试类

新建项目会自带 `src/test/.../ExampleUnitTest.kt`：

```kotlin
package com.example.myapp

import org.junit.Assert.assertEquals
import org.junit.Test

class ExampleUnitTest {

    @Test
    fun addition_isCorrect() {
        assertEquals(4, 2 + 2)
    }
}
```

它基于 **JUnit 4**，跑在开发机的 JVM 上，因此启动快、无设备依赖。JUnit 4 对测试方法有三条硬性要求：

- 必须标注 `@Test`；
- 不能有参数，也不能有返回值；
- 所属类必须是 `public`（Kotlin 默认即 public），且不能是抽象类。

断言用 `org.junit.Assert` 即可。注意参数顺序是 `assertEquals(expected, actual)`，写反了失败信息里的“期望/实际”就会颠倒，排查时容易被误导。断言较多时可以用 Truth 或 AssertJ，失败信息更可读；Kotlin 项目也可以直接用 `kotlin.test` 的 `assertEquals`。

### 访问不到 Android 框架的处理

AGP 会为本地测试生成一份 **Mockable Android Jar**：里面保留了 `android.jar` 的全部公开 API 签名，但方法体被清空。这样引用 `Context` 能编译通过，可一旦真的调用就会抛：

```text
java.lang.RuntimeException: Method getString in android.content.Context not mocked.
```

三条处理路径，按优先级排列：

1. **把依赖抽出去（首选）**。类里需要 `getString()`，就把字符串作为构造参数传进来，而不是传 `Context`。可测性问题往往就是设计问题的显影。
2. **用 Robolectric**。它提供了框架方法的真实实现（`SharedPreferences`、`Looper`、资源加载等），代码不用改。
3. **`unitTests.isReturnDefaultValues = true`**。让未实现的方法返回 `null` / `0` / `false`。这是最后手段：返回值可能是 `null`，导致本该失败的测试静默通过，问题被推迟到线上。

### Robolectric：在 JVM 上跑框架实现

Robolectric 不是“假的 Android”，它加载真实的框架字节码，再用 shadow 类替换掉底层实现（文件系统、`Looper`、`Sensor` 等）。因此在本地测试里 `getSharedPreferences()` 会真的读写一份内存中的文件，`Handler.postDelayed()` 也真的会排队——只是时间可由测试代码控制。

```kotlin
@RunWith(RobolectricTestRunner::class)
@Config(sdk = [34])
class SettingsRepositoryTest {

    private val context: Context = ApplicationProvider.getApplicationContext()

    @Test
    fun `写入的值可以读回`() {
        context.getSharedPreferences("settings", Context.MODE_PRIVATE)
            .edit()
            .putString("theme", "dark")
            .commit()

        assertEquals("dark", SettingsRepository(context).theme)
    }
}
```

几个要点：

- `@Config(sdk = [...])` 指定模拟的 API 级别，不写则用 `targetSdk`。想全局统一，可在 `src/test/resources/robolectric.properties` 里写 `sdk=34`。
- `@Config(qualifiers = "zh-rCN-w360dp-h640dp-xhdpi")` 可以模拟语言、屏幕宽高与密度。
- `ApplicationProvider.getApplicationContext<T>()` 返回的是被测应用的真实类型（若自定义了 `Application`，拿到的是那个子类）。
- **Java 17 及以上必须加 `--add-opens`**，否则 Robolectric 无法反射 JDK 内部类：

```kotlin
android {
    testOptions {
        unitTests.all {
            it.jvmArgs(
                "--add-opens=java.base/java.lang=ALL-UNNAMED",
                "--add-opens=java.base/java.util=ALL-UNNAMED",
                "--add-opens=java.base/java.io=ALL-UNNAMED",
                "--add-opens=java.base/java.net=ALL-UNNAMED",
                "--add-opens=java.base/java.security=ALL-UNNAMED",
                "--add-opens=java.base/java.text=ALL-UNNAMED",
                "--add-opens=java.base/jdk.internal.access=ALL-UNNAMED",
                "--add-opens=java.desktop/java.awt.font=ALL-UNNAMED",
                "--add-opens=jdk.compiler/com.sun.tools.javac.api=ALL-UNNAMED",
            )
        }
    }
}
```

默认的 `Looper` 模式是 **PAUSED**：主线程任务不会自动执行，需要手动推进。这比 `Thread.sleep()` 可靠得多：

```kotlin
@Test
fun `延迟任务在时间推进后才执行`() {
    val handler = Handler(Looper.getMainLooper())
    var fired = false
    handler.postDelayed({ fired = true }, 1_000)

    shadowOf(Looper.getMainLooper()).idle()      // 只跑当前已到期的任务
    assertFalse(fired)

    shadowOf(Looper.getMainLooper()).idleFor(java.time.Duration.ofSeconds(1))
    assertTrue(fired)
}
```

**Robolectric 的边界**：它跑的是 AOSP 实现，不是厂商 ROM。多进程、Binder 跨进程、系统权限授予、传感器、真实渲染都不覆盖。所以它适合替代“与 UI 无关的插桩测试”，不能替代真机验证。

此外，Robolectric 也支持 Compose 测试：加 `@GraphicsMode(GraphicsMode.Mode.NATIVE)` 后 `createComposeRule()` 可以在 JVM 上跑，适合在没有模拟器的 CI 上兜住 UI 回归。前提是 `isIncludeAndroidResources = true`，且依赖要配到 `testImplementation` 而不是 `androidTestImplementation`。

### 让 @Test 按顺序执行

单元测试原则上不应有顺序依赖——每个用例都应能在任意顺序下独立通过。确实需要顺序时（比如集成式的冒烟用例）：

JUnit 4 用 `@FixMethodOrder`，注意它是按**方法名字典序**排的，所以方法名需带序号：

```kotlin
@FixMethodOrder(MethodSorters.NAME_ASCENDING)
class OrderedFlowTest {

    @Test fun step01_prepare() { /* ... */ }

    @Test fun step02_submit() { /* ... */ }
}
```

JUnit 5 用 `@TestMethodOrder` + `@Order`，不必再改方法名：

```kotlin
@TestMethodOrder(MethodOrderer.OrderAnnotation::class)
class OrderedFlowTest {

    @Test
    @Order(1)
    fun prepare() { /* ... */ }

    @Test
    @Order(2)
    fun submit() { /* ... */ }
}
```

只加 `@Order` 而不加 `@TestMethodOrder` 是不生效的——`@Order` 只是给排序器看的元数据，排序器本身要显式声明。

JUnit 5 在 Android 上**不能只加一条依赖**：AGP 的单元测试任务默认走 JUnit 4 的 `Test` 模型，需要通过 Gradle 插件切到 JUnit Platform。

```kotlin
plugins {
    id("de.mannodermaus.android-junit") version "2.0.2"
}

dependencies {
    testImplementation(platform("org.junit:junit-bom:5.14.1"))
    testImplementation("org.junit.jupiter:junit-jupiter")
    // 若同时保留 Robolectric 的 JUnit 4 测试，需要 Vintage 引擎
    testRuntimeOnly("org.junit.vintage:junit-vintage-engine")
}
```

该插件要求 AGP 8.2+、Gradle 8.2+。另外注意 **JUnit 6 的最低要求是 Java 17，且插桩运行需要设备为 API 35+**，因此 Android 项目目前实用的仍是 JUnit 5（5.14.x）。

> Groovy DSL 里写 `testImplementation 'org.junit.jupiter:junit-jupiter:${version}'` 时，**单引号字符串不做插值**，版本号会原样变成字面量 `${version}`。要么改用双引号，要么直接用固定版本。

### 断言与测试替身

“测试替身”不只等于 mock，按用途分四类：

| 类型 | 行为 | 适用 |
| --- | --- | --- |
| Stub | 只返回预设值，不校验调用 | 提供输入数据 |
| Fake | 有一份可用的简化实现（如内存版 Repository） | 替代数据库、网络 |
| Mock | 记录调用并允许校验交互 | 验证“有没有调用” |
| Spy | 包住真实对象，可选择性拦截 | 部分打桩 |

Google 的建议是**优先用 Fake，少用 Mock**。mock 会把测试绑死在实现细节上：一旦把 `repository.load()` 拆成两个方法，测试即全部失败，而行为并未改变。Fake 只需维护一个接口实现，重构时基本无需改动。

MockK 是 Kotlin 项目的首选（对 `final` 类、`object`、扩展函数都友好）：

```kotlin
class LoginViewModelTest {

    private val repository = mockk<UserRepository>()
    private val viewModel = LoginViewModel(repository)

    @Test
    fun `登录成功后状态变为 Success`() = runTest {
        coEvery { repository.login("tom", "123") } returns User("tom")

        viewModel.login("tom", "123")

        assertEquals(LoginState.Success, viewModel.state.value)
        coVerify(exactly = 1) { repository.login("tom", "123") }
    }
}
```

`suspend` 函数用 `coEvery` / `coVerify`；普通函数用 `every` / `verify`。`mockk(relaxed = true)` 可以让未打桩的成员返回默认值，但滥用会掩盖漏打的桩，建议只在断言不关心交互时使用。

### 协程与 Flow

`runTest`、虚拟时间、`TestDispatcher` 的完整用法见 [[9. Kotlin协程：测试与调试#runTest：唯一入口]]。这里只强调 Android 场景下最易出错的一条：`viewModelScope` 内部用的是 `Dispatchers.Main.immediate`，本地 JVM 没有主线程，会直接抛：

```text
Module with the Main dispatcher had failed to initialize.
```

标准解法是把 `Dispatchers.Main` 换掉，并封装成 Rule 复用：

```kotlin
@OptIn(ExperimentalCoroutinesApi::class)
class MainDispatcherRule(
    private val dispatcher: TestDispatcher = UnconfinedTestDispatcher(),
) : TestWatcher() {

    override fun starting(description: Description) = Dispatchers.setMain(dispatcher)

    override fun finished(description: Description) = Dispatchers.resetMain()
}
```

```kotlin
class LoginViewModelTest {

    @get:Rule
    val mainDispatcherRule = MainDispatcherRule()

    // ... 测试体
}
```

`Dispatchers.setMain` 目前仍标注 `@ExperimentalCoroutinesApi`，必须加 `@OptIn`。另外**必须在 `finished` 里 `resetMain()`**：它改的是全局状态，不还原会污染同进程里的其他测试类。

测 `StateFlow` / `SharedFlow` 用 Turbine，逐条断言发射顺序：

```kotlin
@Test
fun `状态流依次发出 Idle、Loading、Success`() = runTest {
    viewModel.state.test {
        assertEquals(LoginState.Idle, awaitItem())

        viewModel.login("tom", "123")

        assertEquals(LoginState.Loading, awaitItem())
        assertEquals(LoginState.Success, awaitItem())
        cancelAndIgnoreRemainingEvents()
    }
}
```

`StateFlow` 会把当前值重放给新订阅者，所以第一个 `awaitItem()` 拿到的是初始值。`awaitItem()` 有默认超时，不会导致测试永久挂起。

## 插桩测试

插桩测试（Instrumented Test）运行在真机或模拟器上，测试代码与 App 代码打包进同一个进程（默认情况下），因此能调用真实的 Android 框架 API、访问真实数据库、验证跨进程行为。

```kotlin
@RunWith(AndroidJUnit4::class)
class ExampleInstrumentedTest {

    @Test
    fun useAppContext() {
        val context = ApplicationProvider.getApplicationContext<Context>()
        assertEquals("com.example.myapp", context.packageName)
    }
}
```

`@RunWith(AndroidJUnit4::class)` 来自 `androidx.test.ext.junit.runners.AndroidJUnit4`。如果整个模块只有 JUnit 4 测试，这个注解可以省略；混用 JUnit 3 与 JUnit 4 时才必须显式指定。

### 运行机制与构建变体

`src/androidTest/` 对所有构建变体都是识别的，**并不存在“只有 debug 变体才能被识别”的限制**。真正决定行为的是 `testBuildType`：

```kotlin
android {
    // 默认值就是 "debug"；改成别的构建类型时，插桩测试会针对该变体构建
    testBuildType = "staging"
}
```

默认跑 `debug`，是因为它可调试、无需签名配置。要改成 `release` 或自定义变体，必须保证该变体有可用的签名配置，否则测试 APK 装不上设备。所以“插桩测试必须在 debug 下”是误读——它只是默认值。

测试运行的常用控制手段：

```bash
# 只跑一个类
./gradlew connectedDebugAndroidTest \
  -Pandroid.testInstrumentationRunnerArguments.class=com.example.LoginActivityTest

# 只跑 small 组（配合 @SmallTest）
./gradlew connectedDebugAndroidTest \
  -Pandroid.testInstrumentationRunnerArguments.size=small

# 直接用 am instrument
adb shell am instrument -w \
  -e class com.example.LoginActivityTest \
  com.example.test/androidx.test.runner.AndroidJUnitRunner
```

`androidx.test.filters` 提供的注解可以直接筛选用例：

| 注解 | 作用 |
| --- | --- |
| `@SmallTest` / `@MediumTest` / `@LargeTest` | 标记耗时等级，配合 `size` 参数过滤 |
| `@SdkSuppress(minSdkVersion = 26)` | 低于指定 API 级别时跳过 |
| `@RequiresDevice` | 只在真机跑，模拟器上跳过 |
| `@FlakyTest` | 标记不稳定用例，可重复执行 |

### 与 UI 无关的插桩测试

这类测试验证的是“必须依赖真实系统环境”的逻辑，典型有四种。

**Parcelable 往返**——序列化逻辑出错只会在跨进程时暴露：

```kotlin
@RunWith(AndroidJUnit4::class)
class LogHistoryTest {

    @Test
    fun parcelable_roundTrip() {
        val source = LogHistory().apply { addEntry("boot", 1L) }

        val parcel = Parcel.obtain()
        source.writeToParcel(parcel, source.describeContents())
        parcel.setDataPosition(0)   // 写完必须回到起点才能读

        val restored = LogHistory.CREATOR.createFromParcel(parcel)
        parcel.recycle()

        assertEquals(source.data, restored.data)
    }
}
```

**Room 数据库**——用内存库，测完即销毁，不污染设备数据：

```kotlin
@RunWith(AndroidJUnit4::class)
class UserDaoTest {

    private lateinit var db: AppDatabase
    private lateinit var dao: UserDao

    @Before
    fun setUp() {
        val context = ApplicationProvider.getApplicationContext<Context>()
        db = Room.inMemoryDatabaseBuilder(context, AppDatabase::class.java).build()
        dao = db.userDao()
    }

    @After
    fun tearDown() = db.close()

    @Test
    fun insertAndQuery() = runTest {
        dao.insert(User(id = 1, name = "Tom"))
        assertEquals("Tom", dao.findById(1)?.name)
    }
}
```

SQLite 的方言、`@Query` 的编译期校验、迁移脚本都只有在真机/模拟器上才真正走一遍，所以 Dao 测试放在这里比放本地更可信。

**ContentProvider / Service**——需要真实 `ContentResolver` 和 Binder，本地测试无法模拟，只能在插桩层验证。

**Activity 生命周期**——用 `ActivityScenario` 驱动，比直接 `startActivity` 更可控，还能模拟重建：

```kotlin
@RunWith(AndroidJUnit4::class)
class DetailActivityTest {

    @get:Rule
    val rule = ActivityScenarioRule(DetailActivity::class.java)

    @Test
    fun recreate_keepsTitle() {
        rule.scenario.onActivity { activity ->
            assertEquals("详情", activity.findViewById<TextView>(R.id.title).text)
        }

        rule.scenario.recreate()   // 模拟配置变更导致的销毁重建

        rule.scenario.onActivity { activity ->
            assertEquals("详情", activity.findViewById<TextView>(R.id.title).text)
        }
    }
}
```

`recreate()` 是验证 `onSaveInstanceState` / `SavedStateHandle` 是否写对的最直接手段。

### UI 交互测试：Espresso

Espresso 面向 View 体系，核心是三段式：`onView(匹配器).perform(操作).check(断言)`。

```kotlin
@RunWith(AndroidJUnit4::class)
class LoginActivityTest {

    @get:Rule
    val rule = ActivityScenarioRule(LoginActivity::class.java)

    @Test
    fun wrongPassword_showsError() {
        onView(withId(R.id.username)).perform(typeText("tom"), closeSoftKeyboard())
        onView(withId(R.id.password)).perform(typeText("wrong"), closeSoftKeyboard())
        onView(withId(R.id.login)).perform(click())

        onView(withText("密码错误")).check(matches(isDisplayed()))
    }
}
```

Espresso 会自动等待主线程消息队列空闲，所以普通点击、输入不需要手写 `sleep`。但**异步任务（网络、线程池、Handler 之外的调度）它看不见**，这时要么把异步源注册成 `IdlingResource`，要么改用显式轮询。

几个高频 API：

| 需求 | API |
| --- | --- |
| 按 id / 文本 / 内容描述查找 | `withId()`、`withText()`、`withContentDescription()` |
| 列表项 | `onData(anything()).atPosition(0)` / `inAdapterView()` |
| 断言可见、可用、文本 | `isDisplayed()`、`isEnabled()`、`withText()` |
| 输入与关闭软键盘 | `typeText()`、`closeSoftKeyboard()` |
| 滚动 | `scrollTo()`、`swipeUp()` |

### UI 交互测试：Compose

Compose 没有 View 树，Espresso 的 `onView` 找不到节点。改用语义树（semantics tree）查找：

```kotlin
class LoginScreenTest {

    @get:Rule
    val composeRule = createComposeRule()

    @Test
    fun cannotSubmit_whenButtonDisabled() {
        composeRule.setContent {
            AppTheme { LoginScreen(canSubmit = false, onLogin = {}) }
        }

        composeRule.onNodeWithText("登录").assertIsNotEnabled()
    }

    @Test
    fun click_invokesCallback() {
        var clicked = false
        composeRule.setContent {
            AppTheme { LoginScreen(canSubmit = true, onLogin = { clicked = true }) }
        }

        composeRule.onNodeWithText("登录").performClick()
        assertTrue(clicked)
    }
}
```

两个工厂函数的区别：

- `createComposeRule()`：只挂一个空宿主 Activity，适合纯 Composable 测试，**必须**加 `debugImplementation("androidx.compose.ui:ui-test-manifest")`；
- `createAndroidComposeRule<MainActivity>()`：启动指定 Activity，适合需要真实页面、`ViewModel`、`SavedStateHandle` 的场景。

Compose 测试同样会自动同步——它等组合、布局、绘制都空闲后才执行下一步。需要干预时用这三个：

```kotlin
// 1. 等某个节点出现（异步加载完成）
composeRule.waitUntil(timeoutMillis = 5_000) {
    composeRule.onAllNodesWithText("加载完成").fetchSemanticsNodes().isNotEmpty()
}

// 2. 手动控制时钟（测试动画、延迟）
composeRule.mainClock.autoAdvance = false
composeRule.mainClock.advanceTimeBy(1_000)

// 3. 查找不在合并语义里的子节点
composeRule.onNodeWithTag("icon", useUnmergedTree = true)
```

`testTag` 是给测试用的稳定标识，比文本可靠（文本会随语言变）。生产代码里加 `Modifier.testTag("login_button")`，测试里用 `onNodeWithTag("login_button")`。

### 跨应用：UI Automator

Espresso 和 Compose Test 都被限制在**被测应用进程内**。要操作系统界面（通知栏、权限弹窗、设置页）或别的 App，必须用 UI Automator：

```kotlin
@RunWith(AndroidJUnit4::class)
class SystemUiTest {

    @Test
    fun openSettingsFromNotification() {
        val device = UiDevice.getInstance(InstrumentationRegistry.getInstrumentation())

        device.pressHome()
        device.openNotification()
        device.findObject(By.text("下载完成")).click()
    }
}
```

2.4.0 起 UI Automator 重做了 API，新增 `uiAutomator { }` 测试作用域、`onElement` / `onElements` 查找、内置等待（`timeoutMs` 默认 10 秒）、`waitForStable` 与截图能力；旧的 `UiDevice` / `UiObject2` 写法仍然可用。升级时注意 2.4 的 API 变化较大，新老两套写法不要混用。

### 隔离执行：Test Orchestrator

默认情况下，一个测试套件里所有用例共享同一个 `Instrumentation` 进程。前一个用例留下的静态变量、单例、登录态会污染后一个，表现为“单跑通过、一起跑失败”。

Orchestrator 让每个用例在自己的 `Instrumentation` 实例里跑：

```kotlin
android {
    defaultConfig {
        // 每个用例结束后 pm clear，连 App 数据一起清掉
        testInstrumentationRunnerArguments["clearPackageData"] = "true"
    }

    testOptions {
        execution = "ANDROIDX_TEST_ORCHESTRATOR"
    }
}

dependencies {
    androidTestUtil("androidx.test:orchestrator:1.6.1")
}
```

代价是每个用例都要重启一次应用，整体耗时明显上升。所以它适合对隔离与稳定性要求高的 CI 流水线，不适合本地频繁调试。

### 无人值守：Gradle 托管设备

CI 上没有现成设备时，可以让 AGP 自己创建、启动、销毁模拟器：

```kotlin
android {
    testOptions {
        managedDevices {
            localDevices {
                create("pixel7api35") {
                    device = "Pixel 7"
                    apiLevel = 35
                    systemImageSource = "aosp"   // 需要 Google 服务时用 "google"
                }
            }
        }
    }
}
```

```bash
./gradlew pixel7api35DebugAndroidTest
```

首次运行会通过 SDK Manager 下载对应系统镜像。无硬件渲染的服务器（如 GitHub Actions）需要额外传 `-Pandroid.testoptions.manageddevices.emulator.gpu=swiftshader_indirect`。

## Monkey 压力测试

前面几节验证的是“该做的事有没有做对”，Monkey 验证的是另一件事：**随机输入是否触发崩溃**。它向设备注入伪随机事件流（点击、滑动、返回、系统键、Activity 跳转），不做任何断言，只盯三种结果——崩溃、ANR、权限异常。所以它属于**稳定性/压力测试**，不能替代功能测试，也读不懂业务。

它的价值在于零成本：无需编写测试代码，一条命令即可在真机上执行数千次随机操作，适合发版前的例行快速验证（快速、无断言的初步检查）。

### 基本用法

```bash
# 语法
adb shell monkey [options] <event-count>

# 最小可用：只在本应用内发 500 个随机事件
adb shell monkey -p com.example.app -v 500
```

未指定 `-p` 时 Monkey 会在**所有已安装应用**中随机操作，包括系统设置，因此通常必须指定 `-p`。实际使用的命令通常如下：

```bash
adb shell monkey \
  -p com.example.app \
  -s 20261112 \
  --throttle 300 \
  --pct-touch 40 \
  --pct-motion 25 \
  --pct-majornav 15 \
  --pct-appswitch 10 \
  --pct-nav 0 \
  --pct-syskeys 0 \
  --pct-anyevent 10 \
  --ignore-timeouts \
  -v -v \
  5000
```

这条命令的含义：种子 `20261112`、事件间隔 300ms、跑 5000 个事件、四成点击两成半滑动、不要方向键和系统键、遇到 ANR 继续跑、输出较详细日志。

### 常用参数

| 参数 | 作用 |
| --- | --- |
| `<event-count>` | 事件总数，必填位置参数 |
| `-p <包名>` | 限定只操作该应用；要多个包就重复写多个 `-p` |
| `-c <category>` | 限定 Activity 类别；不写默认 `LAUNCHER` / `MONKEY` |
| `-s <seed>` | 随机种子，相同种子 + 相同初始状态可复现事件序列 |
| `--throttle <ms>` | 事件间隔毫秒数，默认 0（全速注入） |
| `-v` | 详细级别，每多一个 `-v` 升一级（0 只报开始/结束，1 报每个事件，2 报选中的 Activity） |
| `--pct-touch` | 单点按下/抬起 |
| `--pct-motion` | 按下 + 滑动 + 抬起 |
| `--pct-majornav` | 返回、菜单、确定等“主要”导航键 |
| `--pct-nav` | 方向键（老设备的上下左右） |
| `--pct-trackball` | 轨迹球事件，现代设备上基本可以设为 0 |
| `--pct-syskeys` | Home、音量、电源等系统键 |
| `--pct-appswitch` | 随机 `startActivity()`，用于覆盖应用内各页面 |
| `--pct-anyevent` | 其他所有事件，兜底类别 |
| `--ignore-crashes` | 崩溃后不停止，继续发完剩余事件 |
| `--ignore-timeouts` | ANR 后不停止 |
| `--ignore-security-exceptions` | 权限异常后不停止 |
| `--kill-process-after-error` | 出错后杀掉进程，避免残留状态干扰下一轮 |
| `--monitor-native-crashes` | 同时监控 native 崩溃 |
| `--dbg-no-events` | 只启动到被测 Activity、不产生事件，配合 `-v` 与非零 throttle 观察它会拉起哪些包 |
| `--hprof` | 运行前后各生成一次内存快照（约 5MB，慎用） |
| `--wait-dbg` | 挂起等待调试器附加 |

### 事件比例怎么配

Monkey 的默认配比是为“带方向键的老设备”设计的，`nav`、`trackball` 这类事件在现代触屏应用上基本是浪费。常见做法是重配成“点击为主、滑动其次”：

- 列表类、图文类应用：`--pct-touch 40 --pct-motion 35 --pct-majornav 15 --pct-appswitch 10`；
- 表单、设置类页面多：把 `--pct-touch` 提到 50 以上；
- 必须将 `--pct-syskeys` 设为 0，否则 Home 键会把应用切到后台，后续事件全部落在桌面上，看似“未崩溃”，实际上并未测到应用。

各项之和**不要超过 100**，超过会直接报错退出。简化的做法是如上面的例子将主要类别写全、正好凑到 100，无需猜测未写类别的分配方式。确实不需要的类别显式写 `0`。

### 看输出：崩溃与 ANR

Monkey 的结构化输出是排查的唯一入口，关键行都以 `//` 开头：

```text
:Monkey: seed=20261112 count=5000
:AllowPackage: com.example.app
...
// CRASH: com.example.app (pid 12345)
// Short Msg: java.lang.NullPointerException
// Long Msg: java.lang.NullPointerException: Attempt to invoke virtual method ...
// Build Label: ...
// *** *** *** *** ***
// java.lang.NullPointerException: ...
//     at com.example.app.ui.DetailFragment.onBind(DetailFragment.kt:42)
...
// Monkey finished
```

- `// CRASH:` 后面是包名和 pid，紧跟 `Short Msg` / `Long Msg` 与堆栈；
- `// NOT RESPONDING:` 表示 ANR，同样带 pid；
- `// Monkey finished` 表示事件跑完，正常结束。

**不应使用退出码判断结果**：Monkey 在应用崩溃后往往仍然正常退出。可靠做法是抓日志再匹配：

```bash
adb shell am force-stop com.example.app

adb shell monkey -p com.example.app -s 20261112 --throttle 300 -v -v 5000 \
  > "monkey-20261112.log" 2>&1

if grep -qE "^// (CRASH|NOT RESPONDING)" "monkey-20261112.log"; then
  echo "发现崩溃/ANR，seed=20261112"
  grep -A 20 -E "^// (CRASH|NOT RESPONDING)" "monkey-20261112.log"
  exit 1
fi
echo "本轮通过"
```

Monkey 日志里的堆栈通常被截断，真正的完整栈应通过 logcat 获取：`adb logcat -b crash` 或按时间点抓 `adb logcat -v time`。

### 复现

`-s` 保证的是**事件序列**可复现，不是“崩溃必然重现”。要真正复现，还需保证初始状态一致：

- 固定 seed，并把它写进缺陷单（`seed=20261112 count=5000`）；
- 记录设备分辨率、语言、字体缩放、是否深色模式——不同分辨率下同样的坐标点到的是不同控件；
- 每轮开始前 `adb shell am force-stop` 或 `pm clear`，避免上一轮的登录态、缓存影响路径；
- 应用启动页、引导页、登录墙会吞掉大量随机事件，建议先手动通过一遍再执行。

### 局限与替代

| 局限 | 说明 |
| --- | --- |
| 不做断言 | 只发现崩溃/ANR，页面显示错乱、数据写错都发现不了 |
| 不懂界面 | 纯坐标随机，容易在少数页面上反复打转，覆盖深度有限 |
| 卡在弹窗 | 权限申请、系统对话框它点不动，会一直原地消耗事件 |
| 只测前台 | 应用被切到后台后的事件基本无效，`--pct-syskeys` 必须为 0 |

需要“会看界面”的探索时，换更聪明的方案：Firebase Test Lab 的 **Robo test**（按界面模型自动遍历，能出页面图与崩溃报告）、字节开源的 **Fastbot**（模型驱动的事件生成，覆盖深度明显更好）。Monkey 仍然适合放在 CI 里当一道零成本的冒烟闸门。

## 覆盖率

覆盖率的完整配置与用法已单独整理到 [[8. 代码扫描#单元测试覆盖率]]：开关、报告任务与路径、排除生成代码、多模块汇总、门禁规则都在那一篇。

这里只留一条结论：覆盖率用来找“0% 的类”，不用来当 KPI；不排除 `R`、`BuildConfig`、Hilt、Compose 合成类，数字既不可比也不可信。

## 截图测试

UI 测试判断“点击是否触发响应”，截图测试判断“渲染结果是否发生变化”。Compose 项目可以用官方的 **Compose Preview Screenshot Testing**：把 `@Preview` 直接当测试用例，在 JVM 上渲染并与基准图比对，不需要设备。

在 `src/screenshotTest/kotlin/` 下写：

```kotlin
@PreviewTest
@Preview(showBackground = true, uiMode = Configuration.UI_MODE_NIGHT_YES)
@Composable
fun LoginScreenPreview() {
    AppTheme { LoginScreen(canSubmit = true, onLogin = {}) }
}
```

```bash
# 生成/更新基准图，产物在 src/screenshotTestDebug/reference/
./gradlew updateDebugScreenshotTest

# 与基准图比对，报告在 build/reports/screenshotTest/
./gradlew validateDebugScreenshotTest
```

该能力目前仍是 **alpha**（插件 `com.android.compose.screenshot`，0.0.1-alpha16），API 可能大幅调整；AGP 9.5 之后官方推荐改用 test suites 的配置方式。要更成熟的选择，可以看 Roborazzi（基于 Robolectric）或 Paparazzi。

## 为测试而设计

可测性差通常意味着设计存在问题。几条能显著降低测试成本的约定：

- **依赖从构造函数进**，不要在类内部 `new` 或取全局单例。`class Repo(private val api: Api, private val io: CoroutineDispatcher = Dispatchers.IO)` 既能注入 Fake，也能注入 `TestDispatcher`。
- **不要到处传 `Context`**。业务类只需要字符串、文件目录、`SharedPreferences` 这些具体依赖，把 `getString()` 留在 UI 层。
- **面向接口编程**。Repository 抽成接口，测试用 Fake 实现，生产用真实实现，Hilt 负责绑定。
- **时间、随机数、UUID 要可注入**。否则测试只能断言“不为空”，或者依赖 `Thread.sleep()`。
- **`internal` + `@VisibleForTesting`**。同模块的测试能看见 `internal`，不需要为了测试把方法改成 public；跨模块共享 Fake 时用 AGP 的 `testFixtures`：

```kotlin
android {
    testFixtures { enable = true }
}
```

## 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `Method ... not mocked` | 本地测试调用了 Mockable Jar 的空方法 | 抽离依赖；或改用 Robolectric；`isReturnDefaultValues` 兜底 |
| `Module with the Main dispatcher had failed to initialize` | 本地 JVM 没有主线程 | `Dispatchers.setMain()` + `MainDispatcherRule` |
| `No tests found for given includes` | 方法带参数/返回值，或漏了 `@Test` | 改成无参无返回，检查 import 是否为 `org.junit.Test` |
| Robolectric 首次运行卡在下载 `android-all` | 需要从 Maven Central 拉对应 SDK 的 jar | 配置镜像，或离线：`robolectric.offline=true` + `robolectric.dependency.dir` |
| 单独跑通过，全量跑失败 | 静态状态 / 单例污染 | Orchestrator + `clearPackageData`；或每个用例重建依赖 |
| UI 测试偶发失败 | 动画、异步加载、软键盘 | `animationsDisabled = true`、`IdlingResource`、`waitUntil` |
| `@Order` 不起作用 | 缺 `@TestMethodOrder` | 补上 `@TestMethodOrder(MethodOrderer.OrderAnnotation::class)` |

## 小结

- **本地测试是主力**：纯逻辑、ViewModel、Repository 都应在这一层，毫秒级反馈。
- **Robolectric 是本地测试的增强**，不是插桩测试；它将“需要 Context”的测试从设备迁移回 JVM。
- **插桩测试仅用于必须依赖真机的场景**：真实框架 API、数据库、Binder、UI 交互。
- **UI 测试分三档**：Espresso（View）、Compose Test（语义树）、UI Automator（跨应用）。
- **稳定性交给 Monkey 兜底**：零脚本、只找崩溃与 ANR；固定 `-s`、把 `--pct-syskeys` 收成 0、用日志 grep 判定而不是退出码。
- **测试替身优先 Fake**，mock 只用于校验交互，否则测试会和实现细节焊死。
- **覆盖率单独成篇**：开关、报告任务、排除规则与门禁见 [[8. 代码扫描#单元测试覆盖率]]；核心仍是排除生成代码后再看，定位 0% 的类比关注总分更有价值。
- 覆盖率是结果不是目标；测行为、测边界、测失败路径，比测“每个 getter”有价值得多。
