## 准备工作

C/C++ 源码在不同构建方式下可能输出 `.so`、`.exe`、`.dll` 等不同格式。NDK 开发要做的，是用构建工具把源码编译成 `.so`（Linux 共享库）。主流构建方式有两种：

- **CMake**：Android Studio 默认推荐，脚本是 `CMakeLists.txt`；
- **ndk-build**：基于 Makefile，脚本是 `Android.mk` 和 `Application.mk`。

两者都需要 NDK；用 CMake 还需要安装 CMake。在 Android Studio 的 **SDK Manager → SDK Tools** 中勾选 NDK 和 CMake 即可：

![[ndk2.png]]

*图 1　SDK Tools 中的 NDK。截图为旧版界面，入口名称随版本略有差异。*

![[ndk3.png]]

*图 2　SDK Tools 中的 CMake。*

建议在模块的 `build.gradle.kts` 里显式写 `ndkVersion`，避免不同机器使用不同 NDK 导致构建结果不一致：

```kotlin
android {
    ndkVersion = "28.2.13676358" // 以 SDK Manager 中实际安装的版本为准
}
```

> **关于 Ninja**：Ninja 不是 Google 提供的“第三种 NDK 构建系统”，也不是 CMake/ndk-build 的替代品。CMake 负责读 `CMakeLists.txt` 并生成构建文件，Android Studio 下的 CMake 默认用 **Ninja** 作为底层执行器去调用编译器。日常只需要写 CMake，不需要直接写 Ninja 脚本。

## 构建Native Library

### 基于CMake脚本构建

CMake 的优势是跨平台、脚本简洁，CLion 等 C/C++ IDE 也使用它。Android Studio 新建 Native 项目时默认生成 CMake 工程。

#### 创建CMake构建脚本

C/C++ 源码通常放在模块的 `src/main/cpp` 目录，`CMakeLists.txt` 放在同一目录：

![[ndk4.png]]

*图 3　`src/main/cpp` 下的源码与 `CMakeLists.txt`。*

文件名必须是 `CMakeLists.txt`，不能只写 `CMakeLists`。脚本可以放在项目其他位置，但 Gradle 里的 `path` 要指向实际位置；放在源码目录是 IDE 的默认做法。

#### 配置CMake脚本

一个最小可用的 `CMakeLists.txt`：

```cmake
cmake_minimum_required(VERSION 3.22.1)
project("native-lib")

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_library(native-lib SHARED native-lib.cpp)

target_include_directories(native-lib PRIVATE include)

find_library(log-lib log)
target_link_libraries(native-lib ${log-lib})
```

关键点：

- `add_library` 的第一个参数是目标名，第二个是 `SHARED`（生成 `.so`）或 `STATIC`（生成 `.a`），后面是源文件。
- **源文件路径相对于 `CMakeLists.txt` 所在目录**。`CMakeLists.txt` 在 `src/main/cpp`，所以写 `native-lib.cpp`，不要写 `src/main/cpp/native-lib.cpp`，否则会变成 `src/main/cpp/src/main/cpp/native-lib.cpp`。
- 产物名是 `lib<target>.so`，即 `libnative-lib.so`。`System.loadLibrary("native-lib")` 加载的就是它。
- `target_include_directories` 比全局的 `include_directories` 更好，它把包含路径限制在指定目标上。
- 多个源文件直接列在 `add_library` 里：

```cmake
add_library(native-lib SHARED
    native-lib.cpp
    helper.cpp
    math/vector.cpp)
```

- 多个库可以多次调用 `add_library`，Gradle 会把所有 `SHARED` 库打包进 APK。
- `cmake_minimum_required` 的版本不要低于 AGP/NDK 要求的版本；`3.22.1` 是 Android Studio 长期使用的版本，具体以 SDK Manager 安装的 CMake 为准。

#### 添加NDK API

Android NDK 自带一组 Native API 和库。以 `log` 库为例：

```cmake
find_library(log-lib log)
target_link_libraries(native-lib ${log-lib})
```

`find_library` 把库的路径存到变量里，`target_link_libraries` 再把变量指向的库链接到目标。`log`、`android`、`EGL`、`GLESv3` 等系统库都在 NDK 的默认搜索路径中，写库名即可。

`native_app_glue` 是以源码形式提供的，需要先作为静态库加入：

```cmake
add_library(native_app_glue STATIC
    ${ANDROID_NDK}/sources/android/native_app_glue/android_native_app_glue.c)

target_link_libraries(native-lib native_app_glue ${log-lib} android)
```

#### 添加预构建库

预构建库用 `IMPORTED` 标志，告诉 CMake 不要编译它，只导入：

```cmake
add_library(imported-lib SHARED IMPORTED)

set_target_properties(imported-lib PROPERTIES
    IMPORTED_LOCATION
    "${CMAKE_CURRENT_SOURCE_DIR}/libs/${ANDROID_ABI}/libimported-lib.so")

target_include_directories(native-lib PRIVATE
    "${CMAKE_CURRENT_SOURCE_DIR}/libs/include")

target_link_libraries(native-lib imported-lib)
```

`IMPORTED_LOCATION` 必须是**绝对路径**。`${ANDROID_ABI}` 是当前正在构建的 ABI，把不同 ABI 的 `.so` 放在 `libs/<abi>/` 下即可复用同一份脚本。预构建库的头文件路径也要用绝对路径，或相对于 `CMakeLists.txt` 的路径。

#### 包含其他CMake项目

如果主项目依赖另一个 CMake 子项目，可以用 `add_subdirectory` 把子项目加进来：

```cmake
set(GMATH_DIR "${CMAKE_CURRENT_SOURCE_DIR}/../gmath")
set(GMATH_BINARY_DIR "${CMAKE_CURRENT_BINARY_DIR}/gmath")
file(MAKE_DIRECTORY "${GMATH_BINARY_DIR}")

add_subdirectory("${GMATH_DIR}" "${GMATH_BINARY_DIR}")

add_library(lib_gmath STATIC IMPORTED)
set_target_properties(lib_gmath PROPERTIES
    IMPORTED_LOCATION "${GMATH_BINARY_DIR}/${ANDROID_ABI}/lib_gmath.a")

target_include_directories(native-lib PRIVATE "${GMATH_DIR}/include")
target_link_libraries(native-lib lib_gmath)
```

子项目的输出路径由子项目自己的 `CMakeLists.txt` 决定，`${GMATH_BINARY_DIR}/${ANDROID_ABI}/lib_gmath.a` 只是示例，实际要以子项目的 `LIBRARY_OUTPUT_DIRECTORY` 为准。

#### C++标准库

CMake 的 `ANDROID_STL` 默认是 **`c++_static`**。如果要改成共享 STL：

```kotlin
externalNativeBuild {
    cmake {
        arguments += "-DANDROID_STL=c++_shared"
    }
}
```

`c++_shared` 会依赖 `libc++_shared.so`，Gradle 会自动把它打包进 APK；如果手动拷贝 `.so`，别忘了这个文件。多个共享库共用同一个 C++ 运行时时，通常选 `c++_shared`；只有一个共享库时，`c++_static` 体积更小。

### 基于ndk-build构建

ndk-build 基于 Makefile，常见于早期项目。它仍然可用，但 Google 现在更推荐 CMake；Android Studio 新建 Native 项目默认也是 CMake。

ndk-build 使用 `Android.mk` 和 `Application.mk` 两个脚本，通常放在 `src/main/jni`。`ndk-build` 脚本本质上会执行类似下述命令：

```bash
$GNUMAKE -f <ndk>/build/core/build-local.mk <parameters>
```

`$GNUMAKE` 指向 GNU Make 3.81 或更高版本，`<ndk>` 是 NDK 安装目录。日常不需要手动执行这条命令，Gradle 会调用 ndk-build。

#### Android.mk脚本

`Android.mk` 用于描述源文件、共享库、静态库和可执行文件。它的语法基于 Make，但 NDK 预定义了一组变量和宏。

一个最小模块：

```make
LOCAL_PATH := $(call my-dir)

include $(CLEAR_VARS)

LOCAL_MODULE := hello-jni
LOCAL_SRC_FILES := hello-jni.c

include $(BUILD_SHARED_LIBRARY)
```

逐行解释：

- `LOCAL_PATH := $(call my-dir)`：`my-dir` 返回当前 `Android.mk` 所在目录，必须在文件开头定义，且只定义一次。
- `include $(CLEAR_VARS)`：清理除 `LOCAL_PATH` 外的 `LOCAL_XXX` 变量。每开始一个新模块都要重新 include 一次。
- `LOCAL_MODULE`：模块名，必须唯一、不能含空格。构建系统生成 `.so` 时会自动加 `lib` 前缀；如果模块名已经以 `lib` 开头，则不会重复添加。
- `LOCAL_SRC_FILES`：参与构建的源文件，**用空格分隔**；一行写不下时，行尾用 `\` 续行，而不是用 `\` 分隔文件。
- `include $(BUILD_SHARED_LIBRARY)`：收集当前模块的 `LOCAL_XXX` 信息并生成共享库。

一个 `Android.mk` 可以定义多个模块：每个模块都以 `include $(CLEAR_VARS)` 开始，以某个 `BUILD_*` 或 `PREBUILT_*` 结束。**不是整个文件只能在最后一行调用一次**：

```make
LOCAL_PATH := $(call my-dir)

include $(CLEAR_VARS)
LOCAL_MODULE := hello-jni
LOCAL_SRC_FILES := hello-jni.c
include $(BUILD_SHARED_LIBRARY)

include $(CLEAR_VARS)
LOCAL_MODULE := utils
LOCAL_SRC_FILES := utils.c
include $(BUILD_STATIC_LIBRARY)
```

##### include变量

| 变量 | 用途 |
| :--- | :--- |
| `CLEAR_VARS` | 清理除 `LOCAL_PATH` 外的所有 `LOCAL_XXX` 变量 |
| `BUILD_EXECUTABLE` | 生成可执行文件 |
| `BUILD_SHARED_LIBRARY` | 生成 `.so` 共享库 |
| `BUILD_STATIC_LIBRARY` | 生成 `.a` 静态库 |
| `PREBUILT_SHARED_LIBRARY` | 导入已构建好的 `.so`，此时 `LOCAL_SRC_FILES` 指向该文件 |
| `PREBUILT_STATIC_LIBRARY` | 导入已构建好的 `.a`，此时 `LOCAL_SRC_FILES` 指向该文件 |

##### 目标信息变量

`TARGET_*` 变量用于条件判断：

```make
ifeq ($(TARGET_ARCH_ABI),arm64-v8a)
    # arm64 专用配置
endif
```

| 变量 | 用途 |
| :--- | :--- |
| `TARGET_ARCH` | CPU 架构：`arm`、`arm64`、`x86`、`x86_64` |
| `TARGET_PLATFORM` | API level，格式 `android-xx`，如 `android-23` |
| `TARGET_ARCH_ABI` | ABI：`armeabi-v7a`、`arm64-v8a`、`x86`、`x86_64` |
| `TARGET_ABI` | 同时限定 API 与 ABI，格式 `android-xx-<abi>`，如 `android-23-arm64-v8a` |

`armeabi` 从 NDK r17 起已被移除，不要再使用。

##### 模块描述变量

这些变量以 `LOCAL_` 开头，用于描述当前模块：

| 变量 | 用途 |
| :--- | :--- |
| `LOCAL_PATH` | 当前 `Android.mk` 所在路径，文件开头定义一次 |
| `LOCAL_MODULE` | 模块名，全局唯一、不能含空格 |
| `LOCAL_MODULE_FILENAME` | 可选，替换生成文件的默认名称（`libxxx`），不能改路径或扩展名 |
| `LOCAL_SRC_FILES` | 源文件列表，空格分隔，路径分隔符用 `/` |
| `LOCAL_CPP_EXTENSION` | 可选，指定 `.cpp` 之外的 C++ 扩展名，如 `.cxx` |
| `LOCAL_CPP_FEATURES` | 可选，声明依赖的 C++ 特性，如 `exceptions`、`rtti` |
| `LOCAL_C_INCLUDES` | 可选，头文件搜索路径，相对于 NDK 根目录 |
| `LOCAL_CFLAGS` | 可选，C/C++ 编译标记 |
| `LOCAL_CPPFLAGS` | 可选，仅 C++ 编译标记 |
| `LOCAL_STATIC_LIBRARIES` | 当前模块依赖的静态库模块列表 |
| `LOCAL_SHARED_LIBRARIES` | 当前模块运行时依赖的共享库模块列表 |
| `LOCAL_WHOLE_STATIC_LIBRARIES` | `LOCAL_STATIC_LIBRARIES` 的变体，链接器把相关静态库视为完整归档 |
| `LOCAL_LDLIBS` | 链接共享库/可执行文件时额外的链接器标记，如 `-llog` |
| `LOCAL_LDFLAGS` | 其他链接器标记 |
| `LOCAL_ALLOW_UNDEFINED_SYMBOLS` | 默认 `false`，对静态库无效；为 `false` 时遇到未定义符号会报错 |
| `LOCAL_ARM_MODE` | 设为 `arm` 时以 32 位 ARM 模式生成目标文件 |
| `LOCAL_ARM_NEON` | 仅在 `armeabi-v7a` 下有意义，控制 NEON 支持 |
| `LOCAL_DISABLE_FORMAT_STRING_CHECKS` | 默认开启格式字符串检查；不建议关闭 |
| `LOCAL_EXPORT_CFLAGS` | 导出给依赖模块的 C/C++ 编译标记 |
| `LOCAL_EXPORT_CPPFLAGS` | 导出给依赖模块的 C++ 编译标记 |
| `LOCAL_EXPORT_C_INCLUDES` | 导出给依赖模块的头文件路径 |
| `LOCAL_EXPORT_LDFLAGS` | 导出给依赖模块的链接器标记 |
| `LOCAL_EXPORT_LDLIBS` | 导出给依赖模块的系统库 |
| `LOCAL_SHORT_COMMANDS` | 源文件/依赖很多时设为 `true`，用 @ 语法缩短命令行 |
| `LOCAL_THIN_ARCHIVE` | 设为 `true` 生成瘦归档（只存对象文件路径） |
| `LOCAL_FILTER_ASM` | 过滤汇编文件的 shell 命令 |

##### NDK函数宏

函数宏的调用形式是 `$(call xxx)`：

| 函数宏 | 用途 |
| :--- | :--- |
| `my-dir` | 返回当前 `Android.mk` 所在目录 |
| `all-subdir-makefiles` | 返回当前目录下所有子目录中的 `Android.mk` 列表 |
| `this-makefile` | 返回当前 Makefile 的路径 |
| `parent-makefile` | 返回父级 Makefile 的路径 |
| `grand-parent-makefile` | 返回祖父级 Makefile 的路径 |
| `import-module` | 按模块名导入 `Android.mk`，调用形式 `$(call import-module,<name>)`，`<name>` 是相对于 `NDK_MODULE_PATH` 的路径 |

#### Application.mk脚本

`Application.mk` 指定 ndk-build 的项目级设置。它的很多变量有对应的 `LOCAL_*` 模块级版本，模块级配置优先级更高。

一个常见配置：

```make
APP_ABI := arm64-v8a armeabi-v7a
APP_PLATFORM := android-23
APP_STL := c++_shared
APP_CPPFLAGS := -std=c++17
```

常用变量：

| 变量 | 用途 |
| :--- | :--- |
| `APP_ABI` | 要生成的 ABI 列表，空格分隔；不写时使用 NDK 支持的默认 ABI 集合 |
| `APP_PLATFORM` | 目标 API level，对应 `minSdkVersion`；不写时使用 NDK 支持的最低 API |
| `APP_STL` | C++ 标准库。**默认是 `none`**；常用 `c++_shared`、`c++_static`；`system` 自 r18 起废弃 |
| `APP_CPPFLAGS` | 所有 C++ 编译的标记 |
| `APP_CFLAGS` | 所有 C/C++ 编译的标记 |
| `APP_CONLYFLAGS` | 仅 C 编译的标记 |
| `APP_CXXFLAGS` | 与 `APP_CPPFLAGS` 类似，出现在 `APP_CPPFLAGS` 之后 |
| `APP_LDFLAGS` | 链接可执行文件和共享库的标记 |
| `APP_ASFLAGS` | 汇编源文件（`.s`/`.S`）的编译标记 |
| `APP_ASMFLAGS` | YASM 源文件（`.asm`，仅 x86/x86_64）的标记 |
| `APP_BUILD_SCRIPT` | `Android.mk` 的路径（默认 `jni/Android.mk`），不是目录 |
| `APP_MODULES` | 显式指定要构建的模块列表，对应 `LOCAL_MODULE` |
| `APP_OPTIM` | `release` 或 `debug`，默认 `release` |
| `APP_DEBUG` | 设为 `true` 构建可调试版本 |
| `APP_MANIFEST` | `AndroidManifest.xml` 的绝对路径 |
| `APP_PROJECT_PATH` | 项目根目录的绝对路径 |
| `APP_SHORT_COMMANDS` | 对应 `LOCAL_SHORT_COMMANDS` |
| `APP_THIN_ARCHIVE` | 对应 `LOCAL_THIN_ARCHIVE` |
| `APP_STRIP_MODE` | 传给 `strip` 的参数，默认 `--strip-unneeded`；`none` 表示不剥离 |
| `APP_WRAP_SH` | 要打包的 `wrap.sh` 路径；每个 ABI 还有 `APP_WRAP_SH_<abi>` 变体 |
| `APP_CLANG_TIDY` | 设为 `true` 启用 clang-tidy |
| `APP_CLANG_TIDY_FLAGS` | clang-tidy 的参数 |

`APP_STL` 默认是 `none` 这一点经常被忽略：不设置它，`std::string`、`std::vector` 等符号可能链接失败。使用 C++ 标准库时显式写 `APP_STL := c++_shared` 或 `c++_static`。

## 关联Gradle

写好了 CMake 或 ndk-build 脚本，还要让 Gradle 在构建 APK 时调用它们。

### CMake配置

模块级 `build.gradle.kts`：

```kotlin
android {
    ndkVersion = "28.2.13676358" // 以 SDK Manager 安装的版本为准

    defaultConfig {
        minSdk = 23

        externalNativeBuild {
            cmake {
                arguments += "-DANDROID_STL=c++_shared"
                cppFlags += "-std=c++17"
            }
        }

        ndk {
            abiFilters.addAll(listOf("armeabi-v7a", "arm64-v8a", "x86_64"))
        }
    }

    externalNativeBuild {
        cmake {
            path = file("src/main/cpp/CMakeLists.txt")
        }
    }
}
```

- `path` 指向 `CMakeLists.txt`；`version` 可以省略，省略时使用 SDK Manager 安装的默认 CMake。
- `arguments` 传给 CMake，例如 `-DANDROID_STL=c++_shared`。
- `cppFlags` 传给 C++ 编译器，例如 `-std=c++17`。
- `abiFilters` 限制构建和打包的 ABI；不写时 AGP 会构建 NDK 支持的全部 ABI。
- `ndkVersion` 固定 NDK 版本，避免团队环境不一致。

### ndk-build配置

```kotlin
android {
    externalNativeBuild {
        ndkBuild {
            path = file("src/main/jni/Android.mk")
        }
    }
}
```

`ndkBuild` 可配置的项很少，常见的就是 `path` 和 `buildStagingDirectory`。这也是 ndk-build 逐渐被 CMake 取代的原因之一。

### 预构建so

如果已经有编译好的 `.so`，把它们按 ABI 放进 `src/main/jniLibs`：

```text
app/src/main/jniLibs/
├── arm64-v8a/libfoo.so
├── armeabi-v7a/libfoo.so
└── x86_64/libfoo.so
```

Gradle 会自动把 `jniLibs/<abi>/*.so` 打包进 APK，不需要额外配置。目录结构必须是“ABI 名/库文件”，不能把所有 `.so` 平铺在 `jniLibs` 根目录。

如果自定义了目录，用 `sourceSets` 指定：

```kotlin
android {
    sourceSets["main"].jniLibs.srcDirs("src/main/customJniLibs")
}
```

## ABI与打包

ABI（Application Binary Interface）决定 `.so` 能在哪些 CPU 架构上运行：

| ABI | 位数 | 场景 | 状态 |
| :--- | :--- | :--- | :--- |
| `arm64-v8a` | 64 | 现代 ARM 手机 | 主力，Google Play 要求 64 位 |
| `armeabi-v7a` | 32 | 老 ARM 设备 | 仍可用，但占比持续下降 |
| `x86_64` | 64 | 模拟器 | 常用 |
| `x86` | 32 | 老模拟器 | 逐步淘汰 |
| `armeabi` | 32 | 已移除 | NDK r17 起不再支持 |

默认情况下，AGP 会为 NDK 支持的所有 ABI 生成 `.so` 并全部打包，APK 会因此变大。两种控制方式：

- `abiFilters`：只构建/打包指定 ABI；
- App Bundle：上传 `.aab`，Google Play 按设备 ABI 下发对应的 split，不需要在 APK 里塞所有 ABI。

如果发的是 APK 而不是 AAB，可以用 `splits.abi` 生成按 ABI 拆分的 APK：

```kotlin
android {
    splits {
        abi {
            isEnable = true
            reset()
            include("arm64-v8a", "armeabi-v7a", "x86_64")
            isUniversalApk = false
        }
    }
}
```

## 16 KB页大小

Android 15 起，系统支持配置为 16 KB 内存页的设备。**含 Native 代码的应用必须按 16 KB 对齐重新编译**，否则在 16 KB 设备上可能 `dlopen` 失败。Google Play 对 targetSdk 35+ 的应用有 16 KB 兼容性要求，提交前以 Play Console 的兼容性提示为准。

不同 NDK 版本的处理方式：

- **NDK r28 及以上**：默认按 16 KB 对齐编译，不需要额外参数；
- **NDK r27 及以下**：需要加链接参数。

CMake：

```cmake
target_link_options(native-lib PRIVATE
    "-Wl,-z,max-page-size=16384"
    "-Wl,-z,common-page-size=16384")
```

ndk-build：

```make
LOCAL_LDFLAGS += -Wl,-z,max-page-size=16384 -Wl,-z,common-page-size=16384
```

AGP 8.5.1+ 在打包未压缩的共享库时也会自动做 16 KB 对齐；如果 AGP 较旧，需要升级，或临时开启 `useLegacyPackaging` 让 Gradle 压缩 `.so`。

除了对齐，还要检查代码里是否硬编码了 4 KB 页大小：

- 不要用 `PAGE_SIZE` 常量做内存对齐或 `mmap` 参数；NDK r27+ 在 16 KB 模式下已不再定义 `PAGE_SIZE`；
- 用 `getpagesize()` 或 `sysconf(_SC_PAGESIZE)` 在运行时获取；
- 自定义内存分配器不要用固定的 4 KB/8 KB 阈值。

验证方式：

```bash
# 设备页大小
adb shell getconf PAGE_SIZE

# APK 的 16 KB 对齐检查
zipalign -c -P 16 -v 4 app-release.apk

# 查看 ELF LOAD 段对齐（应为 0x4000）
llvm-readelf -l libnative-lib.so | grep LOAD
```

Android Studio 的 APK Analyzer 和 Lint 也会标记未对齐的 `.so`。第三方 SDK 里的预构建库同样要满足 16 KB 对齐，不能只检查自己编译的库。

## 调试与符号化

Native 调试使用 LLDB，Debug 类型选 `Detect Automatically` 或 `Dual` 即可同时调试 Java/Kotlin 和 C/C++。

崩溃日志里的 Native 栈通常是地址，需要符号化：

```bash
adb logcat | ndk-stack \
  -sym app/build/intermediates/merged_native_libs/debug/out/lib/arm64-v8a
```

`-sym` 指向包含未剥离 `.so` 的目录（不是 APK）。路径随 AGP 版本可能变化，找不到时在 `build/intermediates` 下搜索 `lib<abi>`。

也可以手动用 `llvm-addr2line`：

```bash
llvm-addr2line -e libnative-lib.so -f -C 0x1234
```

Release 包默认会 strip 符号。要定位线上崩溃，需要保留对应版本的未剥离 `.so` 和 mapping/native symbols，上传到崩溃平台；否则只能看到地址。

## 常见问题

| 现象 | 常见原因 | 处理 |
| :--- | :--- | :--- |
| `CMake Error: ... does not appear to contain CMakeLists.txt` | `path` 写错，或文件名不是 `CMakeLists.txt` | 检查 Gradle 的 `path` 和文件名 |
| `Cannot find source file: src/main/cpp/xxx.cpp` | CMake 相对路径以 `CMakeLists.txt` 为基准，重复写了 `src/main/cpp` | 改成 `xxx.cpp` 或用 `${CMAKE_CURRENT_SOURCE_DIR}` |
| `undefined reference to std::__cxx11...` | `APP_STL` 为 `none`，或静态/共享 STL 混用 | 设置 `APP_STL := c++_shared`，统一所有库的 STL |
| `UnsatisfiedLinkError: dlopen failed` | `.so` 没打包、ABI 不匹配、16 KB 未对齐 | 检查 `lib/<abi>/`、`abiFilters`、16 KB 对齐 |
| `armeabi` 构建失败 | NDK r17 起移除 `armeabi` | 改用 `armeabi-v7a` / `arm64-v8a` |
| 运行时找不到 `libc++_shared.so` | 用了 `c++_shared` 但手动打包时漏了该库 | 让 Gradle 打包，或手动把 `libc++_shared.so` 放进 `jniLibs` |
| 改了 C/C++ 代码不生效 | Gradle 没重新执行 native 构建 | Clean + Rebuild，或 Build → Refresh Linked C++ Projects |

NDK 构建的问题大多可以归为三类：**路径**（CMake 相对路径、Gradle `path`）、**ABI**（`abiFilters`、`jniLibs` 目录）、**符号**（JNI 名字、STL、strip）。按这三条排查，比盲目 Clean 有效得多。
