调试（debug）是开发流程中不可或缺的一环，主要作用是查找和定位 bug 的根源。Android 调试的核心手段有两类：

- **启动式调试（Debug）**：由 Android Studio 重新构建、安装并以调试模式启动应用，调试器在应用代码开始执行前接管，因此能覆盖 `Application.onCreate()`、`ContentProvider.onCreate()` 和启动页。
- **附加式调试（Attach）**：应用已经在运行，调试器在任意时刻附加到目标进程。它无法回溯附加之前已经执行过的代码，适合“应用跑到某一步才出问题”的场景。

两者的选择依据不是代码量，而是**问题发生在进程启动阶段，还是运行到某个交互之后**。

## 启动式调试

### 1. 打断点

在待调试代码的行号左侧单击，或把光标放在该行按 `Ctrl+F8`（macOS 为 `Command+F8`），出现红点即表示断点已设置。再次单击可取消。

断点不要打在注释、空行或只有右花括号的行上——这些位置没有可执行指令，断点不会生效。

### 2. 启动调试

在工具栏的目标设备下拉框里选好设备，点击 **Debug**（虫子图标）。如果应用已经在运行，Android Studio 会询问是否重启应用：选择重启才会进入启动式调试；选择取消后，再点 Attach 附加到正在运行的进程。

![[Screenshot 2020-12-11 115850.png]]

*图 1　Debug（虫子）与 Attach（虫子 + 箭头）按钮。截图为旧版界面，图标形状未变，位置可能随版本调整。*

启动时设备会弹出 “Waiting For Debugger” 对话框，提示进程正在等待调试器附加：

![[0DCE878C558CAAE8F7910358E5243FB9.jpg]]

*图 2　等待调试器附加。此时应用进程已经创建，但主线程被挂起，直到调试器连上才继续执行。*

如果长时间停在这个对话框，通常是 Android Studio 没有连上设备：检查 `adb devices` 与 USB 授权；如果用 Attach，确认选中的进程是当前应用。

### 3. 进入 Debug 工具窗口

调试会话建立后，底部会打开 **Debug** 工具窗口：

![[Screenshot 2020-12-11 120844.png]]

*图 3　Debug 工具窗口：上方是步进按钮，左侧是 Frames（调用栈），右侧是 Variables（变量）。截图为旧版界面，当前版本的窗格布局基本一致。*

窗口由几部分组成：

| 区域 | 作用 |
| :--- | :--- |
| 步进工具栏 | Step Over / Step Into / Force Step Into / Step Out / Run to Cursor / Resume / Pause / Stop |
| Frames | 当前线程的调用栈，点击某一帧可切换作用域 |
| 线程选择器 | Frames 上方的下拉框，切换当前线程；调试多线程时必须在这里切换 |
| Variables | 当前帧的 `this`、局部变量、静态变量 |
| Watches | 手动添加的监视表达式 |
| Console | 调试器输出、日志断点的输出 |

## 逐步执行

四个最常用的步进按钮：

| 按钮 | 快捷键 | 行为 | 适用场景 |
| :--- | :--- | :--- | :--- |
| Step Over | `F8` | 执行完当前行；如果当前行有方法调用，把整个方法执行完再停在下一行（方法内部的断点仍会命中） | 方法本身已确认没问题，只想往下走 |
| Step Into | `F7` | 执行到被调用方法的**第一行** | 需要看方法内部实现 |
| Force Step Into | `Alt+Shift+F7` | 强制进入 Step Into 默认会跳过的方法（无行号信息、库方法等） | 确认某个方法到底有没有被调用 |
| Step Out | `Shift+F8` | 把当前方法剩余部分执行完，回到调用处的下一行（内部断点仍会命中） | 方法内部已看清，快速返回调用方 |

两个容易混淆的点：

- **Step Into 不是“一直执行到方法退出”**，它只进入方法并停在第一行；要一次跑完当前方法，用 Step Out。
- **Step Over 也不是“跳过方法不执行”**，方法会完整执行，只是不逐行停在里面；如果方法内部有断点，仍然会中断。

除这四个之外，Debug 工具栏还提供：

| 操作 | 快捷键 | 作用 |
| :--- | :--- | :--- |
| Run to Cursor | `Alt+F9` | 继续运行到光标所在行，相当于临时断点；途中的已有断点仍会命中 |
| Evaluate Expression | `Alt+F8` | 对任意表达式求值，可调用方法（注意副作用） |
| Resume Program | `F9` | 放行到下一个断点 |
| Pause Program | — | 暂停当前应用，用于抓取“没有断点但想看看现场”的状态 |
| Stop | — | 结束调试会话（通常同时停止应用进程） |
| Drop Frame | — | 弹出当前栈帧，回到调用方重新执行 |
| Mark Object | — | 给某个对象打标签，之后在 Variables 里持续跟踪同一个实例 |

`Drop Frame` 只回退**栈帧**，不会回滚已经发生的副作用：已经写出的文件、发出的网络请求、修改过的成员变量都不会复原。用它重试一段纯计算逻辑可以，重试有副作用的代码要谨慎。

## 断点进阶

右键断点可以打开更细的配置；`Ctrl+Shift+F8`（macOS 为 `Command+Shift+F8`）打开 **Breakpoints** 窗口统一管理。

| 断点类型 | 设置位置 | 用途 |
| :--- | :--- | :--- |
| 行断点 | 行号左侧 | 最常用，执行到该行时暂停 |
| 方法断点 | 方法签名行 | 进入或退出方法时暂停；在 Compose 可组合函数上还会列出参数和状态 |
| 字段断点 | 字段声明行 | 读写该字段时暂停，适合查“谁改了它” |
| 异常断点 | Breakpoints 窗口 → Exception Breakpoints | 抛出指定异常时暂停 |
| 条件断点 | 右键断点 → Condition | 只在条件成立时暂停，适合循环和高频回调 |
| 日志断点 | 右键断点 → 取消 Suspend，勾选 Evaluate and log | 不暂停，把表达式结果写入 Logcat，替代临时 `Log.d` |
| 依赖断点 | 右键断点 → Disable until breakpoint is hit | 先命中另一个断点后才生效，用于锁定调用路径 |
| 命中计数 | 右键断点 → Pass count | 第 N 次命中才暂停 |

几个实用细节：

- 条件断点里写的是**表达式**，不要写 `if`，且结果必须是 `Boolean`。例如只在 `id == 5` 时停：

```kotlin
id == 5
```

- 日志断点里直接写要观察的表达式即可，不必再套一层 `Log.d`；输出会进入 Logcat（部分版本同时显示在 Debug 窗口的 Console）：

```kotlin
"item=$item, size=${list.size}"
```

- 异常断点不要选 **Any Exception**。框架内部会抛出大量被正常捕获的异常（类加载、资源查找等），全捕会让应用慢到几乎无法操作。只添加需排查的类型，例如 `NullPointerException`、`IllegalStateException`，或项目自定义的异常。
- 断点默认挂起**所有线程**（Suspend: All）。调试多线程或后台任务时，可以改成 **Thread**，只挂起当前线程，让其他线程继续跑。
- 临时不需要某组断点时，点 **Mute Breakpoints** 一次性静音，比逐个删除省事。

## 附加式调试

应用已经在运行时，点击 **Attach debugger to Android process**：

![[Screenshot 2020-12-11 123237.png]]

*图 4　Attach debugger to Android process 按钮。*

在弹出的 **Choose Process** 窗口中选择目标**进程**，而不是“应用程序”：

- 多进程应用会出现 `com.example.app`、`com.example.app:remote` 等多个条目，要选代码实际运行的那个；
- 未 root 的真机默认只显示**可调试**的进程；模拟器或 root 设备勾选 **Show all processes** 才能看到全部；
- 一个调试会话只连接一个进程；要同时调试多个进程，需要分别附加。

附加式调试有三个限制：

1. **不能回溯**。附加之前已经执行的代码不会再走一遍，所以要在触发操作**之前**把断点设好。
2. **不能调试启动代码**。`Application.onCreate()`、`ContentProvider.onCreate()` 在附加时早已执行完毕；这类问题要用启动式调试，或后面介绍的 `waitForDebugger`。
3. **release 变体默认不可附加**。必须让 build type 带 `debuggable true`；如果同时开了 R8，行号和局部变量可能被优化掉，断点会对不上。

## 让应用等待调试器

如果问题发生在启动阶段，等应用跑起来再 Attach 已经来不及。有三种办法让进程先停住等调试器。

### Debug.waitForDebugger()

在怀疑的启动代码前加一行：

```kotlin
import android.os.Debug

if (BuildConfig.DEBUG) {
    Debug.waitForDebugger()
}
```

进程执行到这一行会阻塞，直到调试器附加。**没有调试器时它会一直等**；如果调用发生在主线程，等同于主线程卡死，所以必须放在 debug 判断里，且问题查完后删除。

> AGP 8.0 起 `BuildConfig` 默认不生成。需要在模块的 `build.gradle.kts` 里开启 `buildFeatures { buildConfig = true }`，或改用 `(applicationInfo.flags and ApplicationInfo.FLAG_DEBUGGABLE) != 0` 判断。

### am set-debug-app

不改代码，让系统在应用启动时等待调试器：

```bash
adb shell am set-debug-app -w --persistent com.example.app
```

| 参数 | 作用 |
| :--- | :--- |
| `-w` | 启动时等待调试器附加 |
| `--persistent` | 每次启动都等待；不加则只生效一次 |

然后正常启动应用，看到 “Waiting For Debugger” 后再 Attach。调试结束后必须清除，否则应用每次启动都会卡在等待框：

```bash
adb shell am clear-debug-app
```

### am start -D

直接以调试模式启动指定 Activity：

```bash
adb shell am start -D -n com.example.app/.MainActivity
```

`-D` 表示等待调试器，效果与 `set-debug-app -w` 类似，但只作用于这一次启动。

## 调试前的准备

### 连接设备

- **USB**：在开发者选项中打开 USB 调试，首次连接时在设备上确认 RSA 指纹。
- **无线（Android 11+）**：开发者选项 → 无线调试 → 使用配对码配对设备；Android Studio 的 Device Manager 提供 Pair Devices Using Wi-Fi，也可以用命令行配对：

```bash
adb pair 192.168.1.10:37123    # 配对端口以设备屏幕为准
adb connect 192.168.1.10:5555 # 连接端口以设备屏幕为准
```

`adb devices` 中状态为 `device` 才能调试；显示 `unauthorized` 表示还没有在设备上确认授权。

### 可调试的构建

调试的前提是安装包带 `debuggable=true`。默认的 `debug` 变体已经满足；自定义 build type 需要显式打开：

```kotlin
android {
    buildTypes {
        create("customDebug") {
            isDebuggable = true
            // 调试阶段关闭混淆，避免行号和局部变量被优化掉
            isMinifyEnabled = false
        }
    }
}
```

`jniDebuggable` 已废弃，包含 C/C++ 的模块同样用 `isDebuggable` 控制。

不要在 `AndroidManifest.xml` 里手写 `android:debuggable="true"`：该属性由构建系统按 build type 注入，手写容易把可调试开关带进正式包。发布包必须是 `debuggable=false`。

`run-as` 也只有可调试应用才能用，常用来查看应用私有目录：

```bash
adb shell run-as com.example.app ls
```

## 日志、崩溃与 ANR

### Logcat

Android Studio 的 Logcat 支持按包名、级别、tag、关键字过滤，常用查询：

```text
package:mine level:ERROR
package:mine tag:MyTag
package:mine message:timeout
```

命令行等价操作：

```bash
# 清空后重新抓
adb logcat -c
adb logcat -v time

# 只看指定 tag
adb logcat -s MyTag

# 只看指定进程
adb logcat --pid="$(adb shell pidof -s com.example.app)"
```

### 崩溃栈

未捕获异常的典型结构如下，先确认第一行异常类型，再看 `Caused by` 链，最后定位到属于应用自身包名的堆栈：

```text
FATAL EXCEPTION: main
Process: com.example.app, PID: 12345
java.lang.NullPointerException: Attempt to invoke virtual method 'int java.lang.String.length()' on a null object reference
    at com.example.app.MainActivity.onCreate(MainActivity.kt:42)
    at android.app.Activity.performCreate(Activity.java:8051)
Caused by: java.lang.IllegalStateException: ...
    at com.example.app.Repo.load(Repo.kt:18)
```

### ANR

ANR（Application Not Responding）表示主线程在限定时间内没有响应输入、广播或服务调用。Logcat 中搜索 `ANR in`，能看到进程名、原因和 CPU 使用情况：

```text
ANR in com.example.app
Reason: Input dispatching timed out (Waiting to send key event because the focused window has not finished processing...)
```

进一步抓现场：

```bash
# 最近一次 ANR 的概要
adb shell dumpsys activity lastanr

# 完整报告（含 ANR traces、系统状态）
adb bugreport
```

现代 Android 的 traces 不再是一个固定的 `traces.txt`，而是 `/data/anr/anr_*` 下的多个文件；普通应用无权限读取，需要 root 或从 bugreport 里取。Android 11（API 30）起还可以用 `ApplicationExitInfo` 读取 `REASON_ANR` 及关联的 trace。

常见 ANR 原因：主线程做磁盘/网络 I/O、主线程等锁、BroadcastReceiver 的 `onReceive()` 超时、Service 启动超时、Binder 调用阻塞。`StrictMode` 可以在开发期提前暴露主线程 I/O：

```kotlin
if (BuildConfig.DEBUG) {
    StrictMode.setThreadPolicy(
        StrictMode.ThreadPolicy.Builder()
            .detectDiskReads()
            .detectDiskWrites()
            .detectNetwork()
            .penaltyLog()
            .build()
    )
}
```

## App Inspection 与 Profiler

`View > Tool Windows > App Inspection` 下集中了几个运行时检查工具：

| 工具 | 用途 | 前提 |
| :--- | :--- | :--- |
| Layout Inspector | 查看 View/Compose 层级、属性；Compose 还能看重组次数 | 可调试应用 |
| Database Inspector | 查看、修改 SQLite/Room 数据，执行 SQL | API 26+，可调试应用 |
| Network Inspector | 查看应用的网络请求与响应 | 可调试应用 |
| Background Task Inspector | 查看 WorkManager、JobScheduler、AlarmManager 任务 | API 26+，WorkManager 2.5+ |
| Profiler | CPU、内存、网络、电量采样 | 可调试或 profileable 应用 |

Database Inspector 的修改会实时反映到运行中的应用；Layout Inspector 也可以开启 Live Updates 持续刷新界面层级。Profiler 的采样本身有开销，调试态还会进一步放大开销，性能数据应来自 profileable 的构建，而不是挂着调试器的 debug 包。

## 常见问题

| 现象 | 常见原因 | 处理 |
| :--- | :--- | :--- |
| 断点灰色、不暂停 | 行上没有可执行代码；build 不是 debuggable；R8 优化掉了 | 换到实际语句；切 debug 变体；调试时关闭 minify |
| 提示 No executable code found at line | 行号映射不到字节码，常见于内联函数、Compose 生成代码、旧安装包 | Clean + Rebuild；在调用处或 lambda 体内下断点 |
| Attach 列表里没有应用 | 应用不可调试；进程未启动；USB 未授权 | 用 debug 变体；先启动应用；`adb devices` 确认状态 |
| 调试时应用极卡甚至 ANR | 断点挂起所有线程；日志断点/条件断点过多 | Suspend 改为 Thread；删掉不必要的断点；用日志断点代替暂停 |
| 内存曲线异常 | 调试器会阻止它发现的对象被 GC | 以非调试运行的数据为准 |
| 多进程断点不命中 | 附加到了主进程，代码在 `:remote` | 在 Choose Process 里选对应进程 |
| 协程断点跳线程 | suspend 恢复后可能换到另一个线程 | 看 Frames/Threads；用条件断点缩小范围 |
| release 包无法调试 | 不可调试或被 R8 混淆 | 临时 `isDebuggable = true` + `isMinifyEnabled = false`，不要发布 |

Compose 还有一个额外注意点：可组合函数在重组时会反复执行，断点可能高频命中。优先用条件断点限定状态，或在方法断点上查看参数与状态，而不是在 Composable 里直接停。

## Native 调试

项目包含 C/C++ 时，Debug 配置的 **Debug type** 决定调试器：

| 类型 | 行为 |
| :--- | :--- |
| Detect Automatically | 有原生代码时自动用 Dual，否则用 Java Only |
| Java Only | 只调 Java/Kotlin 调试器，忽略原生断点 |
| Native Only | 只用 LLDB，Java 断点不生效 |
| Dual | Java 调试器 + LLDB 同时连接，可在两类断点间切换 |

Native 调试要求设备支持 `run-as` 且启用了 `ptrace`：

```bash
adb shell run-as com.example.app pwd
adb shell sysctl kernel.yama.ptrace_scope
```

第二条输出 `0` 或 `unknown key` 才可用；输出其他值说明 ptrace 被限制。原生代码要用 Debug 配置编译（`-O0`/`Debug`），否则会提示 “This function was compiled with optimizations enabled”，变量和行号都可能不准。

## ADB 速查

```bash
# 设备与进程
adb devices
adb shell pm list packages | grep example
adb shell pidof com.example.app

# 启动/停止/清数据
adb shell am start -n com.example.app/.MainActivity
adb shell am force-stop com.example.app
adb shell pm clear com.example.app

# 当前页面与内存
adb shell dumpsys activity top
adb shell dumpsys meminfo com.example.app

# 截图（exec-out 可避免 Windows 下 CRLF 破坏 PNG）
adb exec-out screencap -p > screen.png
```
