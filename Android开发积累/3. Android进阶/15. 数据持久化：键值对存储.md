在 Android 开发中，将数据本地持久化的一种方式，是以 key-value 的形式保存在特定文件中。这种键值对保存数据的方式适用于保存一些简单的配置信息，比如语言、主题或者设置开关等等。如果要保存极为复杂或者体量极为庞大的数据，正常情况下应该选择数据库，而非本章所介绍的键值对数据保存方式。

Android 设备常用的键值对数据存储方案有 SharedPreferences、DataStore 和 MMKV。其中 SharedPreferences 和 DataStore 都是由 Google 官方先后推出，而 MMKV 则是由腾讯开源的。以下逐一说明其适用场景与基本用法。

## SharedPreferences

SharedPreferences 是 Android 设备上最常用也最古老的键值对数据存储方案，可实现简单的数据持久化保存（`.xml` 文件），前提是用户没有特意删除数据，以及硬件设备没有被破坏。

它支持 `boolean`、`float`、`int`、`long`、`String` 以及 `Set<String>` 这几种类型，其他自定义的复合类型**无法直接存储**，一般只能先序列化成字符串或字节数组再保存。

SharedPreferences 将数据保存在自己创建的文件当中，通过保存上一次用户所做的修改或者自定义参数设定，使得程序再次启动后能够依然保持原有设置。通过使用键值对的方式进行存储，SharedPreferences 可以方便地管理写入和读取。

### 基本使用

SharedPreferences 对象的获取方式有两种：

```kotlin
// Activity 中可以直接调用 Context 的方法
val sp = getSharedPreferences("settings", Context.MODE_PRIVATE)

// 非 Activity 需要传入 Context
val sp = context.getSharedPreferences("settings", Context.MODE_PRIVATE)
```

第一个参数是文件名，不是 key；同一个名字在同一个进程中只会有一个 SharedPreferences 实例。

如果只是读取数据，调用对应的 `get` 方法即可：

```kotlin
val theme = sp.getString("theme", "light") ?: "light"
val notifications = sp.getBoolean("notifications", true)
val launchCount = sp.getInt("launch_count", 0)
val tags = sp.getStringSet("tags", emptySet()) ?: emptySet()
```

`getString()` 和 `getStringSet()` 的返回值可能为 `null`，所以通常还要补一个 `?:`。另外不要直接修改 `getStringSet()` 返回的集合，需要修改时先复制一份。

写入数据必须通过 `Editor`：

```kotlin
sp.edit()
    .putString("theme", "dark")
    .putBoolean("notifications", false)
    .putStringSet("tags", setOf("android", "kotlin"))
    .apply()
```

写入之后必须调用 `apply()` 或 `commit()`，否则修改不会生效。两者的区别如下：

| 对比项 | `apply()` | `commit()` |
| :--- | :--- | :--- |
| 返回值 | 无 | `Boolean`，表示是否写入成功 |
| 内存 | 同步更新 | 同步更新 |
| 磁盘 | 异步写入 | 同步写入，阻塞调用线程 |
| 主线程 | 推荐使用 | 可能阻塞主线程，严重时 ANR |
| 适用场景 | 普通配置写入 | 需要确认写入结果、测试、进程退出前必须落盘 |

需要注意，`apply()` 只是把“写磁盘”变成异步，内存中的值会立即更新，所以同一个进程里紧接着读取能读到新值。

只应使用 `MODE_PRIVATE`。`MODE_WORLD_READABLE` 和 `MODE_WORLD_WRITEABLE` 自 API 17 起废弃，在 targetSdk 24 及以上使用会直接抛 `SecurityException`；`MODE_MULTI_PROCESS` 自 API 23 起废弃，行为不可靠，不要用它做跨进程共享。

监听某个 key 的变化：

```kotlin
val listener = SharedPreferences.OnSharedPreferenceChangeListener { prefs, key ->
    // key 发生变化
}
sp.registerOnSharedPreferenceChangeListener(listener)

// 不需要时注销
sp.unregisterOnSharedPreferenceChangeListener(listener)
```

SharedPreferences 内部对监听器是弱引用，`listener` 必须由外部持有强引用，否则可能被 GC 回收后收不到回调。

### SharedPreferences的缺陷

SharedPreferences 虽然很轻量，使用方式比较简单，但也正因为如此，其定位就不是用来存储大体量的复杂数据，所以在存储大体量复杂数据的时候就会暴露出以下显著缺陷：

- **内存占用**

每当用户获取到一个 SharedPreferences 对象时，该对象都会被系统在进程内缓存起来（`ContextImpl` 的静态缓存），同一文件名复用同一实例，直至应用进程被终结。

另一个问题是，每个 SharedPreferences 对象对应一个 `.xml` 文件，文件里的键值对数据会全部加载到内存中，直至应用进程被终结。设备配置较高或数据量较少时影响不大，但低端设备加上大量键值对时，内存占用就会很突出。

- **线程阻塞**

SharedPreferences 在初始化时会异步从磁盘加载 `.xml` 文件，加载时间无法保证。如果初始化后立即调用 `getString()` 等读取方法，调用线程会等待加载完成；如果发生在主线程，阻塞时间过长就可能引发 ANR。

- **类型安全**

SharedPreferences 自身没有机制保证同一个 key 的读写类型一致，完全依赖开发者自觉。如果写入时是 `String`，读取时却调用 `getInt()`，编译期不会报错，运行时抛 `ClassCastException`。

- **多进程支持**

SharedPreferences 不支持可靠的多进程共享。早期的 `MODE_MULTI_PROCESS` 已被废弃，且不保证并发安全。跨进程共享应使用 ContentProvider、AIDL，或明确支持多进程的 MMKV。

- **全量更新**

SharedPreferences 每次提交都会重写整个 `.xml` 文件，哪怕只改了一个键值对。数据量大时，这种全量写入会带来不必要的 I/O 开销。

- **可读性和可维护性**

在较复杂的业务中，key 往往直接硬编码在各个业务逻辑里，没有机制保证每次声明的 key 一致；key 命名不规范时，还会让键值对的含义变得难以维护。

## Jetpack DataStore

[Jetpack DataStore](https://developer.android.google.cn/jetpack/androidx/releases/datastore?hl=zh-cn) 是 Google 在 2020 年推出的数据存储方案，当前稳定版为 **1.3.0**。按照 Google 官方的说法，DataStore“以异步、一致的事务方式存储数据，克服了 SharedPreferences 的一些缺点”，采用的异步方案是 Kotlin 协程和 Flow。

DataStore 提供了两种实现：

- **Preferences DataStore**：键值对存储，不需要预定义 schema，但和 SharedPreferences 一样不保证类型安全；
- **Proto DataStore**：把数据作为自定义类型的实例存储，需要用[协议缓冲区](https://developers.google.cn/protocol-buffers?hl=zh-cn)定义 schema，类型安全由 protobuf 保证。

Proto DataStore 的构建过程较复杂，这里只讨论 Preferences DataStore；下文没有额外说明时，DataStore 均指 Preferences DataStore。

### 依赖

DataStore 不在 Android SDK 中，需要以依赖库方式引入：

```kotlin
dependencies {
    implementation("androidx.datastore:datastore-preferences:1.3.0")

    // 可选：不依赖 Android 的 core，供非 Android 模块或测试使用
    implementation("androidx.datastore:datastore-preferences-core:1.3.0")

    // 可选：RxJava2 / RxJava3 支持
    implementation("androidx.datastore:datastore-preferences-rxjava2:1.3.0")
    implementation("androidx.datastore:datastore-preferences-rxjava3:1.3.0")
}
```

### 创建实例

DataStore 对象的创建方式跟 SharedPreferences 有很大不同。官方推荐的写法是把实例声明为 `Context` 的扩展属性，并用 `preferencesDataStore` 代理创建：

```kotlin
private val Context.dataStore: DataStore<Preferences> by preferencesDataStore(name = "settings")
```

这个属性必须**位于顶层**，并且在一个文件中只创建一次。Google 在注释中的解释是：

> This should only be called once in a file (at the top level), and all usages of the DataStore should use a reference the same Instance. The receiver type for the property delegate must be an instance of Context.

也就是说，DataStore 对象需要通过 `preferencesDataStore` 函数、采用代理方式创建，在一个文件中只有一次调用，并且位于顶层，以确保它是单例的。把它声明为 `Context` 扩展属性，是为了让代理函数能拿到 `Context` 接收器（例如迁移时需要用它访问 SharedPreferences）。

同一个文件不能创建多个 DataStore 实例，否则读写时会抛 `IllegalStateException`（提示同一个文件存在多个活跃的 DataStore）。

### 读写

先定义 key。Preferences 的 key 不是普通字符串，而是带类型的 `Preferences.Key<T>`，由一组顶层工厂函数创建：

```kotlin
private object SettingsKeys {
    val THEME = stringPreferencesKey("theme")
    val NOTIFICATIONS = booleanPreferencesKey("notifications")
    val LAUNCH_COUNT = intPreferencesKey("launch_count")
}
```

常用的工厂函数包括 `intPreferencesKey`、`longPreferencesKey`、`floatPreferencesKey`、`doublePreferencesKey`、`booleanPreferencesKey`、`stringPreferencesKey`、`stringSetPreferencesKey` 和 `byteArrayPreferencesKey`。

读取通过 `data` 属性完成，它返回的是 `Flow<Preferences>`：

```kotlin
val theme: Flow<String> = context.dataStore.data
    .catch { error ->
        if (error is IOException) emit(emptyPreferences()) else throw error
    }
    .map { prefs -> prefs[SettingsKeys.THEME] ?: "light" }
```

`data` 在读取失败时会抛 `IOException`（例如文件损坏），因此需要 `catch`。如果希望文件损坏时自动重建，可以在创建 DataStore 时传入 `ReplaceFileCorruptionHandler`：

```kotlin
private val Context.dataStore: DataStore<Preferences> by preferencesDataStore(
    name = "settings",
    corruptionHandler = ReplaceFileCorruptionHandler { emptyPreferences() }
)
```

`data` 是冷流：每次收集都会读取当前值，并持续发射后续更新。Flow 的详细用法见[[8. Kotlin协程：进阶部分#Kotlin Flow|Kotlin Flow]]。

写入通过 `edit` 完成：

```kotlin
suspend fun setTheme(context: Context, theme: String) {
    context.dataStore.edit { prefs ->
        prefs[SettingsKeys.THEME] = theme
    }
}
```

`edit` 的源码如下：

```kotlin
public suspend fun DataStore<Preferences>.edit(
    transform: suspend (MutablePreferences) -> Unit
): Preferences {
    return this.updateData {
        it.toMutablePreferences().apply { transform(this) }
    }
}
```

Google 在注释中说明了它的语义：

> Edit the value in DataStore transactionally in an atomic read-modify-write operation. All operations are serialized.
>
> The coroutine completes when the data has been persisted durably to disk (after which DataStore.data will reflect the update). If the transform or write to disk fails, the transaction is aborted and an exception is thrown.

因此：

- `edit` 是**挂起函数**，必须在协程中调用；
- 整个读-改-写是**原子事务**，所有操作串行执行；
- 协程只有在数据真正持久化到磁盘后才结束；
- 转换或写盘失败会终止事务并抛异常，不会留下写了一半的数据。

`edit` 底层调用 `updateData`：

```kotlin
public suspend fun updateData(transform: suspend (t: T) -> T): T
```

`updateData` 的转换函数本身也是挂起函数，因此可以在里面做 RPC 之类的耗时操作；`edit` 只是它的 Preferences 专用封装，日常增删改键值对用 `edit` 就够了。

如果只需要读一次、不打算持续观察，可以用 `first()`：

```kotlin
val theme = context.dataStore.data.first()[SettingsKeys.THEME] ?: "light"
```

### 从 SharedPreferences 迁移

`preferencesDataStore` 的 `produceMigrations` 参数可以挂迁移逻辑：

```kotlin
private val Context.dataStore: DataStore<Preferences> by preferencesDataStore(
    name = "settings",
    produceMigrations = { context ->
        listOf(SharedPreferencesMigration(context, "settings"))
    }
)
```

迁移成功后，DataStore 会清理对应的 SharedPreferences；如果删除失败，迁移本身不会因此抛 `IOException`。迁移的核心就是 `SharedPreferencesMigration`，传入的 `context` 来自扩展属性的接收器。

DataStore 文件位于应用[[10. IO操作：在Android中使用#内部存储|内部存储空间]]的 `files/datastore/` 目录下，文件名为 `<name>.preferences_pb`。它是 protobuf 编码的**二进制文件**，不能像 XML 那样直接当文本查看；需要检查内容时，应通过 DataStore API 读取，或用 protobuf 工具解析。

### 多进程

DataStore 1.1 起提供了多进程支持（`MultiProcessDataStoreFactory`），可以让多个进程访问同一个文件并保持可观察性。但它的配置比 MMKV 繁琐，普通单进程应用通常不需要关心；如果核心诉求就是跨进程高频读写，MMKV 更直接。

## MMKV

[MMKV](https://github.com/Tencent/MMKV) 是腾讯于 2018 年开源的一个键值对数据存储方案。MMKV 名字来源于 Memory Mapped Key-Value 的缩写，采用 Linux 的 mmap（内存映射）原理，适用于**高频同步读写**的场景。

### 工作原理

MMKV 的核心是把文件映射到进程的地址空间，让文件磁盘地址和进程虚拟地址空间中的一段虚拟地址建立一一对应关系。建立映射后，进程可以像访问内存一样读写这段区域，操作系统会负责把脏页回写到文件，从而省去显式的 `read` / `write` 系统调用。内核空间对这段区域的修改也会反映到用户空间，因此可以实现不同进程间的文件共享。

mmap 并不等于“绝对不会丢数据”：进程崩溃时仍可能有部分页没有回写。MMKV 通过 CRC 校验和文件恢复机制来降低损坏风险，但重要数据仍应交给数据库或服务端。

详细的设计原理可以参考 MMKV 开发团队的[介绍](https://github.com/Tencent/MMKV/wiki/design)。

### 依赖与初始化

MMKV 当前稳定版为 **2.4.3**：

```kotlin
dependencies {
    implementation("com.tencent:mmkv:2.4.3")
}
```

> MMKV 2.x 只支持 64 位架构、minSdk 23；如果需要 32 位或 API 21–22，请使用 1.3.x LTS 系列。

在自定义 `Application` 中初始化 MMKV 的根目录（默认是 `files/mmkv/`）：

```kotlin
class App : Application() {
    override fun onCreate() {
        super.onCreate()
        val rootDir = MMKV.initialize(this)
        println("mmkv root: $rootDir")
    }
}
```

### 基本使用

使用全局单例存取键值对：

```kotlin
val kv = MMKV.defaultMMKV()

kv.encode("theme", "dark")
val theme = kv.decodeString("theme", "light")

kv.encode("launch_count", 1)
val count = kv.decodeInt("launch_count", 0)

kv.encode("tags", setOf("android", "kotlin"))
val tags = kv.decodeStringSet("tags", emptySet())
```

MMKV 的写入是即时的，`encode` 之后不需要 `apply()` 或 `commit()`。读取时通过不同的 `decodeXxx` 方法区分类型，因此类型安全仍然要由开发者保证：同一个 key 用 `encode` 写入 `String`，却用 `decodeInt` 读取，就会得到错误结果或异常。

`decodeString()` 在 key 不存在时返回 `null`，基本类型的无默认值重载则返回 `0` / `false`。需要明确的兜底值时，优先使用带默认值的重载。

常用 API：

| 操作 | API |
| :--- | :--- |
| 写入 | `encode(key, value)`，支持 boolean、int、long、float、double、String、ByteArray、Set\<String>、Parcelable |
| 读取 | `decodeBool` / `decodeInt` / `decodeLong` / `decodeFloat` / `decodeDouble` / `decodeString` / `decodeBytes` / `decodeStringSet` / `decodeParcelable` |
| 判断存在 | `containsKey(key)` |
| 删除单个 | `removeValueForKey(key)` |
| 删除多个 | `removeValuesForKeys(keys)` |
| 全部 key | `allKeys()` |
| 清空 | `clearAll()` |
| 从 SharedPreferences 导入 | `importFromSharedPreferences(sp)` |

MMKV 实现了 `SharedPreferences` 和 `SharedPreferences.Editor` 接口，所以已有代码可以较低成本地从 SharedPreferences 迁移：

```kotlin
val kv = MMKV.mmkvWithID("settings")
kv.importFromSharedPreferences(oldPrefs)
oldPrefs.edit().clear().apply()
```

### 多进程

`MMKV.defaultMMKV()` 是单进程实例。需要跨进程共享时，必须用 `mmkvWithID` 显式指定 `MULTI_PROCESS_MODE`：

```kotlin
val kv = MMKV.mmkvWithID("settings", MMKV.MULTI_PROCESS_MODE)
```

只写 `MMKV.mmkvWithID("settings")` 仍然是单进程模式，多个进程同时写同一个文件并不安全。这是 MMKV 最常见的误用之一。

## 选型

| 对比项 | SharedPreferences | DataStore | MMKV |
| :--- | :--- | :--- | :--- |
| 读写模型 | 同步 API，`apply()` 异步落盘 | `suspend` / `Flow` | 同步 mmap |
| 类型安全 | 无 | Preferences 无，Proto 有 | 无 |
| 多进程 | 不支持 | 1.1+ 提供多进程工厂 | 支持，需 `MULTI_PROCESS_MODE` |
| 写入方式 | 全量重写 XML | 全量原子替换 | 增量追加 |
| 适合场景 | 老项目、少量配置 | 新项目、协程/Flow、需要事务语义 | 高频写、多进程、较大体量 KV |
| 依赖 | 系统内置 | AndroidX | 第三方 |

新项目优先考虑 DataStore；确实需要多进程或极致写入性能时用 MMKV；老项目的 SharedPreferences 可以保留，遇到性能或类型安全问题再逐步迁移。
