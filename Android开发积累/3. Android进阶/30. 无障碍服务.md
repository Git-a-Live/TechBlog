`AccessibilityService` 是系统托管的后台服务：它接收全系统的界面事件，读取跨应用的节点树，并代替用户执行点击、输入、滚动与手势。它的设计目标是辅助工具（读屏、开关控制、语音操作），因此获得了普通应用无法企及的权限——也正是这些权限，让它成为自动化脚本、辅助点击、应用保活等需求的技术底座。

官方对它的定位有一句明确限定：无障碍服务是专用工具，不是让应用具备无障碍能力的标准方法。想让自己的界面能被 TalkBack 正确朗读，用的是语义（Compose 的 `semantics`、View 的 `contentDescription`）；只有要做通用辅助工具时，才需要构建无障碍服务。

## 两类不同的工作

|类型|目标|技术手段|权限|
|:--|:--|:--|:--|
|应用内无障碍适配|让自己的界面可被读屏正确理解|语义树、内容描述、焦点顺序|无|
|无障碍服务|跨应用读取界面、代替用户操作|`AccessibilityService` + 节点树 + 手势注入|用户手动启用|

两者常被混为一谈。适配属于 UI 质量，任何应用都应该做；服务属于系统级能力，需要用户显式授权，且承担隐私与审核风险。用无障碍服务去实现「自动点击自己应用内的按钮」是错误选型，语义化 + 正常事件回调即可。

## 声明与启用

服务必须在清单中声明，并用系统权限保护，确保只有系统能绑定：

```xml
<service
    android:name=".accessibility.MyAccessibilityService"
    android:exported="true"
    android:label="@string/accessibility_service_label"
    android:permission="android.permission.BIND_ACCESSIBILITY_SERVICE">
    <intent-filter>
        <action android:name="android.accessibilityservice.AccessibilityService" />
    </intent-filter>
    <meta-data
        android:name="android.accessibilityservice"
        android:resource="@xml/accessibility_service_config" />
</service>
```

`BIND_ACCESSIBILITY_SERVICE` 由系统持有，第三方应用无法绑定到该服务。声明之后服务仍不会运行，用户必须在「设置 → 无障碍」中手动启用——没有运行时权限弹窗，也没有 API 可以直接开启。

```kotlin
// 跳转到无障碍设置页，由用户自行开启
startActivity(Intent(Settings.ACTION_ACCESSIBILITY_SETTINGS))

// 判断自身是否已被启用
val am = getSystemService(AccessibilityManager::class.java)
val enabled = am.getEnabledAccessibilityServiceList(AccessibilityServiceInfo.FEEDBACK_ALL_MASK)
    .any { it.resolveInfo.serviceInfo.packageName == packageName }
```

检测结果只用于引导与状态展示，不能作为「用户已授权」的持续断言：用户随时可能在设置中关闭服务，服务也可能被系统回收后重建。运行时的可靠性依赖 `onServiceConnected` 与 `onUnbind`，而不是启动时的一次查询。

## 服务配置

`res/xml/accessibility_service_config.xml` 定义服务监听什么、能做什么：

```xml
<accessibility-service xmlns:android="http://schemas.android.com/apk/res/android"
    android:description="@string/accessibility_service_description"
    android:accessibilityEventTypes="typeWindowStateChanged|typeWindowContentChanged"
    android:packageNames="com.example.target"
    android:notificationTimeout="100"
    android:accessibilityFeedbackType="feedbackGeneric"
    android:accessibilityFlags="flagReportViewIds|flagRetrieveInteractiveWindows"
    android:canRetrieveWindowContent="true"
    android:canPerformGestures="true"
    android:isAccessibilityTool="false"
    android:settingsActivity="com.example.app.SettingsActivity" />
```

|属性|作用|工程含义|
|:--|:--|:--|
|`accessibilityEventTypes`|订阅的事件类型|`typeAllMask` 会收到全系统所有事件，开销显著，应按需精确声明|
|`packageNames`|只接收指定包名的事件|留空表示所有应用，是最容易被审核质疑的配置|
|`notificationTimeout`|同类型事件的最小间隔（毫秒）|系统侧的第一层节流，但仍需业务侧去抖|
|`canRetrieveWindowContent`|是否允许读取窗口内容|节点树相关能力的前提，运行时不可更改|
|`canPerformGestures`|是否允许注入手势|`dispatchGesture` 的前提|
|`isAccessibilityTool`|是否声明为辅助残障用户的工具|默认 false；false 时系统会在一段时间后向用户发送隐私提醒通知|
|`settingsActivity`|服务详情页的「设置」入口|缺失时设置页上的设置按钮不可用|
|`accessibilityFlags`|能力开关组合|`flagReportViewIds` 才能拿到 view id，`flagRetrieveInteractiveWindows` 才能访问多窗口|

运行时可用 `setServiceInfo()` 调整事件类型、包名、超时等参数，用于按业务场景收窄监听范围；`canRetrieveWindowContent` 这类能力声明不在可动态修改之列。

## 生命周期与线程模型

无障碍服务本质仍是 Service，区别在于绑定方是系统而不是应用（见 [[5. Service|Service]]）；读屏类服务把节点文本交给语音引擎朗读（见 [[28. TTS能力开发|TTS]]）。

|回调|时机|注意事项|
|:--|:--|:--|
|`onServiceConnected()`|系统绑定成功|初始化、`setServiceInfo()`、注册控制器回调|
|`onAccessibilityEvent(event)`|匹配配置的事件发生|主线程回调，频率可能很高|
|`onInterrupt()`|系统要求中断反馈|读屏类服务在此停止语音输出|
|`onUnbind(intent)`|服务被解绑|释放资源，返回 false 表示不保留绑定|
|`onDestroy()`|服务销毁|清理监听器与协程|

绑定由系统发起：服务被启用后系统绑定它，进程被回收后系统会重新绑定并再次回调 `onServiceConnected`。应用不需要、也不应该用前台服务或相互唤醒去「保活」一个无障碍服务——这既无效，也会触发商店审核与系统限制。

`onAccessibilityEvent` 在主线程执行，而事件频率以窗口内容变化计可以达到每秒数十次。把节点遍历、网络请求、数据库写入放在回调里会直接造成界面卡顿与 ANR。常见处理是把事件压入队列，按 `windowId` 与事件类型合并后，在后台线程处理，只保留最后一次有效状态。

事件是通知，不是快照：回调触发时界面可能已经再次变化，`event.source` 可能返回 null 或过期节点。可靠的流程是收到事件后重新取 `rootInActiveWindow`，再按需遍历，而不是长期持有节点引用。

## 事件与节点树

常用事件类型：

|事件|触发时机|典型用途|
|:--|:--|:--|
|`TYPE_WINDOW_STATE_CHANGED`|Activity、对话框、页面切换|识别当前前台界面|
|`TYPE_WINDOW_CONTENT_CHANGED`|窗口内容变化|列表刷新、文本更新；频率最高，必须节流|
|`TYPE_VIEW_CLICKED`|控件被点击|行为埋点、操作确认|
|`TYPE_VIEW_FOCUSED`|控件获得焦点|焦点跟随|
|`TYPE_VIEW_TEXT_CHANGED`|可编辑文本变化|输入监听；涉及隐私，谨慎处理|
|`TYPE_WINDOWS_CHANGED`|窗口层级变化|需 `flagRetrieveInteractiveWindows` 才会收到|

节点树是界面内容的抽象表示，入口有三个：

- `event.source`：事件来源节点，可能为 null；
- `rootInActiveWindow`：当前活动窗口的根节点，窗口不可用时为 null；
- `getWindows()`：所有可交互窗口，需要 `flagRetrieveInteractiveWindows`；未设置该 flag 时返回空列表，`AccessibilityNodeInfo.getWindow()` 也返回 null。

遍历与查找：

```kotlin
val root = rootInActiveWindow ?: return
// 按文本查找
val byText = root.findAccessibilityNodeInfosByText("确定")
// 按 view id 查找，需要 flagReportViewIds，且 id 必须是完全限定名
val byId = root.findAccessibilityNodeInfosByViewId("com.example.target:id/confirm")
```

节点是某个时刻的快照。跨事件持有 `AccessibilityNodeInfo` 会在界面重建后失效，表现为 `performAction` 返回 false 或属性读到旧值；需要最新状态时调用 `refresh()`，失败则重新从根节点查找。

`recycle()` 在 API 33 起废弃且调用无效——对象池机制已取消。官方文档中的示例仍保留 `recycle()`，属于历史写法；新代码不必调用，也不必为「忘记回收」而担忧。

节点上的关键属性决定了能做什么：`isClickable`、`isEditable`、`isScrollable`、`isCheckable`、`isEnabled`、`text`、`contentDescription`、`viewIdResourceName`、`boundsInScreen`。`boundsInScreen` 是手势坐标的来源，也是判断元素是否在屏幕内的依据。

`flagIncludeNotImportantViews` 会让被标记为 `importantForAccessibility="no"` 的节点也出现在树中。默认过滤是有意为之：装饰性视图不参与无障碍，包含它们只会增加遍历成本。

## 操作与手势

节点级别的操作通过 `performAction` 完成：

|Action|作用|前提|
|:--|:--|:--|
|`ACTION_CLICK`|点击|`isClickable` 为 true|
|`ACTION_LONG_CLICK`|长按|`isLongClickable` 为 true|
|`ACTION_SET_TEXT`|设置文本|`isEditable` 为 true，需传 Bundle 参数|
|`ACTION_SCROLL_FORWARD` / `BACKWARD`|滚动|`isScrollable` 为 true|
|`ACTION_FOCUS` / `ACTION_ACCESSIBILITY_FOCUS`|输入焦点 / 无障碍焦点|目标可聚焦|

```kotlin
val args = Bundle().apply {
    putCharSequence(
        AccessibilityNodeInfo.ACTION_ARGUMENT_SET_TEXT_CHARSEQUENCE,
        "hello"
    )
}
node.performAction(AccessibilityNodeInfo.ACTION_SET_TEXT, args)
```

`performAction` 返回布尔值，只表示请求是否被接受，不保证界面已经变化。可靠的实现会在操作后校验状态（节点文本、窗口变化事件），失败时重新查找节点并有限次重试。

节点点不动的原因集中在四处：节点不可点击（真正可点击的是子节点）、节点已过期、目标窗口不可交互（例如被遮挡或属于其他用户）、自定义 View 未暴露无障碍操作。逐个排除比盲目重试有效。

全局操作走 `performGlobalAction`，不依赖具体节点：

```kotlin
performGlobalAction(GLOBAL_ACTION_BACK)
performGlobalAction(GLOBAL_ACTION_HOME)
performGlobalAction(GLOBAL_ACTION_RECENTS)
performGlobalAction(GLOBAL_ACTION_NOTIFICATIONS)
```

手势注入用于节点通道覆盖不到的场景，例如画布类界面、需要真实触摸的拖拽：

```kotlin
val path = Path().apply {
    moveTo(300f, 800f)
    lineTo(300f, 400f)
}
val stroke = GestureDescription.StrokeDescription(path, 0, 300)
val gesture = GestureDescription.Builder().addStroke(stroke).build()

dispatchGesture(gesture, object : AccessibilityService.GestureResultCallback() {
    override fun onCompleted(description: GestureDescription?) { /* 完成 */ }
    override fun onCancelled(description: GestureDescription?) { /* 取消 */ }
}, null)
```

前提是配置中声明 `canPerformGestures="true"`。坐标基于屏幕像素，多屏设备可用 `GestureDescription.Builder.setDisplayId()` 指定目标屏幕。单次手势的时长与笔画数存在上限，通过 `getMaxGestureDuration()` 与 `getMaxStrokeCount()` 查询，不要硬编码；超长滑动用 `willContinue` 与 `continueStroke()` 拆成多段连续笔画。

两种通道的取舍：`performAction` 走语义层，不受遮挡与触摸拦截影响，但依赖目标控件暴露 action；`dispatchGesture` 走物理触摸，任何触摸拦截、悬浮窗遮挡都会生效，且坐标随分辨率与布局变化。能用前者时优先前者。

无障碍服务还可以创建 `TYPE_ACCESSIBILITY_OVERLAY` 类型的悬浮窗，显示在其他应用之上。它的输入行为与普通悬浮窗不同：焦点与触摸受系统约束，不能假设可以像应用内窗口一样自由交互。

## 权限收紧与审核

无障碍权限是 Android 上风险最高的授权之一：授予后可以读取屏幕上的全部内容，包括验证码、聊天记录、密码输入框（除明确标记为密码的字段）。系统与商店围绕这一点持续收紧。

- **受限设置（Android 13 起）**：通过浏览器、文件管理器、ADB 等非商店渠道安装的应用，无障碍开关默认不可用，需在应用信息页选择「允许受限设置」后才能开启。
- **辅助工具标识（Android 12 起）**：`isAccessibilityTool="true"` 声明服务的目的是辅助残障用户；未声明时系统会在一段时间后发送隐私提醒通知，Google Play 也会按不同标准审核。
- **商店政策**：Google Play 要求无障碍 API 仅用于帮助残障用户，自动化、辅助点击类应用需明确说明用途，滥用会被下架；国内应用商店普遍采用人工审核，金融类应用还会主动检测无障碍服务是否开启并限制运行。
- **高级保护模式（Android 16）**：系统新增的一键加固模式。公开报道显示，Android Canary 版本正在测试对非辅助工具类应用禁止授予、并自动撤销无障碍权限（Android Authority 拆包，2026-02）；该行为尚未进入稳定版本，但方向明确。

隐私处理是工程义务而非合规装饰：节点树中的文本、输入内容、通知内容都属于用户数据，日志与埋点必须脱敏，默认不上传，确需上传时单独征得同意。

## 工程实践

**收窄监听范围。** 在配置或 `setServiceInfo` 中限定 `packageNames` 与事件类型。全量监听会让服务在每个应用的每次界面变化时被唤醒，耗电与卡顿都会被用户感知。

**事件合并。** 以 `windowId` + 事件类型为键做去抖，只处理最后一次；`TYPE_WINDOW_CONTENT_CHANGED` 尤其需要合并，否则一次列表刷新可能触发数十次遍历。

**状态机而非即时反应。** 交互流程（等待页面 → 查找节点 → 点击 → 校验 → 下一步）写成带超时与重试的状态机，避免在事件回调里堆积判断。节点查找要有超时，操作后要校验结果。

**不抢用户的焦点。** 除用户明确触发，不要主动移动无障碍焦点（`ACTION_ACCESSIBILITY_FOCUS`），否则读屏用户会失去当前位置。

**可观测。** 记录事件类型、包名、窗口 id、节点 class、耗时与操作结果。无障碍问题几乎无法在开发机上复现，日志是唯一的排查依据。

## 调试

```bash
# 查看当前启用的服务（冒号分隔的 package/class 列表）
adb shell settings get secure enabled_accessibility_services
adb shell settings get secure accessibility_enabled

# 测试环境直接启用（产品逻辑不得依赖此方式）
adb shell settings put secure enabled_accessibility_services com.example.app/com.example.app.MyAccessibilityService
adb shell settings put secure accessibility_enabled 1

# 查看系统侧的无障碍状态
adb shell dumpsys accessibility
```

UI 自动化框架（UiAutomator、Espresso）无法直接驱动无障碍服务，服务本身的逻辑应拆成可单测的纯函数：节点筛选、状态迁移、重试策略；与系统交互的部分通过手动用例覆盖。

## 方案对比

|方案|权限来源|适用场景|限制|
|:--|:--|:--|:--|
|应用内语义|无|让自身界面可被读屏|不能跨应用|
|`AccessibilityService`|用户手动启用|读屏、辅助操作、跨应用自动化|审核严格，权限可被随时关闭|
|`UiAutomation`|Shell / 测试框架|自动化测试|仅测试与调试环境|
|`Instrumentation`|测试 APK|单元与集成测试|不能用于生产|
|悬浮窗 + 普通触摸|悬浮窗权限|自身界面叠加|无法操作其他应用内部控件|
