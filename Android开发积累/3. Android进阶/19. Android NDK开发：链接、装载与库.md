Android 应用的 Native 侧运行的是编译为 ELF 的机器码。理解 Native 侧"链接、装载、库"这条链路——ELF 格式、`dlopen` 装载、动态链接（GOT/PLT）、内存布局与调用惯例——是排查 `UnsatisfiedLinkError`、so 加载失败、native 崩溃（tombstone）、native hook 等问题的底层基础。

语言层前置：[[2. 内存模型与未定义行为]]、[[5. 编译四阶段与 NDK 构建链]]、[[6. 符号、ABI 与 STL 链接]]。

## 一、两条编译链路：字节码 vs 机器码

Android 应用内存在两条相互独立的编译链路：

| 维度 | Java/Kotlin 链路 | Native 链路 |
| --- | --- | --- |
| 源码 | `.java` / `.kt` | `.c` / `.cpp` |
| 编译产物 | `.class` → `.dex` | `.o` → `.so` |
| 产物格式 | Dex（ART 专用） | **ELF**（Linux 通用） |
| 执行方 | ART 虚拟机 | CPU 直接执行 |
| "链接"发生在 | dex 合并、R8 优化 | 静态/动态链接（linker） |
| "装载"发生在 | ART 加载 dex | linker 映射 `.so` 进内存 |

**两条链路的本质区别**：

- Java/Kotlin 走"中间语言 + 虚拟机"路线，产物 `.dex` 是平台无关的字节码，交给 ART 翻译执行。
- C/C++ 走"编译器直出机器码"路线，产物 `.so` 是目标平台的 ELF 文件，由 CPU 直接执行，装载和链接由 Android 的 **linker** 完成。

"链接、装载、库"主要在 Native 链路发生。ART 编译产生的 `.oat` 文件本身也是 ELF 格式，因此理解 ELF 同样有助于理解 ART。

## 二、Native 侧：`.so` 就是 ELF

### 2.1 从 `.c` 到 `.so` 的四步

NDK 用 clang 编译，一条 `clang -shared -fPIC foo.c -o libfoo.so` 背后仍是四步：

```
预处理(.i) → 编译(.s 汇编) → 汇编(.o 目标文件) → 链接(.so 共享库)
```

与桌面 Linux 的区别在于：**Android 的 C 库是 Bionic 而非 glibc**，链接的目标库与动态链接器不同（详见第六节）。

### 2.2 ELF 结构与常见段

`.so` 文件就是 ELF（Executable Linkable Format），结构分三块：

```
┌──────────────────┐
│   ELF Header     │  魔数 0x7F 'E''L''F'、机器类型(ARM64)、入口、段表位置
├──────────────────┤
│    Sections      │  .text/.data/.bss/.rodata/.dynsym/.plt/.got ...
├──────────────────┤
│ Section Header   │  段表：描述每个段的名字/长度/偏移/权限
│      Table       │
└──────────────────┘
```

与链接、装载相关的常见段：

| 段名 | 内容 | 备注 |
| --- | --- | --- |
| `.text` | 机器指令 | 只读、可执行 |
| `.data` | 已初始化全局/静态变量 | 可读写 |
| `.bss` | 未初始化全局/静态变量 | 不占文件空间 |
| `.rodata` | 只读数据（const、字符串） | 只读 |
| `.dynsym` / `.dynstr` | 动态符号表 / 符号名字符串表 | **动态链接只使用这两个** |
| `.rela.dyn` / `.rela.plt` | 重定位表 | 记录需要重定位的位置 |
| `.plt` / `.got` | 过程链接表 / 全局偏移表 | 延迟绑定的核心（见第四节） |
| `.dynamic` | 动态链接信息 | 含依赖库列表 `DT_NEEDED` |

可用 NDK 自带工具查看：

```bash
readelf -h libfoo.so      # 文件头：机器类型、类型(ET_DYN)
readelf -S libfoo.so      # 段表
readelf -s libfoo.so      # 符号表
readelf -d libfoo.so      # 动态段：依赖的 so（DT_NEEDED）
nm -D libfoo.so           # 动态符号
```

so 加载报 "not found" 时，用 `readelf -d` 查看其 `DT_NEEDED` 依赖；符号找不到时，用 `nm -D` 查看符号是否导出。

### 2.3 符号与 `extern "C"`：`UnsatisfiedLinkError` 的根因

链接的本质是**目标文件间对符号（函数名/变量名）的引用匹配**。C++ 编译器会做**符号修饰（Name Mangling）**：为支持重载、命名空间，`foo(int)` 编译后的符号名会变成类似 `_Z3fooi`，而非 `foo`。

JNI 注册时，ART 按**原始函数名**（如 `Java_com_example_MainActivity_stringFromJNI`）通过 `dlsym` 查找符号。若 JNI 函数用 C++ 编译且**未加 `extern "C"`**，符号名被修饰，ART 找不到对应符号，抛出 `UnsatisfiedLinkError`。

```c
// 错误：C++ 编译，符号被修饰成 _Z...，ART 找不到
JNIEXPORT jstring JNICALL Java_com_example_MainActivity_stringFromJNI(JNIEnv* e, jobject o)

// 正确：extern "C" 让编译器按 C 规则生成符号（不做修饰）
extern "C" JNIEXPORT jstring JNICALL Java_com_example_MainActivity_stringFromJNI(JNIEnv* e, jobject o)
```

JNI 函数必须加 `extern "C"`，本质是保证**符号命名规则与 `dlsym` 的查找约定一致**。

## 三、装载：so 如何进进程

### 3.1 `System.loadLibrary` 的调用链

`System.loadLibrary("foo")` 最终走到 native 层的 `dlopen`：

```
System.loadLibrary("foo")
  → Runtime.loadLibrary0
    → nativeLoad(name)          // ART 内部
      → dlopen("libfoo.so")     // linker 装载 ELF 进进程地址空间
        → dlsym(...)            // 查找并绑定 JNI 符号
```

该调用链对应两类常见错误：

- `dlopen` 失败（so 不存在 / 依赖缺失 / 架构不匹配）→ `UnsatisfiedLinkError: dlopen failed`
- `dlsym` 找不到符号（未加 `extern "C"`、符号未导出）→ `UnsatisfiedLinkError: ... not found`

### 3.2 进程地址空间与 `/proc/<pid>/maps`

每个 App 进程拥有独立的虚拟地址空间，so 装载后会多出对应的内存映射区。查看 App 进程内存布局：

```bash
adb shell cat /proc/<pid>/maps
```

其中包含 `.so`、dex、栈、堆、`[anon:...]` 匿名映射等，用于排查 native 内存问题、确认 so 是否被加载。

```
高地址 ┌────────────┐
       │   内核空间   │（用户不可访问）
       ├────────────┤
       │  栈 stack   │ 向下增长
       ├────────────┤
       │  so 映射区  │ libfoo.so / libc.so 等
       ├────────────┤
       │  堆 heap    │ 向上增长（malloc 来源）
       ├────────────┤
       │  dex/oat 映射│ 可执行映像
       ├────────────┤
       │   保留区    │ NULL 等不可访问地址
低地址 └────────────┘
```

Android 5.0+ 强制 native 可执行文件与库使用 **PIE/PIC**（地址无关代码），配合 **ASLR**（地址随机化），进程每次启动各 so 的装载基址不同。因此 native 崩溃时的地址需按"相对 so 基址的偏移"解读，而非直接当作绝对地址。

## 四、动态链接：linker、GOT/PLT、延迟绑定

### 4.1 Android 的 linker

Linux 桌面使用 glibc 的 `ld.so`，Android 使用 **Bionic 的 linker**（`/system/bin/linker` 或 `linker64`）。职责相同：装载 so、解析 `DT_NEEDED` 依赖、符号解析、重定位。

### 4.2 GOT 与 PLT：跨 so 函数调用

so 的装载地址不定（ASLR），跨 so 的函数调用不能使用写死的绝对地址，而依赖 **GOT（全局偏移表）** 间接寻址：

- `.got`：存全局变量地址；
- `.got.plt`：存外部函数地址。

### 4.3 延迟绑定（Lazy Binding）

为避免拖慢启动，ELF 默认**延迟绑定**：外部函数首次被调用时才解析符号。核心是 **PLT（过程链接表）** 加一层间接跳转：

```
foo@plt:                    ; 第一次调用走慢路径
    jmp *(foo@GOT)          ; GOT 初始指向下一条指令
    push n                  ; 符号在重定位表的下标
    push moduleID
    jump _dl_runtime_resolve ; linker 解析符号，回填 GOT 真实地址

; 第二次及以后：foo@GOT 已是真实地址，直接跳转（快路径）
```

首次调用后 GOT 被回填，后续调用不再经过 linker，由此实现延迟绑定的加速效果。

### 4.4 与 hook 的关系

PLT/GOT 是 **native hook 的主要作用点**：

- **GOT hook**：改写 `.got.plt` 中的函数指针，使其指向目标函数——不改原代码，但仅能 hook 外部导入函数；
- **inline hook**：修改函数头部指令（`jmp` 跳转）——能 hook 任意函数，但需处理指令边界与 ARM64 分支指令编码。

PLT/GOT 是 Xposed 原生层、性能监控 SDK、逆向保护等技术的基础。

## 五、内存：native 栈、堆与调用惯例

### 5.1 栈与调用惯例（ARM64）

栈保存函数调用的上下文（返回地址、参数、局部变量）。每次函数调用会压入一个**栈帧（Stack Frame）**。

x86 使用 `ebp`（帧指针）+ `esp`（栈顶），ARM64 对应关系：

| 寄存器 | 作用 |
| --- | --- |
| `x29`（FP） | 帧指针，指向当前栈帧底部 |
| `x30`（LR） | 链接寄存器，存返回地址 |
| `x0`~`x7` | 传前 8 个参数 |
| `sp` | 栈顶指针 |

函数进入时压栈保存 `x29`/`x30`，返回时从 `sp` 弹出恢复并 `ret`。**栈回溯（backtrace）即沿 `x29` 帧指针链逐级向上还原调用栈**。

### 5.2 tombstone 与栈回溯

native 崩溃（段错误、SIGSEGV 等）时，Android 在 `/data/tombstones/` 生成 tombstone，包含：

- 崩溃信号（signal 11 = SIGSEGV 段错误）、出错地址；
- 寄存器现场（x0~x30、pc、sp）；
- **backtrace**：一串 `#00 pc 00001234  /data/app/.../libfoo.so (Java_..._stringFromJNI+20)`。

配合带符号的 so（`-g` 编译），用 NDK 的 `llvm-symbolizer` 或 `addr2line` 可将 `pc 00001234` 还原为源码行。栈帧与调用惯例是读懂 backtrace 的前提。

release 构建常开启 `-fomit-frame-pointer` 优化，省掉帧指针后回溯不可靠；崩溃分析时若发现 backtrace 缺帧、错乱，应先检查该编译选项。

### 5.3 堆与内存管理

堆是 `malloc`/`new` 分配内存的来源，由运行库"批发系统空间、零售给程序"：

- 小内存：从已有堆中按算法（空闲链表/位图/对象池）分配；
- 大内存（≥ 128KB 级别）：直接 `mmap` 匿名映射。

Android 的 malloc 实现随版本演进：早期 dlmalloc → jemalloc → 新版 **scudo**（更侧重安全，强化越界/释放后使用检测）。"批发+零售"的模型解释了 native 内存碎片、OOM 的产生，以及 `malloc` 分配的内存物理上可能不连续的原因。

## 六、系统调用与 Bionic

### 6.1 Bionic vs glibc

Android 不使用 glibc，而是 Google 自研的 **Bionic**：更轻量、BSD 风格、为移动设备裁剪。"入口函数 + 系统调用"的模型保持一致：

```
进程启动 → 入口函数(_start) → 初始化堆/I/O → main → exit → _exit(系统调用)
```

App 进程同理：Zygote `fork` 出进程后，Bionic 先完成初始化，`ActivityThread.main()` 才被调用——等价于"入口函数先运行、main 后运行"。

### 6.2 系统调用

用户态程序访问硬件、内存、文件等受限操作，必须通过**系统调用**切换到内核态：

- x86 经典实现：`int 0x80`；
- **ARM64：`svc #0` 指令**，系统调用号置于 `x8` 寄存器，参数置于 `x0`~`x5`。

Binder IPC、文件读写、`fork`、`mmap` 最终都通过系统调用实现，是 Android 进程模型（Zygote fork）、内存映射、IPC 的底层基础。

## 七、实战排查清单

| 现象 | 根因方向 | 排查动作 |
| --- | --- | --- |
| `UnsatisfiedLinkError: dlopen failed` | so 不存在 / 架构不匹配 / 依赖缺失 | 确认 so 是否打进 APK 对应 ABI 目录；`readelf -d` 查看依赖 |
| `UnsatisfiedLinkError: ... not found` | `dlsym` 找不到符号 | 检查 JNI 函数名是否对齐、是否 `extern "C"`、符号是否导出 |
| `libxxx.so not found` | 依赖库缺失 | `readelf -d libfoo.so` 查看 `DT_NEEDED` 缺了谁 |
| native crash（tombstone） | 段错误 / 空指针 / 栈溢出 / 内存踩踏 | 查看 tombstone 的 signal、pc、backtrace，用 `llvm-symbolizer` 还原源码行 |
| backtrace 缺帧、错乱 | 帧指针被优化掉 | 检查是否开启 `-fomit-frame-pointer` |
| 启动慢、so 加载耗时 | 装载 + 动态链接开销 | 用 `systrace`/`perfetto` 查看 `dlopen` 阶段耗时，考虑延迟绑定、按需加载 |

## 小结

Android 中"链接、装载、库"的主线：**`System.loadLibrary` 触发 linker 用 `dlopen` 将 `.so`（ELF）映射进进程、解析符号完成动态链接，`.so` 内代码通过 GOT/PLT 间接寻址并按延迟绑定解析，运行于 Bionic 提供的栈/堆之上，需要时经系统调用进入内核。**
