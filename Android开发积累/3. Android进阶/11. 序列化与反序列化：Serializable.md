序列化是把对象转成字节序列的过程，反序列化是逆过程。目的只有两个：**存储**（写到文件、数据库）和**传输**（跨进程、跨网络）。

Android 里有四种常见方案，定位完全不同：

| 方案 | 本质 | 跨进程 | 可持久化 | 可读性 | 典型场景 |
|:--|:--|:--:|:--:|:--|:--|
| **Serializable** | Java 原生，反射实现 | 可以但慢 | 可以 | 二进制 | Java 生态互通、简单对象落盘 |
| **Parcelable** | Android 专用，手写/生成 | 快 | **不可以** | 二进制 | Intent、Bundle、Binder |
| **JSON** | 文本 | 可以 | 可以 | 好 | 网络接口、配置、跨语言 |
| **XML** | 文本 | 可以 | 可以 | 好 | 配置文件、`res/xml`、跨系统交换 |

本篇讲 Serializable，其余三篇见[[12. 序列化与反序列化：Parcelable]]、[[13. 序列化与反序列化：XML]]、[[14. 序列化与反序列化：JSON]]。

## 用法

`Serializable` 是个**空接口**（标记接口），不含任何方法，实现它就等于告诉 JVM“这个类可以被序列化”。

```kotlin
class User(
    var id: Long,
    var name: String
) : Serializable {
    companion object {
        // 显式声明版本号，取值随意，但要长期保持不变
        private const val serialVersionUID = 1L
    }
}
```

Java 写法：

```java
public class User implements Serializable {
    private static final long serialVersionUID = 1L;
    private long id;
    private String name;
}
```

> Kotlin 里必须写成`companion object`中的`const val`。普通`val`会变成 Companion 类的实例字段，JVM 找不到`serialVersionUID`；`const val`才会编译成外层类的`static final`字段。

### serialVersionUID 的作用

反序列化时，JVM 会比较“字节流里的版本号”和“当前类的版本号”，不一致就抛`InvalidClassException`。

不显式声明时，编译器会根据类的结构（字段、方法、修饰符）**自动算一个**。这意味着：只要给类加个字段、改个方法签名，版本号就变了，之前写出去的数据全部读不回来。

显式声明之后，版本号由开发者控制：

+ 加字段、删字段：老数据仍能读，新增字段取默认值（对象类型为 null，基本类型为 0/false）；
+ 改字段类型、改类名：仍然会失败；
+ **一旦发布就不要改这个值**，它是对外承诺。

### 写入与读取

```kotlin
val file = File(context.filesDir, "user.bin")

// 序列化
ObjectOutputStream(BufferedOutputStream(FileOutputStream(file))).use { output ->
    output.writeObject(user)
}

// 反序列化
val restored = ObjectInputStream(BufferedInputStream(FileInputStream(file))).use { input ->
    input.readObject() as User
}
```

两个注意点：

+ `readObject()`会抛`ClassNotFoundException`（字节流里的类在当前进程找不到），Kotlin 不强制捕获，但要心里有数；
+ 一定要用`use`或 try-with-resources，否则序列化流不会 flush，文件可能是空的。

## 三个容易忽略的语义

### 反序列化不调用构造方法

反序列化时对象的创建走的是 JVM 内部路径，**不会执行本类的构造方法**，字段直接从流里恢复。因此构造方法里的初始化逻辑、校验逻辑在反序列化时统统不生效。

唯一的例外：如果父类没有实现`Serializable`，它的**无参构造方法**会被调用；父类也没有无参构造就会失败。

### transient 不参与序列化

```kotlin
class Session(
    var token: String,
    @Transient var tempCache: ByteArray? = null   // 不写入字节流
) : Serializable
```

`transient`（Kotlin 里是`@Transient`）常用于缓存、连接、大对象这类“可以重建、不该传输”的字段。反序列化后它会是默认值。

### 可以自定义读写逻辑

字段级别的控制不够时，可以自己实现`writeObject` / `readObject`（方法签名固定，不是重写）：

```kotlin
private fun writeObject(output: ObjectOutputStream) {
    output.defaultWriteObject()        // 先按默认规则写
    output.writeInt(version)           // 再补额外信息
}

private fun readObject(input: ObjectInputStream) {
    input.defaultReadObject()
    version = input.readInt()
}

// 反序列化后替换成另一个对象（单例、枚举、规范化对象）
private fun readResolve(): Any = INSTANCE
```

## 安全问题

Serializable 的反序列化会**按字节流里的类名去加载并实例化任意类**，攻击者可以构造一条“gadget chain”，在目标进程里执行代码。这不是理论问题，Java 生态里出过多次这类漏洞。

防护手段：

+ **不要反序列化不可信来源的数据**（网络、用户输入、外部文件）；
+ 需要跨系统交换时用 JSON/XML，只传基本类型，不带任何与代码相关的信息；
+ 可信边界内也尽量限定类型，JDK 9+ 提供`ObjectInputFilter`做类名白名单，但各 Android 版本支持程度不一，不能当作唯一防线。

## 在 Android 上用它的代价

| 问题 | 说明 |
|:--|:--|
| 慢 | 全程反射 + 大量临时对象，序列化一个对象可能比 Parcelable 慢一个数量级 |
| 触发 GC | 临时对象多，列表场景下容易掉帧 |
| 体积大 | 写入类元信息，字节流明显比 Parcelable 大 |
| 不适合 Bundle | `Intent`/`Bundle`走 Binder，超过约 1 MB 会抛`TransactionTooLargeException` |

所以 Android 的常规选择是：**进程内/跨进程传递用 Parcelable，网络与持久化用 JSON**。Serializable 留给两类场景：

1. 需要与既有 Java 代码或框架交互（比如某些缓存库、`HttpSession` 式的对象存储）；
2. 临时把对象整体落盘、且不关心体积与速度。

> 想把对象存到`SharedPreferences`或`Bundle`里时，应先考虑：该对象是否应拆分为若干基本字段？大多数“需要序列化整个对象”的需求，本质是数据结构没设计好。
