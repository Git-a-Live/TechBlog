混淆只是应用代码与资源缩减工作的一部分（参见 [Google 官方文档](https://developer.android.google.cn/studio/build/shrink-code)）。工具层面：**R8 从 AGP 3.4 起即为默认缩减器，ProGuard 已被其取代**——但 ProGuard 的规则语法仍被沿用，因此下文的“ProGuard 规则”实际均面向 R8。

R8 在 release 构建里做三件事：

1. **Shrink（缩减）**：移除用不到的类、方法、字段、资源；
2. **Optimize（优化）**：重写字节码，比如内联、移除无用分支；
3. **Obfuscate（混淆）**：把类、方法、字段重命名成短名，进一步压缩 dex。

混淆的例子（缩短命名）：

```text
androidx.appcompat.app.AlertController -> androidx.appcompat.app.AlertController:
    android.content.Context mContext -> a
    int mListItemLayout -> O
    android.widget.Button mButtonNeutral -> w
```

虽然混淆不会移除代码，但当 dex 索引了大量类、方法、字段时，缩短命名能显著减小体积。代价是：混淆后的堆栈、反射、序列化都认不出原来的名字，需要额外的保留规则与映射文件。

## 启用代码混淆

```groovy
android {
    buildTypes {
        release {
            minifyEnabled true       // 开启缩减 + 优化 + 混淆
            shrinkResources true     // 资源缩减，需要 minifyEnabled 同时开启
            proguardFiles getDefaultProguardFile('proguard-android-optimize.txt'), 'proguard-rules.pro'
        }
    }
}
```

- `proguard-android-optimize.txt`：AGP 自带的默认规则，含必要的 keep；
- `proguard-rules.pro`：项目自定义的规则，放模块根目录。

`getDefaultProguardFile('proguard-android.txt')` 是“只缩减不优化”的版本；要体积最优用 `-optimize.txt`。

## 自定义保留代码

R8 会移除“它认为用不到”的代码，但有一类它看不见的用法：**运行时按字符串名字查找**——反射、JNI、序列化、Parcelable、动态代理都属于这一类。这类代码必须显式保留，判断原则见下一节。

两种保留方式：

1. 在规则文件里写 `-keep`；
2. 在代码里给类/方法加 `@Keep` 注解。

### 判断原则：哪些代码必须维持原形

判断的核心问题只有一个：**这段代码会不会在运行时，被一个不看源码的机制，按它的名字（类名 / 方法名 / 字段名）找到？** 会，就要 keep。R8 只看得到静态引用，看不到“按名字查找”这类调用，所以它无法自己判断。

按“谁在按名字找它”分几类：

| 特征 | 谁在按名字找 | 典型场景 | 需要保留 |
| --- | --- | --- | --- |
| 反射调用 | 应用自身代码 | `Class.forName`、`getDeclaredMethod/Field`、Kotlin `KClass` 反射 | 类名 + 被反射的方法/字段 |
| JNI 调用 | so 里的 native 代码 | `native`/`external` 方法、`GetMethodID`/`GetFieldID` | native 方法名 + so 回调的 Java 方法/字段 |
| 序列化 | 序列化库 / 反序列化方 | `Serializable`、Gson、kotlinx.serialization、Moshi | 字段名（含 `@SerializedName` 指定的 key） |
| Parcelable | 系统 Binder | `CREATOR`、`writeToParcel`/构造方法 | `CREATOR` 字段 + 读写顺序对应的成员 |
| 动态代理 / AOP | 框架运行时 | Retrofit 接口、`Proxy`、EventBus `@Subscribe` | 接口方法名（通常整接口 keep） |
| 注解 + 运行时扫描 | 注解处理 / 框架 | 自定义注解 + 运行时扫描 | 被注解的类/方法 |
| 跨进程 / 跨应用 | 系统 | manifest 声明的组件、AIDL、`android:onClick` | 组件类名 + 约定的方法名 |
| 枚举 | 应用自身代码 | `valueOf`/`values`、`@SerializedName` 常量 | 枚举常量名 |

几条实用的判断原则：

- **出现字符串形式的类名/方法名/字段名即需警惕**：`Class.forName("...")`、`getMethod("...")`、`GetMethodID(..., "...")`——这些字符串中出现的就是必须 keep 的。
- **序列化/网络模型的字段名就是协议**：Gson 默认按字段名映射 JSON key，字段名一旦变更，服务端返回即解析错位；`@SerializedName` 指定的 key 更不可改动。
- **`native`/`external` 方法名是 ABI 的一部分**：无论静态注册（so 导出符号 `Java_..._方法名`）还是动态注册（`RegisterNatives` 的 name 字符串），都按名字绑定，方法名不能重命名；so 里 `GetMethodID`/`GetFieldID` 传的字符串同样不能动。
- **`CREATOR` 是 Parcelable 的固定契约**：字段名固定为 `CREATOR`，系统反序列化时按这个名字找，必须原样保留。
- **manifest 里出现的组件类名**：显式 intent 按全限定名启动，类名不能混淆（Android 默认规则已兜底，自定义场景仍要确认）。

除了“名字”，反射和泛型还依赖字节码里的元信息，需要一并保留：`-keepattributes Signature, InnerClasses, EnclosingMethod, Exceptions, *Annotation*`（行号与文件名见下文「还原堆栈轨迹」）。

### 修改 ProGuard 规则

```groovy
// 保留 MyClass 本身和它内部所有成员
-keep public class MyClass
```

规则格式是 `-<保留选项>, <配置选项> <目标>`。

**保留选项**：

| 选项 | 说明 |
| --- | --- |
| `keep` | 指定要保留的类/成员，作为入口不被移除或混淆 |
| `keepclassmembers` | 若类本身未被移除，则保留其指定成员（不把类作为入口） |
| `keepclasseswithmembers` | 只保留“含特定成员”的类，并原样保留这些特定成员 |
| `keepnames` | 等价 `-keep,allowshrinking`：若没被缩减，则不混淆 |
| `keepclassmembernames` | 保留类与所有成员的名字（不防缩减） |
| `keepclasseswithmembernames` | 保留含特定成员的类的名字 |
| `if` | 条件保留，`<n>` 引用前面匹配到的通配符 |
| `printseeds` | 打印所有被 keep 的类/成员 |

**配置选项**：

| 选项 | 说明 |
| --- | --- |
| `allowshrinking` | 允许把 keep 入口也缩减掉（必要时） |
| `allowoptimization` | 允许优化 keep 入口 |
| `allowobfuscation` | 允许混淆 keep 入口 |
| `includedescriptorclasses` | 含特定修饰符成员的类也一并保留 |

**通配符**：

| 通配符 | 说明 |
| --- | --- |
| `*` | 匹配类名的一部分，不含 `.` 分隔符与子包 |
| `**` | 同 `*`，但含子包 |
| `***` | 匹配任意类型 |
| `?` | 匹配单个字符 |
| `%` | 匹配任意基本类型（含 void） |
| `...` | 匹配任意数量与类型的参数 |
| `$` | 标识内部类 |
| `@` | 按注解类型限定匹配 |
| `<init>` / `<fields>` / `<methods>` | 构造方法 / 任意字段 / 任意方法 |

实际开发中，绝大多数第三方库都会在 AAR 或文档中提供所需的 keep 规则，按说明添加即可。常见的一类是自己写的模型类（给 Gson / kotlinx.serialization 用），要么加 `@Keep`，要么用序列化库官方提供的规则。

### 使用 @Keep 注解

```java
import androidx.annotation.Keep;

@Keep
public void foo() { ... }
```

注意：`@Keep` 来自 **androidx.annotation**（某些第三方库的同名注解含义不同），且依赖 AGP 自带的默认规则才生效。它适合用在“只有反射才访问”的类或方法上。**不应在依赖库中滥用 `@Keep`**——它会阻止 R8 缩减掉库里用不到的部分；库作者更推荐把 keep 规则随 AAR 一起发布（`consumerProguardFiles`）。

## 库模块：把规则随 AAR 发布

编写 Library 时，其所需的 keep 规则应随 AAR 一起分发，而非要求使用方手写：

```groovy
android {
    defaultConfig {
        consumerProguardFiles 'consumer-rules.pro'   // 随 AAR 分发给消费方的规则
    }
}
```

app 模块依赖该库时，规则会自动合并进最终的 R8 处理。

## 还原堆栈轨迹

R8 每次运行都会生成 `mapping.txt`，记录混淆前后的映射关系。文件在：

```text
app/build/outputs/mapping/release/mapping.txt
```

**每次构建都会覆盖上一次的 mapping 文件**，因此发版时必须保存对应版本的副本，否则旧版本线上崩溃的堆栈无法还原。

还原的两种方式：

```bash
# retrace 命令行工具
retrace mapping.txt crash_stack.txt
```

或更简洁的方式：将 mapping 文件**上传到对应的平台**，崩溃平台会自动还原——

- **Google Play Console**：App Bundle 模式下上传，Play 会用它还原 ANR 与崩溃；
- **Firebase Crashlytics**：在 Crashlytics 里上传 mapping，崩溃栈自动还原。

要保证堆栈里保留足够信息，规则文件里通常要有：

```groovy
-keepattributes LineNumberTable,SourceFile
-renamesourcefileattribute SourceFile
```

`LineNumberTable` 保留行号信息，`SourceFile` 保留文件名；`-renamesourcefileattribute` 把所有源文件名统一成 `SourceFile`，映射文件里已经有真实名，堆栈里不需要暴露。

## 应用加固

混淆（R8）做的是**重命名 + 缩减**，真正的逆向分析者仍能反编译出可读的 smali。**加固（壳）** 是另一层：把 dex 加密、运行时由壳解密加载，或把关键代码抽到 so 里执行（指令虚拟化/VMP），大幅提高逆向成本。

### 加固的原理

- **加壳**：把原始 dex 加密打包，运行时由加固厂商注入的壳程序解密后在内存里加载；
- **代码抽取**：把部分方法的字节码抽空，运行时按需还原，让静态反编译看不到关键逻辑；
- **so 加固 / VMP**：把核心逻辑编译进 native 层或虚拟指令，增加动态分析难度。

### 是否要加固

这是一个需要权衡的决策，并非强度越高越好：

| 考量 | 说明 |
| --- | --- |
| 国内渠道 | 等保、金融、政务类应用通常**要求**加固 |
| Google Play | 对加壳敏感，强加固可能导致上架被拒或更新失败；Play 更推荐 App Signing + 代码混淆 |
| 启动性能 | 加壳会增加首启耗时与内存 |
| 兼容性 | 壳与部分设备/系统版本冲突是常见故障源 |
| 信任边界 | 加固把应用安全交给第三方厂商，要评估其可信度 |

国内常见加固厂商：腾讯乐固/御安全、360 加固、梆梆安全、爱加密、网易易盾等，多数提供在线免费版。

### 与加固配合的其他措施

- **Play App Signing**：把签名密钥托管给 Google，避免密钥泄露导致的盗版重签；国内无 Play 时用自管 keystore 并严格保管；
- **防二次打包**：校验签名（`getPackageManager().getPackageInfo(...).signatures`），发现被重签即告警或退出；
- **运行环境检测**：检测 root、Xposed/Frida、模拟器，配合 RASP 动态防护；
- **敏感数据加密 + 混淆**：Token、密钥不应明文存在代码里，配合 NDK 存放与运行时解密。

需要指出的是：**加固并非银弹**。它提高逆向门槛，但不能保证绝对安全；真正敏感的逻辑与密钥，应放在服务端，客户端只做最低限度的必要防护。

## 小结

- R8 是默认缩减器，ProGuard 规则语法沿用；它做缩减 + 优化 + 混淆三件事。
- 凡是运行时“按名字查找”的代码（反射、JNI、序列化、Parcelable、动态代理）都要显式 `-keep` 或 `@Keep`；库作者用 `consumerProguardFiles` 分发规则。
- `mapping.txt` 每次构建都会覆盖，发版必须留存，并上传 Play / Crashlytics 自动还原堆栈。
- 混淆防重命名，加固防反编译；国内合规常要求加固，Play 渠道则以混淆 + App Signing 为主。
- 加固提高门槛、不保证安全，真正的敏感逻辑放服务端。
