## 项目结构化

把成百上千个文件塞进一个 `app` 模块，功能上是能跑的，但维护会变成灾难。稍微好一点的做法是“按类型分目录”（所有 Activity 放一起、所有 Adapter 放一起），可仍然治标不治本——同类型文件夹里的文件彼此可能毫无关系。

项目结构化的本质是：**把强关联的代码组织成一个能独立完成若干功能的集合，再由这些集合互相配合构成完整项目**。在 Android 里，这个“集合”就是 Module。

## 模块化开发

Module（模块）是高内聚、低耦合的文件集合，像积木一样按需组装。划分模块的主要依据是**功能**：登录、支付、图片加载、公共 UI 组件，各自成模块。

> `app` 是一个特殊的模块：它是唯一能直接产出可安装 APK 的应用模块（application module），其余都是库模块（library module）或动态功能模块（dynamic-feature）。

模块化带来几个直接收益：编译可以只编译改动的模块（增量构建）、团队并行开发互不阻塞、公共代码抽成模块复用、单个模块的测试更快。

### Module 的引用

创建 Library 模块后，`settings.gradle(.kts)` 里会多一行：

```groovy
// settings.gradle（Groovy）
include ':mylibrary'
```

```kotlin
// settings.gradle.kts（Kotlin DSL）
include(":mylibrary")
```

引用方式与普通依赖类似，用 `project()`：

```groovy
// 引用方模块的 build.gradle
dependencies {
    implementation(project(':mylibrary'))
}
```

```kotlin
// build.gradle.kts
dependencies {
    implementation(project(":mylibrary"))
}
```

两个要点：

- `project(':mylibrary')` 里的名字**必须**与 `settings.gradle` 里注册的名字完全一致（含大小写与冒号路径）；
- 想让别的模块也能“顺带”看到这个库（比如它出现在公共 API 签名里），用 `api(project(...))`；只是内部使用就用 `implementation(project(...))`，后者不会把依赖暴露给上层模块，减少不必要的重编译。

### 依赖冲突

多个模块（或依赖库）引用了同一个库的不同版本时，就发生依赖冲突。**Gradle 的默认策略是取最高的那个版本**，而不是报错——所以“被引用模块的依赖版本不能高于上层模块”这个说法并不成立。

真正出问题的，是“取最高版本”之后产生了**二进制不兼容**（比如 A 库的新版本删了某个类，别的库还在用）。这时候才有两种选择：

- 把冲突的库统一到一个兼容版本（升或降）；
- 用 `strictly` / `resolutionStrategy.force` 强制指定版本，或用 `exclude` 排除某个传递依赖。

具体写法见 [[5. Gradle编译构建#依赖冲突]]。

### Module 转独立 App

任何包含 Activity 的 Library 模块都可以手动改成能独立运行的应用模块，需要改两处：

**1. AndroidManifest.xml**

可运行应用必须有带 `MAIN`/`LAUNCHER` 的入口 Activity：

```xml
<application>
    <activity
        android:name=".MainActivity"
        android:exported="true">
        <intent-filter>
            <action android:name="android.intent.action.MAIN" />
            <category android:name="android.intent.category.LAUNCHER" />
        </intent-filter>
    </activity>
</application>
```

**2. build.gradle**

```groovy
// 库模块
plugins {
    id 'com.android.library'
}

// 改成应用模块
plugins {
    id 'com.android.application'
}

android {
    namespace 'com.example.mylibrary'
    defaultConfig {
        applicationId 'com.example.mylibrary'   // 库模块没有这一行
        minSdk 23
        targetSdk 36
    }
}
```

改完同步，模块图标会从 Library 变成 App，即可独立编译运行。反向操作（App 转 Library）就是删掉 `applicationId`、把插件换回 `com.android.library`。

### 用版本目录统一管理

现代项目推荐用 **版本目录（Version Catalog）** 统一声明依赖与模块名，避免每个模块里散落一堆版本号。根目录 `gradle/libs.versions.toml`：

```toml
[versions]
coreKtx = "1.13.1"

[libraries]
androidx-core-ktx = { group = "androidx.core", name = "core-ktx", version.ref = "coreKtx" }
```

```kotlin
// 任意模块里引用
dependencies {
    implementation(libs.androidx.core.ktx)
    implementation(project(":mylibrary"))
}
```

版本目录从 AGP 7.4 / Gradle 7.4 起稳定可用，是新建 Android 项目的默认形态。

## 小结

- 模块化按**功能**划分，`app` 是唯一的应用模块。
- 引用用 `project(":mylibrary")`，名字与 `settings.gradle` 严格一致；`api` 才对外暴露。
- 依赖冲突默认取最高版本，只有二进制不兼容才需要强制或排除。
- Library 转 App 只改两处：manifest 的入口 Activity + build.gradle 的插件与 `applicationId`。
- 版本统一交给 Version Catalog，别在每个模块里各写一份版本号。
