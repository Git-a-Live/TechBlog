AndroidManifest.xml 是应用的“户口簿”：它向系统声明应用的组件（Activity、Service、Receiver、Provider）、需要的权限、用到的硬件特性，以及图标、主题、启动入口这些元信息。系统在安装应用时读取它，运行时在启动组件、授予权限、决定能否被别的应用“看见”时也依赖它。

一个容易被忽略的事实：最终生效的 manifest 并非 `src/main` 目录下的那一份，而是构建时由 **Manifest Merger** 将主 manifest、构建类型/产品变体的 manifest 以及所有依赖库的 manifest 合并而成。据此即可解释多数“修改不生效 / 新增了属性”的现象。

## 基本结构

```xml
<?xml version="1.0" encoding="utf-8"?>
<manifest xmlns:android="http://schemas.android.com/apk/res/android">
    <!-- 权限声明 -->
    <uses-permission android:name="android.permission.INTERNET" />
    <!-- 硬件/软件特性声明（也决定 Play 商店里能否检索到该应用） -->
    <uses-feature android:name="android.hardware.camera" android:required="false" />

    <application
        android:allowBackup="true"
        android:icon="@mipmap/ic_launcher"
        android:label="@string/app_name"
        android:theme="@style/Theme.MyApp">

        <!-- 启动入口 Activity -->
        <activity
            android:name=".MainActivity"
            android:exported="true">
            <intent-filter>
                <action android:name="android.intent.action.MAIN" />
                <category android:name="android.intent.category.LAUNCHER" />
            </intent-filter>
        </activity>
    </application>
</manifest>
```

注意：`<manifest>` 标签里已经没有 `package` 属性了。**AGP 7.4 起包名改由 `build.gradle` 里的 `namespace` 决定**，manifest 里的 `package` 属性在 AGP 8 中已被移除，写入会报错。

## 组件与 intent-filter

四大组件都要在 manifest 里注册，Activity/Service/Receiver 尤其如此：

| 组件 | 标签 | 说明 |
| --- | --- | --- |
| Activity | `<activity>` | 界面；只有带 `MAIN` + `LAUNCHER` 的才会出现在桌面 |
| Service | `<service>` | 后台服务 |
| BroadcastReceiver | `<receiver>` | 广播接收器；静态注册受 Android 8+ 后台限制 |
| ContentProvider | `<provider>` | 数据共享；`authorities` 必须唯一 |

`<intent-filter>` 声明组件能响应哪些隐式 Intent（action、category、data）。没有 intent-filter 的组件只能被显式 Intent 启动。

### android:exported

这是近年最易出错的属性。**当应用 targetSdk 为 31（Android 12）+ 时，任何带 `<intent-filter>` 的组件都必须显式声明 `android:exported`**，否则安装直接失败：

```text
Installation did not succeed. The application could not be installed:
INSTALL_PARSE_FAILED_MANIFEST_MALFORMED
```

`android:exported="true"` 表示组件允许被其他应用启动，`false` 表示只有本应用（或同签名、同 uid 的应用）能启动。判断原则：

- 带 `MAIN`/`LAUNCHER` 的入口 Activity → `true`；
- 只给本应用内部用的组件 → `false`；
- 曾经靠“有没有 intent-filter”自动推断的日子已经过去，**必须手动写**。

### android:permission：给组件加权限

`android:exported` 回答“能不能被外部启动”，`android:permission` 回答“具备什么资格的调用方才能启动”。两者是叠加关系：只有 `exported="true"` 的组件，权限检查才有意义；`exported="false"` 时外部本就够不到，权限再严格也轮不到它出场。所以 `exported="false"` 是第一道门，`android:permission` 是“组件必须对外导出”时才加的第二道门。

给组件加权限的本质，是让**调用方**（而不是组件自己）必须持有某个权限才能访问。权限名可以是系统权限（用 `<uses-permission>` 引入，如 `android.permission.SYSTEM_ALERT_WINDOW`），也可以是自己用 `<permission>` 定义的自定义权限：

```xml
<manifest xmlns:android="http://schemas.android.com/apk/res/android">

    <!-- 定义自定义权限，protectionLevel 是必填项 -->
    <permission
        android:name="com.example.myapp.permission.DEADLY_ACTIVITY"
        android:protectionLevel="signature" />

    <application>
        <activity
            android:name=".AdminActivity"
            android:exported="true"
            android:permission="com.example.myapp.permission.DEADLY_ACTIVITY" />
    </application>
</manifest>
```

四个组件的**检查时机**和**失败表现**不一样：

| 组件 | 检查时机 | 调用方没权限时的表现 |
| --- | --- | --- |
| Activity | `startActivity()` / `startActivityForResult()` | 抛 `SecurityException` |
| Service | `startService()` / `stopService()` / `bindService()` | 抛 `SecurityException` |
| BroadcastReceiver | `sendBroadcast()` 返回后、投递前 | **不抛异常**，广播被静默丢弃 |
| ContentProvider | 首次检索 + 每次读写操作 | 抛 `SecurityException` |

最易出错的是广播这一项：接收器未持有权限时，发送方 `sendBroadcast()` 照常返回、不报错，广播只是被静默丢弃。排查“receiver 收不到其他应用广播”的问题时，应先检查权限，而非 intent-filter。

### 广播权限的两个方向（最易混淆）

广播的权限有**两个相反的语义**，混淆会导致异常：

- **接收器上的 `android:permission`**：限制“谁能**向本应用发送**广播”——发送方必须持有该权限；
- **`sendBroadcast(intent, permission)` / `registerReceiver(..., permission, ...)` 传的权限**：限制“谁能**接收**本应用发送的广播”——接收方必须持有该权限。

```kotlin
// 只有持有该权限的接收器才能收到这条广播
sendBroadcast(intent, "com.example.app.permission.SECURE")
```

两者可以同时生效：接收器声明了权限、发送方也指定了权限时，两次检查都要通过，广播才会送达。

### ContentProvider 的读写分离与临时授权

Provider 是四个组件里权限最细的：除了统一的 `android:permission`，还能拆成 `android:readPermission` 和 `android:writePermission` 分别管读和写：

```xml
<provider
    android:name=".MyProvider"
    android:authorities="com.example.myapp.provider"
    android:exported="true"
    android:readPermission="com.example.myapp.permission.READ_DATA"
    android:writePermission="com.example.myapp.permission.WRITE_DATA"
    android:grantUriPermissions="true" />
```

两点需注意：**只授予写权限不意味着能读**（读和写是两把独立的锁）；若需整体保护 provider、又临时将某个 URI 分享出去，应使用 `grantUriPermissions` 配合 `Intent.FLAG_GRANT_READ_URI_PERMISSION` / `FLAG_GRANT_WRITE_URI_PERMISSION`，而非将 provider 整体 `exported="true"` 直接对外暴露。

### 自定义权限的常见问题

给组件加权限通常要用自定义权限，这里集中了几个高发问题：

- **命名必须反向域名**：`com.example.myapp.permission.XXX`。系统不允许**不同签名**的应用声明同名权限——两个 app 都声明了 `com.example.permission.FOO`，后安装的那个会 `INSTALL_FAILED_DUPLICATE_PERMISSION` 装不上。这正是“权限名被抢占”的问题，也说明了使用包名前缀的原因。
- **`protectionLevel` 必填，且决定谁能持有**：
  - `signature`：只有与定义方**同签名**（或系统）的应用能持有，对用户透明、无运行时弹窗，是**自家多个 app 之间做安全 IPC 的首选**；
  - `dangerous`：其他应用要像系统危险权限一样**运行时申请**才拿得到；
  - `normal`：安装即授予（自定义权限几乎用不到）；
  - `signatureOrSystem`：额外对系统开放，第三方不应使用。
- **定义方自动持有**：应用通过 `<permission>` 声明的权限，自身天然持有，无需再 `<uses-permission>`。但若其他 app 通过 `<uses-permission>` 请求了该 `dangerous` 权限，仍需通过运行时授权，且**定义方必须先安装**，否则请求方得到的是未定义、未授予的状态。
- **不应给 LAUNCHER 入口加签名权限**：桌面（Launcher）不持有应用的自定义权限，给入口 Activity 加上 `signature` 权限后，用户无法通过图标进入应用——相当于将自身锁定在外。入口 Activity 只需 `exported="true"`。

### 权限声明的层级

权限也可以挂在 `<application>` 上，作为**所有组件的默认值**：某个组件没单独写 `android:permission` 时，继承 `<application android:permission="...">`。修改此处会影响全部组件，当所有组件突然无法启动时，应优先检查这里。

## 包可见性：queries

从 Android 11（API 30）起，应用默认**看不到**设备上安装了哪些其他应用（包可见性过滤）。若应用需 `startActivity` 启动其他应用，或调用 `queryIntentActivities`、`getPackageInfo` 查询其他包，则需在 manifest 中通过 `<queries>` 声明，或持有 `QUERY_ALL_PACKAGES` 权限（该权限上架时会受到严格审查，应尽量避免使用）。

```xml
<manifest ...>
    <!-- 声明要查询的 Intent 类型，比如能打开网页的应用 -->
    <queries>
        <intent>
            <action android:name="android.intent.action.VIEW" />
            <data android:scheme="https" />
        </intent>
        <!-- 或声明要交互的具体包 -->
        <package android:name="com.example.otherapp" />
    </queries>
</manifest>
```

只发 `startActivity`（不先查询结果）的话，不一定需要 `queries`；但**先 `resolveActivity` 判断“是否有可打开的组件”则必须声明**，否则始终返回 null。

## 备份与恢复

备份配置在 API 31 前后换了格式，这里也是老资料的重灾区：

| 版本 | 配置方式 |
| --- | --- |
| API 30 及以下 | `android:allowBackup` + `android:fullBackupContent="@xml/backup_rules"` |
| API 31 及以上 | `android:dataExtractionRules="@xml/data_extraction_rules"` |

`android:allowBackup` 从 **Android 12 起被标记废弃**（仍会生效，但 Google 推荐用 `dataExtractionRules`）。新的规则文件把“云备份”和“设备间迁移（D2D）”拆成两段，可以只禁云备份、保留换机迁移：

```xml
<!-- res/xml/data_extraction_rules.xml -->
<data-extraction-rules>
    <cloud-backup>
        <!-- 排除所有 shared preferences 里的登录态 -->
        <exclude domain="sharedpref" path="auth.xml" />
    </cloud-backup>
    <device-transfer>
        <include domain="sharedpref" path="." />
    </device-transfer>
</data-extraction-rules>
```

要彻底禁止备份，两段都写 `<exclude domain="root" path="." />`。**注意**：`allowBackup` 默认是 `true`，含 token、账号等敏感数据的应用应当显式关闭，否则用户换机或云备份会导致敏感数据外泄。

## 其他常用属性

| 属性 | 说明 |
| --- | --- |
| `android:localeConfig` | 指向 `@xml/locales_config`，配合 per-app language（API 33+），让应用语言跟随系统之外的独立设置 |
| `android:enableOnBackInvokedCallback` | API 33+ 的预测性返回手势开关，默认已为 true |
| `android:networkSecurityConfig` | 指向网络安全配置，控制明文流量、自定义证书 |
| `android:usesCleartextTraffic` | 是否允许明文 HTTP（API 28+ 默认 false）；正确做法是用 networkSecurityConfig 按域名放开 |
| `android:largeHeap` | 请求更大的堆；仅可缓解一时，长期仍需优化内存 |
| `android:supportsRtl` | 是否支持从右到左布局 |
| `android:hardwareAccelerated` | 是否启用硬件加速，targetSdk 14+ 默认开启 |
| `android:extractNativeLibs` | 是否在安装时解压 so；配合 App Bundle 与 `useLegacyPackaging` 权衡 |

`<uses-sdk>` 里有两个值要分清：`minSdkVersion` 是支持的最低版本，`targetSdkVersion` 是“我针对这个版本的行为做过适配”的声明——系统会按 targetSdk 决定是否启用新版本的行为变更，所以**升级 targetSdk 不是改个数字，而是要把该版本的行为变更逐条过一遍**。而 `compileSdkVersion` 并不在 manifest 中，它位于 `build.gradle`，决定可调用的 API 范围。

## tools 命名空间与合并冲突

当主 manifest 与依赖库的 manifest 对同一个属性有不同取值时，Merger 会报错。用 `tools:` 命名空间来裁决：

```xml
<manifest xmlns:android="http://schemas.android.com/apk/res/android"
    xmlns:tools="http://schemas.android.com/tools">

    <application
        tools:replace="android:allowBackup, android:theme"
        android:allowBackup="false" />

    <!-- 去掉依赖库里某个不需要的权限 -->
    <uses-permission
        android:name="android.permission.READ_CONTACTS"
        tools:node="remove" />

    <!-- 强制合并某个 service 的子标签 -->
    <service android:name=".MyService" tools:node="merge" />
</manifest>
```

| 指令 | 作用 |
| --- | --- |
| `tools:replace` | 用主 manifest 的值覆盖低优先级来源的值 |
| `tools:merge` | 强制合并某个标签（默认策略是不合并就报错） |
| `tools:remove` | 移除低优先级来源声明的这个节点 |
| `tools:node` | 配合 `merge` / `remove` / `replace` 等值 |

优先级从高到低：构建变体的 manifest > 构建类型的 manifest > 产品变体（flavor）的 manifest > 主 `src/main` manifest > 依赖库的 manifest。

合并后的完整结果可以查看，路径是：

```text
app/build/intermediates/merged_manifests/<variant>/AndroidManifest.xml
```

排查属性被修改的来源时，应直接打开该文件，比猜测来源更可靠。

## 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 安装失败 `INSTALL_PARSE_FAILED_MANIFEST_MALFORMED` | targetSdk 31+ 且带 intent-filter 的组件没写 `exported` | 逐个组件补 `android:exported` |
| `resolveActivity` 总是返回 null | API 30+ 包可见性过滤 | 在 `<queries>` 里声明要查询的包或 Intent |
| 合并报 `Manifest merger failed` | 主 manifest 与依赖库属性冲突 | 用 `tools:replace` / `tools:remove` 裁决 |
| 敏感数据进了云备份 | `allowBackup` 默认 true | API 31+ 用 `dataExtractionRules` 排除，低版本 `allowBackup="false"` |
| 外部 app 启动本应用的 Activity/Service 抛 `SecurityException` | 组件加了 `android:permission`，调用方未持有 | 确认是刻意保护，还是遗漏了对调用方的授权 |
| 广播 receiver 收不到，却没有任何异常 | 接收器声明了 `android:permission`，发送方未持有 | 排查时应先检查权限，再检查 intent-filter |
| 别的 app 装不上，报 `INSTALL_FAILED_DUPLICATE_PERMISSION` | 与已安装 app 声明了同名自定义权限且签名不同 | 权限用反向域名命名 |
| `package` 属性报错 | AGP 8 已移除 manifest 的 `package` | 改到 `build.gradle` 的 `namespace` |

## 小结

- manifest 最终是**合并**出来的，不是手写那一份；冲突用 `tools:` 裁决，结果看 `merged_manifests`。
- 包名来自 `namespace`，`package` 属性已被移除。
- targetSdk 31+ 的组件必须显式写 `android:exported`。
- 给组件加 `android:permission` 是 `exported` 之上的第二道门；广播权限的“发/收”两个方向、自定义权限的命名冲突与安装顺序，是最常见的三类问题。
- API 30+ 的包可见性、API 31+ 的备份规则，是两份最容易忽略、又影响上线的现代变更。
- `allowBackup` 默认开，处理敏感数据的应用应显式关闭。
