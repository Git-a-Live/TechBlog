## 为什么协程要专门学测试

协程代码难测，卡在两件事上，跟业务逻辑本身没关系：

1. **时间不可控**：`delay(10_000)`如果真等10秒，一个用例就能把CI拖垮；`withTimeout(3_000)`更是没法验证边界。
2. **调度器不可控**：`Dispatchers.IO`、`Dispatchers.Main`都是**全局单例**，测试里既不能换、也不能等，Android上还依赖真实主线程。

`kotlinx-coroutines-test`针对这两点提供了两个武器：**虚拟时间**（让`delay`瞬间走完）和**可替换调度器**（`TestDispatcher`）。掌握这套API，协程测试的写法就与普通单元测试无异。

## 依赖引入

```kotlin
// 单元测试（JVM）
testImplementation "org.jetbrains.kotlinx:kotlinx-coroutines-test:$specified_version"

// 插桩测试（androidTest）
androidTestImplementation "org.jetbrains.kotlinx:kotlinx-coroutines-test:$specified_version"
```

版本应与项目使用的`kotlinx-coroutines-core`保持一致，避免出现`TestScope`与真实`CoroutineScope`行为不一致的问题。

## runTest：唯一入口

```kotlin
@Test
fun `delay 不会真的等待`() = runTest {
    val start = currentTime
    delay(10_000)
    assertEquals(10_000L, currentTime - start)   // 虚拟时间瞬间推进了10秒
}
```

关键点：

- `runTest`内部使用`TestScope`，它的调度器带**虚拟时钟**，`delay`只是把任务登记在未来的某个虚拟时刻，并不会真的睡眠。
- 整个测试有总超时，可以用`runTest(timeout = 10.seconds) { ... }`显式指定，避免 CI 上偶发挂死后一直卡着。
- 协程测试的入口只有`runTest`：`runBlockingTest`已被移除，带`dispatchTimeoutMs`参数的重载自1.11.0起为**ERROR级废弃**（源码注释：`Error since 1.11.0, warning since 1.7.0, was experimental in 1.6.x`）。

## 两种 TestDispatcher

`runTest`默认使用`StandardTestDispatcher`，也可以手动指定另一个：

| 对比项 | `StandardTestDispatcher` | `UnconfinedTestDispatcher` |
|:--|:--|:--|
| 启动行为 | 新协程**入队**，等调度器执行 | 新协程**立即**在当前线程执行 |
| 与生产的一致性 | 高（协程不会插队执行） | 低（相当于`Dispatchers.Unconfined`） |
| 需要手动推进时间 | 需要`advanceUntilIdle()`等 | 大多不需要 |
| 适用场景 | 绝大多数业务逻辑测试 | 简单场景、状态初始化的断言 |
| 风险 | 忘记推进会得到"过早断言"的假绿 | 掩盖并发顺序问题 |

```kotlin
@Test
fun 标准调度器需要推进() = runTest {          // 默认 StandardTestDispatcher
    var result = 0
    launch { result = 1 }
    assertEquals(0, result)                  // 协程还没跑
    advanceUntilIdle()                       // 推进到空闲
    assertEquals(1, result)
}
```

## 虚拟时间三件套

| API | 作用 |
|:--|:--|
| `runCurrent()` | 只执行**当前虚拟时刻**已排队的任务，时间不前进 |
| `advanceTimeBy(n)` | 把虚拟时钟前推n，执行区间内到期的任务（**左闭右开**：恰好落在终点的任务不会执行） |
| `advanceUntilIdle()` | 一直推进到没有任何待执行任务，常用于"等所有异步都跑完再断言" |

> `advanceTimeBy(n)`的区间是`currentTime()..<currentTime() + n`，因此如果某个任务正好安排在`n`这个时刻，需要再调一次`runCurrent()`把它跑掉。这是最容易写错的地方。

## 调度器注入：让生产代码可替换

测试能不能控制调度器，取决于生产代码怎么写。**不要把`Dispatchers.IO`写死在函数体里**，而是从外部注入：

```kotlin
// 推荐：通过构造参数注入，默认值保留生产行为
class UserRepository(
    private val ioDispatcher: CoroutineDispatcher = Dispatchers.IO
) {
    suspend fun load(): User = withContext(ioDispatcher) {
        api.fetchUser()
    }
}

// 测试时替换成测试调度器
val repo = UserRepository(StandardTestDispatcher(testScheduler))
```

`runTest`的`TestScope`里可以直接拿到`testScheduler`，这样被测代码与测试共享同一个虚拟时钟，`advanceUntilIdle()`才能推动它内部的`delay`。

## 测 ViewModel：替换 Main 调度器

`viewModelScope`内部用的是`Dispatchers.Main.immediate`，在JVM单元测试里没有主线程，会直接抛`Module with the Main dispatcher had failed to initialize`。解决办法是`Dispatchers.setMain()`：

```kotlin
@OptIn(ExperimentalCoroutinesApi::class)
class UserViewModelTest {

    private val dispatcher = StandardTestDispatcher()

    @Before
    fun setUp() {
        Dispatchers.setMain(dispatcher)      // 用测试调度器顶替 Main
    }

    @After
    fun tearDown() {
        Dispatchers.resetMain()              // 必须还原，否则污染同JVM的其他测试
    }

    @Test
    fun `加载成功后状态为 Success`() = runTest {
        val vm = UserViewModel(FakeUserRepository())
        vm.load()
        advanceUntilIdle()                   // 推动 viewModelScope 里的协程
        assertEquals(UiState.Success, vm.uiState.value)
    }
}
```

两个注意点：

1. `setMain`/`resetMain`目前仍标注`@ExperimentalCoroutinesApi`，需要`@OptIn`。
2. `setMain`是**全局副作用**，漏掉`resetMain()`会让后续测试继续用测试调度器，出现"单跑通过、全跑失败"的经典问题。

## 测 Flow

**有限流**直接收集成集合断言：

```kotlin
@Test
fun `过滤掉偶数`() = runTest {
    val result = flowOf(1, 2, 3, 4).filter { it % 2 == 1 }.toList()
    assertEquals(listOf(1, 3), result)
}
```

**无限流、`StateFlow`、`SharedFlow`**推荐用[Turbine](https://github.com/cashapp/turbine)（`app.cash.turbine:turbine:1.2.1`，2025-06发布，仓库仍在维护）：

```kotlin
@Test
fun `状态先 Loading 后 Success`() = runTest {
    val vm = UserViewModel(FakeUserRepository())
    vm.uiState.test {
        assertEquals(UiState.Loading, awaitItem())
        vm.load()
        assertEquals(UiState.Success, awaitItem())
        cancelAndIgnoreRemainingEvents()
    }
}
```

Turbine的价值在于把"等下一个发射"变成挂起调用（`awaitItem()`），不必靠`delay`猜时序，也不用自己处理超时。

## 常见坑

1. **`runTest`不能嵌套**：内层再次调用会抛`IllegalStateException`。
2. **在`runTest`里用真实调度器**（如`Dispatchers.IO`）会跳出虚拟时间，断言可能早于任务完成；要么注入测试调度器，要么用`advanceUntilIdle()`之外的手段等待。
3. **`UnconfinedTestDispatcher`让`launch`立刻执行**，容易写出"看起来通过、生产环境顺序不同"的测试。
4. **`GlobalScope`启动的协程不受`runTest`控制**，测试会在协程完成前结束——这也是不建议用`GlobalScope`的又一理由。
5. **`withTimeout`走的是虚拟时钟**：在`runTest`里超时判断由调度器推进，不占真实时间。因此`advanceUntilIdle()`有可能直接把超时"推"出来——写测试时要按虚拟时间计算超时点，而不是按真实耗时估算。

## 调试手段

- **命名协程**：`launch(CoroutineName("upload")) { ... }`，日志里能区分是哪个协程。
- **打开调试模式**：JVM参数加`-Dkotlinx.coroutines.debug`，协程的`toString()`会带上`@coroutine#N`，异常栈里也能看到协程边界。
- **`kotlinx-coroutines-debug`** 模块提供`DebugProbes`，可以dump所有活跃协程（含状态与栈），用于排查"协程泄漏"；仅限调试环境，生产不要开。

## 小结

| 场景 | 工具 |
|:--|:--|
| 一般挂起函数/仓库层 | `runTest` + 虚拟时间 + 注入`TestDispatcher` |
| ViewModel | 追加`Dispatchers.setMain(StandardTestDispatcher())` |
| Flow（有限） | `toList()`直接断言 |
| Flow（无限/热流） | Turbine的`test{}` + `awaitItem()` |
| 排查协程泄漏 | `DebugProbes` + `CoroutineName` |
