## 延迟初始化

在 Java 中，声明变量却没有马上赋值的情形有很多，尤其是使用全局变量的时候。没有马上赋值（即未初始化）的变量默认为 `null`，在使用时需要做判空处理。对于追求空安全的 Kotlin 而言，未初始化的变量总是一个巨大的隐患，因而会迫使开发者在声明变量的同时必须初始化，或者允许该类型为空，然后在每个用到该变量的地方都做判空处理。

Kotlin 还给出了另一种解决方案，那就是先用 `lateinit` 关键字来修饰变量，等到正式调用之前再进行赋值，从而实现初始化的延迟，并且不需要声明变量类型可为空，以确保空安全。

`lateinit` 的使用范围比“类里的 `var`”要宽，但也有明确的边界：

- 只能修饰 `var`，不能修饰 `val`；
- 变量必须是**非空类型**，且**不能是基本类型**（`Int`、`Long`、`Boolean` 等）；
- 可以声明在类体中、顶层作用域，也可以声明为局部变量；
- 不能声明在主构造函数的参数里；
- 不能带自定义的 `getter` / `setter`。

```kotlin
class WeatherStation {
    lateinit var latestReading: String

    fun update(reading: String) {
        latestReading = reading
    }

    fun printReading() {
        println(latestReading)
    }
}
```

`lateinit` 的实现方式是把字段先置为 `null`，访问时用 `null` 判断是否已经初始化（`isInitialized` 查的也是这个）。基本类型字段没有 `null` 这个哨兵值可用，因此被排除在外。

如果在赋值之前就访问，抛出的并不是空指针异常，而是 `UninitializedPropertyAccessException`：

```text
kotlin.UninitializedPropertyAccessException: lateinit property latestReading has not been initialized
```

因此，在无法确定是否已经赋值的场景（例如依赖注入、单元测试的 `@Before`），应当先用 `isInitialized` 判断：

```kotlin
class WeatherStation {
    lateinit var latestReading: String

    fun printReading() {
        if (this::latestReading.isInitialized) {
            println("Latest reading: $latestReading")
        } else {
            println("No reading available")
        }
    }
}
```

`isInitialized` 只能用于当前作用域内**本来就能访问**的属性：同一个类中的属性、外部类的属性，或同一个文件中的顶层属性。

> `lateinit` 本身不提供任何线程安全保障。多线程环境下“先判断再赋值”仍可能竞争，需要自行加锁；`by lazy` 默认线程安全，但它只能用于 `val`，不能替代需要重新赋值的 `lateinit var`。

`val` 不能用 `lateinit`，但 `val` 并不要求“必须在声明处赋值”，只要在构造过程结束前完成赋值即可——声明处、`init` 块、构造函数体内都算：

```kotlin
class Config {
    val host: String

    init {
        host = loadHost()
    }

    private fun loadHost(): String = "localhost"
}
```

如果 `val` 需要推迟到**第一次访问**时才计算，则使用属性委托 `by lazy`，详见[[4. 反射#lazy函数|lazy函数]]。

两者的分工可以总结为：

| 对比项 | `lateinit var` | `by lazy` |
| :--- | :--- | :--- |
| 适用声明 | `var` | `val` |
| 类型可否可空 | 必须非空 | 可以可空 |
| 基本类型 | 不支持 | 支持 |
| 赋值次数 | 可多次赋值 | 只初始化一次 |
| 初始化时机 | 手动赋值 | 首次访问 |
| 线程安全 | 不保证 | 默认 `SYNCHRONIZED` |
| 判断是否已初始化 | `::prop.isInitialized` | `lazyValue.isInitialized()` |

## 扩展函数

扩展函数是指在不修改某个类的源码的情况下，仍然可以向该类添加的新函数，这就是“扩展”含义的由来。扩展函数在很多情况下可以让 API 变得更加简洁、丰富和面向对象，尤其是一些不可继承类，利用扩展函数可以在不修改源码的前提下扩充它们的 API。

扩展函数的定义语法如下：

```kotlin
fun ClassName.methodName(param: ParamType): ReturnType {
    // TODO
}
```

相比于定义一个普通函数，定义扩展函数只需要在函数名前加上 `类名.` 的语法结构，就表示将该函数添加到指定类（任何类都可以）中了。上述代码中的 `ClassName` 部分被称为 Receiver（接收器），Receiver 在扩展函数中可以用 `this` 访问。扩展函数可以定义在任意一个现有类当中，不一定要像 Java 那样新创建一个文件，同时最好将扩展函数定义成顶层方法，以使其拥有全局访问域。

```kotlin
fun String.lastChar(): Char = this[length - 1]

println("kotlin".lastChar()) // n
```

在 JVM 上，扩展函数会被编译成一个**静态方法**，接收者作为第一个参数传入，因此它没有额外的运行时开销，也不存在“真的把方法塞进了那个类”这回事。

理解扩展函数的关键在于：**它是静态解析的**。调用哪个扩展函数，取决于变量的**编译期类型**，而不是运行期的实际类型；扩展函数也不能被重写。

```kotlin
open class Animal
class Dog : Animal()

fun Animal.describe() = "Animal"
fun Dog.describe() = "Dog"

fun printDescription(animal: Animal) {
    println(animal.describe()) // 输出 Animal，而不是 Dog
}

printDescription(Dog())
```

同样的原因，如果类本身已经有一个同名同签名的成员函数，那么**成员函数永远优先**，扩展函数不会被调用：

```kotlin
class Foo {
    fun bar() = "member"
}

fun Foo.bar() = "extension"

println(Foo().bar()) // member
```

扩展函数还有几条边界需要记住：

- 不能访问接收者的 `private` / `protected` 成员，扩展并没有获得特殊的访问权限；
- 扩展属性不能有 backing field，因此不能写初始化器，必须显式提供 `getter`（`var` 还要提供 `setter`）：

```kotlin
val String.lastChar: Char
    get() = this[length - 1]

var StringBuilder.firstChar: Char
    get() = this[0]
    set(value) {
        this.setCharAt(0, value)
    }
```

- 接收者可以为可空类型，此时函数体内需要用 `this?` 或判空处理，这种写法常用于给可空类型补充默认行为：

```kotlin
fun Any?.toStringOrEmpty(): String = this?.toString() ?: ""
```

- 扩展函数也可以声明为某个类的成员，这种“成员扩展函数”只在那个类的作用域内可见，并且同时拥有两个接收者：扩展接收者和分发接收者。

## 密封类

在 Kotlin 中把 `when` 当作**表达式**使用时，编译器要求它穷尽所有情况，否则就必须补一个 `else` 分支。这有两个问题：一是其他分支已经包含所有的状态情况了，`else` 分支是多余的；二是新增状态情况时，如果忘记在 `when` 中添加指定分支语句，那么就会默认走 `else` 分支，可能无法满足需要。为了解决这一问题，Kotlin 使用了密封类机制。

所谓密封类，是指在声明一个可继承类时用 `sealed` 关键字来修饰。密封类自身永远是抽象类，不能直接实例化，它的构造器只能是 `protected`（默认）或 `private`。

```kotlin
sealed class Result<out T> {
    data class Success<T>(val data: T) : Result<T>()
    data class Failure(val error: Throwable) : Result<Nothing>()
    object Loading : Result<Nothing>()
}
```

子类的声明位置有一条明确但常被写错的规则：**直接子类必须与密封类位于同一个包、同一个模块中**。Kotlin 1.5 起已经不再要求“同一个文件”，子类可以分散在同一包的不同文件里；它们可以是顶层声明，也可以嵌套在其它具名类、接口或对象中，但不能是局部类或匿名对象。间接子类（即某个直接子类再派生的类）不受这条限制。

```kotlin
// FileA.kt
package com.example.result

sealed class Result<out T>
```

```kotlin
// FileB.kt
package com.example.result

data class Success<T>(val data: T) : Result<T>()   // 合法：同包不同文件
```

密封类最直接的价值体现在 `when` 上：编译器知道全部直接子类，因此可以检查分支是否穷尽，不需要 `else`。

```kotlin
fun <T> render(result: Result<T>): String = when (result) {
    is Result.Success -> result.data.toString()
    is Result.Failure -> result.error.message ?: "unknown error"
    Result.Loading -> "loading"
}
```

穷尽性检查的强度随版本收紧过：`when` 作为**表达式**时一直要求穷尽；作为**语句**时，Kotlin 1.6 起对以枚举、密封类或 `Boolean` 为主题的 `when` 给出警告，Kotlin 1.7 起升为编译错误。因此新增子类后，所有漏掉分支的 `when` 都会在编译期暴露出来。

Kotlin 1.5 还引入了**密封接口**，规则与密封类一致，但实现方可以实现多个密封接口，更适合用来表达“封闭的错误类型”这类层次：

```kotlin
sealed interface Error

sealed class IOError : Error
class FileReadError(val file: File) : IOError()
class DatabaseError(val source: String) : IOError()

object RuntimeError : Error
```

密封类与枚举的差别在于：枚举常量是单例，所有常量共享同一个结构；密封类的子类可以各自携带不同的数据，也可以有多个实例。因此“状态机里每个状态带不同 payload”更适合用密封类，“一组固定常量”用枚举更合适。枚举不能继承密封类（它已经继承了 `Enum`），但可以实现密封接口。

需要遍历所有子类时，可以用反射的 `KClass.sealedSubclasses`，详见[[4. 反射#KClass常用API|KClass 常用 API]]。
