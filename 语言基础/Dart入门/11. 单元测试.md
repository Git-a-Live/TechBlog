`fromJson` 的正确性依赖外部接口的实际响应：字段是否齐全、可选字段缺失时走哪个分支、数组长度是否与预期一致。手工运行 CLI 只能覆盖少数输入，接口字段调整后也很难立刻发现回归。

单元测试把“给定输入 → 期望输出”固化为可重复执行的断言。测试数据使用真实响应的快照，测试对象是纯函数式的反序列化逻辑，不依赖网络，因此运行快速且结果稳定。

## 测试的对象与价值

适合单元测试的目标：

- 数据模型的 `fromJson` / `toJson` 往返；
- 参数解析器对各种非法输入的反应；
- 字符串格式化、计算属性等纯函数；
- 错误类型与消息是否符合契约。

不适合用单元测试覆盖的目标：

- 真实网络请求的端到端行为（应使用集成测试或契约测试）；
- 依赖系统时间、随机数、文件系统的逻辑（需要注入替身）；
- UI 布局与交互（需要 Widget 测试或集成测试）。

单元测试的核心收益是“重构安全网”：修改实现后，只要公开行为不变，测试应全部通过；测试失败则精确指出哪条契约被破坏。

## 依赖与目录

`test` 包声明在 `dev_dependencies` 中：

```yaml
# wikipedia/pubspec.yaml
dev_dependencies:
  lints: ^5.0.0
  test: ^1.24.0
```

开发依赖只在开发与测试阶段使用，不会传递给依赖该包的下游项目，也不应被 `lib/` 中的生产代码导入。测试代码放在 `test/`，文件名以 `_test.dart` 结尾，`dart test` 默认递归查找这些文件。

```text
wikipedia/
├── lib/
│   └── src/model/
│       ├── article.dart
│       ├── search_results.dart
│       ├── summary.dart
│       └── title_set.dart
└── test/
    ├── model_test.dart
    └── test_data/
        ├── cat_extract.json
        ├── dart_lang_summary.json
        └── open_search_response.json
```

测试数据与测试代码分离，便于更新快照、复用样本，也避免在测试文件中嵌入大段转义字符串。

## 第一个测试

```dart
import 'dart:convert';
import 'dart:io';

import 'package:test/test.dart';
import 'package:wikipedia/src/model/article.dart';
import 'package:wikipedia/src/model/search_results.dart';
import 'package:wikipedia/src/model/summary.dart';

const String dartLangSummaryJson = './test/test_data/dart_lang_summary.json';
const String catExtractJson = './test/test_data/cat_extract.json';
const String openSearchResponse = './test/test_data/open_search_response.json';

void main() {
  group('deserialize example JSON responses from wikipedia API', () {
    test('deserialize summary into a Summary object', () async {
      final String pageSummaryInput =
          await File(dartLangSummaryJson).readAsString();
      final Map<String, Object?> pageSummaryMap =
          jsonDecode(pageSummaryInput) as Map<String, Object?>;
      final Summary summary = Summary.fromJson(pageSummaryMap);

      expect(summary.titles.canonical, 'Dart_(programming_language)');
    });
  });
}
```

测试文件本身是一个普通的 Dart 程序，入口为 `main`。`test()` 注册一个测试用例，`expect()` 断言实际值与匹配器一致。

路径 `./test/test_data/...` 相对于包的根目录。`dart test` 以包根目录为工作目录启动测试进程，因此从 `wikipedia/` 执行时路径成立；从仓库根目录执行需要先进入包目录，或使用 `dart test wikipedia` 并调整路径策略。

## group 与 test

```dart
void main() {
  group('deserialize example JSON responses from wikipedia API', () {
    test('deserialize Dart summary', () async { ... });

    test('deserialize Cat article', () async { ... });

    test('deserialize Open Search results', () async { ... });
  });
}
```

| 函数 | 作用 |
|------|------|
| `group(description, body)` | 把相关测试组织在一起，可嵌套，失败时输出分组路径 |
| `test(description, body)` | 定义一个测试用例，body 可以是同步或异步函数 |
| `setUp(body)` | 每个测试前执行，用于创建共享状态 |
| `tearDown(body)` | 每个测试后执行，用于释放资源 |
| `setUpAll(body)` | 分组内所有测试开始前执行一次 |
| `tearDownAll(body)` | 分组内所有测试结束后执行一次 |

测试描述应说明“在什么条件下得到什么结果”，而不是“测试函数名”。失败信息会拼接分组与用例描述，描述越具体，定位越快。

共享状态优先通过 `setUp` 创建，而不是在 `group` 外定义可变全局变量。测试之间不应有顺序依赖；需要主动暴露顺序问题时，可用 `--test-randomize-ordering-seed=random` 随机化执行顺序，依赖顺序的测试会因此间歇失败。

## 匹配器

`expect(actual, matcher)` 的第二个参数是匹配器，描述实际值应满足的条件：

| 匹配器 | 断言 |
|--------|------|
| `equals(expected)` | 深度相等，集合比较元素 |
| `same(expected)` | 同一对象引用 |
| `greaterThan(n)` / `lessThan(n)` | 数值比较 |
| `greaterThanOrEqualTo(n)` | 大于等于 |
| `contains(value)` | 字符串包含子串、集合包含元素 |
| `isEmpty` / `isNotEmpty` | 空集合、空字符串、空 map |
| `isNull` / `isNotNull` | 空值判断 |
| `isA<T>()` | 运行时类型判断 |
| `throwsA(matcher)` | 执行时抛出匹配的异常 |
| `predicate<T>(fn)` | 自定义谓词 |

```dart
expect(summary.titles.canonical, 'Dart_(programming_language)');
expect(articles.first.title.toLowerCase(), 'cat');
expect(results.results.length, greaterThan(1));
expect(summary.extract, isNotEmpty);
```

`equals` 对集合做逐元素比较，对 map 做逐键值比较；`same` 才比较引用。断言对象时，如果类没有重写 `==`，`equals` 退化为引用比较，此时应断言关键字段而不是整个对象。

`expect` 的第三个参数 `reason` 会在失败信息中追加说明：

```dart
expect(results.results.length, greaterThan(1),
    reason: 'opensearch 至少应返回两条结果');
```

## 异步测试

测试回调声明为 `async` 后，测试框架会等待返回的 Future 完成再判定结果：

```dart
test('load summary from file', () async {
  final input = await File(dartLangSummaryJson).readAsString();
  final map = jsonDecode(input) as Map<String, Object?>;
  final summary = Summary.fromJson(map);
  expect(summary.pageid, isA<int>());
});
```

如果忘记 `async` 而在回调里使用 `await`，代码无法通过编译；如果返回了 Future 但没有 `await`，测试会在异步工作完成前结束，断言可能被跳过。

异步异常的断言使用 `expectLater`：

```dart
test('reject invalid summary', () async {
  await expectLater(
    () async => Summary.fromJson(<String, Object?>{}),
    throwsFormatException,
  );
});
```

`expect` 用于同步值，`expectLater` 返回 Future，适合需要等待的匹配器（异步异常、Stream 事件）。默认单个测试超时为 30 秒，可通过 `timeout: Timeout(Duration(seconds: 5))` 调整。

## 测试数据

三个样本分别覆盖不同的响应形状：

| 文件 | 顶层类型 | 覆盖点 |
|------|----------|--------|
| `dart_lang_summary.json` | object | 完整摘要，含 `description` |
| `cat_extract.json` | object | `query.pages` 嵌套结构，页面对象含 `extract` |
| `open_search_response.json` | array | 四元素数组，标题与 URL 两个子数组 |

样本应来自真实响应，去除与测试无关的大字段，但保留结构特征：可选字段、嵌套层级、数组长度。手工构造的“理想 JSON”容易漏掉真实接口的空值与缺字段情况。

样本更新策略：

- 接口新增可选字段：旧样本仍应通过，新增一个包含新字段的样本。
- 接口字段改名或类型变化：测试失败，先确认是接口变更还是解析缺陷，再决定改代码或改样本。
- 样本包含用户数据或令牌：脱敏后再提交。

## 异常路径

只测试成功路径会遗漏解析器的防御逻辑。至少覆盖：

```dart
test('throws when required field is missing', () {
  expect(
    () => Summary.fromJson(<String, Object?>{'pageid': 1}),
    throwsFormatException,
  );
});

test('throws when field has wrong type', () {
  expect(
    () => Summary.fromJson(<String, Object?>{'pageid': 'not-an-int'}),
    throwsFormatException,
  );
});
```

`Summary.fromJson` 的模式匹配在字段缺失或类型不符时落到 `_` 分支并抛出 `FormatException`，上述断言验证的是这一契约。若实现改为返回 `null` 或默认对象，测试应立即失败。

异常断言应使用具体类型或匹配器，避免 `throwsA(anything)` 这类“只要抛错就算通过”的写法；后者无法区分预期异常与实现缺陷。

## 运行与过滤

```bash
cd wikipedia
dart test
```

输出中的符号含义：

| 符号 | 含义 |
|------|------|
| `+n` | 已通过 n 个测试 |
| `-n` | 已失败 n 个测试 |
| `~n` | 已跳过 n 个测试 |

```text
00:02 +4: All tests passed!
```

常用选项：

| 命令 | 作用 |
|------|------|
| `dart test -r expanded` | 逐条打印测试结果，便于定位 |
| `dart test -n "Summary"` | 只运行名称匹配的测试 |
| `dart test --coverage=coverage` | 生成覆盖率数据 |
| `dart test --test-randomize-ordering-seed=random` | 随机顺序，暴露顺序依赖 |

失败时先看第一条失败：后续失败可能是同一原因引发的连锁反应。堆栈中应定位到测试代码与实现代码的交界处，而不是只看最底层的框架帧。

## 边界与取舍

- 测试公开行为，不测试私有实现。私有方法通过公开 API 间接覆盖，重构时测试不应随之改写。
- 一个测试只验证一个概念。多个断言可以存在于同一用例，但应围绕同一行为。
- 避免在测试中复制实现逻辑。用固定期望值，而不是用与实现相同的算法计算期望值。
- 网络、时间、随机数需要注入替身。`package:http/testing.dart` 提供 `MockClient`，可在不发起真实请求的情况下验证 API 客户端；`package:mockito` 适合更复杂的交互验证，但需要代码生成。
- 测试不是越多越好。覆盖关键契约与边界条件即可，重复断言同一行为的测试只会增加维护成本。

测试把“接口形状”固化为可执行文档。下一节在模型与测试的基础上构建 API 客户端：构造带查询参数的 URI、检查状态码、在失败时抛出异常，并把函数与模型统一导出，见 [[12. 网络请求与 API 客户端|网络请求与 API 客户端]]。
