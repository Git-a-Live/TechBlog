单个文件可以容纳几百行代码，但命令解析、网络访问、数据模型混在一起后，复用与测试都会变得困难。Dart 用“包（package）”作为分发与依赖的单位，用“库（library）”作为编译与可见性的单位：一个包可以包含多个库，库通过 `import` 使用其他库，通过 `export` 决定对外暴露哪些声明。

这一节把命令行参数解析逻辑从应用入口剥离出来，做成独立的 `command_runner` 包，并让 `cli` 通过路径依赖引用它。

## 包与库的区别

| 概念 | 边界 | 载体 | 作用 |
|------|------|------|------|
| 包 | 发布、依赖解析的最小单位 | 含 `pubspec.yaml` 的目录 | 声明名称、版本、依赖，供其他包引用 |
| 库 | 编译、命名空间、私有性的单位 | 一个 `.dart` 文件（可含 `part`） | 组织声明，控制导入导出 |
| 文件 | 物理存储单位 | `.dart` 文件 | 通常一个文件即一个库 |

一个包至少包含 `pubspec.yaml` 与 `lib/` 目录。包的名称在 `pubspec.yaml` 的 `name` 字段声明，导入时使用 `package:<name>/<path>`，路径相对于该包的 `lib/`。

```dart
import 'package:cli/cli.dart';          // 引用本包 lib/cli.dart
import 'package:command_runner/command_runner.dart'; // 引用依赖包
```

## 创建库包

```bash
dart create -t package command_runner
```

`-t package` 指定库包模板，生成的目录结构如下：

```text
command_runner/
├── lib/
│   ├── command_runner.dart        # 公开入口
│   └── src/
│       └── command_runner_base.dart # 实现细节
├── example/
│   └── command_runner_example.dart
├── test/
│   └── command_runner_test.dart
├── analysis_options.yaml
├── CHANGELOG.md
├── LICENSE
├── pubspec.yaml
└── README.md
```

与 `console` 模板相比，库包没有 `bin/`，因为它不被直接执行，而是被其他包导入。`example/` 是可运行的示例，用于演示 API 用法，也可以作为手工验证入口。

模板生成的占位类需要替换：

```dart
// lib/src/command_runner_base.dart
class CommandRunner {
  /// Runs the command-line application logic with the given arguments.
  Future<void> run(List<String> input) async {
    print('CommandRunner received arguments: $input');
  }
}
```

## 公开入口与实现分层

`lib/` 根目录下的文件是包的公开入口，`lib/src/` 存放实现细节。入口文件只做声明与导出：

```dart
/// A simple command runner to handle command-line arguments.
///
/// More extensive documentation for this library goes here.
library;

export 'src/command_runner_base.dart';
```

`library;` 是不带名称的库指令，作用是给整个库挂文档注释与库级注解（如 `@TestOn`、`@deprecated`）。也可以写成 `library command_runner;` 显式命名，但库名不参与导入路径解析，通常省略。

`export` 把另一个库的声明重新暴露给当前库的使用者：

```dart
export 'src/command_runner_base.dart';
export 'src/arguments.dart';
export 'src/exceptions.dart' show ArgumentException;
```

`export` 与 `import` 的方向不同：

```text
实现库 src/command_runner_base.dart
        │  export（重新暴露）
        ▼
公开入口 command_runner.dart
        │  import（使用）
        ▼
调用方 cli/bin/cli.dart
```

`import` 让当前库可以使用目标库的声明；`export` 让“导入当前库的人”也能看到目标库的声明。二者都不改变目标库自身的可见性规则。

## 私有性与 src 约定

Dart 的私有性以库为单位：以下划线开头的标识符（`_options`、`_removeDash`）只在声明它的库内可见，其他库即使位于同一个包也无法访问。

`lib/src/` 不是语言强制的私有目录，而是社区约定：表示“实现的内部结构，可能随时调整”。分析器提供 `implementation_imports` 规则，当其他包直接导入 `package:foo/src/...` 时给出警告。把实现放在 `src/`、在 `lib/foo.dart` 中集中 `export`，可以获得两个好处：

1. 调用方只依赖稳定的入口路径，内部文件重命名不会破坏下游。
2. 包的公开 API 由入口文件的 `export` 列表显式定义，新增内部文件不会意外泄露。

需要选择性暴露时，`show` 与 `hide` 可以过滤声明：

```dart
export 'src/arguments.dart' show Option, OptionType, ArgResults;
export 'src/internal.dart' hide DebugPrinter;
```

`import` 同样支持 `show`/`hide`，用于限制当前库可见的符号范围。

## 路径依赖

`command_runner` 位于本地目录，尚未发布到 pub.dev，因此 `cli` 使用路径依赖：

```yaml
# cli/pubspec.yaml
name: cli
publish_to: none

environment:
  sdk: ^3.8.0

dependencies:
  http: ^1.3.0
  command_runner:
    path: ../command_runner
```

`path` 相对于当前 `pubspec.yaml` 所在目录解析。`publish_to: none` 阻止误发布到 pub.dev，同时避免“应用包引用本地路径依赖”的分析器警告。

等价的命令行写法：

```bash
dart pub add command_runner --path ../command_runner
```

然后解析依赖：

```bash
cd cli
dart pub get
```

路径依赖不参与版本求解，直接使用目标目录的当前内容，修改 `command_runner` 后无需重新 `pub get`。这适合多包工程在开发期同步演进；发布后应改为 hosted 依赖并声明版本约束。

## 使用依赖包

`cli/bin/cli.dart` 导入新包并替换原有分发逻辑：

```dart
import 'package:command_runner/command_runner.dart';

void main(List<String> arguments) async {
  var runner = CommandRunner();
  await runner.run(arguments);
}
```

`main` 声明为 `async` 后可以 `await` 运行结果，保证进程在命令执行完毕后再退出，也让异常沿 Future 链向上传播。`var runner` 的类型由构造函数推断为 `CommandRunner`。

此时原先的 `printUsage`、`searchWikipedia`、`getWikipediaArticle` 已从入口移除，后续章节会把它们重新实现为包内的命令与 API 客户端。

## 版本约束

`pubspec.yaml` 的依赖值可以是版本约束、路径、Git 仓库或 SDK 包：

| 写法 | 含义 |
|------|------|
| `http: ^1.4.0` | `>=1.4.0 <2.0.0` |
| `http: '>=1.2.0 <1.5.0'` | 显式区间 |
| `http: any` | 任意版本，不推荐 |
| `command_runner: {path: ../command_runner}` | 本地路径 |
| `foo: {git: url, ref: tag}` | Git 仓库 |
| `test: {sdk: test}` | SDK 内置包 |

应用包应提交 `pubspec.lock`，确保不同机器与 CI 得到完全一致的依赖版本；库包通常不提交锁文件，因为下游会自行求解版本，锁文件对下游无效。

## 依赖方向

多包工程的价值不只是“文件分开”，更在于约束依赖方向：

```text
cli  ──────►  command_runner
 │                  │
 └──────►  wikipedia
```

`cli` 依赖两个库包，库包之间互不依赖，也不反向依赖 `cli`。这样 `command_runner` 可以在其他 CLI 项目中复用，`wikipedia` 可以被测试或其他前端调用，而 `cli` 只承担参数拼装与输出。

依赖方向一旦反过来（库包导入应用入口），测试就需要启动整个应用，复用也无从谈起。拆分时先确定“谁被谁使用”，再决定包边界。

## 工程约定

- 一个包只解决一个领域问题，包名直接描述职责，如 `command_runner`、`wikipedia`。
- 公开 API 集中在 `lib/<package>.dart`，内部实现放 `lib/src/`。
- 库代码不依赖 `dev_dependencies`，测试依赖只出现在 `test/`。
- 应用包设置 `publish_to: none`，库包保留发布配置与 `CHANGELOG.md`。
- 路径依赖只用于开发期，发布前改为版本约束。

包提供了分发边界，库提供了可见性边界，`export` 则是两者的连接点。下一节在这个包内实现 `Option`、`ArgResults` 等数据模型，开始使用类、构造函数、getter 与枚举表达命令行参数的结构，见 [[5. 类、对象与枚举|类与对象]]。
