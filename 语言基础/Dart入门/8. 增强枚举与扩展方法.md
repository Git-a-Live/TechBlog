基础枚举只能表达“有哪几个值”，无法给每个值附带数据，也不能定义行为。控制台颜色恰好需要两者：每个颜色有固定的 RGB 分量，还要能把分量转换成 ANSI 转义序列并作用到文本上。

Dart 的增强枚举（enhanced enum）允许枚举声明字段、常量构造函数、方法与静态成员，使每个枚举值成为一个携带数据的常量实例。扩展方法（extension）则解决另一类问题：`String` 是 `abstract final` 类，不能被继承或实现，但仍需要给它增加项目专用的格式化能力。

## 基础枚举的边界

```dart
enum OptionType { flag, option }
```

这种枚举只有成员名与索引，适合表示互斥的分类。需要附加数据时，常见替代方案是并列的常量表或 `Map`：

```dart
class ConsoleColors {
  static const red = [242, 93, 80];
  static const yellow = [249, 248, 196];
}
```

这种写法丢失了类型约束：颜色列表可以被随意传入任意三个整数，也无法保证“所有颜色都被处理”。增强枚举把“取值范围固定”和“每个值携带数据”结合起来。

## 增强枚举

```dart
enum ConsoleColor {
  lightBlue(184, 234, 254),
  red(242, 93, 80),
  yellow(249, 248, 196),
  grey(240, 240, 240),
  white(255, 255, 255);

  const ConsoleColor(this.r, this.g, this.b);

  final int r;
  final int g;
  final int b;
}
```

语法要点：

- 枚举值列表以分号结束，之后才能声明构造函数与成员。
- 构造函数必须是 `const`，因为每个枚举值都是编译期常量实例。
- 实例字段必须是 `final`，枚举值不可变。
- 每个枚举值调用同一个构造函数，传入各自的参数。
- 枚举可以定义方法、getter、operator、静态成员，也可以实现接口。
- 枚举不能被其他类 `extends`、`with` 或 `implements`；枚举自身可以实现接口。

`ConsoleColor.red.r` 得到 `242`，`ConsoleColor.values` 按声明顺序返回全部成员。增强枚举同样支持 `name`、`index`、`byName`。

## ANSI 颜色序列

终端通过 ESC 字符（`\x1B`）引导的控制序列改变文本样式。设置真彩前景色的格式为：

```text
ESC [ 38 ; 2 ; R ; G ; B m
```

各部分含义：

| 片段 | 含义 |
|------|------|
| `ESC[` | 控制序列引导符（CSI） |
| `38` | 设置前景色 |
| `2` | 使用 24 位真彩色 |
| `R;G;B` | 红、绿、蓝分量，取值 0–255 |
| `m` | 图形模式结束符 |

背景色把 `38` 换成 `48`；`ESC[0m` 重置全部属性。把序列封装进枚举：

```dart
const String ansiEscapeLiteral = '\x1B';

enum ConsoleColor {
  lightBlue(184, 234, 254),
  red(242, 93, 80),
  yellow(249, 248, 196),
  grey(240, 240, 240),
  white(255, 255, 255);

  const ConsoleColor(this.r, this.g, this.b);

  final int r;
  final int g;
  final int b;

  String get foregroundCode => '$ansiEscapeLiteral[38;2;$r;$g;${b}m';

  String get backgroundCode => '$ansiEscapeLiteral[48;2;$r;$g;${b}m';

  static String get reset => '$ansiEscapeLiteral[0m';

  String applyForeground(String text) => '$foregroundCode$text$reset';

  String applyBackground(String text) => '$backgroundCode$text$reset';
}
```

`applyForeground` 在文本前插入前景色、末尾追加重置，避免颜色泄漏到后续输出。若只输出颜色码而不重置，之后的所有终端文本都会继承该颜色。

终端兼容性：现代终端（Windows Terminal、iTerm2、GNOME Terminal、VS Code 集成终端）普遍支持真彩色；旧版 Windows 控制台需要启用虚拟终端处理，否则会显示原始转义字符。命令行工具应在检测到不支持时提供无色模式，而不是假设所有终端都能解析。

## 扩展方法

`String` 不能被子类化，但项目需要给字符串增加 `errorText`、`titleText` 之类的语义化格式化。扩展方法提供了静态分派的语法糖：

```dart
extension TextRenderUtils on String {
  String get errorText => ConsoleColor.red.applyForeground(this);
  String get instructionText => ConsoleColor.yellow.applyForeground(this);
  String get titleText => ConsoleColor.lightBlue.applyForeground(this);
}
```

调用形式与实例成员一致：

```dart
print('Warning'.errorText);
print('Usage: ...'.titleText);
```

扩展内的 `this` 指向接收者，即 `'Warning'`。扩展可以声明：

- 实例 getter、方法、operator；
- 静态方法与静态字段；
- 泛型参数；
- 针对可空类型的扩展，如 `extension on String?`。

扩展不能声明实例字段。它不改变原类型的接口，也不产生新的运行时类型；编译器把 `'x'.errorText` 重写为 `TextRenderUtils('x').errorText`，属于静态解析。

这带来两条重要规则：

1. 扩展成员按变量的静态类型解析，不参与动态分派。若变量声明为 `Object`，即使实际值是 `String`，也看不到 `String` 的扩展成员。
2. 两个扩展为同一类型定义同名成员时，调用处会产生歧义编译错误；可以用显式扩展应用消除歧义：`TextRenderUtils(s).errorText`。

未命名的扩展（`extension on String { ... }`）只在声明它的库内可见，适合内部辅助；需要跨库使用时必须命名。

## 按词换行

帮助文本需要限制每行宽度。按空格切分后逐词累加，超过宽度就换行：

```dart
extension TextRenderUtils on String {
  List<String> splitLinesByLength(int length) {
    final List<String> words = split(' ');
    final List<String> lines = <String>[];
    final StringBuffer buffer = StringBuffer();

    for (final word in words) {
      final int candidate =
          buffer.isEmpty ? word.length : buffer.length + 1 + word.length;
      if (candidate > length && buffer.isNotEmpty) {
        lines.add(buffer.toString());
        buffer.clear();
      }
      if (buffer.isNotEmpty) {
        buffer.write(' ');
      }
      buffer.write(word);
    }

    if (buffer.isNotEmpty) {
      lines.add(buffer.toString());
    }
    return lines;
  }
}
```

这个实现的边界行为：

| 情况 | 结果 |
|------|------|
| 单词恰好等于宽度 | 单独成行 |
| 单词超过宽度 | 单独成行，行宽超出限制 |
| 连续多个空格 | `split(' ')` 产生空串，会写入多余空格 |
| 空字符串 | 返回空列表 |

需要严格处理连续空格时，应使用正则 `split(RegExp(r'\s+'))` 并过滤空串。超长单词（如 URL）无法在不破坏语义的前提下按字符截断，通常允许其超出宽度。

`StringBuffer` 在这里承担累积职责，避免每次拼接都创建新字符串。它的行为详见 [[9. 字符串构建与输出回调|字符串构建]]。

## 用 switch 分配样式

回显命令按词序循环使用三种颜色：

```dart
List<String> prettyWords = [];
final words = arg.commandArg!.split(' ');
for (var i = 0; i < words.length; i++) {
  final word = words[i];
  switch (i % 3) {
    case 0:
      prettyWords.add(word.titleText);
    case 1:
      prettyWords.add(word.instructionText);
    case 2:
      prettyWords.add(word.errorText);
  }
}
return prettyWords.join(' ');
```

`i % 3` 的取值只可能是 0、1、2，三个分支覆盖全部情况。Dart 3 的非空 `case` 执行完自动结束，不需要 `break`；如果某个 `case` 留空，则会贯穿到下一个分支，可用于多个值共享逻辑。

`switch` 语句对 `int` 不做穷尽性检查，缺少分支时未匹配的值会静默跳过。对枚举或密封类，编译器会检查是否覆盖全部成员，这更适合用枚举表达的状态机。

## 命令实现

把颜色能力组合进一个具体命令：

```dart
class PrettyEcho extends Command {
  PrettyEcho() {
    addFlag(
      'blue-only',
      abbr: 'b',
      help: 'When true, the echoed text will all be blue.',
    );
  }

  @override
  String get name => 'echo';

  @override
  bool get requiresArgument => true;

  @override
  String get description => 'Print input, but colorful.';

  @override
  String? get help =>
      'echos a String provided as an argument with ANSI coloring,';

  @override
  String? get valueHelp => 'STRING';

  @override
  FutureOr<String> run(ArgResults arg) {
    if (arg.commandArg == null) {
      throw ArgumentException(
        'This argument requires one positional argument',
        name,
      );
    }

    final words = arg.commandArg!.split(' ');
    final prettyWords = <String>[];
    for (var i = 0; i < words.length; i++) {
      final word = words[i];
      switch (i % 3) {
        case 0:
          prettyWords.add(word.titleText);
        case 1:
          prettyWords.add(word.instructionText);
        case 2:
          prettyWords.add(word.errorText);
      }
    }
    return prettyWords.join(' ');
  }
}
```

`requiresArgument` 为 `true`，`run` 中仍要检查 `commandArg` 是否为空：前者用于帮助信息与解析阶段的提示，后者防止直接调用命令时绕过校验。两层检查针对不同入口，不能互相替代。

## 设计取舍

增强枚举适合“固定集合 + 每项附带常量数据”的场景，例如颜色、日志级别、HTTP 方法。它把数据与行为收拢在类型内部，`switch` 时还能获得穷尽性检查。

扩展适合“给已有类型补充项目内工具”的场景，尤其是无法修改源码的 SDK 类型。它的局限同样明确：静态解析、不能有状态、可能与同类型上的其他扩展冲突。扩展成员过多时，调用方难以判断某个方法来自 SDK 还是项目代码，应控制扩展的数量与职责范围。
