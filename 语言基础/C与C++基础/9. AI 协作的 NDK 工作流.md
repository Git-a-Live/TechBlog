AI 能生成可编译的 JNI 代码与 CMake 配置，但无法对结果负责：它不知道目标设备的 ABI、不知道这条路径在低端机上的耗时、也无法在设备上复现崩溃。协作的有效性取决于三件事：任务描述是否携带足够约束、生成结果是否经过结构化验收、失败反馈是否包含可定位的证据。

语言层与构建层的判断力最终要固化为流程，否则每次协作都从零开始。

## 分工边界

| 环节 | AI 适合承担 | 人必须承担 |
| --- | --- | --- |
| 需求 | 补充实现方案、列举边界条件 | 确定功能边界与质量门槛 |
| 编码 | 生成候选实现、批量改写、补样板 | 判断所有权、线程模型、错误处理是否成立 |
| 构建 | 编写 CMake 片段、解释报错 | 确认 ABI、STL、标准版本与 `minSdk` 的一致性 |
| 验证 | 生成测试用例、构造边界输入 | 在真机复现、判断崩溃归因 |
| 维护 | 解释旧代码、定位可疑片段 | 评估改动风险与回归范围 |

判断标准很简单：**结论需要设备或运行期证据的环节，不能只由 AI 给出。** 语言层的语法与库用法可以采信，涉及内存布局、符号解析结果、崩溃原因的判断必须验证。

## 任务描述模板

一次可执行的任务描述包含七项约束。缺少任何一项，生成结果都需要多轮返工。

| 项 | 内容 | 缺失后果 |
| --- | --- | --- |
| 目标 | 函数职责、输入输出、调用时机 | 生成无关实现 |
| ABI | `arm64-v8a` / `armeabi-v7a`，是否两者都要 | 宽度假设错误、类型截断 |
| 构建 | NDK 版本、C++ 标准、STL 选择 | 标准库特性不可用或链接失败 |
| 线程 | 在哪个线程调用，是否跨线程回调 | 误用 `JNIEnv`、缺少 attach |
| 所有权 | 谁分配、谁释放、是否可跨线程持有 | 泄漏或悬垂 |
| 错误处理 | 返回码、异常、日志级别 | 静默失败或异常挂起 |
| 约束 | `minSdk`、性能上限、不允许的依赖 | 使用高版本 API、引入多余库 |

两种描述的差别不在篇幅，而在可验证性：

```text
约束缺失：
帮我写一个 JNI 方法，把图片转成灰度。

约束齐备：
实现 JNI 方法 Java_com_example_Image_nativeToGray。
输入：jbyteArray，长度由 GetArrayLength 取得，内容为 RGBA_8888。
输出：新建 jbyteArray，长度为 width * height，调用方负责释放。
约束：arm64-v8a 与 armeabi-v7a 都要支持；C++17；单 .so，使用 c++_static；
      minSdk 24；不引入第三方库。
线程：在 Java 调用线程内同步执行，不创建线程。
错误：参数为空或长度为 0 时返回 nullptr，不抛 Java 异常。
性能：1080p 图像单帧不超过 20 ms，允许使用 NEON 但需提供标量回退。
```

约束齐备的描述中每条约束都对应一个可检查的点：ABI 决定 `int` 与指针宽度，线程模型决定是否需要 attach，错误约定决定返回路径，性能上限决定是否需要基准测试。

## 生成代码的验收清单

验收分三层，每层都有明确的通过条件。

### 编译层

| 检查项 | 通过条件 |
| --- | --- |
| 警告 | `-Wall -Wextra` 下无新增警告 |
| ABI | 目标 ABI 全部构建通过，无宽度相关警告 |
| 标准 | `CMAKE_CXX_STANDARD` 或 `cxx_std_*` 已显式声明 |
| STL | 单 `.so` 用 `c++_static`，多 `.so` 传递 STL 对象用 `c++_shared` |
| 符号 | JNI 函数在 `extern "C"` 中，`llvm-nm` 可见 `Java_*` 符号 |

### 语义层

| 检查项 | 通过条件 |
| --- | --- |
| 引用配对 | 每个 `Get*` 都有对应的 `Release*`，覆盖所有返回路径 |
| 局部引用 | 循环内创建的对象已 `DeleteLocalRef` 或使用 `PushLocalFrame` |
| 全局引用 | 缓存的 `jclass`、回调对象有对应的 `DeleteGlobalRef` |
| 异常 | 调用可能抛异常的函数后有 `ExceptionCheck` |
| 线程 | 跨线程使用前重新获取 `JNIEnv`，attach 与 detach 配对 |
| 所有权 | 返回的缓冲区有明确的释放方，接口文档与实现一致 |
| 宽度 | `jlong` 用 `int64_t` 接收，未用 `long` 或 `int` |

### 运行层

| 检查项 | 通过条件 |
| --- | --- |
| 冒烟 | 正常输入、空输入、超长输入三条路径均无崩溃 |
| 压力 | 循环调用 1 万次，内存与引用计数稳定 |
| 检查工具 | ASan 构建下无越界、悬垂、重复释放报告 |
| 低端设备 | 在最弱目标机型上验证耗时与内存 |

前两层可以在本地完成，第三层必须在设备上完成。只通过前两层的代码不能视为可交付。

## 最小复现的构造方法

崩溃或行为异常时，最小复现是人与 AI 之间最高效的沟通材料。构造步骤：

1. **剥离业务**：删除与问题无关的分支、日志、UI 代码，保留触发路径；
2. **固定输入**：把随机或外部输入替换为常量，确保每次运行条件一致；
3. **二分注释**：注释掉一半逻辑，确认问题是否仍出现，逐步缩小范围；
4. **固定构建**：锁定单个 ABI、固定优化级别与 C++ 标准，排除构建差异；
5. **保留证据**：记录崩溃信号、fault addr、backtrace 与所用 `.so` 的构建路径。

复现规模的目标是“一个源文件、一个入口、一条命令可运行”。达到这一规模后，AI 对根因的判断才有意义，因为此时它面对的是完整上下文，而不是被截断的片段。

## 迭代循环

```text
描述任务（七项约束）
      │
      ▼
生成候选实现
      │
      ▼
静态审查（编译层 + 语义层清单）
      │  不通过 → 指出具体条目与证据，要求定点修改
      ▼
构建与真机验证
      │  失败 → 提供完整错误、构建参数、设备 ABI
      ▼
最小复现（必要时）
      │
      ▼
修复并回归（压力 + ASan）
```

循环中有两条纪律：

- **定点反馈**：一次只反馈一个问题，附上错误全文与已排除项。把“跑不起来”拆成“链接报 `undefined reference to 'AAudioStreamBuilder_openStream'`，`minSdk` 为 24，目标 API 为 26”，修复概率显著提高；
- **不接受无证据的结论**：AI 判断“这是 JNI 引用泄漏”时，要求给出泄漏点与计数依据；无法给出时，按未定处理，继续收集证据。

## 何时不应交给 AI

| 场景 | 原因 |
| --- | --- |
| 加密、签名、许可证校验 | 生成结果难以审计，错误代价高 |
| 性能关键路径的最终实现 | 需要实测数据驱动，生成代码只能作为起点 |
| 跨团队二进制接口 | ABI 与所有权约定必须由人确定并写入文档 |
| 许可不明的代码复现 | 存在许可证污染风险 |
| 崩溃根因判定 | 需要设备证据，AI 只能提供假设 |

## 记录与回归

验收清单应固化为可执行的形式，而不是停留在文档：

- 编译层检查写成 CI 脚本，构建失败即阻断；
- 语义层检查写成代码评审模板，逐条勾选；
- 运行层检查写成仪器测试，覆盖空输入、超长输入与循环调用。

只有这样，AI 生成的下一版代码才会被同一套标准约束，而不是依赖每次人工回忆。

## 小结

AI 协作的效率取决于约束的质量，而不是提示词的措辞。任务描述需要覆盖目标、ABI、构建、线程、所有权、错误处理与约束七项，每项都对应可检查的验收点。验收分编译、语义、运行三层，前两层本地可完成，第三层必须在设备上完成。最小复现是反馈的核心材料，规模应压缩到一个文件、一个入口、一条命令。把清单固化为脚本与测试之后，协作才具备可持续性。
