Native 崩溃的形态只有几类：立即触发的信号、延迟暴露的堆破坏、优化后行为改变。三者的共同前提是同一套内存模型：对象存放在哪一段区域、生命周期由谁决定、越界与悬垂为什么属于未定义行为而不是“读到脏数据”。

操作系统笔记中的“栈与堆”停留在概念层；C 语言层面的对象布局、存储期与对齐规则决定了崩溃的时机与可观测现象。

## 地址空间布局

一个 64 位 Android 进程的地址空间按用途分段，每段有独立的权限。

```text
高地址
┌──────────────────────┐
│      内核空间         │  用户态不可访问
├──────────────────────┤
│      栈（主线程）      │  向下增长，可读写
├──────────────────────┤
│          ↓           │
│                      │
│          ↑           │
├──────────────────────┤
│  共享库映射（.so）     │  r-x / r--，只读段不可写
├──────────────────────┤
│  堆（malloc 区域）     │  向上增长，可读写
├──────────────────────┤
│  .bss（未初始化全局）   │  零初始化，可读写
├──────────────────────┤
│  .data（已初始化全局）  │  可读写
├──────────────────────┤
│  .rodata（字符串常量）  │  只读
├──────────────────────┤
│  .text（机器码）       │  可执行、只读
└──────────────────────┘
低地址
```

`.text` 与 `.rodata` 的只读属性由页表强制。改写字符串字面量会触发 `SIGSEGV`，原因不是“语法错误”，而是写入了一个没有写权限的页。ELF 段的完整结构见 [[19. Android NDK开发：链接、装载与库|链接、装载与库]]。

## 存储期与生命周期

C 的对象有四种存储期，决定对象何时创建、何时销毁、位于哪一段。

| 存储期 | 声明位置 | 生命周期 | 典型区域 |
| --- | --- | --- | --- |
| 自动（automatic） | 函数内的局部变量 | 进入作用域创建，离开销毁 | 栈 |
| 静态（static） | 全局变量、`static` 局部变量 | 程序启动到结束 | `.data` / `.bss` |
| 动态（allocated） | `malloc` / `new` | 显式释放为止 | 堆 |
| 线程（thread） | `_Thread_local` / `thread_local` | 线程创建到结束 | TLS 区 |

`static` 局部变量只初始化一次，跨调用保留值；它的初始化发生在首次执行到声明处（C++ 中由编译器插入守卫变量保证线程安全），这一点与全局变量的启动期初始化不同。

## 栈

每次函数调用创建一个栈帧，保存返回地址、上一帧指针、局部变量与临时值。栈帧随函数返回整体回收，回收动作只是移动栈指针，不清零内容。

```c
int *bad(void) {
    int local = 42;
    return &local;      /* 返回后栈帧失效，指针悬垂 */
}
```

该函数返回的地址在调用方继续调用其他函数后会被覆盖。是否崩溃取决于后续调用栈的深度，属于典型的“偶发、不可复现”。

栈容量有限：主线程通常为 MB 级，`pthread` 创建的线程更小。两类常见溢出：

- 深度递归没有终止条件；
- 在栈上声明大数组，例如 `char buf[4 * 1024 * 1024]`。

栈溢出的表现是 `SIGSEGV`，fault addr 通常紧邻栈边界，tombstone 中该线程的栈回溯会显示极深的重复帧。

## 堆

堆由分配器管理。`malloc` 返回一块至少满足最大基础类型对齐要求的连续内存，`free` 将块归还分配器。分配器自身需要在块前后维护元数据，这就是越界写会破坏“与自己无关的后续分配”的原因。

```c
int *p = (int *)malloc(10 * sizeof(int));
if (p == NULL) {
    /* 分配失败 */
}
/* 使用 p[0..9] */
free(p);
p = NULL;               /* 防止悬垂，可选但推荐 */
```

几个容易忽略的语义：

| 调用 | 语义 | 边界 |
| --- | --- | --- |
| `malloc(0)` | 返回可释放的指针或 `NULL`，取决于实现 | 不得解引用 |
| `free(NULL)` | 合法，空操作 | — |
| `realloc(p, n)` | 可能搬迁并返回新地址 | 失败返回 `NULL`，原块仍然有效，不能直接覆盖 `p` |
| `calloc(n, size)` | 分配并清零，带乘法溢出检查 | 溢出时返回 `NULL` |

`realloc` 的正确写法必须使用临时变量：

```c
void *tmp = realloc(p, new_size);
if (tmp == NULL) {
    /* p 仍然有效，按失败路径处理 */
} else {
    p = tmp;
}
```

直接写 `p = realloc(p, n)`，失败时原指针丢失，造成泄漏。

Android 11 起默认分配器为 Scudo，它在 `free` 时校验块头，能主动发现 double free 与部分越界写，并以 `SIGABRT` 终止进程，日志中出现 `Scudo ERROR` 或 `heap corruption` 字样。这类报告说明破坏发生在更早的位置，崩溃点只是最先被检测到的位置。

## 未定义行为的定义与后果

C 标准对未定义行为的表述是：程序的行为不受标准约束，实现可以做任何事，包括“看起来正常工作”。编译器在优化时以“未定义行为不会发生”为前提进行推导，因此 UB 的实际后果不是“结果随机”，而是“代码可能被整体改写”。

两个典型例子：

```c
/* 有符号溢出是 UB，编译器可假定 x + 1 > x 恒成立 */
int always_true(int x) {
    return x + 1 > x;      /* -O2 下直接返回 1 */
}
```

```c
/* 先解引用再判空，判空分支可被删除 */
int deref(int *p) {
    int v = *p;
    if (p == NULL) {
        return -1;
    }
    return v;
}
```

第二例在 `-O0` 下可能“正常”返回 -1，在 `-O2` 下直接崩溃。优化级别改变现象，是 UB 参与优化的直接证据。

## 常见未定义行为清单

| 类别 | 具体形式 | 典型表现 |
| --- | --- | --- |
| 越界 | 读写数组边界之外 | 静默破坏或 `SIGSEGV` |
| 悬垂 | 使用已 `free` 的指针、返回局部变量地址 | 读到旧值或崩溃 |
| 重复释放 | 对同一指针 `free` 两次 | Scudo 报 `double-free` |
| 未初始化 | 读取未赋值的自动变量 | 值不确定，优化后行为变化 |
| 有符号溢出 | `INT_MAX + 1` | 分支被优化掉 |
| 移位 | 移位位数大于等于类型宽度、负数左移 | 结果不确定 |
| 空指针 | 解引用 `NULL` | fault addr 接近 0 |
| 严格别名 | 用不兼容类型指针访问同一对象 | 读写被重排后丢失 |
| 序列点 | `i = i++ + 1` 一类无顺序保证的表达式 | 结果随编译器变化 |
| 字符串字面量 | 改写只读段 | `SIGSEGV` |

无符号整数溢出是良定义的（按模回绕），有符号溢出不是。这一差异常被用来解释“为什么哈希计算用 `uint32_t`”。

## 崩溃与静默破坏

| 形态 | 机制 | 可观测现象 |
| --- | --- | --- |
| 立即崩溃 | 访问非法页、对齐错误、执行非法指令 | 当场 `SIGSEGV` / `SIGBUS` / `SIGILL` |
| 迟延崩溃 | 堆元数据被破坏，后续分配或释放时检测到 | 崩溃点远离肇事点 |
| 静默错误 | 越界写到相邻对象、读到悬垂但未被复用的内存 | 结果错误但进程存活 |

第三类最难定位，因为没有任何信号。把这类问题变可观测的手段是内存检查工具。

## 用 ASan 把隐性问题变成显性报告

AddressSanitizer 在每次内存访问前后插入检查，并维护已释放区域的隔离区，可以直接报告越界、悬垂与重复释放，附带分配与释放的调用栈。

```c
int main(void) {
    char *buf = (char *)malloc(8);
    buf[8] = 'x';        /* 越界写一个字节 */
    free(buf);
    return 0;
}
```

以 `-fsanitize=address -g` 编译后运行，报告会给出错误类型、访问地址、越界偏移，以及分配点与访问点的完整调用栈。相比 tombstone，ASan 报告直接指出“哪一行写了多少字节”，不需要再从寄存器与内存映射反推。

在 Android 上使用 ASan 需要按 NDK 文档配置构建参数与启动包装脚本，并要求 API 21 及以上；具体做法见 [[8. Native 崩溃定位]]。

## 审查清单

| 检查项 | 判定方式 |
| --- | --- |
| 每个 `malloc` 是否有对应的 `free` | 沿所有返回路径走一遍 |
| `realloc` 是否使用临时变量 | 搜索 `= realloc(` 的直接赋值 |
| 数组下标是否可能等于长度 | 检查循环条件与 `<=` |
| 是否返回局部变量地址 | 搜索 `return &` |
| 释放后是否仍在使用 | 检查 `free` 之后的引用 |
| 大数组是否在栈上 | 检查局部数组长度 |
| 是否存在有符号溢出 | 检查 `int` 累加与乘法 |
| 判空是否在使用之后 | 检查解引用与判空的顺序 |

## 小结

内存模型把对象分到不同区域，存储期决定对象的销毁时机，越界与悬垂之所以危险，是因为它们触碰了标准未定义的边界，而编译器会以“UB 不发生”为前提重写代码。立即崩溃、迟延崩溃与静默错误是同一批错误的三种表现，定位手段分别是 tombstone、Scudo 报告与 ASan。审查时围绕“分配与释放是否配对、下标是否可达长度、指针在释放后是否仍被引用”三条主线展开，可以覆盖绝大多数缺陷。
