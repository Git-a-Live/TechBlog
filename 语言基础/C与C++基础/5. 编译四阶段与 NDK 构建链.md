NDK 工程的构建失败大多不发生在语法层面，而发生在“谁负责哪一步”的边界上：源文件找不到头文件、CMake 变量没生效、ABI 与设备不匹配、链接时缺符号。这些问题要求对从 `.cpp` 到 `.so` 的完整链路有清晰的分层认识。

预处理、编译、汇编、链接四个阶段各有明确的输入输出，把它们映射到 Gradle、CMake、clang 三层，可以判断任何一个配置项最终落在哪一步。一次不依赖 Gradle 的手工编译足以验证这条链路是否被正确理解。

## 四个阶段

```text
native-lib.cpp
     │  预处理  clang -E
     ▼
native-lib.i        展开 #include、替换宏、处理条件编译
     │  编译    clang -S
     ▼
native-lib.s        目标架构的汇编
     │  汇编    clang -c
     ▼
native-lib.o        ELF 可重定位目标文件（含符号表与重定位表）
     │  链接    clang（调用 ld.lld）
     ▼
libnative-lib.so    ELF 共享库（符号已解析、地址已重定位）
```

| 阶段 | 输入 | 输出 | 主要工作 |
| --- | --- | --- | --- |
| 预处理 | `.c` / `.cpp` | `.i` | 头文件展开、宏替换、条件编译、去注释 |
| 编译 | `.i` | `.s` | 语法语义检查、优化、生成汇编 |
| 汇编 | `.s` | `.o` | 汇编转机器码，生成符号表与重定位项 |
| 链接 | `.o` + 库 | `.so` / 可执行文件 | 符号解析、重定位、段合并 |

### 预处理

`#include` 是文本替换，不是模块导入。头文件被原样插入到包含点，因此头文件中的定义会在每个包含它的编译单元中各出现一次。这也是头文件需要 include guard、全局变量定义需要放在 `.c`/`.cpp` 中的原因。

```c
#include <stdio.h>
#define BUFFER_SIZE 1024

#if defined(__aarch64__)
/* arm64 专用分支 */
#endif
```

预处理阶段不进行类型检查。宏展开导致的语法错误会在编译阶段才暴露，报错位置指向展开后的代码，与源文件的对应关系需要借助 `-E` 观察。

### 编译

编译器把预处理后的代码翻译为中间表示，做优化后生成目标架构汇编。类型检查、模板实例化、内联、常量折叠都在这一阶段完成。

优化级别直接影响代码形态：`-O0` 保留变量与栈帧，便于调试；`-O2` 会内联、重排、删除未使用变量，栈回溯可能缺少部分帧。未定义行为在 `-O2` 下的表现与 `-O0` 不同，原因见 [[2. 内存模型与未定义行为]]。

### 汇编

汇编器把汇编文本转成机器码，输出 ELF 可重定位文件。该文件包含 `.text`、`.data`、`.bss` 等段，以及符号表与重定位表。此时代码中的外部符号（如 `__android_log_print`）地址尚未确定，只留下重定位记录。

### 链接

链接器读取所有 `.o` 与库，完成两件事：

1. **符号解析**：把每个未定义符号匹配到某个目标文件或库中的定义；
2. **重定位**：按最终地址修正指令与数据中的引用。

链接顺序对静态库敏感：链接器从左到右扫描，只提取当前未定义符号所需的成员。被依赖的库必须放在依赖者之后，否则符号在那次扫描时还未产生需求。

```bash
clang++ main.o -lfoo -lbar -o app    # main 依赖 foo，foo 依赖 bar
```

## 一次手工编译

不经过 Gradle 与 CMake，直接用 NDK 提供的 clang 包装脚本编译，可以看清每一层的输入输出。前提是已安装 NDK，并设置 `ANDROID_NDK_HOME`。

```bash
# 工具链目录（Windows 宿主）
NDK_BIN="$ANDROID_NDK_HOME/toolchains/llvm/prebuilt/windows-x86_64/bin"

# 编译为目标文件：目标三元组决定架构与最低 API
"$NDK_BIN/aarch64-linux-android21-clang++" \
    -c native-lib.cpp -o native-lib.o -fPIC -std=c++17

# 链接为共享库
"$NDK_BIN/aarch64-linux-android21-clang++" \
    -shared -o libnative-lib.so native-lib.o -llog
```

命令名中的 `aarch64-linux-android21` 是目标三元组加 API 级别，含义是“AArch64 架构、Linux 内核、Android 环境、最低 API 21”。API 级别决定可用符号集合：调用高于该级别的系统函数，链接可能通过，运行时在旧设备上失败。

`-fPIC` 生成位置无关代码，共享库必需。`-llog` 链接 `liblog.so`，对应 `__android_log_print`。

目标三元组与 ABI 的对应关系：

| ABI | 目标三元组前缀 | 指针宽度 | `long` 宽度 |
| --- | --- | --- | --- |
| `arm64-v8a` | `aarch64-linux-android` | 8 | 8 |
| `armeabi-v7a` | `armv7a-linux-androideabi` | 4 | 4 |
| `x86_64` | `x86_64-linux-android` | 8 | 8 |
| `x86` | `i686-linux-android` | 4 | 4 |

`long` 的宽度差异是移植缺陷的常见来源：在 `armeabi-v7a` 上 `long` 为 4 字节，在 `arm64-v8a` 上为 8 字节。把指针或 `long` 存入 `int` 的代码在 64 位下会截断。

## 三层职责

| 层 | 输入 | 输出 | 职责 |
| --- | --- | --- | --- |
| Gradle（AGP） | `build.gradle.kts` | 构建任务图 | 决定 ABI、`minSdk`、NDK 版本、是否启用 native 构建 |
| CMake | `CMakeLists.txt` | Ninja 构建文件 | 声明目标、源文件、编译选项、链接库 |
| clang / ld.lld | 源文件与目标文件 | `.o` / `.so` | 四阶段的实际执行 |

Gradle 不直接编译 C/C++，它调用 CMake 生成 Ninja 文件，再由 Ninja 调用 clang。CMake 不编译代码，它只生成构建描述。理解这三层的关键是：**任何一个配置项都要确认它最终落在哪一层的参数上**。

### Gradle 侧配置

```kotlin
android {
    ndkVersion = "27.3.13750724"

    defaultConfig {
        minSdk = 24
        externalNativeBuild {
            cmake {
                cppFlags += "-std=c++17"
            }
        }
        ndk {
            abiFilters += listOf("arm64-v8a", "armeabi-v7a")
        }
    }

    externalNativeBuild {
        cmake {
            path = file("src/main/cpp/CMakeLists.txt")
            version = "3.22.1"
        }
    }
}
```

`ndkVersion` 未显式声明时使用 AGP 的默认 NDK，版本不一致会导致本地可编译、CI 失败。`abiFilters` 决定产物包含哪些 ABI，遗漏 `arm64-v8a` 会导致 64 位设备无法加载。

### CMake 侧配置

```cmake
cmake_minimum_required(VERSION 3.22.1)
project(native-lib LANGUAGES C CXX)

add_library(native-lib SHARED native-lib.cpp)

target_compile_features(native-lib PRIVATE cxx_std_17)

find_library(log-lib log)
target_link_libraries(native-lib ${log-lib})
```

`target_compile_features` 比在 `cppFlags` 中手写 `-std=c++17` 更可靠：前者由 CMake 转换为对应编译器的参数，并参与特性检查。官方文档说明 CMake 的默认 C++ 标准取 clang 的默认值（当前为 C++14），使用 C++17 及以上必须显式指定，遗漏时会出现“本地能编、换 NDK 版本报错”的现象。

`find_library(log-lib log)` 必须在 `target_link_libraries` 之前执行，否则变量为空，链接命令缺少 `-llog`。

## 产物位置

AGP 把 native 产物放在构建目录下，按变体与 ABI 分目录：

```text
app/build/intermediates/cxx/Debug/<hash>/obj/
├── arm64-v8a/
│   └── libnative-lib.so
└── armeabi-v7a/
    └── libnative-lib.so
```

该目录下的 `.so` 未经过 strip，保留符号表，是 `ndk-stack` 符号化的输入。打包进 APK 的副本经过 strip，体积更小但无法还原行号。

## 常见构建失败

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| `CMake Error: could not find NDK` | `ndkVersion` 指向未安装版本 | 在 SDK Manager 安装对应版本，或改为已安装版本 |
| `fatal error: 'xxx.h' file not found` | 头文件路径未加入 `target_include_directories` | 补 include 目录，确认相对路径 |
| `undefined reference to ...` | 缺库、链接顺序错误、C/C++ 混用未加 `extern "C"` | 见 [[6. 符号、ABI 与 STL 链接]] |
| `error: unknown type name 'jstring'` | 未包含 `jni.h` | 包含 `<jni.h>`，确认 CMake 已链接 NDK 头文件目录 |
| 设备安装后 `UnsatisfiedLinkError` | APK 未包含设备 ABI | 检查 `abiFilters` 与设备架构 |
| 修改 `.cpp` 后不重新编译 | Ninja 时间戳或缓存异常 | 删除 `app/.cxx` 与 `build` 后重建 |

## 小结

构建链路的四个阶段各自有明确的输入输出：预处理展开文本，编译生成汇编，汇编产出可重定位目标文件，链接完成符号解析与重定位。Gradle、CMake、clang 分别负责任务编排、构建描述与代码生成，任何配置项都要能定位到具体一层。ABI 由目标三元组决定，`long` 与指针宽度随 ABI 变化，是移植缺陷的主要来源。产物目录中未 strip 的 `.so` 是后续崩溃符号化的基础。
