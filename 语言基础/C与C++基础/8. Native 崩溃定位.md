Native 崩溃没有 Java 异常栈，进程直接被信号终止，留下的证据是信号类型、出错地址与一份混合了机器码地址的调用栈。定位过程本质上是三步还原：从地址还原到函数，从函数还原到代码行，从代码行还原到错误的内存操作。

前提是构建产物保留符号。打包进 APK 的 `.so` 经过 strip，只能得到函数名与偏移；构建目录中未 strip 的副本才包含调试信息。符号化的工具参数与常见误判都围绕这条差异展开。

## 证据来源

| 来源 | 内容 | 获取方式 |
| --- | --- | --- |
| logcat | `DEBUG` 标签下的 signal、fault addr、backtrace | `adb logcat`，或 Android Studio Logcat |
| tombstone 文件 | 完整崩溃转储，含全部线程栈、内存映射、寄存器 | `/data/tombstones/tombstone_XX`，需 root 或模拟器 |
| DropBoxManager | 系统保存的崩溃记录 | `adb shell dumpsys dropbox --print data_app_native_crash` |
| bugreport | 上述内容的汇总 | `adb bugreport` |
| ASan 报告 | 越界、悬垂、重复释放的精确位置 | 带 ASan 构建的应用运行输出 |

普通应用无法读取 `/data/tombstones`，logcat 中的 `DEBUG` 段是最常用的入口。系统在进程崩溃时会输出一段以 `*** *** ***` 开头的记录，内容与 tombstone 基本一致。

## tombstone 结构

```text
*** *** *** *** *** *** *** *** *** *** *** *** *** *** *** ***
Build fingerprint: 'google/...'
ABI: 'arm64'
pid: 12345, tid: 12345, name: com.example.app  >>> com.example.app <<<
signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0x0000000000000000
    x0  0000000000000000  x1  0000007ffc123456  ...
backtrace:
      #00 pc 0000000000012a4c  /data/app/.../lib/arm64/libnative-lib.so (Java_com_example_Native_crash+24)
      #01 pc 0000000000012b10  /data/app/.../lib/arm64/libnative-lib.so (Java_com_example_Native_run+56)
```

各字段的判读顺序：

1. **pid / tid / name**：崩溃进程与线程。`tid` 与 `pid` 不同时，崩溃发生在线程而非主线程，需要先确认该线程在做什么。
2. **signal 与 code**：信号编号与二级原因。`SEGV_MAPERR` 表示访问了未映射地址，`SEGV_ACCERR` 表示地址已映射但权限不足。
3. **fault addr**：触发异常的地址。接近 `0x0` 通常是空指针解引用，接近栈边界通常是栈溢出。
4. **backtrace**：从崩溃点向外的调用链，`#00` 是最内层。
5. **memory map**：地址区间与对应文件，用于判断某个地址属于哪个库或哪段内存。

## 信号与归因

| 信号 | 编号 | 常见原因 |
| --- | --- | --- |
| `SIGSEGV` | 11 | 空指针解引用、越界访问、写只读段、悬垂指针 |
| `SIGABRT` | 6 | `abort()`、`assert` 失败、C++ 未捕获异常、Scudo 检测到堆破坏 |
| `SIGBUS` | 7 | 未对齐访问、映射文件被截断、访问超出映射范围 |
| `SIGILL` | 4 | 执行了非法指令，常见于 ABI 不匹配或代码损坏 |
| `SIGFPE` | 8 | 整数除零、`INT_MIN / -1` |
| `SIGTRAP` | 5 | 断点指令、`__builtin_trap` |

`SIGABRT` 的信息通常不止信号本身。Scudo 的报告包含 `Scudo ERROR: invalid chunk state` 一类的描述，紧随其后的 `abort message` 字段会说明是 double free、堆破坏还是分配器内部校验失败。这类崩溃的肇事点早于崩溃点。

## 符号化

`backtrace` 中的 `pc` 是运行期地址，无法直接对应源码行。符号化工具依赖未 strip 的 `.so` 与其中的调试信息。

### 未 strip 的产物位置

```text
app/build/intermediates/cxx/Debug/<hash>/obj/
├── arm64-v8a/libnative-lib.so      ← 含符号表与调试信息
└── armeabi-v7a/libnative-lib.so

app/build/intermediates/merged_native_libs/debug/out/lib/arm64-v8a/
└── libnative-lib.so                 ← 已 strip，与 APK 内一致
```

符号化必须使用 `obj/<abi>/` 下的版本。`merged_native_libs` 与 APK 内的副本已删除调试信息，只能得到函数名。

### ndk-stack

```bash
# 从文件读取
ndk-stack -sym app/build/intermediates/cxx/Debug/<hash>/obj/arm64-v8a \
          -dump crash.txt

# 直接过滤 logcat
adb logcat | ndk-stack -sym app/build/intermediates/cxx/Debug/<hash>/obj/arm64-v8a
```

`ndk-stack` 解析 `backtrace` 行，把 `pc` 地址映射为 `文件:行号`。输出形如：

```text
#00 pc 0000000000012a4c  libnative-lib.so (Java_com_example_Native_crash+24)
      crash.cpp:17
```

没有源码行号时，先确认 `.so` 是否与崩溃版本一致、是否未 strip、是否用 `-g` 编译。

### addr2line

单个地址可以直接用 `llvm-addr2line` 换算：

```bash
llvm-addr2line -C -f -e libnative-lib.so 0x12a4c
```

`-C` 反修饰名称，`-f` 输出函数名，`-e` 指定库文件。这里的地址是库内偏移，不是运行期地址；需要先从 memory map 中取该库的映射基址做减法：

```text
运行期 pc - 映射基址 = 库内偏移
```

直接把手上的运行期 `pc` 传给 `addr2line` 会得到错误的行号或 `??`。

## 回溯缺失的原因

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 只有 `pc`，没有函数名 | `.so` 已 strip | 换用未 strip 的产物 |
| 帧数很少，中间断层 | 优化内联、尾调用 | 降低优化级别复现，或依赖 ASan 报告 |
| `#00` 之后的帧全错 | 栈被越界写破坏 | 用 ASan 定位破坏点 |
| 符号名被修饰 | 缺少反修饰 | 加 `-C` 或 `llvm-cxxfilt` |
| 崩溃在 `libc.so` | 实际错误发生在调用方 | 看上一帧与参数，结合 fault addr 判断 |

调试构建建议保留 `-g` 与 `-fno-omit-frame-pointer`。`-O2` 不一定导致无法定位，但内联会让“崩溃行”指向调用点而不是真实语句，此时 ASan 报告比 tombstone 更直接。

## ASan 与 HWASan

| 工具 | 检测对象 | 环境要求 | 开销 |
| --- | --- | --- | --- |
| ASan | 越界、悬垂、重复释放、栈溢出 | API 21 及以上，可调试应用，需 `wrap.sh` | 较高，约 2 倍内存 |
| HWASan | 同上，基于硬件标记 | `arm64` 设备、Android 10 及以上 | 较低，但需要支持标记的硬件 |

构建侧需要在 CMake 中同时加编译与链接参数：

```cmake
target_compile_options(native-lib PRIVATE -fsanitize=address -fno-omit-frame-pointer -g)
target_link_options(native-lib PRIVATE -fsanitize=address)
```

运行侧通过 `wrap.sh` 注入 `ASAN_OPTIONS`，并按 NDK 文档把脚本放入对应 ABI 的资源目录。ASan 与 HWASan 不能同时启用。

ASan 报告的价值在于它直接给出“哪一行、访问了哪个地址、越界多少字节”，并附带分配点与释放点的完整调用栈。堆破坏类问题在 tombstone 中表现为崩溃点与肇事点分离，在 ASan 报告中则是单一调用链，定位成本相差一个数量级。

## 定位流程

```text
logcat / tombstone
        │ 读 signal、code、fault addr、tid
        ▼
判断崩溃类型
        │ 空指针 / 越界 / 堆破坏 / 栈溢出 / 除零
        ▼
取对应版本的未 strip .so
        │ obj/<abi>/，与崩溃构建号一致
        ▼
ndk-stack 或 addr2line 还原函数与行号
        │
        ▼
对照源码确认内存操作，构造最小复现
        │
        ▼
ASan 复现验证根因
```

## 常见误判

| 误判 | 实际情况 |
| --- | --- |
| 崩溃线程就是肇事线程 | 堆破坏的崩溃点通常晚于破坏点，肇事的是另一个线程 |
| fault addr 为 0 就一定是空指针 | 也可能是结构体偏移访问，基址为 0 时 fault addr 等于成员偏移 |
| 崩溃在 `memcpy` 就是 `memcpy` 的问题 | 通常是长度或目标缓冲区错误，责任在调用方 |
| `SIGABRT` 是业务代码调用了 `abort` | 多数来自 Scudo 检测、未捕获异常或 `assert` |
| 换成 `-O0` 后不复现，问题已解决 | 优化改变了 UB 的可见性，缺陷仍在 |
| 只在某个机型崩溃，是机型兼容问题 | 更可能是 ABI、页大小或系统库版本差异，需逐项排除 |

## 小结

Native 崩溃的证据链从信号开始：信号类型限定错误类别，fault addr 区分空指针与权限问题，backtrace 给出调用位置，memory map 把地址归属到具体库。符号化依赖未 strip 的构建产物，`ndk-stack` 处理整段 backtrace，`llvm-addr2line` 处理单个偏移，两者都要求库与崩溃版本严格一致。堆破坏类问题的崩溃点与肇事点分离，必须借助 ASan 才能把两者连起来。定位的终点不是“改掉崩溃行”，而是构造出能稳定复现的最小案例。
