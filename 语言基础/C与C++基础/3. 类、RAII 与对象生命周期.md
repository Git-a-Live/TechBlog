C 的资源管理靠成对的函数调用维持，出错时依靠人工检查每条返回路径。C++ 把这套约定编码进对象生命周期：构造函数获取资源，析构函数释放资源，对象离开作用域时释放必然发生，包括提前返回与异常展开的路径。这一机制称为 RAII（Resource Acquisition Is Initialization）。

NDK 代码中的 `JNIEnv`、`jstring`、文件描述符、锁都可以用 RAII 封装。审查 AI 生成的 C++ 代码时，判断“资源是否会泄漏”主要看两点：资源是否被某个对象的析构函数接管，以及该对象是否可被拷贝。

## 从 struct 到 class

C 的结构体只能装数据，操作数据的函数独立存在，通过参数传入指针。C++ 的类把数据与操作放在一起，并引入访问控制。

```c
/* C 风格 */
struct Buffer {
    char *data;
    size_t size;
};

void buffer_init(struct Buffer *b, size_t n);
void buffer_free(struct Buffer *b);
```

```cpp
// C++ 风格
class Buffer {
public:
    explicit Buffer(size_t n) : data_(new char[n]), size_(n) {}
    ~Buffer() { delete[] data_; }
    Buffer(const Buffer &) = delete;
    Buffer &operator=(const Buffer &) = delete;

    char *data() { return data_; }
    size_t size() const { return size_; }

private:
    char *data_;
    size_t size_;
};
```

两者的区别不在语法，而在“忘记调用 `buffer_free`”这类错误在 C++ 版本中不再可能发生：`Buffer` 对象销毁时析构函数一定执行。

## 构造与析构

构造函数负责建立对象的不变式，析构函数负责归还资源。成员按声明顺序初始化，与初始化列表的书写顺序无关；析构顺序与构造顺序相反。

```cpp
class Connection {
public:
    Connection(const std::string &host, int port)
        : host_(host), port_(port), fd_(-1) {   // 按声明顺序：host_ → port_ → fd_
        fd_ = ::socket(AF_INET, SOCK_STREAM, 0);
        if (fd_ < 0) {
            throw std::runtime_error("socket failed");
        }
    }

    ~Connection() {
        if (fd_ >= 0) {
            ::close(fd_);
        }
    }

private:
    std::string host_;
    int port_;
    int fd_;
};
```

三条边界：

1. 初始化列表的顺序由成员声明顺序决定，写成相反顺序会触发 `-Wreorder`，且实际初始化顺序仍以声明为准；
2. 构造函数抛出异常时，已构造完成的成员会按逆序析构，对象本身不析构，因此构造函数内部分配的资源需要由成员对象或智能指针接管；
3. 析构函数默认 `noexcept`，异常从析构函数逃逸会直接调用 `std::terminate`，析构中不应抛出异常。

构造函数内调用虚函数不会派发到派生类：构造基类部分时，对象的动态类型仍是基类。

## 拷贝、赋值与移动

编译器会按需生成四个特殊成员函数：拷贝构造、拷贝赋值、移动构造、移动赋值。默认实现是逐成员处理，对指针成员只复制地址，不复制所指对象。

```cpp
class Buffer {
public:
    explicit Buffer(size_t n) : data_(new char[n]), size_(n) {}
    ~Buffer() { delete[] data_; }
private:
    char *data_;
    size_t size_;
};

{
    Buffer a(16);
    Buffer b = a;      // 逐成员拷贝：b.data_ 与 a.data_ 指向同一块内存
}                      // 两次析构，同一指针被 delete[] 两次
```

这段代码在作用域结束时触发 double free。修复方式有三种：禁用拷贝、实现深拷贝、改用能表达所有权的成员。

| 方案 | 写法 | 适用场景 |
| --- | --- | --- |
| 禁用拷贝 | `Buffer(const Buffer &) = delete;` | 资源唯一、不允许复制 |
| 深拷贝 | 自定义拷贝构造与拷贝赋值 | 值语义容器 |
| 交给智能指针 | 成员改为 `std::unique_ptr<char[]>` | 默认选择，见 [[4. STL 与智能指针]] |

需要自定义析构、拷贝构造、拷贝赋值三者之一时，通常三者都要定义，这条经验称为 Rule of Three。C++11 引入移动语义后扩展为 Rule of Five：析构、拷贝构造、拷贝赋值、移动构造、移动赋值。

移动构造接受右值引用，接管源对象的资源并把源对象置于可析构状态：

```cpp
class Buffer {
public:
    Buffer(Buffer &&other) noexcept
        : data_(other.data_), size_(other.size_) {
        other.data_ = nullptr;
        other.size_ = 0;
    }

    Buffer &operator=(Buffer &&other) noexcept {
        if (this != &other) {
            delete[] data_;
            data_ = other.data_;
            size_ = other.size_;
            other.data_ = nullptr;
            other.size_ = 0;
        }
        return *this;
    }
private:
    char *data_ = nullptr;
    size_t size_ = 0;
};
```

`std::move` 本身不移动任何东西，它只是把表达式转换为右值引用，真正的资源转移发生在移动构造或移动赋值中。被移动后的对象仍然有效，但值未指定，只能析构或重新赋值。

不需要手写任何特殊成员时，全部交给编译器生成，这条经验称为 Rule of Zero。它应当是默认选择：资源交给标准库类型管理，业务类只组合这些成员。

C++17 起，用纯右值初始化对象时编译器必须省略拷贝/移动（guaranteed copy elision），`Buffer b = make_buffer();` 不再要求类型可移动。

## 虚函数与对象布局

带虚函数的类，其对象在起始位置多一个指向虚函数表的指针（vptr），表内存放各虚函数的实际地址。具体布局由 ABI 决定，Itanium C++ ABI（Android 使用的 ABI）把 vptr 放在偏移 0。

```cpp
class Shape {
public:
    virtual ~Shape() = default;
    virtual double area() const = 0;
};

class Circle : public Shape {
public:
    explicit Circle(double r) : r_(r) {}
    double area() const override { return 3.141592653589793 * r_ * r_; }
private:
    double r_;
};
```

```text
Circle 对象布局（64 位，示意）

┌──────────────┐
│  vptr        │ ──→ Circle 的虚函数表：析构、area
├──────────────┤
│  r_          │  8 字节
└──────────────┘
```

三条必须遵守的规则：

1. 通过基类指针删除派生对象时，基类析构函数必须是 `virtual`，否则行为未定义；
2. 派生类重写虚函数应标注 `override`，让编译器检查签名是否真正匹配；
3. 按值传递基类对象会发生切片：派生类部分被丢弃，虚函数派发失效。

```cpp
void print_area(Shape s);       // 切片：s 是 Shape 对象，不是 Circle
void print_area(const Shape &s); // 正确：引用保留动态类型
```

`Shape` 含纯虚函数，本身不能实例化；上例的按值传参在编译期即被拒绝，但基类若有非纯虚实现则可以通过编译，问题留到运行期。

## RAII 在 NDK 中的形态

JNI 的字符串与数组接口都是成对调用，天然适合封装为栈对象。

```cpp
class ScopedUtfChars {
public:
    ScopedUtfChars(JNIEnv *env, jstring s)
        : env_(env), s_(s), chars_(env->GetStringUTFChars(s, nullptr)) {}

    ~ScopedUtfChars() {
        if (chars_ != nullptr) {
            env_->ReleaseStringUTFChars(s_, chars_);
        }
    }

    ScopedUtfChars(const ScopedUtfChars &) = delete;
    ScopedUtfChars &operator=(const ScopedUtfChars &) = delete;

    const char *c_str() const { return chars_; }
    explicit operator bool() const { return chars_ != nullptr; }

private:
    JNIEnv *env_;
    jstring s_;
    const char *chars_;
};
```

使用方不再需要记住释放：

```cpp
extern "C" JNIEXPORT jstring JNICALL
Java_com_example_Native_greeting(JNIEnv *env, jobject, jstring name) {
    ScopedUtfChars chars(env, name);
    if (!chars) {
        return nullptr;
    }
    std::string out = "hello, ";
    out += chars.c_str();
    return env->NewStringUTF(out.c_str());
}
```

封装边界有两条：

- `JNIEnv *` 是线程相关的，封装对象不能跨线程传递或长期保存；跨线程需要先 `AttachCurrentThread` 获取当前线程的 `JNIEnv`；
- 局部引用在 native 方法返回时由虚拟机统一释放，RAII 封装主要解决循环内的引用表增长，不解决跨方法存活问题。局部引用在循环中的处理见 [[7. JNI 边界语义]]。

## 常见审查问题

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 离开作用域崩溃 | 默认拷贝导致 double free | 禁用拷贝或改智能指针成员 |
| 基类指针删除派生对象崩溃 | 基类析构非虚 | 加 `virtual ~Base()` |
| 派生类重写未生效 | 签名不匹配，未加 `override` | 加 `override` 让编译器报错 |
| 按值传参后行为异常 | 对象切片 | 改传引用或指针 |
| 成员初始化值不符预期 | 初始化列表顺序与声明顺序不一致 | 按声明顺序书写 |
| 析构中抛异常导致终止 | 析构函数默认 `noexcept` | 析构内吞掉异常或改为显式 `close()` |
| 移动后源对象仍被使用 | 误认为 `std::move` 会清空源对象 | 移动后只析构或重新赋值 |

## 小结

RAII 的价值在于把“释放”从人工路径检查变成语言保证的结构：资源由成员持有，析构按逆序自动执行，提前返回与异常展开都不会跳过。拷贝语义是这套结构的薄弱点，默认的逐成员拷贝会把唯一资源复制成两份，因此需要显式禁用、深拷贝或改为智能指针。虚函数带来运行期派发，同时引入虚析构、切片与对象布局三条约束。JNI 的成对接口适合封装为栈对象，但封装对象必须与创建它的线程同生命周期。
