链接错误的信息量通常很低：`undefined reference to 'foo(int)'`、`duplicate symbol`、`dlopen failed: library "libc++_shared.so" not found`。这三类错误分别对应符号解析、符号重复定义与运行期依赖缺失，根因都在“符号与 ABI 如何跨编译单元、跨库传递”。

ELF 格式、GOT/PLT 与动态装载机制见 [[19. Android NDK开发：链接、装载与库|链接、装载与库]]。工程侧需要判断的是符号如何命名、静态库与共享库的链接差异、STL 运行时的选择，以及这些选择如何决定错误形态。

## 符号

符号是目标文件中对函数、全局变量、段位置的命名记录。链接器通过符号表完成解析，动态链接器通过动态符号表完成运行期绑定。

```bash
llvm-nm -C libnative-lib.so       # -C 反修饰 C++ 名称
llvm-readelf -s libnative-lib.so  # 完整符号表
llvm-readelf -d libnative-lib.so  # 动态段：NEEDED、SONAME、RPATH
```

`nm` 输出的类型字母含义：

| 字母 | 含义 | 说明 |
| --- | --- | --- |
| `T` / `t` | `.text` 段符号 | 大写为全局，小写为局部 |
| `D` / `d` | `.data` 段符号 | 已初始化全局变量 |
| `B` / `b` | `.bss` 段符号 | 未初始化全局变量，不占文件空间 |
| `R` / `r` | `.rodata` 段符号 | 只读数据 |
| `U` | 未定义 | 本单元引用、需由其他单元提供 |
| `W` / `w` | 弱符号 | 可被强符号覆盖 |

符号的绑定属性决定重复定义时的行为：

- **全局（global）**：默认绑定，多个同名强符号会导致重复定义错误；
- **局部（local）**：加 `static` 或使用 `-fvisibility=hidden`，仅在编译单元或库内可见；
- **弱（weak）**：允许未定义，允许被强符号覆盖，用于可替换实现。

共享库应默认隐藏内部符号，只导出必要接口：

```cmake
set_target_properties(native-lib PROPERTIES
    CXX_VISIBILITY_PRESET hidden
    C_VISIBILITY_PRESET hidden)
```

未隐藏时，内部函数会进入动态符号表，可能与其他库的同名符号冲突，也会增大库体积。

## 名称修饰

C++ 支持重载、命名空间与类成员，编译器必须把类型信息编码进符号名，这套编码规则称为 name mangling，Android 使用的规则是 Itanium C++ ABI。

```cpp
void foo(int);              // _Z3fooi
void foo(double);           // _Z3food
namespace net { void foo(int); }  // _ZN3net3fooiEv
struct Shape { void area(); };    // _ZN5Shape4areaEv
```

`extern "C"` 关闭名称修饰，让符号保持 C 语言的扁平命名：

```cpp
extern "C" void foo(int);   // 符号名就是 foo
```

JNI 的静态注册依赖这一机制：虚拟机按 `Java_包名_类名_方法名` 的规则用 `dlsym` 查找函数，如果函数带 C++ 链接，符号会被修饰成 `_Z...`，查找必然失败，运行期报 `UnsatisfiedLinkError`。因此静态注册的 native 函数必须写在 `extern "C"` 块中。

头文件同时供 C 与 C++ 使用时，用条件编译隔离：

```cpp
#ifdef __cplusplus
extern "C" {
#endif

int native_init(const char *path);

#ifdef __cplusplus
}
#endif
```

反修饰用 `llvm-cxxfilt`：

```bash
llvm-cxxfilt _ZN5Shape4areaEv    # Shape::area()
```

## 静态库与共享库

| 维度 | 静态库 `.a` | 共享库 `.so` |
| --- | --- | --- |
| 本质 | 多个 `.o` 的归档 | 已链接的 ELF 共享对象 |
| 链接时机 | 构建期，成员被复制进产物 | 构建期记录依赖，运行期装载 |
| 体积 | 每个使用方各含一份 | 全进程一份 |
| 更新 | 需重新链接 | 替换 `.so` 即可 |
| 符号可见性 | 进入最终产物 | 通过动态符号表导出 |

静态库的链接按需提取：链接器只把“当前存在未定义符号”的成员拉入产物。这带来两个后果：

1. 库的排列顺序重要，被依赖者放在依赖者之后；
2. 库中未被任何符号引用的目标文件不会进入产物，依赖其静态构造函数的代码可能静默失效。

共享库可以在链接期要求所有符号必须解析，提前暴露缺失依赖：

```cmake
target_link_options(native-lib PRIVATE "-Wl,--no-undefined")
```

Android 默认允许共享库存在未定义符号（由运行期解析），不加该选项时，缺失的依赖会推迟到 `dlopen` 阶段才暴露。

## 三类链接错误

### undefined reference

链接期报错，说明某个 `U` 符号找不到定义。

| 根因 | 判别方式 | 修法 |
| --- | --- | --- |
| 缺少库 | 错误信息中的符号属于已知第三方库 | 补 `target_link_libraries` |
| 链接顺序错误 | 库存在但排在依赖者之前 | 调整顺序，被依赖者靠后 |
| C/C++ 混用未加 `extern "C"` | 错误信息中的符号带参数列表，如 `foo(int)` | 在被调方头文件补 `extern "C"` |
| ABI 不匹配 | 32 位目标链接了 64 位 `.a` | 按 ABI 分别提供库 |
| 只声明未定义 | 符号由本工程提供 | 补实现或补源文件到 `add_library` |

C 与 C++ 混用是最常见的一类：C 源文件编译出的符号是 `foo`，C++ 代码声明时按 C++ 规则生成 `_Z3fooi`，两者对不上。错误信息里出现带类型信息的签名，基本可以判定为这一问题。

### duplicate symbol

同一符号在多个目标文件中都有强定义。

| 根因 | 典型场景 | 修法 |
| --- | --- | --- |
| 头文件中定义全局变量 | `int g_count = 0;` 写在 `.h` | 头文件改 `extern`，定义放 `.c`/`.cpp` |
| 头文件中定义非 inline 函数 | 普通函数写在 `.h` | 加 `inline` 或移到源文件 |
| 同一实现被编入两个库 | 两个静态库含同一 `.o` | 合并库或改为共享库 |
| 模板显式实例化重复 | 显式实例化放在头文件 | 实例化集中到一个编译单元 |

C++17 起可以用 `inline` 变量在头文件中定义全局变量，语义是“全程序唯一实例”，可替代 `extern` 加定义的写法。

### 运行期装载失败

链接通过，安装后崩溃或抛异常。

| 错误信息 | 根因 | 修法 |
| --- | --- | --- |
| `dlopen failed: library "libc++_shared.so" not found` | 使用了共享 STL 但未打包 | 改 `c++_static`，或确保 `libc++_shared.so` 随 APK 打入 |
| `cannot locate symbol "AAudioStreamBuilder_openStream"` | 调用的 API 高于 `minSdk` | 提高 `minSdk` 或改用 `dlopen` 动态查找 |
| `is 32-bit instead of 64-bit` | ABI 与进程不匹配 | 检查 `abiFilters` 与设备架构 |
| `unsigned-lib.so: has text relocations` | 旧版 Android 对文本重定位的限制 | 用 `-fPIC` 重新编译 |

`UnsatisfiedLinkError` 的完整消息通常包含 `dlopen failed` 与具体原因，定位时先读冒号后的部分，不要只看异常类型。

## STL 运行时选择

NDK 自 r18 起只提供 libc++，以静态库 `libc++_static.a` 与共享库 `libc++_shared.so` 两种形态存在。

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 应用只有一个 `.so` | `c++_static` | 链接器可裁剪未用代码，体积最小，无额外依赖 |
| 多个 `.so` 且互相传递 STL 对象 | `c++_shared` | 全进程一份 STL，避免跨库 `new`/`delete` 与 ODR 冲突 |
| 多个 `.so` 但接口只走 C ABI | `c++_static` | STL 对象不跨库边界，静态链接安全 |

官方文档明确指出：静态运行时装进多个共享库时，同一函数或对象会出现多份定义，违反 ODR；跨库释放内存、跨库捕获异常都可能崩溃。这条约束是多 `.so` 工程必须选共享 STL 的原因。

默认值随构建系统不同：

- CMake 的 `ANDROID_STL` 默认为 `c++_static`；
- ndk-build 的 `APP_STL` 默认为 `none`，即不链接任何 STL。

ndk-build 工程未显式设置 `APP_STL` 时，任何使用标准库的代码都会在链接期报大量 `undefined reference`，这是默认值差异造成的，不是代码问题。

## C++ 标准与 libc++

CMake 的 C++ 标准默认取 clang 的默认值（官方文档标注当前为 C++14），使用 C++17 及以上必须显式指定：

```cmake
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)
```

或用目标级写法 `target_compile_features(native-lib PRIVATE cxx_std_17)`。`CMAKE_CXX_EXTENSIONS OFF` 关闭 GNU 扩展，保证代码在不同编译器下行为一致。

libc++ 对较新标准的支持取决于 NDK 版本中的 libc++ 版本，标准版本提升后需确认目标 NDK 是否支持对应库特性。

## ABI 兼容

| ABI | 架构 | 指针 | `long` |
| --- | --- | --- | --- |
| `arm64-v8a` | AArch64 | 8 | 8 |
| `armeabi-v7a` | ARMv7 | 4 | 4 |
| `x86_64` | x86-64 | 8 | 8 |
| `x86` | i386 | 4 | 4 |

ABI 差异不止指针宽度：结构体对齐、`enum` 底层类型、位域布局、函数调用约定都可能不同。跨 ABI 复用 `.so` 一定失败，跨 ABI 复用序列化数据也可能因结构体布局不同而解析错误。

C++ 的 ABI 兼容性更严格：不同 STL 实现、不同编译器的 name mangling 与类布局都可能不同。C++ 接口不适合作为跨团队、跨版本的二进制边界，稳定的边界是 C ABI。

## 审查清单

| 检查项 | 判定方式 |
| --- | --- |
| JNI 函数是否在 `extern "C"` 中 | 搜索 `JNIEXPORT` 与 `extern "C"` 的配对 |
| 头文件是否有全局变量定义 | 检查 `.h` 中的非 `extern` 变量 |
| 库的链接顺序 | 被依赖者是否在依赖者之后 |
| 是否设置了 `--no-undefined` | 共享库应尽早暴露缺失符号 |
| 多 `.so` 工程的 STL 选择 | 是否为 `c++_shared` |
| C++ 标准是否显式声明 | 检查 `CMAKE_CXX_STANDARD` 或 `cxx_std_*` |
| 内部符号是否隐藏 | 检查 `CXX_VISIBILITY_PRESET` |
| `minSdk` 与所用 API | 高版本 API 是否有运行期判断 |

## 小结

符号是链接的通货，C++ 通过名称修饰把类型信息编码进符号名，`extern "C"` 是跨语言边界的唯一稳定形式。静态库按需提取成员，链接顺序与“未被引用的目标文件不会进入产物”是两类隐蔽问题。共享库的依赖缺失会推迟到运行期，`--no-undefined` 可以把问题提前到构建期。STL 的选择由“是否存在多个 `.so` 且传递 STL 对象”决定，默认值在 CMake 与 ndk-build 之间不同。ABI 兼容的边界应停在 C 接口。
