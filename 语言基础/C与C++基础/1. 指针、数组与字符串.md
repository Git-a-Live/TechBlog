Native 代码中出现频率最高的三类缺陷是数组越界、字符串边界错误和指针所有权混乱。三者的根因都落在同一组概念上：地址、指针算术、数组退化、C 字符串的终止约定。读 JNI 代码时如果对这几项没有把握，函数签名里的 `const char *`、`jbyteArray` 与 `GetStringUTFChars` 就只是记号，无法判断哪一行可能越界。语法形式本身见 [[0. C与C++语法速查]]。

示例按 64 位 Android ABI（`arm64-v8a`、`x86_64`）给出，32 位 ABI（`armeabi-v7a`、`x86`）的差异单独标注。

## 地址模型

进程看到的是虚拟地址空间，每个变量占据一段连续字节，首字节的地址就是变量地址。`&` 取地址，`*` 解引用。指针本身也是变量，在 64 位进程中占 8 字节，在 32 位进程中占 4 字节。

```c
int value = 42;
int *p = &value;      // p 存放 value 的首地址
*p = 43;              // 通过地址改写 value
```

```text
栈上的布局（64 位，示意）

高地址
┌──────────────┐
│      ...     │
├──────────────┤  ← &value，4 字节存放 43
│    value     │
├──────────────┤  ← &p，8 字节存放 value 的地址
│      p       │
├──────────────┤
│      ...     │
└──────────────┘
低地址
```

指针的类型不是装饰。类型决定解引用的宽度（`int *` 读 4 字节，`char *` 读 1 字节），也决定指针算术的步长。

## 指针算术

对指针加 1，增加的是所指类型的大小，不是 1 字节。

```c
int a[5] = {10, 20, 30, 40, 50};
int *p = a;
char *c = (char *)a;

p + 1        // 地址增加 4
c + 1        // 地址增加 1
*(p + 2)     // 30
```

三个边界条件必须同时成立，指针运算才是合法行为：

1. 指针指向某个数组元素，或指向数组末尾的下一个位置；
2. 运算结果仍落在 `[首元素, 末尾后一位置]` 区间内；
3. 解引用时指针必须指向真实存在的元素，末尾后一位置只能用于比较，不能解引用。

越出该区间的指针算术是未定义行为，编译器在优化后可能产生任意结果，不能依赖“地址算出来还能读”这种观察。

`void *` 不携带元素大小，标准不允许对 `void *` 做算术；GCC/Clang 将其按 1 字节处理属于扩展。需要按字节遍历时显式转换为 `char *` 或 `unsigned char *`。

## 数组与指针的关系

数组名在大多数表达式中退化为指向首元素的指针，但数组本身不是指针。三个例外场景保留数组类型：`sizeof`、`&`、`_Alignof`。

```c
int a[5];
int *p = a;

sizeof(a)    // 20
sizeof(p)    // 8（64 位）
sizeof(&a)   // 8，&a 的类型是 int (*)[5]
```

函数参数中的数组声明等价于指针，长度信息在传参时丢失：

```c
void f(int a[5]);     // 实际类型是 int *
void g(int a[]);      // 同上
```

因此所有接收数组的函数都必须额外传入长度，这也是 JNI 中 `GetArrayLength` 存在的原因。

| 表达式 | 类型 | 含义 |
| --- | --- | --- |
| `a` | `int *`（退化后） | 首元素地址 |
| `&a` | `int (*)[5]` | 整个数组的地址，值与 `a` 相同，步长为 20 |
| `a[0]` | `int` | 首元素 |
| `*(a + i)` | `int` | 等价于 `a[i]` |
| `&a[i]` | `int *` | 第 i 个元素的地址 |

二维数组的退化只发生一层。`int m[3][4]` 的 `m` 退化为 `int (*)[4]`，即“指向含 4 个 int 的数组”的指针，`m[i]` 才是 `int *`。这一层差异解释了为什么二维数组作参数时必须写成 `void f(int m[][4])`，第二维长度不能省略。

## const 与指针

`const` 修饰的是它左边最近的类型；左边没有类型时修饰右边。从右往左读可以消除歧义。

| 声明 | 含义 | 能否改指向 | 能否改目标值 |
| --- | --- | --- | --- |
| `const int *p` | 指向常量 int 的指针 | 能 | 不能 |
| `int * const p` | 常量指针，指向 int | 不能 | 能 |
| `const int * const p` | 两者皆常量 | 不能 | 不能 |

JNI 与系统 API 中大量使用 `const char *`，语义是“函数只读这段字符，不接管所有权”。这一约定与所有权无关，不能据此判断字符串由谁释放。

## C 字符串

C 没有字符串类型。字符串是以 `'\0'` 结尾的 `char` 数组，长度由终止符决定，不单独存储。

```c
char s1[] = "abc";        // 4 字节：'a' 'b' 'c' '\0'
const char *s2 = "abc";   // 指向只读区，4 字节（含终止符）
sizeof(s1)                // 4
sizeof(s2)                // 8，指针大小
strlen(s1)                // 3，不含终止符
```

`s1` 可写；`s2` 指向只读段，改写它是未定义行为，在 Android 上通常表现为 `SIGSEGV`。字面量在只读段中可能被合并，两个内容相同的字面量地址可能相等，不能依赖地址区分。

字符串长度的计算是线性扫描，`strlen` 的复杂度是 O(n)。在循环条件中反复调用 `strlen` 会把整体复杂度推到 O(n²)。

### 边界函数

| 函数 | 行为 | 风险点 |
| --- | --- | --- |
| `strcpy(dst, src)` | 复制到终止符 | 不检查 `dst` 容量，必然可溢出 |
| `strncpy(dst, src, n)` | 最多复制 n 字节 | 源串不短于 n 时不写终止符 |
| `strcat(dst, src)` | 追加 | 同 `strcpy` |
| `snprintf(dst, n, fmt, ...)` | 格式化并截断 | 返回值是“本应写入的长度”，不是实际写入长度 |
| `strnlen(src, n)` | 最多扫描 n 字节 | 源串没有终止符时返回 n，需另行判断 |

`snprintf` 的返回值语义是截断检测的依据：

```c
char buf[8];
int n = snprintf(buf, sizeof(buf), "%s", "0123456789");
// n == 10，buf 内容为 "0123456"，实际写入 7 字节 + 终止符
if (n >= (int)sizeof(buf)) {
    // 发生截断
}
```

`snprintf` 始终写终止符（容量大于 0 时），这一点优于 `strncpy`。

### 带边界检查的复制

```c
#include <stddef.h>
#include <string.h>

/* 返回 0 表示完整复制，1 表示发生截断，-1 表示参数非法。
   src 必须以 '\0' 结尾；来源不可信时应改用 strnlen 限定扫描上界。 */
int copy_truncated(char *dst, size_t cap, const char *src) {
    if (dst == NULL || cap == 0 || src == NULL) {
        return -1;
    }
    size_t n = strlen(src);
    size_t copy = (n < cap - 1) ? n : cap - 1;
    memcpy(dst, src, copy);
    dst[copy] = '\0';
    return (n > copy) ? 1 : 0;
}
```

该实现的边界条件是 `src` 已终止。若字符串来自不可信输入（网络、文件、JNI 传入的字节数组），先用 `strnlen(src, cap)` 限定扫描范围，再判断是否在 `cap` 内找到终止符。

## 所有权与函数接口

C 没有所有权语法，所有权只能靠接口约定表达。审查 native 代码时，每个指针都要能回答“谁分配、谁释放、生命周期到哪结束”。

| 接口形态 | 所有权含义 | 审查点 |
| --- | --- | --- |
| `const char *f(void)` | 返回内部或静态缓冲区 | 调用方不得释放；下次调用可能被覆盖 |
| `char *f(void)` | 通常由调用方 `free` | 必须确认文档约定，未说明则视为可疑 |
| `int f(char **out)` | 输出参数，函数内部分配 | 调用方负责释放；失败路径是否置空 |
| `void f(char *buf, size_t n)` | 调用方提供缓冲区 | 容量是否足够，函数是否保证终止 |
| `void f(const char *s)` | 只读借用 | 函数不得保存指针供异步使用 |

最后一条在 JNI 中尤其关键：`GetStringUTFChars` 返回的指针在 `ReleaseStringUTFChars` 之后失效，把它存进成员变量或传给其他线程，属于悬垂指针。

## JNI 中的对应写法

字符串跨边界时，Java 的 `String` 与 native 的 `char *` 是两种表示：前者是 UTF-16，后者是 modified UTF-8。转换必须成对调用。

```c
JNIEXPORT jstring JNICALL
Java_com_example_Native_greeting(JNIEnv *env, jobject thiz, jstring name) {
    const char *chars = (*env)->GetStringUTFChars(env, name, NULL);
    if (chars == NULL) {
        return NULL;                 /* 分配失败，异常已挂起 */
    }
    char buf[128];
    snprintf(buf, sizeof(buf), "hello, %s", chars);
    (*env)->ReleaseStringUTFChars(env, name, chars);
    return (*env)->NewStringUTF(env, buf);
}
```

三个审查点：

1. `GetStringUTFChars` 与 `ReleaseStringUTFChars` 必须成对，提前返回的每条路径都要释放；
2. `buf` 是栈数组，`snprintf` 负责截断，目标缓冲区容量由 `sizeof` 给出；
3. `NewStringUTF` 接受 modified UTF-8，`\0` 会被编码为两字节，普通 ASCII 与 UTF-8 子集可直接传入。

数组接口遵循同样的成对规则：

```c
jbyte *bytes = (*env)->GetByteArrayElements(env, arr, NULL);
if (bytes != NULL) {
    /* 读写 bytes */
    (*env)->ReleaseByteArrayElements(env, arr, bytes, 0);  /* 0 表示回写并释放 */
}
```

第四个参数为 `JNI_ABORT` 时不回写，用于只读场景；为 `0` 时把修改同步回 Java 数组。

## 常见缺陷模式

| 现象 | 根因 | 定位手段 |
| --- | --- | --- |
| 偶发崩溃，地址接近 0 | 空指针解引用 | tombstone 的 fault addr 接近 `0x0` |
| 崩溃发生在无关函数 | 之前的越界写破坏了堆元数据 | ASan、scudo 的 heap corruption 报告 |
| `strlen` 越界读 | 字符串缺少终止符 | ASan 的 heap-buffer-overflow |
| 长度计算差一 | 把 `strlen` 当作含终止符 | 检查 `+1` 与容量比较 |
| 释放后仍可读 | 悬垂指针，内存尚未被复用 | ASan 的 use-after-free |
| 两次释放 | 所有权不清晰 | scudo 的 double-free 报告 |
| 32 位正常、64 位崩溃 | 指针宽度或 `long` 宽度假设错误 | 对照 ABI 检查 `sizeof` |

## 小结

指针的合法性由“指向哪个对象、偏移多少、是否仍在该对象内”三者共同决定，类型只负责解释宽度与步长。数组名在传参时退化为指针，长度信息随之丢失，所有接收数组的接口都必须显式传长度。C 字符串以终止符定义长度，边界计算全部围绕“容量是否包含终止符”展开。所有权没有语言层面的表达，只能通过接口约定与成对调用维持，这也是 JNI 代码审查中最容易漏掉的一环。
