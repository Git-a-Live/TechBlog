JNI 是两套运行时之间的唯一通道：Java 侧由 ART 管理对象与垃圾回收，Native 侧由 C/C++ 直接操作内存。跨越这条边界的每个值都要经过类型映射，每个对象引用都要遵守虚拟机的生命周期规则，每个可能抛出 Java 异常的函数都要检查挂起状态。

注册方式、方法查找与调用流程见 [[17. Android NDK开发：JNI部分|JNI 部分]]。审查视角集中在四类问题：类型宽度、引用归属、线程绑定、异常状态，它们对应 AI 生成 JNI 代码时最常见的错误形态。

## 类型映射

| Java 类型 | JNI 类型 | C/C++ 对应 | 宽度 |
| --- | --- | --- | --- |
| `boolean` | `jboolean` | `unsigned char` | 1 |
| `byte` | `jbyte` | `int8_t` | 1 |
| `char` | `jchar` | `uint16_t` | 2 |
| `short` | `jshort` | `int16_t` | 2 |
| `int` | `jint` | `int32_t` | 4 |
| `long` | `jlong` | `int64_t` | 8 |
| `float` | `jfloat` | `float` | 4 |
| `double` | `jdouble` | `double` | 8 |
| `String` | `jstring` | 不透明指针 | 指针宽度 |
| 任意对象 | `jobject` | 不透明指针 | 指针宽度 |
| 类对象 | `jclass` | 不透明指针 | 指针宽度 |
| 数组 | `jarray` 及子类型 | 不透明指针 | 指针宽度 |

`jlong` 固定 64 位，与 ABI 无关。`armeabi-v7a` 上 C 的 `long` 只有 32 位，用 `long` 接收 `jlong` 会截断：

```c
/* 错误：32 位 ABI 下 long 为 4 字节 */
JNIEXPORT void JNICALL Java_com_example_Native_setDeadline(JNIEnv *env, jobject, jlong ms) {
    long deadline = ms;      /* 高 32 位丢失 */
}

/* 正确：使用定宽类型 */
JNIEXPORT void JNICALL Java_com_example_Native_setDeadline(JNIEnv *env, jobject, jlong ms) {
    int64_t deadline = ms;
}
```

`jboolean` 只有 0 与 1 两种有效值，`JNI_TRUE` 定义为 1。把任意非零值写入 `jboolean` 在部分虚拟机上会被视为非法值。

`jobject` 及其子类型都是不透明指针，不能直接访问字段。字段与方法必须通过 `GetFieldID`、`GetMethodID`、`Get<Type>Field` 等函数操作，这一约束在 C 与 C++ 中的写法不同：

```c
(*env)->GetObjectClass(env, obj);        /* C：env 是函数表指针 */
```

```cpp
env->GetObjectClass(obj);                /* C++：JNIEnv 有成员函数封装 */
```

## 方法签名

JNI 用描述符字符串定位方法与字段，格式由 Java 虚拟机规范定义。

| Java 类型 | 描述符 |
| --- | --- |
| `int` | `I` |
| `long` | `J` |
| `boolean` | `Z` |
| `void` | `V` |
| `String` | `Ljava/lang/String;` |
| `int[]` | `[I` |
| `byte[][]` | `[[B` |
| `Object` | `Ljava/lang/Object;` |

方法签名是参数描述符加返回值描述符：

```text
void log(String tag, int level)   →  (Ljava/lang/String;I)V
long now()                        →  ()J
```

描述符写错时，`GetMethodID` 返回 `NULL` 并抛出 `NoSuchMethodError`。签名不能凭记忆书写，用 `javap` 从 class 文件读取：

```bash
javap -s -p com.example.NativeBridge
```

## JNIEnv 与线程

`JNIEnv *` 是线程私有的，不能跨线程传递，也不能缓存后在其他线程使用。跨线程调用 Java 需要先用 `JavaVM` 获取当前线程的 `JNIEnv`。

```c
static JavaVM *g_vm = NULL;

JNIEXPORT jint JNICALL JNI_OnLoad(JavaVM *vm, void *reserved) {
    g_vm = vm;
    return JNI_VERSION_1_6;
}
```

native 线程回调 Java 的标准流程：

```c
void notify_from_native_thread(jobject callback) {
    JNIEnv *env = NULL;
    jint state = (*g_vm)->GetEnv(g_vm, (void **)&env, JNI_VERSION_1_6);
    bool attached = false;

    if (state == JNI_EDETACHED) {
        if ((*g_vm)->AttachCurrentThread(g_vm, &env, NULL) != JNI_OK) {
            return;
        }
        attached = true;
    } else if (state != JNI_OK) {
        return;
    }

    jclass cls = (*env)->GetObjectClass(env, callback);
    jmethodID mid = (*env)->GetMethodID(env, cls, "onEvent", "(I)V");
    if (mid != NULL) {
        (*env)->CallVoidMethod(env, callback, mid, 1);
    }

    if (attached) {
        (*g_vm)->DetachCurrentThread(g_vm);
    }
}
```

三条约束：

1. 已经 attach 的线程不能重复 attach，`GetEnv` 的返回值用于区分状态；
2. 只有本次 attach 的线程才需要 detach，主线程与 Java 创建的线程不能 detach；
3. attach 之后线程会一直存活到 detach，长驻线程应保持 attach 状态，避免频繁 attach/detach 的开销。

## 引用管理

JNI 引用不是 C 指针，它指向虚拟机的引用表条目。引用分三类，生命周期与可见范围不同。

| 类型 | 创建方式 | 生命周期 | 可跨线程 | 释放方式 |
| --- | --- | --- | --- | --- |
| 局部引用 | JNI 函数返回值、`NewLocalRef` | 当前 native 方法返回时 | 否 | `DeleteLocalRef` 或返回时自动 |
| 全局引用 | `NewGlobalRef` | 直到显式删除 | 是 | `DeleteGlobalRef` |
| 弱全局引用 | `NewWeakGlobalRef` | GC 可回收，引用自动失效 | 是 | `DeleteWeakGlobalRef` |

局部引用在方法返回时由虚拟机统一释放，正常情况下不需要逐个删除。问题出现在循环中：

```c
for (int i = 0; i < count; ++i) {
    jobject item = (*env)->CallObjectMethod(env, list, get_mid, i);
    /* 每轮产生一个局部引用，未释放会撑满局部引用表 */
    (*env)->DeleteLocalRef(env, item);
}
```

局部引用表溢出时抛出 `JNI ERROR (app bug): local reference table overflow`，进程直接终止。批量创建时可用 `PushLocalFrame` / `PopLocalFrame` 划定作用域，一次释放整帧。

全局引用不随方法返回释放，会阻止对象被 GC 回收。缓存 `jclass`、Java 回调对象时必须成对使用 `NewGlobalRef` 与 `DeleteGlobalRef`；泄漏的全局引用会让类加载器无法卸载，表现为内存持续增长。

弱全局引用不阻止 GC，对象被回收后引用失效。判断有效性用 `IsSameObject(ref, NULL)`：

```c
if ((*env)->IsSameObject(env, weak_ref, NULL)) {
    /* 对象已被回收，需要重建 */
}
```

## 字符串

Java 的 `String` 是 UTF-16 序列，JNI 提供两套访问方式。

| 函数对 | 编码 | 单位 | 适用场景 |
| --- | --- | --- | --- |
| `GetStringUTFChars` / `ReleaseStringUTFChars` | modified UTF-8 | `char` | 传给只接受 `char *` 的 C 接口 |
| `GetStringChars` / `ReleaseStringChars` | UTF-16 | `jchar` | 需要原生长度或处理补充平面字符 |

modified UTF-8 与标准 UTF-8 有两处差异：`U+0000` 编码为两字节 `0xC0 0x80`，补充平面字符按 UTF-16 代理对分别编码。因此 `strlen` 的结果与 Java 的字符数不对应。

```cpp
extern "C" JNIEXPORT jint JNICALL
Java_com_example_Native_length(JNIEnv *env, jobject, jstring s) {
    const char *utf = env->GetStringUTFChars(s, nullptr);
    if (utf == nullptr) {
        return -1;                    /* 分配失败，异常已挂起 */
    }
    size_t bytes = strlen(utf);
    env->ReleaseStringUTFChars(s, utf);
    return env->GetStringLength(s);   /* UTF-16 码元数，不是字节数 */
}
```

`GetStringLength` 返回 UTF-16 码元数，一个补充平面字符占两个码元；`GetStringUTFLength` 返回 modified UTF-8 的字节数。三者不能混用。

`ReleaseStringUTFChars` 之后指针立即失效，不能保存到成员变量或传给异步任务。

## 数组

数组访问有两种模式，区别在于是否复制。

| 函数 | 行为 | 适用场景 |
| --- | --- | --- |
| `Get<Type>ArrayRegion` / `Set<Type>ArrayRegion` | 复制指定区间 | 只访问一部分，或数据量小 |
| `Get<Type>ArrayElements` / `Release<Type>ArrayElements` | 可能复制，也可能锁定原数组 | 需要整体访问，且希望改动回写 |

`Release` 的最后一个参数决定是否回写：

- `0`：把修改复制回 Java 数组，然后释放缓冲区；
- `JNI_ABORT`：丢弃修改，直接释放，用于只读场景。

```c
jbyte *data = (*env)->GetByteArrayElements(env, arr, NULL);
if (data != NULL) {
    /* 只读使用 */
    (*env)->ReleaseByteArrayElements(env, arr, data, JNI_ABORT);
}
```

`GetPrimitiveArrayCritical` 期间虚拟机处于临界区，不能调用其他 JNI 函数、不能阻塞、不能分配 Java 对象。该接口用于大数组的高频访问，普通场景没有使用必要。

## 异常

Java 异常在 native 侧表现为“挂起状态”，不会自动展开 C 栈。调用可能抛出 Java 异常的函数后，必须先检查，再决定返回还是清理。

```c
jmethodID mid = (*env)->GetMethodID(env, cls, "parse", "(Ljava/lang/String;)I");
if (mid == NULL) {
    return -1;                       /* NoSuchMethodError 已挂起 */
}

jint result = (*env)->CallIntMethod(env, obj, mid, str);
if ((*env)->ExceptionCheck(env)) {
    (*env)->ExceptionDescribe(env);  /* 打印到 logcat，调试期使用 */
    (*env)->ExceptionClear(env);     /* 清除后可以继续调用 JNI */
    return -1;
}
```

四条规则：

1. 异常挂起时，多数 JNI 函数不允许调用，只有释放类函数（`Release*`、`Delete*Ref`、`ExceptionCheck` 等）例外；
2. `ExceptionDescribe` 只用于调试，生产代码应记录日志后清除；
3. 清除异常后可以继续调用 JNI，但 Java 侧的异常已消失，需要由 native 返回错误码通知上层；
4. native 主动抛异常用 `ThrowNew`，抛出后应立即返回，让异常在 Java 侧传播。

## 审查清单

| 检查点 | 具体表现 |
| --- | --- |
| 链接形式 | JNI 函数是否在 `extern "C"` 中，签名是否与 `javap` 一致 |
| 字符串释放 | 每条返回路径是否都执行了 `ReleaseStringUTFChars` |
| 数组释放 | `Release<Type>ArrayElements` 的模式参数是否正确 |
| 局部引用 | 循环内创建的对象是否 `DeleteLocalRef` |
| 全局引用 | 缓存的 `jclass`、回调对象是否有对应的 `DeleteGlobalRef` |
| 线程绑定 | 跨线程使用是否重新 `AttachCurrentThread`，是否误用缓存的 `JNIEnv` |
| 异常检查 | 调用可能抛异常的函数后是否 `ExceptionCheck` |
| 宽度类型 | `jlong` 是否用定宽类型接收 |
| 长度语义 | 是否混用字节数、UTF-16 码元数、字符数 |

## 小结

JNI 边界的错误集中在四处：类型宽度、引用归属、线程绑定、异常状态。类型映射要求使用定宽类型，`jlong` 与 `long` 的差异在 32 位 ABI 上直接导致截断。引用分局部、全局、弱全局三类，局部引用随方法返回释放但在循环中必须手动管理，全局引用泄漏会阻止类加载器卸载。`JNIEnv` 线程私有，跨线程必须先 attach。Java 异常在 native 侧只是挂起标志，必须在每次可能抛异常的调用后检查并清理。审查生成代码时按这四条逐一核对，可以覆盖绝大多数运行期崩溃与泄漏。
