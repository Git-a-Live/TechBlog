AI 生成的 C++ 代码几乎全部依赖标准库：容器承担数据组织，智能指针承担所有权表达。审查这类代码不需要能写模板，但必须能判断三件事：容器操作是否导致迭代器或引用失效、传参是否产生了不必要的大对象拷贝、所有权是否被 `shared_ptr` 过度共享。

Native 代码反复使用的标准库部分集中在 `vector`、`string`、`map`/`unordered_map` 与三种智能指针，它们覆盖了数据组织与所有权表达两类需求。

## 容器是值语义

标准容器持有元素的值，拷贝容器即拷贝全部元素。函数按值接收容器时会发生完整复制。

```cpp
void process(std::vector<int> v);          // 复制全部元素
void process(const std::vector<int> &v);   // 只读借用，无复制
void process(std::vector<int> &&v);        // 接管所有权
```

对 `std::string` 与 `std::vector` 这类动态容器，按值传参的成本与元素数量成正比。审查时看到按值传容器，先确认是否真的需要副本。

容器内的元素地址在容器发生重新分配后失效，这一性质决定了“保存元素指针”的写法风险极高。

## vector 的容量与失效

`vector` 连续存储，`size()` 是元素个数，`capacity()` 是已分配空间可容纳的元素个数。`push_back` 在容量不足时重新分配，把全部元素搬到新地址。

```cpp
std::vector<int> v;
v.reserve(1024);          // 预分配容量，避免多次搬迁
for (int i = 0; i < 1024; ++i) {
    v.push_back(i);       // 不触发重新分配
}
v.shrink_to_fit();        // 请求释放多余容量，非强制
```

扩容倍数由实现决定，常见为 1.5 或 2 倍。倍数决定 `push_back` 的均摊复杂度为 O(1)，但单次扩容是 O(n) 的搬迁。

失效规则按容器分别成立：

| 操作 | 失效范围 |
| --- | --- |
| `vector::push_back` 未扩容 | 尾后迭代器失效，元素引用不变 |
| `vector::push_back` 触发扩容 | 全部迭代器、指针、引用失效 |
| `vector::insert` / `erase` | 插入/删除位置及其后的迭代器失效 |
| `vector::reserve` | 容量变化时全部失效 |
| `deque::push_front` | 迭代器失效，元素引用保持有效 |
| `list` / `forward_list` | 仅被删除元素的迭代器失效 |
| `map` / `set` | 仅被删除元素的迭代器失效 |
| `unordered_map` 触发 rehash | 全部迭代器失效，元素指针与引用保持有效 |

下面的循环是典型错误：

```cpp
std::vector<int> v = {1, 2, 3, 4};
for (auto it = v.begin(); it != v.end(); ++it) {
    if (*it % 2 == 0) {
        v.erase(it);      // erase 后 it 失效，再 ++it 是未定义行为
    }
}
```

正确写法使用 `erase` 的返回值：

```cpp
for (auto it = v.begin(); it != v.end(); ) {
    if (*it % 2 == 0) {
        it = v.erase(it);   // 返回下一个有效位置
    } else {
        ++it;
    }
}
```

## string 与短字符串优化

`std::string` 管理一段连续字符，`c_str()` 返回以 `'\0'` 结尾的只读指针。该指针在下一次非 const 操作后可能失效。

```cpp
const char *p = s.c_str();
s += "tail";              // 可能重新分配，p 悬垂
```

多数实现采用短字符串优化（SSO）：较短的字符串直接存放在对象内部，不分配堆内存。SSO 的阈值由实现决定，不能作为接口契约依赖。

`std::string_view`（C++17）是非 owning 的字符视图，只保存指针与长度，复制成本恒定，但不延长源数据生命周期。

```cpp
std::string_view view(const std::string &s) {
    return s;             // view 指向 s 的内部缓冲区
}
// s 销毁后继续使用 view 是悬垂访问
```

`string_view` 适合函数参数，不适合作为返回值或长期保存的成员，除非源数据的生命周期明确长于视图。

## map 与 unordered_map

| 维度 | `std::map` | `std::unordered_map` |
| --- | --- | --- |
| 底层结构 | 红黑树 | 哈希表 + 链地址法 |
| 查找复杂度 | O(log n) | 平均 O(1)，最坏 O(n) |
| 元素顺序 | 按 key 有序 | 无序 |
| 迭代器稳定性 | 仅删除元素失效 | rehash 后全部迭代器失效 |
| 适用场景 | 需要有序遍历、范围查询 | 只做键值查找 |

`operator[]` 在键不存在时会插入默认值，这一行为常被误用为查找：

```cpp
std::map<std::string, int> counters;
if (counters["missing"] == 0) {   // 插入了一个值为 0 的条目
    // ...
}
```

只查询不插入应使用 `find` 或 `contains`（C++20）。需要“不存在则插入”的语义时，`try_emplace` 比 `operator[]` 更明确。

## 智能指针

### unique_ptr

独占所有权，不可拷贝，只能移动。默认删除器下对象大小与裸指针相同，没有运行期开销。

```cpp
auto buf = std::make_unique<char[]>(1024);   // C++14，数组特化
auto conn = std::make_unique<Connection>("127.0.0.1", 8080);

std::unique_ptr<FILE, int (*)(FILE *)> file(std::fopen("a.txt", "rb"), &std::fclose);
```

`get()` 返回裸指针但不转移所有权，`release()` 放弃所有权并返回裸指针，`reset()` 释放当前对象并接管新对象。

```cpp
void use(Connection *c);              // 不接管所有权
void take(std::unique_ptr<Connection> c); // 接管所有权
```

函数签名使用裸指针表示“借用”，使用 `unique_ptr` 按值表示“接管”，这一约定比注释更可靠。

### shared_ptr

共享所有权，内部含对象指针与控制块指针，控制块的引用计数保证最后一个持有者释放对象。

```cpp
auto cfg = std::make_shared<Config>();
auto copy = cfg;              // 引用计数 +1
```

`make_shared` 在一次分配中同时创建对象与控制块，优于 `shared_ptr<T>(new T)` 的两次分配，也避免了异常路径上的泄漏。

引用计数本身是原子操作，多个线程同时拷贝同一个 `shared_ptr` 实例是安全的；但多个线程同时读写同一个 `shared_ptr` 对象（例如一个线程赋值、另一个线程读取）不是安全的，需要额外同步。被指向对象的并发访问与 `shared_ptr` 无关。

循环引用会导致对象永不释放：

```cpp
struct Node {
    std::shared_ptr<Node> next;
    std::shared_ptr<Node> prev;   // 双向链表中两端互相持有，计数永不归零
};
```

`weak_ptr` 不增加引用计数，通过 `lock()` 提升为 `shared_ptr`，失败返回空。

```cpp
struct Node {
    std::shared_ptr<Node> next;
    std::weak_ptr<Node> prev;     // 打破循环
};
```

控制块在强引用计数与弱引用计数都归零后才释放。

### 所有权表达的选择

| 场景 | 类型 |
| --- | --- |
| 独占资源，单一持有者 | `std::unique_ptr` |
| 需要共享生命周期 | `std::shared_ptr` |
| 观察共享对象，不延长生命周期 | `std::weak_ptr` |
| 仅借用，不涉及所有权 | 裸指针或引用 |

`shared_ptr` 的成本高于 `unique_ptr`：一次原子增减、一个控制块、两次指针解引用。默认应选 `unique_ptr`，只在确实需要共享生命周期时升级。

## 模板的定位

标准容器与智能指针都是类模板，使用时由编译器按具体类型实例化，生成对应的机器码。模板的定义必须对使用点可见，因此实现通常放在头文件中；这也是“模板库只有头文件”的原因。

审查时不需要推导模板元编程，只需要能读懂实例化后的语义：`std::vector<std::string>` 是“元素为 string 的动态数组”，其拷贝成本等于逐个拷贝 string。模板报错信息冗长，定位方法是看错误链最内层的“required from”与实际类型不匹配处。

## NDK 场景中的组合

JNI 全局引用需要显式释放，可以交给智能指针的自定义删除器：

```cpp
struct GlobalRefDeleter {
    JNIEnv *env;
    void operator()(jobject obj) const {
        if (obj != nullptr) {
            env->DeleteGlobalRef(obj);
        }
    }
};

using GlobalRef = std::unique_ptr<_jobject, GlobalRefDeleter>;
```

该封装的前提是 `JNIEnv` 与对象同线程使用；跨线程持有全局引用时，删除器需要在目标线程重新获取 `JNIEnv`，不能直接保存创建线程的指针。

## 审查清单

| 检查项 | 判定方式 |
| --- | --- |
| 容器是否按值传参 | 搜索 `void f(std::vector<` 形式 |
| 是否保存了容器元素的指针 | 检查 `&v[i]` 的长期持有 |
| `erase` 是否使用返回值 | 检查循环内的 `erase` |
| `c_str()` 是否跨操作保存 | 检查指针赋值与后续修改 |
| `operator[]` 是否被当作查找 | 检查只读访问 |
| `shared_ptr` 是否成环 | 检查双向关系与回调持有 |
| 是否用 `shared_ptr` 表达独占 | 检查传参形式与 `use_count` |
| 删除器是否捕获线程相关对象 | 检查 `JNIEnv` 生命周期 |

## 小结

标准容器提供值语义与自动扩容，代价是元素地址不稳定，所有长期保存的指针与迭代器都必须重新审视。`string` 的 `c_str()` 与 `string_view` 都不拥有数据，生命周期由源对象决定。智能指针把所有权写进类型：`unique_ptr` 表达独占且零开销，`shared_ptr` 表达共享但引入控制块与原子操作，循环引用需要用 `weak_ptr` 切断。审查生成代码时，绝大多数资源问题都能归结为“所有权表达是否与真实持有关系一致”。
