布局问题的特征是"代码能跑，界面不对"。这类问题无法靠阅读代码定位，必须观察运行时的树结构、实际约束与实际尺寸。Android Studio 把检查器、属性编辑器与性能窗口直接嵌入 IDE，浏览器版 DevTools 作为深入分析的补充。

## 两种形态：内置面板与浏览器版

| 形态 | 打开方式 | 覆盖能力 |
| --- | --- | --- |
| 内置 Flutter Inspector | `View` > `Tool Windows` > `Flutter Inspector` | widget 树、属性、布局约束、跳转源码 |
| 内置 Flutter Performance | `View` > `Tool Windows` > `Flutter Performance` | widget 重建次数统计（Debug 模式） |
| 内置属性编辑器 | 侧边栏的 Flutter Property Editor 图标 | 所选 widget 的属性查看与修改 |
| 浏览器版 DevTools | `Open DevTools` | Inspector、Performance、Memory、Network、Debugger、App Size、Logging |

内置面板覆盖日常布局调试所需的全部能力，浏览器版用于帧耗时、内存、网络等深入分析。

## DevTools 的能力范围

DevTools 是随 Flutter SDK 提供的调试工具集，以 Web 应用形式运行，通过 VM Service 协议与运行中的应用通信。

| 面板 | 作用 |
| --- | --- |
| Inspector | 查看 widget 树、选中节点、查看约束与尺寸、跳转源码 |
| Performance | 帧耗时、UI / 光栅线程分布、卡顿定位 |
| Memory | 堆快照、对象分配、泄漏排查 |
| Network | HTTP 请求记录（需应用侧启用） |
| Debugger | 断点、单步、变量查看 |
| App Size | 构建产物体积分析 |
| Logging | 结构化日志 |

布局调试主要使用 Inspector 与其中的 Layout Explorer、属性编辑器。

## 与 Android 调试工具的对应

| Android Studio 工具 | Flutter 侧 | 差异 |
| --- | --- | --- |
| Layout Inspector | Flutter Inspector | 展示 element 树而非 View 树，含组合展开的中间节点 |
| CPU Profiler | DevTools Performance | 按 UI 线程与光栅线程拆分帧耗时 |
| Memory Profiler | DevTools Memory | 堆快照对比，定位未释放的控制器与订阅 |
| Logcat | `Run` / `Console` 窗口 | Dart 输出与原生日志分处两地 |
| Apply Changes | 热重载 | 前者依赖 ART 增量机制，后者注入 kernel |
| APK Analyzer | App Size | 按 Dart 库与原生库拆分体积 |

Android 开发者容易在 Layout Inspector 中找不到 Flutter 控件：Flutter 的 UI 不在 View 树中，`MainActivity` 之下只有一个渲染表面。检查 Flutter 布局必须使用 Flutter Inspector。

## 在 Android Studio 中启动 DevTools

前置条件是应用已在运行，`Run` 或 `Debug` 均可；断点调试与重建统计需要 `Debug`。

三个入口：

1. `Run` 或 `Debug` 窗口工具栏中选择 `Open DevTools`。
2. `Flutter Inspector` 面板的 `More Actions` 菜单中选择 `Open DevTools`。
3. `Find Action`（`Ctrl`+`Shift`+`A`）中搜索 `Open DevTools`。

选择后，IDE 启动 DevTools 服务并打开浏览器实例，地址带有 `uri` 查询参数，指向当前会话的 VM Service，无需手动连接。

独立实例只在少数场景使用：需要脱离 IDE 单独查看，或 IDE 内的入口异常。此时在终端执行 `dart devtools`，再在连接栏粘贴 `flutter run` 输出的 VM Service 地址。IDE 内打开的实例与独立实例功能一致，差别只在连接方式。

## Flutter Inspector 与 element 树

Inspector 展示的树是 **element 树**，不是源码中的 widget 嵌套关系。两者存在系统性差异：

- 组合器会展开。源码中一个 `Container`，树中对应 `Padding`、`DecoratedBox`、`ConstrainedBox`、`SizedBox` 等多个节点。
- 组合 widget 会展开为其 `build` 的返回值。`Tile` 在树中展开为 `Container` → `Center` → `Text`。
- 框架插入的节点会出现，例如 `Semantics`、`RepaintBoundary`、`MediaQuery` 等。

因此树深度通常大于源码层级。异常信息中出现的组件名，往往是展开后的中间节点。

选中任一节点后可以获取：

| 信息 | 用途 |
| --- | --- |
| widget 类型与 key | 确认是哪一个实例 |
| `size` | 实际布局尺寸，验证是否符合预期 |
| `constraints` | 父级传入的约束，判断是"被限制"还是"自适应" |
| 子级列表 | 定位结构缺失或多出的节点 |
| 源码位置 | 直接跳转到对应 `build` 方法 |

Layout Explorer 提供 flex 布局的可视化：主轴方向、剩余空间、每个子级的 `flex` 与 `fit` 分布，用于判断 `Expanded` 是否按预期分配。它只对 `Row`、`Column`、`Flex` 生效。

## 属性编辑器

在 IDE 侧边栏点击 Flutter Property Editor 图标（浏览器版位于 Inspector 的 Properties 标签），属性编辑器列出所选 widget 的全部构造参数，包含值、类型与是否使用默认值。

它的关键能力是**可写回**：修改数值后直接写入磁盘上的 `.dart` 源文件，保存或热重载后在运行中的应用上生效。这把"改代码 → 重载 → 观察"的循环压缩成"改数值 → 观察"。

边界条件：

| 场景 | 是否可编辑 |
| --- | --- |
| 字面量数值（`width: 60`） | 可编辑 |
| 枚举与布尔值 | 可编辑 |
| 表达式结果（`switch` 取值、方法调用） | 不可编辑，只读展示 |
| 由父级传入的值 | 编辑会改写父级源码中的实参 |

属性编辑器适合微调尺寸、间距、颜色，不适合改动结构。结构调整仍需编辑源码。

## 无界约束

Flutter 开发中出现频率最高的布局异常，成因是同一条规则的反面：子级收到的约束在某个方向上没有上限（`maxWidth` 或 `maxHeight` 为 `double.infinity`），而该子级的设计前提是"尽可能占满父级"。

### 触发条件

| 场景 | 无界方向 | 原因 |
| --- | --- | --- |
| `Row` 中的横向 `ListView` | 水平 | `Row` 给非 flex 子级无界宽度 |
| `Column` 中的 `ListView` | 垂直 | 同上，方向为垂直 |
| `Column` 中的 `Expanded`，且 `Column` 高度无界 | 垂直 | 剩余空间无从计算 |
| 可滚动视图嵌套可滚动视图 | 内层滚动方向 | 外层在该方向不限高/宽 |
| `Row` 中未包裹的 `TextField` | 水平 | `TextField` 需要明确宽度 |

`ListView` 在交叉方向（垂直列表的水平方向）会尝试填满父级，在主轴方向则假定可以无限延伸。把它放进同为横向的 `Row`，交叉方向变成水平，父级给出的水平约束为无界，于是异常。

### 异常表现

调试模式下抛出 `RenderBox was not laid out`、`Vertical viewport was given unbounded height`、`Horizontal viewport was given unbounded width` 一类信息，并伴随红色的错误块与堆栈。堆栈首行指向触发异常的组件构造位置，而不是约束来源，因此需要结合检查器回溯。

### 定位步骤

1. 读取异常首行，确认是哪个方向、哪个组件。
2. 在检查器中找到该组件，查看其 `constraints`。若某一方向为 `maxWidth: Infinity` 或 `maxHeight: Infinity`，即为无界。
3. 沿树向上找到第一个"本应限高/限宽却没有限"的节点，通常是 `Row`、`Column` 或滚动视图。
4. 在最靠近该节点的位置补上约束，而非在报错的最深层打补丁。

### 修复手段

| 手段 | 效果 | 适用 |
| --- | --- | --- |
| `Expanded` | 占据主轴剩余空间，给出确定尺寸 | 弹性填充 |
| `SizedBox(width/height:)` | 给出固定尺寸 | 尺寸已知 |
| `shrinkWrap: true` | 让滚动视图按内容收缩 | 列表项少、嵌套滚动 |
| `mainAxisSize: MainAxisSize.min` | 让 `Column`/`Row` 只包裹内容 | 高度无界的 `Column` |
| `constraints: BoxConstraints(maxHeight:)` | 显式限定上限 | 需要上限但不定死尺寸 |

`shrinkWrap` 会让列表在布局阶段遍历全部子项，破坏按需布局的优势，只适合子项数量少且确定的情形。数量大时应重构结构，取消嵌套滚动。

## 一条可复用的排查路径

1. **读异常**：首行给出方向与组件类型。
2. **看树**：在检查器中确认该组件的实际位置与父子关系，排除"代码写的不是实际生效的那一份"。
3. **看约束**：区分"父级给的空间不对"与"自身想占的空间过大"。
4. **看尺寸**：对比 `size` 与 `constraints`，判断是被压扁还是溢出。
5. **改约束源头**：优先调整提供约束的那一层，而不是在末端硬编码尺寸。

溢出（overflow）与无界约束是两类不同问题：溢出发生在约束**有限但不够**时，表现为黄黑条纹与 `A RenderFlex overflowed by X pixels`；无界约束发生在约束**无限**时，表现为异常与错误块。两者的定位入口相同，修复方向相反——溢出需要缩小内容或允许滚动，无界需要补充上限。

## 本节小结

内置 Flutter Inspector 与浏览器版 Inspector 展示的是同一棵 element 树，深度大于源码层级，因为组合器与组合 widget 都会展开。选中节点可读取 `size` 与 `constraints`，这是区分"被限制"与"自适应"的唯一可靠依据。属性编辑器支持把数值改动写回源文件，适合微调而非结构调整。无界约束的本质是子级设计前提与父级约束冲突，定位要沿树向上找到约束缺失的那一层，修复手段按"弹性、固定、收缩、显式上限"的顺序选择。内置面板覆盖日常布局调试，浏览器版补齐帧耗时、内存与网络分析。
