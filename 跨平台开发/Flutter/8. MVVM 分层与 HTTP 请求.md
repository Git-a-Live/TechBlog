界面代码同时承担网络请求、数据解析与渲染时，任何一处改动都会牵连全局，且无法脱离 UI 测试。分层的目的不是形式，而是让"取数据"与"画界面"各自可独立验证。

## 三层职责

MVVM 把客户端应用拆成三层，依赖方向单向：View → ViewModel → Model。

| 层 | 职责 | 依赖 | 可测试性 |
| --- | --- | --- | --- |
| Model | 数据操作：网络、缓存、持久化、平台能力 | 不依赖 Flutter | 纯 Dart 单测 |
| ViewModel | 持有状态、调用 Model、把结果转换为 UI 可用字段 | 依赖 Model | 注入假 Model 即可测 |
| View | 把状态映射为 widget 树 | 依赖 ViewModel | widget 测试 |

核心约束有两条：

- **Model 不 import Flutter**。除 `dart:io`、`dart:convert` 等标准库外，不引入 `package:flutter/*`。这保证 Model 可以在纯 Dart 环境中运行与测试。
- **View 不直接调用 Model**。View 只读取 ViewModel 的字段、只调用 ViewModel 的方法。数据流向单一，状态变化只有一个入口。

## 与 Android 网络层的对应

| Android | Flutter | 说明 |
| --- | --- | --- |
| Retrofit + OkHttp | `http` 包 | 请求发送与响应解析 |
| `HttpUrl.Builder` | `Uri.https` | URL 构造与编码 |
| `suspend fun` | `Future` + `async` / `await` | 异步调用 |
| Moshi / kotlinx.serialization | `fromJson` + 模式匹配 | JSON 反序列化 |
| Repository | `ArticleModel` | 数据源封装 |
| `Result<T>` | 异常 | 失败传递方式 |

Android 侧通常由 Repository 返回 `Result` 或抛出异常，ViewModel 再转成 UI 状态；这里的 `ArticleModel` 职责相当于 Repository，只是省去了接口层。协程的 `suspend` 与 Dart 的 `async` 都是"挂起当前函数、不阻塞线程"，区别在调度：Kotlin 协程可在不同 `Dispatcher` 间切换，Dart 只有单线程事件循环，CPU 密集任务必须交给 `Isolate`。`Isolate` 有独立堆、不共享内存，与 Android 线程（共享进程内存）不是同一模型。

## 项目准备

以下命令在 Android Studio 的内置 Terminal（`Alt`+`F12`）中执行，创建完成后用 `File` > `Open` 打开项目根目录。

```bash
flutter create wikipedia_reader --empty
cd wikipedia_reader && flutter pub add http
```

`flutter pub add` 把依赖写入 `pubspec.yaml` 的 `dependencies` 并立即解析下载。`http` 是官方维护的 HTTP 客户端，提供顶层函数 `get`、`post` 与 `Client` 类。

数据模型集中放在 `lib/summary.dart`，包含 `Summary`、`ImageFile`、`TitlesSet` 三个类，以及 JSON 反序列化逻辑。

## Model：请求的构造与执行

```dart
class ArticleModel {
  Future<Summary> getRandomArticleSummary() async {
    final uri = Uri.https(
      'en.wikipedia.org',
      '/api/rest_v1/page/random/summary',
    );
    final response = await get(uri);

    if (response.statusCode != 200) {
      throw const HttpException('Failed to update resource');
    }

    return Summary.fromJson(jsonDecode(response.body) as Map<String, Object?>);
  }
}
```

方法返回 `Future<Summary>` 而非 `Summary`。`Future` 表示"未来某个时刻可用的值"，调用方必须用 `await` 或回调处理，编译期就强制面对异步性。

### 为什么用 Uri.https 而不是字符串拼接

| 方式 | 问题 |
| --- | --- |
| `'https://en.wikipedia.org/api/rest_v1/page/random/summary'` | 查询参数需手工编码，特殊字符（空格、中文、`&`、`#`）会破坏 URL 结构 |
| `Uri.https(authority, path, queryParameters)` | 自动处理百分号编码、路径拼接与协议头 |

带查询参数的写法：

```dart
final uri = Uri.https('en.wikipedia.org', '/w/api.php', {
  'action': 'query',
  'titles': 'Flutter (software)',
});
```

`Uri.https` 会按 URI 规则对路径与查询参数做编码，避免手工拼接最常见的错误来源。

### async 与 await 的实际语义

Dart 是单线程事件循环模型，`async` / `await` 不创建线程，也不把代码移到后台。

- `async` 把函数标记为异步，函数体被编译为状态机，返回值包装为 `Future`。
- `await` 在等待的 `Future` 未完成时**挂起当前函数**，把控制权交还事件循环，线程可以去执行其他任务。
- `Future` 完成后，函数从挂起点恢复执行。

因此 `await get(uri)` 期间界面不会卡死，但也不存在"后台线程"。真正耗时的 CPU 计算需要 `Isolate`，网络 IO 由操作系统异步完成，本身不占用 Dart 线程。

### 错误处理的位置

HTTP 请求有三类失败：

| 失败类型 | 表现 | 处理位置 |
| --- | --- | --- |
| 网络不可达、DNS 失败、超时 | `SocketException`、`TimeoutException` | Model 不捕获，向上抛 |
| 服务端返回非 200 | `response.statusCode != 200` | Model 主动抛 `HttpException` |
| 响应体格式不符 | `FormatException`（来自 `jsonDecode` 或 `fromJson`） | Model 不捕获，向上抛 |

Model 的职责是"把异常形态统一"，而不是"吞掉异常"。抛给 ViewModel 后，由 ViewModel 决定如何呈现给用户。选择抛异常而非返回 `null` 的理由是：`null` 与"合法但内容为空"无法区分，调用方容易漏判；异常强制调用方显式处理。

`HttpException` 来自 `dart:io`，在 Web 平台上不可用。跨 Web 与移动端的项目应自定义异常类型，避免平台差异导致的编译失败。

## JSON 解析：模式匹配

`jsonDecode` 返回 `Object?`，其运行时类型是 `Map<String, dynamic>`、`List<dynamic>`、`String`、`num`、`bool` 或 `null`。直接下标取值需要大量 `as` 转换与判空：

```dart
final title = (json['titles'] as Map)['normalized'] as String;
```

字段缺失时抛 `TypeError`，错误信息指向强制转换的位置而非缺失的字段，排查困难。

`Summary.fromJson` 使用 map 模式匹配，把"结构校验"与"取值"合并为一次匹配：

```dart
static Summary fromJson(Map<String, Object?> json) {
  return switch (json) {
    {
      'titles': final Map<String, Object?> titles,
      'pageid': final int pageId,
      'extract': final String extract,
      'extract_html': final String extractHtml,
      'thumbnail': final Map<String, Object?> thumbnail,
      'originalimage': final Map<String, Object?> originalImage,
      'lang': final String lang,
      'dir': final String dir,
      'description': final String description,
      'content_urls': {
        'desktop': {'page': final String url},
        'mobile': {'page': String _},
      },
    } =>
      Summary(
        titles: TitlesSet.fromJson(titles),
        pageId: pageId,
        extract: extract,
        extractHtml: extractHtml,
        thumbnail: ImageFile.fromJson(thumbnail),
        originalImage: ImageFile.fromJson(originalImage),
        lang: lang,
        dir: dir,
        description: description,
        url: url,
      ),
    // 省略无图片、无描述的分支
    _ => throw FormatException('Could not deserialize Summary, json=$json'),
  };
}
```

几个语法要素：

| 语法 | 含义 |
| --- | --- |
| `{'key': pattern}` | map 模式，要求键存在且值匹配子模式 |
| `final Map<String, Object?> titles` | 声明模式，匹配后把值绑定到新变量并做类型校验 |
| `String _` | 通配符，只校验类型不绑定变量 |
| `_ => ...` | 兜底分支，前面的模式全部不匹配时执行 |

与前一种写法相比，模式匹配把校验前移到结构描述中：字段缺失、类型不符、嵌套层级不对，都表现为"该分支不匹配"，最终落到 `_` 抛出的 `FormatException`，异常信息携带完整原始 JSON，定位成本低。

`Summary.fromJson` 一共写了三个分支，对应三种响应形态：含图片与描述、含图片无描述、无图片。分支顺序即匹配优先级，越具体的模式越靠前。这是可选字段组合较多时的通用处理方式——枚举所有合法形态，而非在解析后逐字段判空。

## 可空字段的表达

| 字段 | 类型 | 为空的语义 |
| --- | --- | --- |
| `description` | `String?` | 该条目无简短描述 |
| `thumbnail` | `ImageFile?` | 无缩略图 |
| `originalImage` | `ImageFile?` | 无原图 |

可空类型在编译期强制调用方处理空值，`summary.description!` 的感叹号是"此处已确认非空"的断言，一旦判断失误会在运行期抛异常。更稳妥的写法是与空值判断合并：

```dart
if (summary.description != null)
  Text(summary.description!, /* ... */),
```

`hasImage` 这类派生判断封装为 getter，避免在多处重复组合 `originalImage != null && thumbnail != null`。

## 本节小结

MVVM 的价值在于依赖单向与职责单一：Model 不依赖 Flutter，可脱离 UI 测试；View 不直接触达 Model，状态变化只有一个入口。请求构造使用 `Uri.https` 而非字符串拼接，避免编码错误。`async` / `await` 是单线程上的挂起恢复，不是多线程。Model 的职责是抛出统一形态的异常，而非吞掉异常。JSON 解析使用 map 模式匹配，把结构校验与取值合一，缺失字段与类型错误统一落到兜底分支并携带原始数据。
