ViewModel 只负责保存状态与发出通知，把状态映射为像素的工作由 View 完成。`ListenableBuilder` 是这两者之间的连接点：它监听一个 `Listenable`，在收到通知时只重建自己的 `builder` 子树。

## 监听式重建

```dart
ListenableBuilder(
  listenable: viewModel,
  builder: (context, child) {
    return const Center(child: Text('Loading...'));
  },
)
```

`ListenableBuilder` 接受两个必要参数：

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `listenable` | `Listenable` | 被监听对象，`ChangeNotifier` 是其子类 |
| `builder` | `Widget Function(BuildContext, Widget?)` | 重建时执行的回调 |

`builder` 是**回调**而非子 widget。这一设计把"如何构建"推迟到每次重建时求值，因此可以在其中读取最新状态、使用 `if` / `switch` 决定返回哪棵子树。第二个参数 `child` 用于传入与状态无关、无需重建的子树，作为优化手段；不使用时写成 `_`。

与 `setState` 的对比：

| 维度 | `setState` | `ListenableBuilder` |
| --- | --- | --- |
| 状态位置 | `State` 内部 | 外部对象（ViewModel） |
| 重建范围 | 调用 `setState` 的 element 子树 | `builder` 返回的子树 |
| 状态共享 | 需提升到共同祖先 | 多处监听同一对象 |
| 状态与 UI 的耦合 | 高，二者在同一类中 | 低，二者分离 |

`ListenableBuilder` 内部在 `initState` 时 `addListener`，在 `dispose` 时 `removeListener`，把订阅生命周期与自身 element 绑定，调用方无需手工管理。

## 与 collectAsState 的对应

| Compose | Flutter |
| --- | --- |
| `StateFlow` + `collectAsStateWithLifecycle()` | `ChangeNotifier` + `ListenableBuilder` |
| `when (uiState)` | `switch` + record 模式 |
| `sealed interface UiState` | 三个并列字段 |
| 重组范围由读取位置决定 | 重建范围由 `builder` 决定 |

Compose 依靠快照系统在读取状态时自动订阅，Flutter 需要显式传入 `listenable`。两者的共同点是重建范围局部化：Compose 只重组读取了该状态的作用域，Flutter 只重建 `builder` 返回的子树。

`sealed interface` 与三字段并列的差别在约束力。前者由编译器保证状态互斥，后者依赖赋值逻辑维护。Dart 3 的密封类同样可以表达互斥状态，代价是需要自定义相等判断并显式调用 `notifyListeners()`。

## View 的三层结构

一个页面拆成三层，职责各自独立：

| 组件 | 类型 | 职责 |
| --- | --- | --- |
| `ArticleView` | `StatefulWidget` | 持有 ViewModel，触发首次加载，搭建页面骨架 |
| `ArticlePage` | `StatelessWidget` | 布局：滚动容器、内容区、操作按钮 |
| `ArticleWidget` | `StatelessWidget` | 内容：图片、标题、描述、正文的条件渲染 |

### 为什么最外层必须是有状态的

```dart
class _ArticleViewState extends State<ArticleView> {
  final ArticleViewModel viewModel = ArticleViewModel(ArticleModel());

  @override
  void initState() {
    super.initState();
    viewModel.fetchArticle();
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Wikipedia Flutter')),
      body: Center(
        child: ListenableBuilder(
          listenable: viewModel,
          builder: (context, _) {
            // 状态到 UI 的映射
          },
        ),
      ),
    );
  }
}
```

三点约束决定了这一结构：

1. **ViewModel 必须只创建一次**。放在 `build` 中会导致每次重建新建实例、重复请求。`State` 字段只在首次挂载时初始化，符合要求。
2. **首次加载需要明确时机**。`initState` 在 element 挂载后调用，此时发起请求不会影响首帧构建。
3. **资源需要释放**。`State.dispose()` 是调用 `viewModel.dispose()` 的唯一合适位置。

### 状态到 UI 的映射

三个字段的组合状态用一条 `switch` 表达式处理：

```dart
builder: (context, _) {
  return switch ((
    viewModel.isLoading,
    viewModel.summary,
    viewModel.error,
  )) {
    (true, _, _) => const CircularProgressIndicator(),
    (_, _, final Exception e) => Text('Error: $e'),
    (_, final summary?, _) => ArticlePage(
      summary: summary,
      nextArticleCallback: viewModel.fetchArticle,
    ),
    _ => const Text('Something went wrong!'),
  };
},
```

被匹配的对象是一个三元 record `(bool, Summary?, Exception?)`。分支使用的模式：

| 模式 | 含义 |
| --- | --- |
| `(true, _, _)` | 第一项为 `true`，其余不关心 |
| `(_, _, final Exception e)` | 第三项非空且类型为 `Exception`，绑定到 `e` |
| `(_, final summary?, _)` | 第二项非空，绑定到 `summary` 并提升为非空类型 |
| `_` | 兜底 |

`final summary?` 中的 `?` 是空值模式：匹配成功即保证值非空，因此分支内 `summary` 的类型是 `Summary` 而非 `Summary?`，不需要再加感叹号。这是模式匹配相对"判空 + 断言"的实际收益。

分支顺序等价于优先级：

1. 加载中优先。请求进行中即使残留旧数据也显示进度，避免用户误以为新内容已就绪。
2. 错误次之。错误优先于数据，保证失败不会被旧数据掩盖。
3. 数据再次。
4. 兜底。三个字段都为初始值时（尚未加载、无错误、无数据）落入该分支。

最后一条分支不能省略：`switch` 表达式要求穷尽，而 `(false, null, null)` 这一组合在前三个分支中无法匹配。

### 单向数据流

`ArticlePage` 只接收数据与回调：

```dart
ArticlePage(
  summary: summary,
  nextArticleCallback: viewModel.fetchArticle,
)
```

`viewModel.fetchArticle` 是方法引用，类型为 `Future<void> Function()`，可直接赋给 `VoidCallback`（`void Function()`）——返回 `Future` 的函数可以替代无返回值的函数位置，返回值被忽略。按钮点击时调用，触发一次新的加载。

View 不修改任何字段，只读取字段、调用方法。数据的写入全部发生在 ViewModel 内部，因此状态变化的路径唯一，不存在"某处直接改了字段导致界面不同步"的可能。

## 内容区的组合

`ArticleWidget` 展示一篇摘要，包含四类内容与三类条件：

```dart
class ArticleWidget extends StatelessWidget {
  const ArticleWidget({super.key, required this.summary});

  final Summary summary;

  @override
  Widget build(BuildContext context) {
    return Padding(
      padding: const EdgeInsets.all(8),
      child: Column(
        spacing: 10,
        children: [
          if (summary.hasImage) Image.network(summary.originalImage!.source),
          Text(
            summary.titles.normalized,
            overflow: TextOverflow.ellipsis,
            style: Theme.of(context).textTheme.displaySmall,
          ),
          if (summary.description != null)
            Text(
              summary.description!,
              overflow: TextOverflow.ellipsis,
              style: Theme.of(context).textTheme.bodySmall,
            ),
          Text(summary.extract),
        ],
      ),
    );
  }
}
```

| 手法 | 作用 |
| --- | --- |
| `if (条件)` 元素 | 条件为假时该位置不生成 widget，而非生成空占位 |
| `Image.network(url)` | 从网络加载图片，加载中与失败时有默认占位行为 |
| `overflow: TextOverflow.ellipsis` | 超出可用宽度时以省略号截断，防止长标题撑破布局 |
| `textTheme.displaySmall` / `bodySmall` | 用主题槽位建立视觉层级 |

`Column` 的 `spacing: 10` 统一了四项之间的垂直间距，替代了逐个计算 `SizedBox` 高度的写法。图片、标题、描述、正文四者的间距相同，符合"同一容器内元素等价间隔"的排版习惯；若需要差异化间距，仍需插入显式 `SizedBox`。

文本层级的选择依据是信息重要性：标题用 `displaySmall`（大字号、轻字重，属于展示级），描述用 `bodySmall`（小字号，属于辅助信息），正文用默认 `bodyMedium`。这样在切换主题或字体缩放时，层级关系保持一致。

## 完整的页面骨架

```dart
class ArticlePage extends StatelessWidget {
  const ArticlePage({
    super.key,
    required this.summary,
    required this.nextArticleCallback,
  });

  final Summary summary;
  final VoidCallback nextArticleCallback;

  @override
  Widget build(BuildContext context) {
    return SingleChildScrollView(
      child: Column(
        children: [
          ArticleWidget(summary: summary),
          ElevatedButton(
            onPressed: nextArticleCallback,
            child: const Text('Next random article'),
          ),
        ],
      ),
    );
  }
}
```

`SingleChildScrollView` 让内容在超出视口时可滚动，同时保持内部的 `Column` 按内容高度布局。它与 `ListView` 的区别在于：前者一次性布局全部子项，适合内容数量确定且不多的页面；后者按需布局，适合长列表。

按钮位于内容之后，滚动到页面底部才可见。若需要常驻可见的操作入口，应改用 `Scaffold.floatingActionButton` 或固定在底部的容器。

## 错误呈现的边界

```dart
(_, _, final Exception e) => Text('Error: $e'),
```

直接拼接异常对象会向用户显示 `HttpException: Failed to update resource` 之类的技术信息。教程场景下这足以验证链路，正式产品需要把异常映射为用户可理解的文案，并把原始异常写入日志。映射层可以放在 ViewModel（暴露 `errorMessage` 字段），也可以放在 View（按异常类型分支），取决于是否需要保留异常类型供其他逻辑使用。

## 本节小结

`ListenableBuilder` 把监听与重建绑定在自身 element 上，重建范围限于 `builder` 返回的子树，状态与 UI 由此解耦。View 的最外层必须有状态，以保证 ViewModel 唯一创建、首次加载有明确时机、释放有落点。状态到 UI 的映射使用 record + `switch` 模式匹配，分支顺序即优先级，空值模式免去断言，兜底分支保证穷尽。数据流单向：View 只读字段、只调方法，写入全部发生在 ViewModel 内部。
