## 常用Compose布局

传统 View 布局 → 相似作用的 Compose 布局，快速查阅对照：

| 传统 View 布局 | Compose 布局 | 备注 |
|---|---|---|
| FrameLayout | `Box` | |
| LinearLayout(vertical) | `Column` | |
| LinearLayout(horizontal) | `Row` | |
| ConstraintLayout | `ConstraintLayout` | `androidx.constraintlayout.compose` |
| CoordinatorLayout | `Scaffold` + `Box` | 仅结构对等，滚动协调用 `Modifier.nestedScroll` |
| ScrollView | `Column` + `verticalScroll` | |
| NestedScrollView | `LazyColumn` | |
| SwipeRefreshLayout | `PullToRefreshBox` | Material3 |
| Fragment 容器 | `NavHost` + `composable` | |
| Space（或写死尺寸的空 View） | `Spacer` | 占位；`Modifier.weight(1f)` 可撑开剩余空间 |
| Divider | `HorizontalDivider` / `VerticalDivider` | Material3 |

> **选型逻辑的转变**：View 时代为「性能」选布局（所以追着 ConstraintLayout 扁平化），Compose 时代为「可读性」选布局（可直接用 Column/Row/Box 嵌套），唯一仍需为性能考虑的，只剩「大数据量列表 → 必须用 Lazy 系列」。

Compose 布局分三类：
- **基石**：`Column` / `Row` / `Box`，可组合构建任意布局（官方称 "often these building blocks are all you need"）
- **可替代**：`ConstraintLayout`，官方明说"优势并不明显"，只有复杂相对约束（跨节点对齐、chain、barrier、基线）才用
- **不可替代**：`Lazy` 系列，懒加载，大数据量列表必须用（普通 `Column` 循环渲染会卡死）

## 混编：Compose 与 View 互操作

Compose 并非封闭体系，与 View 体系可双向桥接：Compose 里嵌 View 用 `AndroidView`，View 里嵌 Compose 用 `ComposeView`。

### AndroidView —— Compose 里嵌 View

WebView、MapView、AdView、SurfaceView 这类没有 Compose 版本的组件，要用 `AndroidView` 把 View 体系的组件包进 Compose：

```kotlin
@Composable
fun WebViewScreen(url: String) {
    AndroidView(
        factory = { context ->
            WebView(context).apply {
                settings.javaScriptEnabled = true
                webViewClient = WebViewClient()
            }
        },
        update = { webView -> webView.loadUrl(url) }
    )
}
```

- `factory`：只在首次组合执行一次，创建 View 实例
- `update`：每次重组执行，用最新 state 同步 View（**不要在 factory 里依赖会变的 state**）
- 需要「彻底重建」View（如登录态切换）时，用 `key()` 包裹：

```kotlin
key(sessionToken) {
    AndroidView(
        factory = { context -> WebView(context).apply { /* 初始化 */ } },
        update = { webView -> webView.loadUrl(url) }
    )
}
```

`key` 的值一变，块内内容整体销毁重建（`remember` 状态也会重置）；仅更换 url 时，用 `update` 中的 `loadUrl` 即可，无需重建。

### ComposeView —— View 里嵌 Compose

反向桥接：在 View 体系（XML 布局、WindowManager 悬浮窗、某些要求 View 容器的场景）里嵌入 Compose。`ComposeView` 本身是个 View，用 `setContent` 写入 Compose 内容后，即可作为普通 View 使用：

```kotlin
val composeView = ComposeView(context).apply {
    setContent {
        Text("Hello Compose")
    }
}
// 之后将 composeView 作为普通 View 使用：添加至容器，或 windowManager.addView(composeView, params)
```

也可以在 XML 里声明：

```xml
<androidx.compose.ui.platform.ComposeView
    android:id="@+id/compose_view"
    android:layout_width="match_parent"
    android:layout_height="match_parent" />
```

典型场景：
- 老项目渐进式迁移：XML 页面里放一个 ComposeView，先运行起来，再逐步将 View 替换为 Compose
- 系统级悬浮窗：`WindowManager.addView` 一个 ComposeView，窗口由 WindowManager 管理、UI 由 Compose 编写

## Widget 快速入门

桌面小组件（AppWidget），用 Glance 库以 Compose 风格编写。依赖：

```kotlin
implementation("androidx.glance:glance-appwidget:1.2.0")
```

最小实现 = 4 个文件：

**1. Widget 本体**（`MyWidget.kt`）：

```kotlin
class MyWidget : GlanceAppWidget() {
    override suspend fun provideGlance(context: Context, id: GlanceId) {
        provideContent {
            Text("Hello Widget")
        }
    }
}
```

**2. Receiver**（`MyWidgetReceiver.kt`）：

```kotlin
class MyWidgetReceiver : GlanceAppWidgetReceiver() {
    override val glanceAppWidget: GlanceAppWidget = MyWidget()
}
```

**3. 布局配置**（`res/xml/my_widget_info.xml`）：

```xml
<appwidget-provider xmlns:android="http://schemas.android.com/apk/res/android"
    android:minWidth="110dp"
    android:minHeight="40dp"
    android:updatePeriodMillis="1800000"
    android:initialLayout="@layout/glance_default_loading_layout"
    android:resizeMode="horizontal|vertical"
    android:widgetCategory="home_screen" />
```

**4. Manifest 注册**：

```xml
<receiver
    android:name=".MyWidgetReceiver"
    android:exported="false">
    <intent-filter>
        <action android:name="android.appwidget.action.APPWIDGET_UPDATE" />
    </intent-filter>
    <meta-data
        android:name="android.appwidget.provider"
        android:resource="@xml/my_widget_info" />
</receiver>
```

注意事项：
- **Glance 不是完整 Compose**：组件、Modifier 都要从 `androidx.glance.*` 导入（跟 `androidx.compose.*` 是两个包），只支持 Text/Image/Button/Row/Column/Box 等基础件；LazyColumn、Canvas、动画、Material3 都不支持
- **`initialLayout` 必须写 `@layout/glance_default_loading_layout`**：Glance 库自带的，漏写会导致异常
- **`updatePeriodMillis` 最小 30 分钟**（1800000ms），设置更小会被系统忽略；且周期不精确，要精确刷新需主动调 `GlanceAppWidget().update()`
- **`provideGlance` 是 suspend 函数**：可以取数据，但要快，不应在其中执行耗时网络请求

## Modifier

Modifier 是修饰符，给 composable 加「装饰」——尺寸、间距、背景、边框、点击等。它不可变、可链式调用：

```kotlin
Text(
    text = "Hello",
    modifier = Modifier
        .fillMaxWidth()
        .padding(16.dp)
        .background(Color.Blue)
        .clickable { }
)
```

**顺序决定结果**：Modifier 从左到右依次「包裹」，尤其 `padding` 和 `background` 的顺序直接改变效果：

```kotlin
Modifier.padding(16.dp).background(Color.Blue)  // 背景在 padding 之内，四周留白无背景色
Modifier.background(Color.Blue).padding(16.dp)  // 背景覆盖整块（含 padding）
```

常用分类：

| 用途 | Modifier | 说明 |
|---|---|---|
| 尺寸 | `size` / `fillMaxSize` / `fillMaxWidth` / `fillMaxHeight` | 固定尺寸 / 占满 |
| 间距 | `padding` | 参与测量，会占据空间 |
| 位移 | `offset` | 仅视觉偏移，**不改变布局**（区别于 padding） |
| 权重 | `weight` | 只在 Row/Column 作用域内可用 |
| 外观 | `background` / `border` / `clip` / `shadow` | 背景 / 边框 / 圆角 / 阴影 |
| 行为 | `clickable` / `verticalScroll` / `horizontalScroll` | 点击 / 滚动 |
| 对齐 | `align` | 只在 Box 作用域内可用 |

注意事项：

**1. `weight` 只在 Row/Column 作用域内可用**
`Modifier.weight(1f)` 是 `RowScope` / `ColumnScope` 的扩展函数，只能在 `Row {}` 或 `Column {}` 的 lambda 里调用，在 Row/Column 之外使用（如放 Box 中）会编译报错。它按权重比例分配剩余空间：

```kotlin
Row {
    Text("左", Modifier.weight(1f))  // 分到 1/3 剩余宽度
    Text("右", Modifier.weight(2f))  // 分到 2/3 剩余宽度
}
```

**2. `padding` 影响布局，`offset` 不影响**
`padding` 参与测量，会实际改变组件的布局尺寸；`offset` 只在绘制阶段做视觉平移，**不参与测量、也不影响周围组件的排布**。所以「真留白」用 padding，「视觉微调」用 offset——但 offset 偏移过度会超出父容器边界而被裁剪，且其占据的位置仍为原位置，易与相邻组件重叠。

**3. `clickable` 要放在 `padding` 之前**
`clickable().padding()` → 点击范围包含 padding 区域，整块可点击；`padding().clickable()` → padding 区域无响应。若需「带内边距的按钮整块可点击」，应写 `clickable().padding()`。

**4. `fillMaxSize` / `fillMaxHeight` 会占满约束**
`fillMaxSize` 会占满父容器给的全部剩余空间。在 `Column` / `LazyColumn` 这类滚动容器里，`fillMaxHeight` 拿到的可能是「无限高度」约束，会导致约束异常；需要「按内容大小」而非「占满」时，改用 `wrapContentSize`。

**5. Modifier 可抽变量复用**
一段通用的修饰链可抽为变量复用，亦可用 `then()` 追加：

```kotlin
val base = Modifier.padding(16.dp).fillMaxWidth()
Text("A", modifier = base)
Text("B", modifier = base.then(Modifier.padding(top = 8.dp)))
```

## State初探

### 声明式的思维转变

传统 View 是「命令式」：界面为静态的，开发者需手动调用 `textView.setText(...)` 去改它。Compose 是「声明式」：开发者声明「界面由 state 决定」，state 一变，界面自动重算：

```kotlin
// 命令式（View 时代）：每次都要手动同步
textView.text = "$count"

// 声明式（Compose）：声明「文本 = count」，count 变了自动更新
Text("$count")
```

这就是 State 存在的意义。

### 三件套：remember + mutableStateOf + by

```kotlin
@Composable
fun Counter() {
    var count by remember { mutableStateOf(0) }
    Column {
        Text("点击 $count 次")
        Button(onClick = { count++ }) { Text("+1") }
    }
}
```

分别说明三者的作用：

**① `mutableStateOf(0)`** —— 创建一个「可观察的容器」，将 0 包装其中。它返回 `MutableState<Int>`，通过 `value` 读写：

```kotlin
val count = mutableStateOf(0)
count.value = 1      // 改 value，触发重组
println(count.value) // 读 value
```

**② `by` 委托** —— 语法糖。`var count by mutableStateOf(0)` 等价于上面那种写法，`by` 使开发者能像操作普通变量一样 `count++`，编译器自动翻译成 `count.value++`。需要 import：`androidx.compose.runtime.getValue` / `setValue`。使用该语法时，变量必须是可变的，即使用`var`修饰符。

**③ `remember { }`** —— 最易被忽略，但至关重要。`mutableStateOf` 只负责「值变了通知重组」，`remember` 负责「重组时记住同一个 state 对象」。

**为什么 remember 必不可少？** 因为重组会**重新执行整个 @Composable 函数**。如果不 remember：

```kotlin
var count = mutableStateOf(0)  // 每次重组都创建一个新对象，值归零
```

点击 +1 后 count 变为 1 → 触发重组 → 函数重新执行 → `mutableStateOf(0)` 又创建一个归零的 state → **状态始终无法递增**。`remember` 在首次执行时创建并缓存，之后的重复执行直接返回缓存的同一对象。

### 重组（recomposition）

state 一变，所有「读取了这个 state」的 composable 重新执行，没读的会跳过（智能跳过）：

```kotlin
@Composable
fun Demo() {
    var a by remember { mutableStateOf(0) }
    var b by remember { mutableStateOf(0) }
    Text("A = $a")                 // 读取了 a
    Text("B = $b")                 // 读取了 b
    Button(onClick = { a++ })      // 只改 a
    // 点击按钮后只有 Text("A = $a") 重组，Text("B = $b") 跳过
}
```

### remember 的进阶

**`remember(key)`**：key 变化时才重新计算，常用于「参数变化时重建对象」：

```kotlin
val bitmap = remember(imageUrl) { loadImage(imageUrl) }  // imageUrl 变了才重新加载
```

**`rememberSaveable`**：普通 `remember` 遇到配置变化（旋转屏幕）或进程被回收即会丢失；`rememberSaveable` 把值存进 Bundle，跨旋转和进程重建保留：

```kotlin
var count by rememberSaveable { mutableStateOf(0) }
```

注意它只能存 Bundle 支持的类型（基本类型、String、Parcelable 等），自定义类型要传一个 `Saver`。

### 推导状态：derivedStateOf

一个值由其他 state 推导而来时，用 `derivedStateOf`，只在推导结果真正变化时才触发重组：

```kotlin
// count 在 1~10 之间变化，showButton 一直是 false，不会额外重组；注意使用状态推导的变量是不可变的，必须用val修饰符
val showButton by remember { derivedStateOf { count > 10 } }
```

### 状态提升（state hoisting）

把 state 从子 composable「提升」到父级，子 composable 变成无状态的（仅接收 value 与回调）。好处：可复用、可预览、可测试，也是 MVI 单向数据流的雏形：

```kotlin
// 有状态：state 封装在内部，无法复用、难以测试
@Composable
fun Counter() {
    var count by remember { mutableStateOf(0) }
    Button(onClick = { count++ }) { Text("$count") }
}

// 无状态：state 提升到调用方，Counter 仅负责渲染
@Composable
fun Counter(count: Int, onIncrement: () -> Unit) {
    Button(onClick = onIncrement) { Text("$count") }
}
```

### 常见问题

1. **忘记 `remember`**：state 每次重组重置，点击无效（最常见）。
2. **`remember` 不跨配置变化**：旋转屏幕即丢失，跨配置变化需用 `rememberSaveable`。
3. **state 要「整体替换」才触发重组**：`mutableStateOf` 通过 `equals` 判断值是否变化。所以 `data class` 用 `copy()` 生成新对象，`List` 用新列表（`list + item`），不可原地调用 `list.add()`。
4. **集合有专门的可观察版本**：`mutableStateListOf()` / `mutableStateMapOf()`，内部已处理「改动通知重组」，不用手动 `copy`。
